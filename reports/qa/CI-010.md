## Latest hosted finding: lazy Home entry

Hosted run `32251245628` advanced materially further:

```text

```

The canonical screenshot journey completed all six frames and the contact sheet accounted for all six.
The only failure was the non-visual `LiveSiteNavigationSmokeTest` at its initial Home -> Bloom transition:

```text
Action performScrollTo() failed.
Expected exactly '1' node but could not find any node that satisfies: Open Bloom Flowers
```

This is a Compose lazy-list test issue, not a hosted SiteSkin/runtime regression. The screenshot test
runs first and records visited sites; by the time the smoke returns to Home, Recent sites can push the
`Suggested integrations` card far enough below the viewport that its Bloom button has no semantics node
yet. Looking up the child first and then calling `performScrollTo()` therefore cannot work reliably.

The follow-up harness fix drives Home's scrollable `LazyColumn` with
`performScrollToNode(hasText(openBloomLabel))`, then asserts the materialised target is displayed before
clicking it. The helper is shared by the screenshot and smoke tests so both are independent of persisted
Recent/Favourites content and execution order. Application data is deliberately not cleared between
tests; persisted Home state is valid product state that acceptance should tolerate.

## Two-stage hosted preflight

### Stage 1: deployed Bloom freshness

Before any emulator work, the workflow resolves current `denrzv/bloom-flowers@main` from
`refs/heads/main` with `git ls-remote`, then fetches:

`https://denrzv.github.io/deployment.json`

The deployment must declare:

- `sourceRepository == "denrzv/bloom-flowers"`;
- `sourceSha ==` the SHA resolved from current Bloom `main`.

Evidence is persisted as:

- `artifacts/hosted-deployment.json` — exact Pages deployment metadata;
- `artifacts/hosted-deployment-validation.txt` — expected/actual source repository, expected/actual
  SHA, and `freshness_verdict`.

A mismatch fails before the manifest is fetched and prints an explicit remediation to run
`Publish Bloom Flowers` in `denrzv/denrzv.github.io`, wait for the Pages deploy, and rerun the hosted
workflow.

### Stage 2: SiteSkin semantic contract

Only after `freshness_verdict=PASS`, CI fetches:

`https://denrzv.github.io/.well-known/siteskin.json`

The run then fails fast unless all of the following are true:

- `presentation.hub == "drawer"`;
- `presentation.dock == ["catalog", "cart", "profile"]` in order;
- bottom navigation contains `home`, `catalog`, `cart`, `profile`;
- quick actions contain `call-shop`.

The fetched JSON is stored as `artifacts/hosted-siteskin.json` and the semantic verdict as
`artifacts/hosted-siteskin-validation.txt`, using `contract_verdict=PASS|FAIL`.

This separation means diagnostics can now distinguish three classes without inference from Compose
failures: stale Pages deployment, fresh deployment with an incompatible manifest, and a fresh/valid
manifest followed by an actual runtime UI/navigation failure.

## Workflow contract

`Android screenshots` supports both manual dispatch and relevant `push` events on `main`. Path filters
cover Android/browser/SiteSkin/evidence code, the hosted preflight script, Gradle inputs and the workflow
itself. Docs-only or report-only changes do not match. Runs share one concurrency group with
`cancel-in-progress: false`.
