## Edge cases

- **invalid manifest → regular browser mode** — N/A, no validation path is touched. An invalid
  manifest never reaches this component; the drawer only exists inside `PROTECTED_INTEGRATED`.
- **origin change / redirect** — N/A, no change. Teardown runs through the one `IntegratedOverlay?`
  and its three existing resets; no visibility state was added, asserted by the unedited
  `the hub has one visibility state and both surfaces read it`.
- **offline with cached manifest** — N/A, no network, cache or transport path is touched.
- **oversized or malformed payload** — N/A at the protocol layer. The presentation analogue is a site
  publishing the twenty `menu` entries `SPEC.md` §8 permits: the panel bounds at the maximum and
  scrolls, nothing is capped, and the reachable scrim strip is what `HUB_DRAWER_MAX_FRACTION < 1`
  guarantees. Scenario 18 covers it, unexecuted.
- **accessibility (TalkBack, font scale)** — the scrim is a gesture and publishes no semantics node,
  so TalkBack meets no screen-sized control in front of the menu; Back remains the accessible
  dismissal path and is structural, through `UX-022`'s dialog window. Rows keep their 48 dp targets
  and `UX-015`'s navigation-only selection. At 200% font scale the content is taller and the response
  is the scrolling that already existed — `everyPermittedMenuEntryIsReachableAtLargeText` passes
  unedited. Font scale is deliberately not an input to the height rule; the reasoning is at its
  declaration.
- **RTL** — `Alignment.TopStart` resolves against layout direction; no physical constant exists in the
  file, asserted, with five spellings refused. Unexecuted on a device.
- **320 dp width** — the panel is `fillMaxWidth(0.88f)` capped at 360 dp, unchanged by this ticket;
  the height rule is width-independent.
