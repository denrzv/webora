# QA Report: UX-002
Status: QA_PASSED

## Scope

The browser-owned token layer and nothing that consumes it: `WeboraColorScheme` (14 roles, two
projections), the type/radius/spacing scales, the Material derivation, `WeboraTheme` in
`MainActivity`, `res/values-night/themes.xml`, ten bundled vector icons, `WeboraIconButton`, and the
`contrastRatio` lift shared with `SiteSkinTheme`.

Not in scope, and deliberately unchanged: every surface's structure. `BrowserScreen`, `HomeScreen`,
`OnboardingScreen`, `PrivacySettingsScreen` and `BrowserErrorPage` keep their layout; `UX-003` and
`UX-004` rebuild them. Nothing yet reads an icon or a chrome geometry token.

## Edge cases

- **invalid manifest → regular browser mode** — N/A as a code path; unchanged by this ticket. Worth
  stating positively though: the browser palette *is* what a failed manifest degrades to, and after
  this ticket that fallback state is better specified than before rather than newly fragile.
- **origin change / redirect** — N/A. No origin is read, stored or compared anywhere in the change.
- **offline with cached manifest** — N/A. Nothing here performs or observes network work.
- **oversized or malformed payload** — N/A. No parsing. The nearest analogue is the icon set, and it
  is compiled into the APK: a website cannot add a file to `res/drawable`, which is exactly why a
  bundled vector needs none of `NET-003`'s signature check, size cap or bounded decode.
- **accessibility (TalkBack, font scale)** — Partially covered, and the split matters.
  - **Gate (JVM):** browser-palette contrast in both projections, completeness, the closure and
    pairing properties, the non-optional accessible name on `WeboraIconButton`, the hardened wrapper
    exemption. All in `docs/accessibility/CONFORMANCE.md` with their negative controls.
  - **Evidence (device):** `BrowserFontScaleTest` at 200% now composes `WeboraTheme` rather than
    Material's baseline, so it finally measures the type scale the product ships — but it has still
    never been executed, which `A11Y-001` already lists as a known gap. This ticket **changes what
    that test would measure** and does not close the gap. No TalkBack run.
  - The type scale is smaller than Material's at several steps (`bodyMedium` 13 sp vs 14 sp), so the
    first execution of that test is more informative than it was before, not less.

## Notes

**Two negative controls initially passed, and both were treated as findings rather than as noise.**

1. *Scenario 19.* Moving `WeboraIconButton` to its own file — which `C3` says must turn the build red
   — did not. `BrowserSurfaceConventionsTest`'s exemption was a plain `contains("fun WeboraButton(")`
   over the whole file text, and the new wrapper's KDoc quoted that rule while explaining it, thereby
   exempting its own file from it. The exemption is now a line-anchored declaration match with a test
   pinning both directions. This hole predates `UX-002`; the only way to trip it is to add a second
   wrapper, which nothing had done since `A11Y-001` wrote the rule.
2. *`/review` FINDING-1.* The closure assertion accepted `onSurface = divider`. Membership is not
   pairing; `TASK-FIX-1` added the pairing assertion, and its control demonstrates the gap rather
   than merely asserting it existed.

**The vector XML is validated by `assembleDebug`, which is not in the gate.** `scripts/pre-commit-check.sh`
runs `test`, the inspector-absence check and detekt; none of those invokes AAPT2, so a malformed
drawable would reach CI rather than the pre-commit run. It was verified manually here (scenario 17).
Adding an assemble to the gate is a build-time decision with a runtime cost, and belongs to whoever
owns the gate's shape rather than to this ticket — recorded as a gap, not fixed silently.

**No visual verification.** The palette is measured, not looked at. Surfaces keep their current
structure, so what changed visually is colour, type and shape on unrebuilt layouts; the first real
look comes from `UX-003`'s rebuild and the hosted screenshot journey after it. Nothing in this ticket
claims a screen looks right — only that every colour pair on it has been measured.

**One handoff to `UX-003`, unresolved on purpose.** Direction A draws unselected dock slots at 38%
opacity. At that opacity an enabled control reads as disabled and its glyph can fall below 3:1
whatever token sits underneath. This ticket supplies tokens, not opacity, so it cannot fix it;
`docs/plan/UX-002.md` records that unselected navigation state should be a colour role rather than an
alpha multiplier.
