# QA Report: UX-021
Status: QA_PASSED

Issue: [#104](https://github.com/denrzv/webora/issues/104)

## Scope

The transport-security state and its two visible surfaces: `TransportSecurity` growing from two
values to four and becoming browser-observed `BrowserState` rather than a scheme test at projection
time; the integrated header's full-width `Secure · domain` row replaced by a compact inline chip; and
regular chrome's identity reading the same state. `BrowserSession`, `AddressResolver`, discovery,
consent and activation are untouched and were verified only as *unchanged*.

Verified on `7ec8eb3`, branch `claude/bloom-flowers-reference-y5ybs7`, based on `origin/main`
`6d73e45`.

## Edge cases

- **invalid manifest → regular browser mode** — Covered by construction and unchanged. The chip is
  composed only inside `PROTECTED_INTEGRATED`; an invalid manifest never reaches integrated mode, and
  regular chrome reads the *same* `TransportSecurity` field, so the two variants cannot classify one
  page differently (AC-12).
- **origin change / redirect** — Scenarios 6, 7 and 9. `PageStarted` resets to `UNKNOWN`
  unconditionally, and `Page` preserves state only while the observed `SiteOrigin` equals the
  committed one — so a same-document change keeps a confirmed connection and a cross-origin one does
  not. Leaving an exact origin removes the header and the shield with the rest of integrated chrome.
- **offline with cached manifest** — N/A. No network, cache or manifest path is touched. A cached
  configuration still traverses activation, and the shield still requires its own positive evidence
  from a completed main frame.
- **oversized or malformed payload** — N/A. No remote payload reaches this state. The chip displays
  the browser-derived registrable domain and a compiled label, never manifest text.
- **accessibility (TalkBack, font scale)** — Partially verified. Verified by the JVM gate: both new
  colour pairs are in `WeboraColorSchemeTest`'s reflected table; the two shields share one outline
  with distinct interior marks, so meaning never rests on colour alone; the chip carries a
  browser-authored `contentDescription` combining transport meaning and domain (AC-13). **Not
  verified on a device:** actual TalkBack output, and the 200% font-scale layout — which scenario 22
  shows is the weakest part of this ticket.

## Result

Status: QA_PASSED

Notes:

- **The chip's 200% font-scale behaviour is a known, measured limitation, not an unknown.** The review
  proposed raising `SECURITY_CHIP_MAX_WIDTH`; measuring the row refuted the fix while confirming the
  symptom. On a 320 dp host the brand row has 280 dp, of which Back, the logo and three gaps take
  116 — leaving 164 dp for the title *and* the chip. At 100% scale the chip's content is ~117 dp, so
  the 160 dp cap never binds; at 200% it wants ~198 dp, so available width binds at 164 first. Raising
  the cap to 200 dp widens the chip by 4 dp and takes the title from 4 dp to 0. The cap therefore
  stayed, the arithmetic is recorded at its declaration, and the real problem — one row cannot hold
  Back, a logo, a manifest title and a full domain at 200% — is filed as `UX-023`.
- **The instrumented half is compiled, not executed.** Scenarios 19, 20 and 23 are Unknown: this
  checkout has no emulator. That includes the new identity floor, so the assertion that would catch a
  future shrink has itself never run. Instrumented results are evidence and are never promoted to a
  gate claim — `A11Y-001`'s rule, and the posture `CI-002`–`CI-005` each recorded.
- The security model itself is fully covered by the JVM gate: every transport transition, the
  single-owner mapping, the colour measurements and the no-manifest-colour contract all fail on the
  developer machine if they regress.
