The emulator's Wi-Fi dropped in the same second the user allowed SiteSkin, and the asset request
went out into a network that was being torn down. The manifest fetch, ten seconds earlier at
`17:41:22`, had gone out over a working one — which is why the skin activated at all and only the
logo is missing.

### The finding

**The refusal was correct. What is not correct is that it is permanent.**

`BrowserScreen`'s effect is keyed on `integrated?.configuration`, and
`BrowserState.forObservedOrigin` deliberately returns the *same* `Integrated` instance for every
same-origin page start. So the key never changes while the user stays on the site, the effect never
re-runs, and nothing ever asks again. Wi-Fi came back **6.4 seconds later** and Webora did not
notice: that origin shows a monogram for the rest of the visit, with the logo one HTTP request away
the whole time.

That is not an emulator artefact. It is what a site owner's users get on any connection that blinks
at the wrong moment, and it is a better explanation of runs 11 and 15 than a systematically-losing
race ever was — a network blip during app start-up is common on a cold emulator, and the asset load
is the one request that happens at the least stable moment, immediately after a user interaction
several seconds into the session.

**So `TASK-6` is a bounded retry, and only for this one stage.** `TRANSPORT_UNAVAILABLE` is the only
outcome that is transient by definition. A refusal is not retried — the server answered and the
browser declined the answer, so asking again would hammer a site whose logo legitimately 404s. A
decode failure is not retried either; the same bytes decode the same way. `NET-003`'s caps,
allow-list, same-origin recheck and monogram fallback are untouched.

## Run 16 and 17's other failure, which is not this ticket's

The journey ended on `CI-005`'s guard rather than on the new assertion:

```
Refusing to capture 03-siteskin-integrated: the page region rendered, but Webora never owned
the screen at the moment a frame was taken, within 20000ms.
```

`rendered-03-siteskin-integrated.txt` records twenty consecutive attempts over 20.3 s, every one
`REJECTED Application Not Responding: com.android.systemui owned the screen when the frame was
taken`. `focus-03-siteskin-integrated.txt` shows `MainActivity` focused at the *point* check that
ran first — precisely the gap `CI-005` was written to close, working as designed.

Not caused by this ticket's wait: the trace existed after 891 ms, so the added wait was under a
second. Same root cause as the Wi-Fi drop — the run's `system_server` was thrashing at that moment,
with `Long monitor contention` on `BroadcastQueue.processNextBroadcast` for 541–755 ms across six
threads and a `com.google.android.gms` package-modified storm in the same second.

It recurred on run 17, so it is now four runs out of nine — 13, 16, 17 — and run 17's logcat shows
**five** processes ANR in sixteen seconds (`com.android.systemui`, `com.android.phone`, `LatinIME`,
`com.google.android.as`, `googlequicksearchbox:interactor`), each preceded by
`Timeout executing service`. The device is starving, not just System UI, and `CI-005`'s guard is
doing exactly its job by refusing a contested screen.

Opened as **`CI-006`**, with the two tempting fixes ruled out in the entry: do not lengthen the
capture deadline, and do not dismiss from the capture loop. Run 18 shows a quiet device produces the
frame on the first attempt at 478 ms, so the fix belongs in readiness, not in the guard.
