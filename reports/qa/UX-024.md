## Edge cases

- **Invalid manifest → regular browser mode.** N/A — no validation logic changed. Structurally
  reinforced rather than merely unaffected: the hub composes only under `ChromeHandoff`'s
  `PROTECTED_INTEGRATED` projection, which a rejected manifest never reaches, so a failed validation
  leaves `BrowserNavigationShell` — with its own Reload — as the only navigation surface.
- **Origin change / redirect.** Every main-frame page start emits `RendererEffect.DiscoverManifest`,
  which sets `overlay = null` for the owning tab; an exact-origin departure additionally drops
  Integrated mode, removing the header and its `Popup` from composition. So an open bouquet cannot
  survive into another origin either by state or by structure. `SKIN-004`'s activation path is
  untouched.
- **Offline with cached manifest.** N/A — `NET-002`'s cache is not read, written or keyed by anything
  this ticket adds. A cache-served activation produces the same `SiteSkinConfiguration` and therefore
  the same header, with the same three browser commands, whose enabled state comes from the tab's
  observed history rather than from the manifest's provenance.
- **Oversized or malformed payload.** N/A — no parsing, no limits, no diagnostics. The hub's item
  count is a compiled `listOf` of three, so no manifest collection size reaches it; `SiteSkinLimits`
  is not consulted because there is no remote string or collection on this surface to bound.
- **Accessibility (TalkBack, font scale).** Covered rather than N/A. Each bubble is a
  `WeboraIconButton`, so the one `MINIMUM_TOUCH_TARGET` owner enforces 48 dp and a
  `contentDescription` is a compile-time requirement; enabled state is the semantics `Disabled`
  property, not colour (`A11Y-001`). The collapsed hub carries `siteskin_open_navigation` — a
  browser-authored name distinct from `R.string.back`, so a screen-reader user is told the control
  opens navigation rather than performs it. Scenario 14 pins reachability at 320 dp × 200%; the
  bubbles are icon-only and fixed-size, so scale cannot grow them out of the host.
  `BrowserSurfaceConventionsTest` scans the new composables automatically — its set is discovered
  from `@Composable`, not listed — and passed unedited, which covers the no-string-literal and
  no-raw-Material-button rules.
- **Tab isolation (`BROWSE-006`/`BROWSE-009`).** Not in the template and worth answering: the hub's
  callbacks are the selected tab's `onBack`, `controller::goForward` and `onRefresh`, all resolved in
  `RegularBrowser` where `controller` and `state` are already the selected tab's. No renderer
  callback, no `WebViewEvent`, no `BrowserSession.update` was touched, so no cross-tab write is
  reachable through this surface. A tab switch resets the overlay at its existing site.
- **Capture integrity (`CI-002`…`CI-005`).** The bouquet's `Popup` overhangs `BROWSER_CONTENT_TAG` by
  about 40 dp. No canonical frame opens it, and no capture policy, deadline, threshold, dismissal or
  exclusion was edited. The constraint — never capture a frame with the bouquet open under
  `requirePageContent = true` — is recorded in `CLAUDE.md`, the plan and both hosted tests, and is
  currently enforced by prose rather than by a test, which is stated in the review rather than
  claimed otherwise.
