# Review: UX-014
Date: 2026-08-15
Status: RESOLVED

## Summary

The implementation preserves the existing exact-origin/mode and asset-publication boundaries while
replacing only protected integrated top chrome with the UX-013 primitive. Browser identity and Back
remain structurally separate from trusted site branding. One medium test-evidence gap must be fixed
before QA: the new adaptive top-bar layout is instrumented at compact/large-text size for only one
theme/motion pairing rather than every PRD-required pairing.

## Findings

### FINDING-1 · Medium · PRD AC-5/AC-6
**File:** `app/src/androidTest/java/app/webora/browser/siteskin/SiteSkinTopBarTest.kt`

Resolved by `TASK-FIX-1`: `compactLargeTextKeepsOwnedBrandIdentityAndBackSeparate` now iterates
light/standard, dark/standard, and dark/reduced at 320 dp/200%, applying the same required-node,
48 dp Back, and brand-before-identity assertions to each pairing. Instrumentation compilation and
the full pre-commit gate pass.

Originally, `compactLargeTextKeepsOwnedBrandIdentityAndBackSeparate` covered 320 dp/200% only with
`darkTheme = false, reducedMotion = true`. Existing default tests cover light/standard but not the
same compact large-text geometry under dark/standard and dark/reduced inputs.

Fix: iterate the compact fixture across light/standard, dark/standard, and dark/reduced presentation
inputs and assert the same required tagged nodes, 48 dp Back target, and brand-before-identity bounds
for every pairing. This also proves the closed motion field does not conditionally remove slots.

## Not findings

- The top bar does not add tabs/overflow buttons. M9 assigns their new fixed dock placement to
  UX-015; UX-014 preserves their existing separately browser-owned reachability rather than
  duplicating them.
- `ExpressiveMotionPolicy` currently selects no visible animation. Standard and reduced rendering
  being identical is allowed: motion is decorative and optional, while wiring the policy now keeps
  later decoration from bypassing the platform choice.
- The curved header reads no safe-drawing inset. `BrowserScreen` already owns the single global
  `WindowInsets.safeDrawing` application; reading it again would double-pad the surface.
- The identity uses `MaterialTheme` inside a SiteSkin-coloured parent. The application root is
  `WeboraTheme`, making this the intended browser-token ownership boundary, not an accidental
  Material default or manifest-derived colour.
- Removing the old preview is not a runtime regression; the validated configuration constructor
  prevents a small literal preview model from creating the new closed presentation. Instrumented
  fixtures provide executable layout evidence instead.
