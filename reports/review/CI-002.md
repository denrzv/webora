## Summary

CI-002 removes the cause of the `System UI isn't responding` frames, replaces implicit readiness
with an observed and recorded one, and makes a contaminated capture impossible to publish by
checking who owns the screen immediately before each screenshot.

## Architecture

| Concern | Assessment |
|---|---|
| Production boundary | No `src/main` change. No new dependency, permission, or manifest-facing behaviour. |
| Ownership of the decision | One object, `ScreenEvidencePolicy`, with no second copy. The shell gate deliberately reports the focused window and never classifies it, and its self-test asserts that non-duplication rather than leaving it to a comment. |
| Source-set placement | `src/screenshotPolicy/java` reaches `test` and `androidTest` and no variant, so the JVM gate proves the decision and the device consumes the same bytes. Follows the `debugRelease` → `src/release/java` precedent, including AGP 9's need for both `java.srcDir` and `kotlin.srcDir`. |
| Cause versus symptom | The build moved out of the emulator step; the guard is defence in depth. Verified by the green run: `75 actionable tasks: 1 executed, 74 up-to-date`, against 72 executed in the run that produced the contaminated frames. |
| Diagnostics | Readiness samples, the APK precondition, per-capture focus lines, interference records and refused-capture dumps all reach the artifact. Existing artifact names, paths and upload globs are unchanged, so `DEVX-002` starts from the layout it planned against. |
| Failure surface | Every wait is bounded and every bound is diagnosed; there is no path where the guard cannot decide and the capture proceeds anyway. |

## Security

| Property | Assessment |
|---|---|
| What may be dismissed | An allow-list of one process in one dialog shape. No `else` branch dismisses; a System UI *crash*, an ANR in any other process and an unrecognised window are all failures. |
| What can never be hidden | A Webora crash or ANR dialog is `Blocked` with the observed window in the message. Negative control 1 (allow-listing the app package) fails exactly that case. |
| Input provenance | The verdict reads window titles AOSP builds from a **process name**. No translated string, page content, dialog text or manifest field reaches the classification, so a website has no path into it. |
| Fail-closed | Absent, null, unparseable and disagreeing focus states are refusals, not passes — the no-op failure mode a capture guard cannot afford. Negative control 3 covers the disagreement case. |
| Workflow privilege | Unchanged: `workflow_dispatch` only, `contents: read`, no secret, emulator action still pinned to its commit SHA. |
| Consent | Untouched. The journey still clicks the browser-owned `Allow` and still asserts the exact canonical `https://denrzv.github.io` identity. |
| Test hooks in the product | None. Nothing was added to `src/main` to make automation easier; the guard reads the device as a person would. |

## Findings

### FINDING-1 · Medium · gate coverage
**File:** `.github/workflows/ci.yml`

The readiness self-test is wired into `scripts/pre-commit-check.sh` and therefore runs locally and
nowhere else. CI does not run that script: `guardrails` runs the pre-commit hooks, `android` runs
Gradle tasks, and `detekt` runs detekt. The repository already mirrors gate items into CI
individually — `:app:assertInspectorAbsentFromReleaseVariants` has its own step for exactly this
reason — so a shell gate that exists only in the local script can be regressed by any pull request
without CI noticing.

Fix: give it a step in the `guardrails` job, which is where the repository's other shell checking
already lives. **Resolved by `TASK-FIX-2`.**

```yaml
      - run: pre-commit run --all-files
      - name: Emulator readiness gate self-test
        run: bash scripts/android-emulator-ready-selftest.sh
```

## Not findings

- **`WAIT_VIEW_IDS` contains `android:id/aerr_wait`, which the current policy can never reach.**
  Only the ANR dialog is dismissable and that is an `AlertDialog`, so `button2` is the expected id.
  The second id stays because the id is not public API and the failure mode of guessing wrong is a
  red run rather than a wrong press: with the exactly-one-match rule, tolerating both spellings
  cannot make the harness press something ambiguous.
- **A successful capture writes `diagnostics/focus-<label>.txt` even when nothing was wrong.** That
  is the reconciliation channel the research note owed: the fixtures in `ScreenEvidencePolicyTest`
  are shaped by hand, and this is what lets them be checked against a real API 33 device. It is an
  excerpt of the lines that decided the verdict, not a second classification.
- **The dismissal path did not execute in either hosted run.** Expected, and stated as a risk in the
  PRD before the runs happened: removing the contention should stop producing System UI ANRs. It is
  why the proof of the decision lives in JVM negative controls rather than in a green run.
- **The boot-animation condition is trivially satisfied while the workflow passes `-no-boot-anim`.**
  It is kept because that flag lives in the workflow and can be removed there; the self-test pins
  all three spellings (`running`, `stopped`, unset) so the branch is exercised even when the device
  cannot exercise it.
- **`ScreenEvidencePolicy` has no build-level absence check like the inspector's.** The inspector
  needed one because it is declared in a variant source set and could be compiled into a shipped
  APK. This file is in no variant at all, and the property that matters — that no browser code
  depends on harness policy — is enforced by the compiler: a `src/main` reference to it does not
  build. A dead class in the APK would be the worst outcome, not a security one.
- **`docs/DEVELOPER_PLAN.md` is not updated.** It records the intended execution order for M7, which
  this ticket followed; `ROADMAP.md` is the tracker and carries the tick.
- **The job log does not say whether a dialog was dismissed** — only the artifact does. Presentation
  of evidence in the job summary is `DEVX-002`'s scope, and it is listed there. Handed over rather
  than pre-empted.
