# Review: UX-023

Source of record: `docs/BACKLOG.md` § `UX-023` (no GitHub issue)

## Summary

The trust chip moves to a row of its own when the brand row cannot hold it beside the site's title.
One pure decision over width, font scale and the browser-derived domain length; one
`BoxWithConstraints` consuming it; one new row. Three commits, 10 files.

The structural claim worth checking is the negative one: `git diff --name-only origin/main..HEAD`
touches no renderer, event-routing, discovery, consent, capture-policy or `spec/` file, so criterion
10 is met by construction and verifiable from the diff rather than from a test.

## Findings

### FINDING-1 · High · the inline cap survived the wrap, so the ellipsis did too (fixed, `TASK-FIX-1`)

**File:** `SiteSkinTopBar.kt`, `SiteSkinSecurityChip`

`SECURITY_CHIP_MAX_WIDTH` is `widthIn(max = 160.dp)` on the chip itself, and the wrapped row called
the same composable. So at 200% on a 320 dp host the chip was given a row to itself, 280 dp of space,
and **was still capped at 160 dp** — while `example.co.uk` at that scale needs ~208. The domain went
on rendering as `example.c…`.

That is criterion 1 failing, in the one branch the whole ticket exists to add.

**The instrumented case could not have caught it.** `SECURITY_CHIP_FLOOR` is 140 dp; a chip pinned at
exactly 160 clears it comfortably. A width floor below the cap can never detect the cap. This is
`UX-021`'s own lesson arriving one ticket later — there, `assertTrue(width > 0f)` passed on a chip
showing one character, and the answer was a floor that means something.

Fix: the cap becomes a parameter defaulting to `SECURITY_CHIP_MAX_WIDTH`, and
`SiteSkinIdentityRow` passes `Dp.Unspecified`. The constant exists to stop the chip starving the
site's title *in the brand row*; on a row with no title it has nothing to ration. The enclosing
`Row`'s constraint still bounds the chip, so nothing can overflow the header.

The new assertion is `assertWidthIsAtLeast(SECURITY_CHIP_MAX_WIDTH + 1.dp)` — *more* than the inline
cap, which is the direct statement that the cap is not binding here, and the constant is now
`internal` so the test names it rather than restating 160.

**Note this does not reopen `UX-021`'s decision.** That review proposed raising the cap for the
*inline* row, and measuring refuted it: the binding constraint there is available width, and a
larger cap trades the site's title for a character of domain. Here there is no title on the row and
no trade — which is exactly why the wrap was the fix and tuning the constant was not.

### FINDING-2 · Medium · a security assertion keyed on first-occurrence-in-file (fixed in TASK-2)

`the security identity is laid out after the flexible title` compares `indexOf("SiteSkinSecurityChip(")`
against `indexOf("Modifier.weight(1f)")`. Adding a second call site above `BrandRow` inverted it, and
the plan had predicted the assertion would pass unedited.

Fixed by moving the declaration below `BrandRow` — file order is incidental — rather than by relaxing
the assertion. Recorded because the fragility is real and its own KDoc had already named it
("would make that depend on declaration order for an unrelated reason"). TASK-3's
`both identity placements keep the chip away from site content` is the durable statement: in `INLINE`
the chip follows the weighted title; in `OWN_ROW` it shares its row with no site content at all,
which is a stronger guarantee than ordering and does not depend on where anything sits in the file.

### FINDING-3 · Low · two assertions that passed for the wrong reason (fixed in TASK-3)

- `one width read` counted bare `BoxWithConstraints` and scored the **import**. Counting
  `BoxWithConstraints(` is the mechanism — `UX-020`'s "assert the application, not the declaration".
- The title check was `onNodeWithText(...).assertIsDisplayed()`, which `UX-009` established passes
  over a title clipped to nothing, because clipping happens in the parent's draw while the semantics
  tree keeps full text and unclipped bounds. Now a 100 dp bounds floor.

## Not findings

- **`BoxWithConstraints` is a subcomposition.** It re-subcomposes on size change, not per frame, and
  the header's size is stable during a page's life. The PRD's performance NFR is met.
- **The wrapped row adds ~28 dp of height when it fires.** `EXPRESSIVE_HEADER_MIN_HEIGHT` is a
  minimum, so no constant changes and the header already grows with content.
- **A 16-character domain now wraps at 100% on a 320 dp host.** Stated in the plan rather than
  discovered here. Inline it left the title 22 dp — an ellipsis and nothing else — so the wrap is the
  better layout. The hosted emulator is 360 dp, where `denrzv.github.io` stays inline, so
  `CI-009`/`CI-010`'s frames are unaffected.
- **`headerIdentityPlacement` is evaluated on every recomposition of the header.** It is four
  arithmetic operations on primitives; hoisting it would need a `remember` keyed on three values that
  are already cheap to read.

## Verdict

**Sound, with one high-severity fix.** FINDING-1 is the kind a review exists for: the feature was
structurally complete, every test was green, and the acceptance criterion it was written for was
still failing — because the assertion protecting it could not see past a constant. The wrap without
that fix would have shipped a taller header that changed nothing a user could read.

Hosted acceptance for `CI-009`/`CI-010` should be re-taken with `BROWSE-011`'s, though the frames are
expected unchanged: the emulator is 360 dp and the reference integration's domain stays inline at
default scale.
