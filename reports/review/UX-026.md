# Review: UX-026
Date: 2026-08-19
Status: OPEN

## Summary

Three changes across two production files: a browser-owned scrim gesture with a consuming panel, a
pure height rule, and a top-start content-sized panel. `UX-022`'s `Dialog` is kept, `BrowserBack.kt`
is untouched, no state is added, and `siteskin-core`, the schema, the fixtures and Bloom's manifest
are not edited at all.

The strongest thing in the ticket is not the fix — it is that **two of the six negative controls
passed on their first run**, both against assertions this ticket had just written, and both for the
same reason: a presence check over a scope that contained the defect as well as the fix. Those are
recorded in the tasklist and in `CLAUDE.md` rather than quietly repaired.

## Architecture

| Concern | Assessment |
|---|---|
| Where the decision lives | `hubDrawerHeight` is a pure function in its own file, drivable by the JVM gate — the `headerIdentityPlacement` / `rendererMountAction` / `refreshAction` shape, for `CI-003`'s reason. |
| What stayed a composable | Alignment, the scrim gesture and the consuming node cannot leave one, and are covered by a source contract scoped to `SiteSkinHubDrawer`'s body. |
| State | None added. The one `IntegratedOverlay?` and its three resets are untouched, so `UX-022`'s and `UX-024`'s lifecycle argument still holds without restatement. |
| Blast radius | `SiteSkinHubDrawer.kt` and one new file. `HubDrawerContent` keeps its signature and body, so every `UX-022` instrumented case drives it unedited. |
| Reuse | `heightIn` plus the content column's **existing** `verticalScroll` produces wrap-then-scroll with no new mechanism; nothing was added to make long menus scroll because they already did. |
| Duplication | `HUB_DRAWER_MAX_FRACTION` and `HUB_DRAWER_MIN_HEIGHT` exist once, in the file that reads them, with their arithmetic at the declaration. The test carries its own copies deliberately, so changing a value is a visible test edit. |

## Security

| Property | Assessment |
|---|---|
| Manifest → dimension | Closed by the signature. `hubDrawerHeight(available: Dp)` takes one dimension; an `itemCount: Int` fails the reflective case, and the declaration-line half closes the erasure hole a `fontScale: Float` would otherwise walk through. |
| Manifest → dismissal | No site value reaches the scrim, the gesture, the alignment or the fraction. The site cannot disable outside-tap or Back dismissal because neither reads anything it supplies. |
| Reachable scrim | `HUB_DRAWER_MAX_FRACTION < 1` is a dismissal guarantee: a full-height panel leaves no scrim, and a site with twenty `menu` entries is exactly the case that would reach it. Asserted from both sides. |
| Trust surface | Unchanged. The hub still carries no origin and no TLS state; `UX-021`'s chip stays in the browser-owned header the whole time the drawer is open. |
| Dispatch | Unchanged. Rows still emit the trusted `NavigationItem`; a scrim tap dispatches nothing, asserted. |
| Accessibility as a security surface | The scrim is a gesture and publishes no semantics node, so it neither claims a role nor competes with the rows; Back remains the accessible dismissal path. |
| Origin lifecycle | Not on this path. No new discovery, activation, teardown, network, storage or asset behaviour. |

## Findings

### FINDING-1 · Low · assertion message does not describe the assertion
**File:** `app/src/test/java/app/webora/browser/siteskin/SiteSkinHubDrawerContractTest.kt:187`

The literal-dimension ban is whole-window, and its message names only heights. A future `padding(8.dp)`
in that composable would fail with a message sending the reader to the height policy, which is not
what tripped. The *rule* is right — every dimension in this composable comes from a named constant or
the height rule — so the message should say that rather than the rule being narrowed to match it.

Current:
```kotlin
assertFalse("a literal dp bound would be a second height policy", ".dp)" in window)
```

Fix: state the rule that is actually being enforced, and pin the height chain separately so a second
`heightIn` cannot appear beside the first.

### FINDING-2 · Medium · an acceptance criterion claimed with no evidence
**File:** `app/src/main/java/app/webora/browser/siteskin/SiteSkinHubDrawer.kt:220`

PRD criterion 11 — empty groups render no heading and reserve no space — was claimed by TASK-3 and is
tested by nothing. `HubGroup`'s `if (items.isEmpty()) return` shipped with `UX-022` and has never had
an assertion, in either suite.

That was tolerable while the criterion was about tidiness. It is not now: **it is load-bearing for
this ticket's own sizing claim.** A group that reserved a heading and its spacing for an empty
collection would inflate a compact panel by ~28 dp per empty group, and the reference integration has
one — Bloom's `menu` is empty, so the drawer draws exactly the case with no coverage. A regression
there would show up as "the compact drawer is not very compact" and nothing would fail.

Bloom's model is already built in `SiteSkinHubDrawerTest`, so the assertion is one line:
`SITESKIN_HUB_MENU_TAG` must not exist for a configuration whose `menu` is empty.

## Not findings

- **`pointerInput(onDismiss)` keyed on a lambda.** A changed key restarts the gesture detector, which
  would drop a tap in flight. It is correct here: Compose memoizes `{ onOverlayChange(null) }` because
  its capture is stable, so the key does not churn — and if `onDismiss` genuinely changed, restarting
  is the behaviour you want rather than a detector still holding the old callback.
- **`consumesPanelTaps` consuming every change.** It runs in the Main pass at the panel, and Compose
  dispatches Main children-first, so rows and the scroll have already taken what they need; consuming
  an already-consumed change is a no-op. It does not compete with either.
- **`HubDrawerContent` keeps an unused `modifier` parameter.** It is the standard Compose signature
  and instrumentation composes it directly. The contract asserts the *call site* passes none, which is
  what keeps the inset read on the measuring box; the parameter existing does not weaken that.
- **`windowInsetsPadding` after `testTag` shrinking the tapped area.** It does not. Padding measures
  its child with reduced constraints and reports child + padding, so on a `fillMaxSize` chain the node
  is still full-size and the gesture covers all of it.
- **`Dp.Infinity` from `BoxWithConstraints`.** `max` becomes infinite and `min` stays 180; `heightIn`
  accepts that and the panel wraps. Not reachable inside a full-screen dialog, and safe if it were.
- **Alignment changed from `CenterStart` to `TopStart`.** The asserted property is that the horizontal
  anchor is direction-aware; the forbidden list grew rather than shrank, per `UX-024`'s rule about
  editing an ordered assertion.
- **Run 45's failure is not this ticket's regression.** It predates the branch and is the baseline
  `CI-010` acceptance is being re-taken from.
