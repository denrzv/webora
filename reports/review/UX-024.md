# Review: UX-024
Date: 2026-08-18
Status: RESOLVED

## Summary

`UX-024` consolidates integrated Back, Forward and Refresh into one browser-owned navigation hub,
deletes `BROWSE-011`'s standalone refresh row, and reduces `UX-015`'s five dock commands to three.
The shape is right: the decision left the composable (`browserNavigationActions`), the state
collapsed to one closed value (`IntegratedOverlay`) rather than growing a third boolean, and the two
bouquets share a visual language and **no type**, which is the only genuinely new attack surface the
ticket creates.

Five tasks, all green, each pushed before the next started. Nineteen negative controls run across
TASK-1 through TASK-3, every one recorded with the specific cases it fails — including one that
initially failed *nothing* because it did not compile, which is the finding worth keeping from the
whole exercise.

Three findings, none blocking correctness: two are stale or missing prose that the plan explicitly
called for, and one is a headline claim resting on a source scan where a pixel assertion is cheap.

## Architecture

| Concern | Assessment |
|---|---|

| One state, not three flags | ✅ `IntegratedOverlay?` replaces `siteActionsExpanded`; every existing reset became `= null` at its existing site and no new reset site was introduced. Exclusion is what the type says. |
| Back precedence | ✅ `Popup` in its own window consumes Android/predictive Back before `BrowserBackHandler`. `BrowserBack.kt` is untouched — no second handler racing `BROWSE-002`'s single contract. |
| Layout budget | ✅ The hub takes Back's exact 48 dp slot, so `HEADER_FIXED_WIDTH` did not move and `HeaderIdentityPlacementTest` passed **unedited**. That is the evidence, not the intention. |
| Dock reduction | ✅ Measured, not assumed: 280 dp of slot width gives three slots 93.3 dp against five at 56.0. No geometry constant changed; `BrowserSiteSkinLayoutTest` needed only a parameter rename. |
| Complexity | ⚠️ `RegularBrowser` crossed both detekt ceilings (cyclomatic 14/10, cognitive 16/15) and needed three extractions. Each is a real seam with a documented reason, but the function is at its limit and the next addition will need the same treatment. |
| Duplication | ⚠️ `openNavigationHub()` exists in the smoke test and is inlined in the showcase. Two copies of one interaction, and they already differ (see FINDING-2). |

## Findings

### FINDING-1 · Low · stale prose naming a control that no longer exists
**File:** `app/src/main/java/app/webora/browser/siteskin/HeaderIdentityPlacement.kt:19`, `:63`

The plan's TASK-2 listed this file as **"Modified — KDoc only"** and the edit was never made. The
arithmetic is unchanged and correct, which is the point of the ticket; but the prose explaining it
names a `BrowserBack` that no longer exists, so the next reader measuring the row goes looking for
a control that is not there. This repository's own rule — a scan reads executable lines because
prose participates in the rules it describes — cuts both ways: prose that survives the code it
describes is how a measurement becomes uncheckable.

Current:
```kotlin
 * gutters leave 280 dp on a 320 dp host. The brand row's fixed children — Back 48, spacer 8, logo
 * 40, spacer 12, spacer 8 — take [HEADER_FIXED_WIDTH], so the title and the chip share what is
...
/** Back 48 + 8, logo 40 + 12, and the 8 dp before the chip. */
private val HEADER_FIXED_WIDTH = 116.dp
```

Fix: name the navigation hub, and record *why* the number did not move — that is the load-bearing
fact for anyone changing the leading slot again.

### FINDING-2 · Medium · `CI-008` prerequisite asserted on one of two transition controls
**File:** `app/src/androidTest/java/app/webora/browser/visual/LiveSiteScreenshotTest.kt:174`

`CI-008` requires a browser-owned transition control's displayed and enabled semantics to be
asserted **immediately before it is invoked**, because a click followed by a destination timeout
cannot say whether the action was unavailable or whether the transition failed. This ticket put a
*second* control between the user and the navigation, and the showcase asserts the prerequisite on
the bubble but not on the hub:

```kotlin
waitUntilNodeExists(hasTestTag(SITESKIN_NAV_HUB_TAG))
composeRule.onNodeWithTag(SITESKIN_NAV_HUB_TAG).performClick()
waitUntilNodeExists(hasTestTag(SITESKIN_BACK_TAG))
composeRule.onNodeWithTag(SITESKIN_BACK_TAG).assertIsDisplayed().assertIsEnabled().performClick()
```

A hub that composed but did not open would fail at `waitUntilNodeExists(SITESKIN_BACK_TAG)` with a
timeout naming the *bubble*, which is the ambiguity `CI-008` exists to remove. The smoke test's
`openNavigationHub()` already does it correctly, so the two copies of one interaction disagree —
which is also the reason to have one copy.

Fix: assert `assertIsDisplayed().assertIsEnabled()` on the hub before clicking it, in both files.
This can only make the evidence refuse earlier, per `CI-008`'s own constraint.

### FINDING-3 · Low · criterion 10 rests only on a source scan
**File:** `app/src/androidTest/java/app/webora/browser/siteskin/SiteSkinTopBarTest.kt`

"The header composes one fewer row" is a headline claim of the ticket — it is where the 40 dp comes
from — and its only assertion is `ROW_CANDIDATES.filter { it in header }` over the source. That
catches a returning `BrowserControlRow` and would not catch a differently-named second browser row,
or a hub that grew vertical chrome of its own. `UX-009` is the precedent: an assertion about
*provenance* answered a different question from the one that mattered, and only measuring the box
told them apart.

Fix: assert in pixels at default scale that the header is shorter than the two-row layout it
replaced. Content is 20 + 48 + 20 = 88 dp against a 96 dp minimum, so the header should measure its
floor; a bound comfortably under the old 136 dp fails if any second browser row returns without
pinning an exact number that font metrics could move.

### FINDING-4 · High · the hosted-evidence guard is invisible to Gradle's up-to-date check
**File:** `app/build.gradle.kts:208`, `app/src/test/java/app/webora/browser/evidence/ExpressiveBloomJourneyContractTest.kt:99`

**Found by running FINDING-2's negative control, which appeared not to bite.** Dropping the hub's
prerequisite from `LiveSiteScreenshotTest` left `./gradlew :app:testDebugUnitTest` **green with exit
0 and no test XML written at all** — the task was `UP-TO-DATE`. With `--rerun-tasks` the same edit
fails `canonical visual story is six showcase frames in order` immediately.

```
--- default invocation (what the gate runs) ---
exit=0
--- forced rerun ---
exit=1
   FAILED: ExpressiveBloomJourneyContractTest :: canonical visual story is six showcase frames in order
```

`ExpressiveBloomJourneyContractTest` reads the hosted `androidTest` sources by relative path, and
`testDebugUnitTest` declares **no** input covering them. So the entire `SHOWCASE_MARKERS` /
`SMOKE_MARKERS` / frame-inventory guard — the thing standing between an edited hosted journey and a
silently reduced one — passes on any incremental build where only those files changed. Which is
exactly the change it exists to catch.

This is pre-existing and not introduced by `UX-024`; it went unnoticed because every previous ticket
that edited a hosted test also edited this contract file in the same run, which invalidates the task
for an unrelated reason. `SPEC-001` records the identical lesson and its fix: the corpus
*"declares it via `inputs.dir`, so editing a fixture reruns the tests instead of hitting an
up-to-date check."*

Fix: declare `src/androidTest/java` as an input of the `Test` task and pass its absolute path as a
system property, the same shape `webora.app.src` and `webora.app.res` already use. The relative path
is its own latent hazard — `SiteSkinTopBarContractTest` records why: *"the working directory a test
runs in is not a contract, and a scan that silently fails to find its subject is a scan that passes
for the wrong reason."*

## Not findings

- **`onOverlayChange` clears `browserMenuVisible` even when closing.** Looks like a behaviour change
  from `onSiteActionsDismiss`, which did not. It is a no-op: `onOpenBrowserMenu` sets `overlay =
  null`, so the menu being visible implies no overlay is open, and an overlay being open implies the
  menu is not. Collapsing both into one handler is what removes the asymmetry that could drift.
- **The global SiteSkin toggle does not reset `overlay`.** `onSiteSkinEnabledChange(false)` clears
  `pendingConsent` and deactivates, but not the overlay — and this is genuinely unreachable rather
  than merely covered. Settings is reached through More, which sets `overlay = null` before the sheet
  opens, so no overlay can be open when the toggle is touched. Re-entry to integrated mode requires a
  page start or a configuration change, and both already reset. Adding a defensive line here would
  read as a third reset site for a state whose whole design is that it has none.
- **`ExpressiveBloomJourneyContractTest` dropped `assertFalse(source.contains("SITESKIN_DOCK_BACK_TAG"))`.**
  This looks like a weakened separation between the showcase and the diagnostic smoke traversal. The
  constant no longer exists, so asserting its absence from any file is vacuous — `UX-020`'s "assert
  the application, not the constant" in its other direction. The traversal is still discriminated by
  `PRODUCT_LINK_TEXT`, `waitForProductLink` and `SITESKIN_FORWARD_TAG`, which the showcase does not
  use.
- **The hub's dispatch could in principle be wired to a site action.** It cannot: `onCommand` is
  `(BrowserNavigationCommand) -> Unit` and `dispatchSiteItem` is `(NavigationItem) -> Unit`. The
  boundary is the type system, not a scan, which is why no test asserts it directly.
- **`BrowserNavigationHubState` lives in `BrowserNavigationCommands.kt`, away from the composable
  that consumes it.** detekt's `MatchingDeclarationName` fires on a file with exactly one top-level
  class-like declaration whose name differs from the file's; the types file already declares two, so
  it is the correct home for a third rather than a workaround.
- **No animation.** Deliberate and argued in the plan and `CLAUDE.md`: the issue permits an instant
  transition, and `UX-013`'s policy obligation passes to the first ticket adding a *real* decorative
  transition. Shipping the browser's first animation inside a security-relevant overlay no local gate
  can observe is the wrong place to spend it.
- **Integrated Back is now two taps.** Not a defect — issue #122 directs the consolidation
  explicitly, and the alternative (hub in the header *and* Back in the dock) is the duplicate-controls
  outcome the same paragraph forbids. Recorded as a cost in the PRD and `CLAUDE.md`, to be re-checked
  against the first hosted frames.

## Resolution

All four findings addressed as `TASK-FIX-1..4`, each its own commit and each pushed before the
next began.

| Finding | Fix | Evidence |
|---|---|---|
| 1 | `HEADER_FIXED_WIDTH`'s KDoc names the hub and records that the first term is a *footprint*, not a command | `HeaderIdentityPlacementTest` still passes unedited |
| 2 | One `openNavigationHub()` per file, asserting displayed-and-enabled before the click; the helper's prerequisite is pinned in `SHOWCASE_MARKERS` | dropping it fails `canonical visual story is six showcase frames in order` |
| 3 | Instrumented height bound under the old two-row 136 dp, paired with presence assertions so a header that never composed cannot clear it | compiles; runs on a device |
| 4 | `src/androidTest/java` declared as a `Test` input and passed as `webora.app.androidTest` | both hosted-journey controls now fail on the gate's plain invocation, where they previously returned exit 0 with no XML |

## Verdict

**Approved with four findings**, filed as `TASK-FIX-1..4`. Three are this ticket's: stale prose the
plan asked for, a `CI-008` gap created by adding a second control to a transition that had one, and a
headline claim resting on a source scan.

The fourth is not this ticket's and is the most important. `FINDING-4` was found *by running
`FINDING-2`'s control*, which appeared to bite nothing: the hosted-evidence guard is invisible to
Gradle's up-to-date check, so editing a hosted journey and running the gate passes regardless of what
was written. A control that fails to fail is the signal this repository already knows to chase —
`UX-022` recorded one from the other side — and chasing it here found a gate hole that has been open
for several tickets.
