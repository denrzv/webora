# Review: CI-005
Date: 2026-08-13
Status: RESOLVED

## Summary

Makes the frame written to the artifact one that was clean on **both** capture properties at the
instant it was taken. `captureWhenRendered` previously validated content and nothing else; ownership
had been established once, before a polling loop that then re-screenshotted for seconds.

Hosted run 14 is why: a green job shipped `03-siteskin-integrated.png` with `System UI isn't
responding` over a blank page. And the obstruction was not a contaminant of the measurement — it
*was* the measurement. Three attempts at `differing=0.0023` against a white modal, then `0.3048` the
moment the dialog arrived. The dialog's window is 27.4% of the measured region; a real page had
measured `0.7530`.

The fix is one pure function and one loop. Everything interesting is in what it refuses to do.

## Architecture

| Concern | Assessment |
|---|---|
| Placement | Correct and consistent. `candidateVerdict` joins `focusVerdict` and `RenderedContentPolicy.verdict` in `src/screenshotPolicy/java`, shared into `test` and `androidTest` and into no variant. Three capture-time decisions, three pure functions, one home. |
| Composition over replacement | `candidateVerdict` takes the two existing verdicts as arguments and edits neither policy. Both fixture suites pass unedited, which is the structural evidence that the change stayed in its seam. |
| Two cases, not three | `Accept` / `Retry` only. The capture deadline already owns "give up"; a `Reject` would be a second authority on ending the run, free to disagree with the first. |
| Cost discipline | Blank polls `continue` before the dump. The loop can run forty times, and `CI-004` found run 13's System UI ANR was raised by System UI's own dump service — a harness that polls dumps harder may provoke what it detects. One extra dump per captured frame, three per journey. |
| Separation from `CI-004` | Same file, disjoint functions. `requireAppOwnsScreen` and `dismissSystemAnr` are untouched; a capture loop that pressed buttons would be a second, unbudgeted dismissal path. |
| Diagnostics | `owner=` on the accepted frame, `REJECTED <reason>` per discarded candidate, and `RENDERED BUT CONTESTED` as an ending distinct from `NEVER RENDERED`. Run 14's file recorded four attempts and could not say the frame it kept was contested. |

## Security

| Property | Assessment |
|---|---|
| Direction of change | The ticket's own constraint — *this may only ever make the harness refuse more* — holds. Every branch added is a condition on acceptance; no path accepts a frame that the old code rejected. |
| Ownership source | `dumpsys window` → `focusVerdict`, never pixels. Research recorded the refusal explicitly: pixel inference is the recognise-it-by-looks heuristic `CI-002` rejected, it cannot separate a System UI ANR from a Webora crash dialog from a page drawing a grey card, and a website controls the third. |
| The obstruction is not a region | No masking of the dialog's rect out of the measurement. That would score a page still blank and still covered, and `excluded` keeps its existing meaning — browser-owned chrome composed inside the page box. |
| Threshold untouched | `MINIMUM_DIFFERING_FRACTION` unchanged. The blank page measured `0.0023` and the obstruction `0.3048`; no bar separates them, so tuning would have fixed nothing while weakening a check that works. |
| Dismissal boundary | A `DismissableSystemAnr` is a `Retry` here and never a press. The allow-list, the budget and the `interference-*` records stay where `CI-002` put them. |
| Deadline | Not extended. Discarded candidates consume it like any other poll; no compensation for time lost to a contested screen, which would be the `SETTLE_TIMEOUT_MILLIS` shortcut in a new costume. |

## Findings

### FINDING-1 · Informational · the hosted run cannot support the claim it looks like it supports
**File:** `docs/tasklist/CI-005.md`, `TASK-5`

Run 15 is green, and a green run is exactly as consistent with "the new path never fired" as with
"it fired and recovered". Distinguishing them needs a `REJECTED` line in a `rendered-*.txt`, and this
session cannot download artifacts.

The tasklist says so in those terms rather than implying the fix is field-proven, and the 8m06s
journey time is recorded as an observation explicitly *not* treated as evidence, because boot time on
this profile varies by minutes.

No code change. Listed because the tempting sentence — "verified on run 15" — would have been false,
and this ticket exists because a green run was believed once already.

## Not findings

- **`candidateVerdict` is a top-level function rather than an object member.** `focusVerdict` hangs
  off `ScreenEvidencePolicy` and `verdict` off `RenderedContentPolicy`, so a third object would be
  the consistent choice. It takes both other verdicts as inputs and belongs to neither policy;
  inventing `CandidateVerdictPolicy` to hold one function would be ceremony. The file is named for
  the type, which is what a reader greps for.
- **`content as ContentVerdict.Rendered` in the accept branch.** The cast is safe by construction —
  `Accept` is returned only for that pairing — but the compiler cannot see it through the verdict.
  The alternative is threading the fraction through `Accept`, which would put page measurement inside
  a verdict about ownership. Localised cast, one line from its guarantee.
- **Blank attempts carry no ownership column.** Deliberate and stated in the plan: it would need the
  per-poll dump ruled out on contention grounds. A column that is sometimes true is worse than one
  that is honestly scoped to the frame that was kept.
- **The residual window between screenshot and dump.** Research §5 states it: an obstruction present
  during the capture and gone by the read would slip through. One shell round trip against a 500 ms
  poll, and ANR dialogs do not vanish spontaneously — they are dismissed, and nothing dismisses
  inside this loop. Bracketing would close it at twice the dump cost; the trade is recorded rather
  than silently taken.
- **`contested` is a `var` in a loop.** It is a single latch feeding one message at the end. A
  functional restructure would obscure that the two endings differ only in what was seen.
- **No test drives the guard's loop.** It needs an emulator. The sequence test drives the decision in
  run 14's order, which is the part that was wrong; the loop is compile-checked and evidenced by run
  15.

**Negative controls: three, and the third exists because the first two were not enough.**

1. *Content decides alone* — fails 5 of 8. `owned and rendered is accepted` and `owned but blank is
   retried` still pass, which is the point: the happy path cannot tell the implementations apart.
2. *`Blocked` + `Rendered` accepts* — fails 3, **not the 1 the plan predicted**. The sweep and the
   retry floor catch it too. Recorded as run rather than as forecast.
3. *The sequence* — added during `TASK-2` after noticing `TASK-1` had proved the function on single
   pairs only, which is exactly what research risk 4 warned against: the defect was in *when* the
   function is called. Run 14's order is accepted under the reverted verdict.

## Verdict

**Accept.** One informational finding, already recorded in the tasklist rather than needing a fix. No
`TASK-FIX` is warranted: the finding is a limit on what evidence exists, not a defect in the change.

The thing to keep visible: this ticket exists because a screenshot harness twice reported a green
result it had not earned, and the fix was found by reading the harness's own diagnostics rather than
by reasoning about what should have happened. The diagnostics improvements here are not a side
deliverable — they are what makes the next occurrence a one-line diagnosis instead of three runs.
