# Review: A11Y-001
Date: 2026-08-10
Status: RESOLVED

## Summary
Reviewed `main...a11y-001-accessibility` — 28 files, +1474/-121, six tasks plus one pre-requisite.

The change is structurally sound: each accessibility guarantee has a single enforcement point and a
test that fails when a call site bypasses it, rather than a per-screen sweep that decays. Two
negative controls were run and both are load-bearing. Two findings, both in the *enforcement* rather
than the behaviour — which is the right place for them, since a hole in the gate is how the sweep
comes back.

## Architecture

| Concern | Assessment |
|---|---|
| Enforcement point per guarantee | **Good.** Touch target lives in one wrapper; copy lives in `strings.xml`; the label bound lives in the pure model. None is a call-site convention. |
| Scan-based conventions | **Good, with a hole.** Discovering `@Composable` sources rather than listing them is the right shape, and the coverage floor stops it passing vacuously. The button rule's regex is narrower than the rule it states — see FINDING-1. |
| Pure decisions outside composition | **Good.** `browserAnnouncement`, `accessibleLabel`, `scheme(darkTheme)` and `securityPresentation` are all JVM-testable, so the gate actually covers them. |
| Deviation from plan: announcement derived from state, not a transition | **Correct call.** A Compose live region announces on content change, so the derived value already is the transition. The planned `(previous, current)` signature would have added a second place for it to go stale. |
| Deviation from PRD: polite progress, assertive failure | **Correct call.** Announcing every navigation assertively interrupts the user on every page. |
| `@StringRes` on `SuggestedSite` / `OnboardingPage` | **Better than planned.** Makes a hard-coded name a compile error, which the scan could not have achieved without guessing. |
| Layout: status region now always occupies 4 dp | Acceptable, arguably better — no layout shift when loading starts. |
| Module boundary | Untouched. `:siteskin-core` gained nothing; the app reads `SiteSkinLimits.MAX_LABEL_LENGTH` rather than copying it. |

## Findings

### FINDING-1 · Medium · convention gate is narrower than the rule it states
**File:** `app/src/test/java/app/webora/browser/browser/BrowserSurfaceConventionsTest.kt:~100`

The rule is "browser-owned UI may not reach a raw Material button". The regex implements "may not
import exactly `Button` or `TextButton`, unaliased". Three bypasses survive it:

- `import androidx.compose.material3.Button as MaterialButton`
- `import androidx.compose.material3.OutlinedButton` (and `FilledTonalButton`, `ElevatedButton`)
- `import androidx.compose.material3.IconButton`

`SiteSkinChrome.kt` already imports `FloatingActionButton` and compensates by hand with
`browserTouchTarget()` — which is exactly the call-site convention this ticket exists to abolish,
and which the scan cannot see.

Current:
```kotlin
val RAW_BUTTON_IMPORT = Regex("""^import androidx\.compose\.material3\.(Text)?Button$""")
```

Fix: match any Material button-like import including aliases, and move the FAB into the wrapper file
so the single exemption stays single.
```kotlin
val RAW_BUTTON_IMPORT = Regex("""^import androidx\.compose\.material3\.\w*Button( as \w+)?$""")
```

### FINDING-2 · Low · the status region claims an empty description when it has nothing to say
**File:** `app/src/main/java/app/webora/browser/browser/BrowserScreen.kt` — `BrowserStatusRegion`

When `browserAnnouncement` returns `null` the node is still given `contentDescription = ""` and a
live region. An empty description is not silence: it publishes a focusable, nameless node into the
accessibility tree, which is the same category of mistake as a blank security claim that the rest of
this ticket is careful to avoid.

Current:
```kotlin
val mode = announcement?.liveRegionMode() ?: LiveRegionMode.Polite
Box(
    Modifier.fillMaxWidth().height(STATUS_REGION_HEIGHT)
        .semantics { liveRegion = mode; contentDescription = text }
        .testTag(BROWSER_STATUS_TAG),
)
```

Fix: attach the semantics only when there is an announcement. Losing them is safe — the only state
that yields `null` here is one where `RegularBrowser` is not composed at all.

## Not findings

- **The security row publishes a description alongside its child `Text` nodes rather than replacing
  them.** This looks like a doubled announcement, and it is verbose. It is deliberately identical to
  `SiteSkinTopBar.SecurityIdentity`, which shipped in `SKIN-002` and is pinned by an instrumented
  `assertContentDescriptionEquals`. Making the two modes match was the point of the change;
  switching both to `clearAndSetSemantics` would be a real improvement but cannot be verified here —
  no emulator is available — so changing proven code on an unrunnable assertion is the worse trade.
  Recorded as a known gap ("no end-to-end TalkBack run") rather than silently altered.
- **`SiteSkinChromeModel` still keeps its own 5/5/20 caps instead of `SiteSkinLimits`.** That
  duplication is the deliberate defense-in-depth `SKIN-003` documented. Only the *label* bound reads
  the core constant, and only because the PRD flagged silent divergence as a risk for that one.
- **`BrowserAccessibility.kt` imports the raw Material buttons.** It is the wrapper; the exemption is
  detected by the file declaring `WeboraButton`, not by filename, so a rename cannot widen it.
- **The 4 dp status region is present even when idle.** Reserving the space avoids a layout shift on
  every navigation, which is itself an accessibility improvement.
- **`MIN_SOURCES = 6` looks arbitrary.** It is a floor against a broken source path, not a target;
  the tree currently discovers eight.

## Resolution
Both findings fixed as `TASK-FIX-1` and `TASK-FIX-2` in new commits, not by amending history.

- FINDING-1: the rule now matches any `androidx.compose.material3.*Button` import including aliases,
  and `SiteSkinChrome`'s raw `FloatingActionButton` moved behind `WeboraFloatingActionButton` so the
  exemption stays a single file. Controlled by adding `OutlinedButton` and an aliased `Button` import
  to `SiteSkinChrome`: the rule names both; the previous regex matched neither.
- FINDING-2: `BrowserStatusRegion` attaches live-region semantics only when there is an announcement.

## Verdict
Two `TASK-FIX` micro-tasks, both applied. No behavioural defect found in the shipped accessibility guarantees; both
findings are in how durably they are enforced. The security-relevant claims each hold and each carry
a negative control.
