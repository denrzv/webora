# Review: UX-018
Date: 2026-08-16
Status: RESOLVED

## Summary

Reviewed the privacy-settings modal change against the UX-018 PRD, current browser window ownership,
SiteSkin trust boundaries, Back dispatch, nested clear-data confirmation, and Compose test coverage.
The change moves window policy to a dedicated host while leaving privacy content and persisted state
unchanged. No actionable findings remain.

## Architecture

| Concern | Assessment |
|---|---|
| Window ownership | PASS — `PrivacySettingsDialog` owns modal presentation and dismissal; `PrivacySettingsScreen` remains reusable scrollable content. |
| Browser state | PASS — `BrowserScreen` retains one `settingsVisible` flag and one dismissal callback; browsing, consent, and preferences are not copied into dialog state. |
| Insets | PASS — the dialog applies `safeDrawing` within its own window and no longer receives the underlying browser window's inset modifier. |
| Nested confirmation | PASS — clear-data confirmation remains an independent later-composed `AlertDialog`; cancel returns to the still-open settings modal. |
| Complexity | PASS — the new host has six parameters, one straight-line composition, and no duplicated state or branching. |

## Security

| Property | Assessment |
|---|---|
| Page input isolation | PASS — a platform Compose `Dialog` blocks the underlying app/WebView window while open. |
| Opaque presentation | PASS — a full-size Material background surface covers page pixels in the dialog content region. |
| Back priority | PASS — platform dialog Back dispatch calls `onDismissRequest` before the activity/browser handler; connected test uses a real Back event. |
| SiteSkin isolation | PASS — no configuration, remote color, asset, URL, or callback enters `PrivacySettingsDialog`; stored origins remain display-only browser data. |
| Accessibility | PASS — localized existing content, vertical scrolling, safe insets, and standard dialog Back behavior remain; existing 200% content coverage compiles. |

## Findings

None.

## Not findings

- **The status and navigation bar regions use the dialog window's system treatment rather than the
  content `Surface`.** They do not expose or enable the page; system-bar ownership remains with
  Android while the modal content region is fully opaque and safe-inset content stays reachable.
- **`PrivacySettingsScreen` itself still has no background.** It is deliberately content-only and is
  now hosted by the full-size opaque `PrivacySettingsDialog` in production; direct content tests do
  not need to create a second window.
- **Clear browsing data opens a second dialog while settings remains composed.** This is required so
  cancel returns to settings and confirmation stays explicit. Runtime verification confirms the
  confirmation is above settings and cancel dismisses only that confirmation.
- **No custom `BackHandler` was added.** The dialog window is the correct dispatcher boundary; a
  competing activity-level handler risks allowing browser history to win or double-invoking dismiss.
