## Summary

The implementation correctly reuses one browser-owned shell, preserves the active-tab and Android
back boundaries, and adds strong manifest-isolation and accessibility semantics tests. One compact
width geometry defect must be fixed before QA: six mandatory 48 dp targets cannot fit within the
current 20 dp horizontal gutters on a 320 dp screen.

## Findings

### FINDING-1 · Medium · compact touch-target geometry
**File:** `app/src/main/java/app/webora/browser/browser/BrowserChrome.kt`

Current:
```kotlin
.padding(horizontal = WeboraSpacing.GUTTER, vertical = WeboraSpacing.SMALL)
```

At 320 dp width this leaves 280 dp, but six required 48 dp targets require 288 dp. The final action
can overflow or clip even though isolated-node tests prove each child requests 48 dp.

Fix:
```kotlin
.padding(horizontal = WeboraSpacing.LARGE, vertical = WeboraSpacing.SMALL)
```

Add a shell-level compact-width assertion proving its bounds remain within the host and all six
actions remain displayed.

## Not findings

- Keeping Tabs in overflow as well as directly in the dock is intentional compatibility, not a
  duplicate implementation; both dispatch the same browser callback.
- Home passes inert callbacks for disabled Back/Forward/Reload. They cannot dispatch because the
  Material controls are disabled, and the API remains uniform across modes.
- Integrated mode still replaces the bottom product slot. `UX-012`, not this ticket, owns its
  transition contract; the existing top-bar browser Back/security boundary remains intact.
- `safeDrawing` includes more than the navigation bar, but it is applied exactly once at the screen
  root and is the repository's established edge-to-edge contract.
