## Findings

### FINDING-1 · Medium · accessibility semantics accuracy
**File:** `app/src/main/java/app/webora/browser/siteskin/SiteSkinChrome.kt:156`

Current:
```kotlin
private fun MenuItem(label: String, icon: String?, selected: Boolean = false, ...)
```

The default applies “Not selected” to quick actions, favourite, and every browser command. Those
items are actions, not members of the active navigation selection set, so assistive technology is
given a false state contract. The current instrumentation covers dock targets but does not render
the hub and therefore cannot detect the regression.

Fix:
```kotlin
private fun MenuItem(label: String, icon: String?, selected: Boolean? = null, ...)
```

Apply `stateDescription` only when `selected != null`, and add a Compose test that renders the hub,
asserts selected/not-selected semantics only on navigation, separate headings, typed callback
dispatch, and no selection state on quick/browser actions.

## Not findings

- Header Back and dock Back are intentionally both present: UX-008/UX-014 require the fixed header
  escape while UX-015 explicitly requires Back in the M9 dock; neither is site-controlled.
- More and the brand control opening the same hub is intentional. The surface maintains separately
  attributed site and browser sections and avoids a second menu authority.
- Reconstructing expressive presentation for top and dock does not widen trust; the factory is pure
  and both calls consume the same trusted configuration and browser/platform inputs.
- `BrowserMenuCommand.TABS` remains in the closed shared browser vocabulary even with the fixed Tabs
  dock command. Keeping one vocabulary avoids release/debug command drift; it does not allow a site
  to create or dispatch Tabs.
