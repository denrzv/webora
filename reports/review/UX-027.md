# Review: UX-027

Status: RESOLVED

Issue: [#128](https://github.com/denrzv/webora/issues/128)
Reviewed at `1bc20ec` on `claude/bloom-flowers-reference-y5ybs7`, based on `origin/main` `7fe22ba`.

## Summary

A blackholed logo request exhausted `NET-004`'s three attempts in 33 seconds and was then never
retried, because the load effect keys on a configuration instance that deliberately never changes.
The fix is a later opportunity — a same-origin page start — not a bigger burst. Three commits.

## The diagnosis is the deliverable

The plan refused to name a defect before reproducing, and that discipline paid twice.

**TASK-1's reproduction went green**, with Bloom's real manifest, the real 512 × 512 PNG, the real
source, loader and publication guard. That excluded resolution, transport policy, media validation,
decode gating, publication and the configuration-identity association *by evidence*. Had the fix been
guessed from the issue's section 4 — "check for stale `remember`, incorrect `key`, non-observable
mutable state" — it would have been a composition change for a defect that is not in composition.

**The device then named the cause**, through the inspector `NET-004` built for exactly this:

```
Produced by  TRANSPORT_UNAVAILABLE      HTTP status  —
Load took    32863 ms                   Attempts     3
Transport → Outcome CACHED, Cache FRESH_HIT
```

`3 × CALL_TIMEOUT_SECONDS + 1 s + 2 s = 33 s` against 32 863 ms. Every attempt hit the full call
timeout with no server answer. And `FRESH_HIT` means the manifest never made a request, so SiteSkin
activating was never evidence the network was reachable — the two are independent and only one of
them called out.

## Findings

### FINDING-1 · The fix must not be a bigger burst (accepted as designed)

Raising `MAX_ATTEMPTS` is the obvious response and it is wrong twice over: it moves the boundary a
third time — `NET-004` already moved it from 0 s to 33 — and it lengthens a stall the user is already
sitting through, since each attempt costs a full 10-second timeout. `retriesBrandAsset` instead uses
a trigger the browser already observes. Verified not to spin: no page start, no retry.

### FINDING-2 · The retry must not widen what is acceptable (controlled)

The pressure in this ticket runs toward publishing more eagerly, and the guard that would be relaxed
is the one stopping one origin's brand over another's page. `publishesBrandAsset`, `NET-003`'s caps,
the allow-list, the signature match and the same-origin recheck are all untouched, and
`BrandAssetLoaderTest` passes **unedited** — which is the check that the fix changed how often the
browser asks, never what it will accept.

### FINDING-3 · `NET-004`'s exclusions had no test naming them (fixed)

They were argued in prose and enforced by a single `==`. They are now asserted by name — a rejection
means the server answered, the same bytes decode the same way, an undeclared logo has nothing to
request — beside a reflective sweep over every other stage. Both halves matter: the sweep alone would
let a newly added stage become retryable by omission.

## Not findings

- **The 10-second call timeout is unchanged.** Shortening it would make the browser give up sooner on
  a slow-but-working network; it is not implicated by a blackhole.
- **`Load took 32863 ms` is a stall the user sees.** It is bounded, off the main thread, and
  cancellable; shortening it is a separate trade against slow networks and belongs to its own ticket.
- **The reproduction stubs `BitmapFactory`.** A JVM has none; that is why `BrandAssetDecoder` is an
  interface, and everything either side of it is real.
