# Review: CI-003
Date: 2026-08-12
Status: RESOLVED

## Summary

Makes the screenshot harness wait for **drawn pixels** in the page region before capturing the
integrated frame, instead of treating a populated semantics tree as evidence that anything was
painted.

Verified on hosted run **11** (`31589153900`, `7629c620`): `PASSED differing=0.7530 after 696ms`,
and the owner confirmed frame 03 shows both the page and the top bar. The ticket's premise held —
this was a 696 ms timing race, not a product defect.

The ticket cost two hosted runs to get right, and both detours are the interesting part of this
review: run 10 passed on Webora's own chrome, and the stated cause of that pass was itself wrong.

## Architecture

| Concern | Assessment |
|---|---|
| Placement of the rule | Correct and load-bearing. `RenderedContentPolicy` sits beside `ScreenEvidencePolicy` in `src/screenshotPolicy/java`, shared into `test` and `androidTest` and into no variant. It takes an `IntArray`, never a `Bitmap` — an Android type in the signature would move the decision into a source set the gate cannot compile. |
| Split of concerns | Held. The guard reads, waits and records; the policy decides. Identical to `CI-002`'s split, and the reason a checkout with no `/dev/kvm` can still fail the rule. |
| Ordering | `requireAppOwnsScreen` before `captureWhenRendered`. Ownership is `CI-002`'s question and must be settled before pixels are worth reading. |
| Scope discipline | The check measures the page region only. A broken top bar would stay visible in the evidence rather than being absorbed by a longer wait — which is what made "unpainted vs absent" answerable at all. |
| Test-tag in `main` | `BROWSER_CONTENT_TAG` follows `BROWSER_SECURITY_TAG`/`BROWSER_STATUS_TAG`. Established pattern, carries a KDoc explaining why the chrome must stay outside it. |

## Security

| Property | Assessment |
|---|---|
| Website influence | Correctly stated as **directional** rather than absent. A pixel check reads pixels the website drew; the achievable property is that page content can make the check **refuse**, never permit. The PRD's original "no website-controlled value may influence the decision" was corrected in research rather than inherited. |
| `CI-002` guarantees | Untouched. `ScreenEvidencePolicy`, the readiness gate, the prebuilt-APK precondition and the one permitted dismissal keep their behaviour and tests. This ticket adds a condition and relaxes none. |
| Fail-closed | An empty sample array is `Blank`, never a pass and never a throw. A deadline with no rendered frame fails the run. |
| Threshold integrity | 1% is justified as a liveness bar and pinned from both sides by tests, so raising it to quiet a run breaks a test. **It was never raised**, including when doing so would have made run 10 look correct. |
| Diagnostics | Records every sample with fraction, modal colour and elapsed time — and now on success too. No secret or page-derived text reaches the file beyond the measured colours. |

## Findings

### FINDING-1 · Low (integrity) · the inspector overlay is still inside the measured region
**File:** `app/src/androidTest/java/app/webora/browser/visual/LiveSiteScreenshotTest.kt:chromeInsidePageRegion`

`chromeInsidePageRegion` excludes `SITESKIN_QUICK_ACTIONS_TAG` and nothing else. The `SiteSkin
inspector` floating action also composes inside `BROWSER_CONTENT_TAG` and is not excluded. Measured
from run 11's diagnostic, the quick action is `126×126 = 15,876 px` against a region of
`1080×1757 = 1,897,560 px` — **0.84%**. Two chrome buttons of that size clear the 1% threshold
together, so a completely blank page could still satisfy the check on Webora's own UI.

Invisible today: the page renders at 75%, two orders of magnitude above the bar.

**Deliberately not fixed here.** `DEVX-003` removes the inspector from canonical evidence outright,
which closes this without a second exclusion to maintain. Recorded in `docs/BACKLOG.md` under
`DEVX-003` with the alternative (add the exclusion to `chromeInsidePageRegion`) if that plan changes,
and in `docs/ROADMAP.md` so the dependency is visible from the milestone view.

### FINDING-2 · Informational · the run-10 diagnosis was wrong and is corrected in place
**File:** `docs/tasklist/CI-003.md`, `TASK-FIX-1`

`TASK-FIX-1` asserted the quick action cleared the bar at ~1.04%, from an estimate off a 360 px
contact-sheet tile. Run 11's diagnostic gives the real geometry: 0.84%, below threshold. The fix was
right for the right reason — chrome must not count as page content — but the arithmetic behind the
stated cause was not. `TASK-5` records the correction and names `FINDING-1` as the probable actual
cause.

No code change. Listed because a tasklist that quietly reconciles a wrong number is worse than one
that carries the correction.

## Not findings

- **A 20-second deadline on a 696 ms condition looks generous.** It is sized for a cold emulator
  under load, not for the observed case. Tightening it toward the measurement would buy nothing and
  convert a slow runner into a red run.
- **`BrowserErrorPage` inside the measured region counts as rendered.** Deliberate, and recorded in
  the plan. It is browser-owned drawn content and legitimately non-blank; whether an error page is
  *correct* is the journey's assertions to decide. Making this check pretend an error page is a blank
  screen would let one failure impersonate another.
- **Frames 01 and 02 have no content requirement.** Home has no renderer and therefore no page
  rectangle; frame 02's evidence is the consent dialog and its canonical origin, not the dimmed page
  behind it. Requiring content on 02 would measure a scrim.
- **`captureWhenRendered` re-screenshots on every poll rather than reusing one bitmap.** That is the
  point: the returned bitmap is the one that satisfied the check, so the frame saved is the frame
  verified. Reusing a stale capture would make the check a claim about a picture nobody kept.
- **The policy's `HashMap` modal-colour count is not the fastest possible.** ~110k samples per poll
  on a device that is otherwise idle; `CI-002`'s contention concern is about sustained runner work
  during device life, and this is a bounded read of an already-captured bitmap.
- **No JVM test covers the guard's polling or the semantics-bounds read.** They need an emulator.
  Compile-checked with `:app:compileDebugAndroidTestKotlin` and evidenced by run 11; recorded as
  instrumented evidence, never promoted to a gate claim.

## Verdict

**Accept.** `FINDING-1` is a real residual hole with an owner (`DEVX-003`) and a written fallback;
`FINDING-2` is a correction already recorded. Neither warrants a `TASK-FIX` here — one would
duplicate a ticket that is already scheduled, and the other is documentation that has been done.

The ticket's own verdict is worth keeping visible: **it built an instrument that twice reported a
green result it had not earned**, and both times the fix came from measuring rather than from
adjusting the number until the run looked right.
