# Review: UX-002
Date: 2026-08-13
Status: RESOLVED

## Summary

The ticket builds `ADR-013`'s Direction A as a closed fourteen-role browser palette with the Material
types derived from it, adds the five-step type scale, the radius and spacing steps, ten bundled
vector icons, `WeboraIconButton`, and the `values-night` window theme. `MainActivity` composes
`WeboraTheme`. `contrastRatio` is shared by both palettes.

The security half — `C2`, no manifest value reaches a browser token — is tested from two sides with
negative controls proving each side catches what the other cannot. That is the part `ADR-013` handed
over by name, and it is done properly.

Two structural decisions are better than the plan asked for and worth keeping: `ColorScheme`'s
constructor has no default arguments, so an omitted Material role is a **compile** error rather than
a silently-defaulted purple; and the completeness/closure assertions are reflected rather than
listed, so they cover roles nobody has written yet.

Four findings. One is a real hole in a security-adjacent assertion (`FINDING-1`); one is a
correctness problem in *evidence* rather than in the product, and it is the one that would have
quietly degraded `A11Y-001`'s font-scale claim (`FINDING-2`). Both are cheap.

Separately, and recorded here because it is the most interesting thing the ticket produced: the
negative control for `C3`'s placement rule **passed when it should have failed**, and the reason was
that the new wrapper's own KDoc — quoting the rule — exempted its file from it. That was found and
fixed inside TASK-7, not left for review.

## Architecture

| Concern | Assessment |
|---|---|
| Layer shape | Good. A closed role model with the Material type derived from it mirrors `SKIN-001`'s projector with the input removed, which makes the asymmetry between the two palettes legible instead of accidental. |
| Dependency direction | Clean after TASK-7. `browser` → `design` only; `WeboraChrome` deliberately declares no touch-target token, so `MINIMUM_TOUCH_TARGET` keeps one name and one owner. The cycle that would have created was noticed and removed rather than tolerated. |
| No runtime guard on the browser palette | Correct, and the reasoning is recorded in three places. A compiled token below its target must be a build failure; a runtime correction would ship it silently repaired. |
| Values vs. decisions | Strong. The six figures `ADR-013` published are asserted out of the code, and the chip's deliberate sub-threshold separation is pinned so "fixing" it is a visible reversal. |
| Scope discipline | Held. No surface was restyled; `UX-003`/`UX-004` still own their rebuilds. The one handoff (Direction A's 38%-opacity unselected dock slots) is recorded rather than silently solved. |
| Icon mechanism | Right call, and `UX-005` inherits it rather than inventing a second one — which is precisely why `DEVELOPER_PLAN.md` sequences that ticket behind this one. |
| Reflection in tests | Justified. `kotlin-reflect` was not added; a dependency taken on to satisfy a test is still a dependency. |

## Security

| Property | Assessment |
|---|---|
| `C2` — no manifest value reaches a browser token | **Enforced**, two independent mechanisms, both with negative controls. A compile-time reference fails only the scans; a token that moves fails only the sweep. Neither control alone would have justified two halves. |
| The sweep can fail for the right reason | Yes. It asserts the SiteSkin scheme *did* carry the manifest's colours, so a sweep that stopped exercising the projection fails instead of passing by doing nothing. |
| Identity-chip colours are browser-owned | Yes, and named as the sharpest form of the leak: a manifest-derived colour there is `HARDEN-002`'s impersonation surface arriving through colour instead of text. |
| `SiteSkinColorScheme` remains the entire website-influenceable colour surface | Unchanged. `SiteSkinTheme`'s projection, guard, defaults and dark derivation are untouched; only the shared helper moved. |
| New remote input | None. No fetch, no parse, no decode, no permission, no persisted state. |
| Icons as an attack surface | None. A website cannot add a file to `res/drawable`, which is why a bundled vector needs none of `NET-003`'s signature check, size cap or bounded decode. |
| `ADR-006` / `ADR-010` | Untouched. The browser palette is what a failed manifest degrades *to*, and it is now better specified than before. |

## Findings

### FINDING-1 · Medium · closure is by value, so a mis-paired role passes
**File:** `app/src/test/java/app/webora/browser/design/WeboraThemeTest.kt:30`

`every Material colour comes from the browser palette` asserts that each derived colour is a **value**
the palette declares. That is the right property for "no Material default", but it says nothing about
which value went where. `onSurface = scheme.divider` would pass: `divider` is a declared browser
colour. It would also put a 1.3:1 hairline under every piece of body text on a surface.

The measured table covers the pairs today's mapping happens to produce; nothing asserts the mapping
*only* produces those pairs. Material's own naming gives the missing assertion for free — for every
role `onX` there is a role `x`, and the two are a foreground/background pair by construction.

Current:
```kotlin
val declared = scheme.colorRoles().values.toSet()
materialColorScheme(scheme).colorRoles()
    .filterValues { it !in declared }
```

Fix: add a second assertion that pairs each `onX` with `x` in the derived scheme and requires 4.5:1,
including `inverseOnSurface`/`inverseSurface`, whose names do not follow the prefix rule. Every pair
the current mapping produces already clears it, so this is a guard rather than a repair — which is
the point: it fails on the *next* mapping, not this one.

### FINDING-2 · Medium · the instrumented harnesses still compose a Material default
**File:** `app/src/androidTest/java/app/webora/browser/browser/BrowserFontScaleTest.kt:82`, `BrowserSiteSkinLayoutTest.kt:35`, `app/src/debug/java/app/webora/browser/browser/BrowserRecoveryTestActivity.kt:14`

`MainActivity` composes `WeboraTheme`, so the product and the hosted screenshot journey are correct.
The instrumented harnesses are not: each wraps its content in a bare `MaterialTheme { }`.

`BrowserFontScaleTest` is the one that matters. `docs/accessibility/CONFORMANCE.md` records it as the
**evidence** for WCAG 1.4.4 — "200% font scale without overlap or truncation of anything
load-bearing" — and it now measures Material's baseline type scale rather than Webora's. The scales
differ at every step (`bodyMedium` 14 sp vs 13 sp, `headlineLarge` 32 sp vs 28 sp), so the evidence
describes a build nobody runs. That is the same category of defect `CI-002` and `CI-003` exist to
prevent, one layer up: a green check about the wrong thing.

`BrowserRecoveryTestActivity` is smaller but the same shape — a debug activity rendering browser
chrome under a palette the browser no longer uses.

Fix: compose `WeboraTheme` in all three. `internal` is visible from `androidTest`, which is already
relied on for `BrowserScreen`.

### FINDING-3 · Low · the icon budget is evadable by a resource qualifier
**File:** `app/src/test/java/app/webora/browser/design/BrowserIconContractTest.kt:120`

`drawables()` reads `res/drawable` only. `res/drawable-night/`, `res/drawable-v24/` or any other
qualified directory is a real drawable directory that the scan does not see, so both the budget and
the geometry contract can be sidestepped without meaning to — a `drawable-night` variant of an icon
is an ordinary thing to add.

Fix: enumerate every directory whose name is `drawable` or starts with `drawable-`.

### FINDING-4 · Low · the theme rebuilds its constants on every composition
**File:** `app/src/main/java/app/webora/browser/design/WeboraTheme.kt:24`

`materialColorScheme(...)`, `weboraTypography()` and `weboraShapes()` all allocate on each
composition of the theme root. The values are compile-time constants, so the work is pure waste. The
practical cost is near zero — the root recomposes rarely and `MaterialTheme` copies the scheme
anyway — but there is no reason to compute a constant repeatedly, and hoisting removes the question
rather than answering it each time someone reads the function.

## Not findings

- **The identity chip fails 3:1 against its ground (1.27 / 1.29).** Deliberate, ruled on by
  `ADR-013`, and now asserted as a decision. A chip is a status display rather than an interactive
  control, so WCAG 1.4.11 does not govern its boundary, and identity is carried by text at 10.49:1
  plus a glyph and a word. Do not "fix" it.
- **`divider` at 1.44:1 and `scrim` are unmeasured.** They are named decorative exemptions with
  written reasons, and a test requires the reason to be non-blank. Material's `outline` — the role
  that *does* need 3:1 — takes `muted`, not `divider`.
- **`secondary` and `tertiary` are the same colour as `primary`.** Direction A has one accent.
  Giving Material two more would mean deciding two more colours, which is amending `ADR-013` rather
  than implementing it.
- **The error family has no red.** Same reason. It reuses the already-measured `notSecure`/`container`
  pair with the roles swapped, so it introduces no unmeasured colour.
- **Two `Shapes` roles keep Material's 32 dp and 48 dp.** They are `internal` to Material 3 and no
  public API can set them. Adding those radii to `WeboraRadius` to make the scan pass would be
  inventing values to satisfy a test; the exclusion is structural (`$module` name mangling) and the
  limitation is recorded.
- **The display type roles are capped at 28 sp.** Webora draws nothing bigger; Material's 45–57 sp
  display sizes would be a scale nobody uses.
- **`WeboraChrome` has no touch-target token.** Removed on purpose in TASK-7. One name, one owner —
  and the geometry layer is exactly where a target would get shrunk to make a design fit.
- **Ten icons, not `C6`'s eight.** `C6`'s list predates the direction: it names `stop`, which
  Direction A does not draw, and omits `search`, `more` and `warning`, which it does.
- **The drawables declare `#FF000000`.** Never rendered. `Icon` applies `ColorFilter.tint` over the
  whole painter, so the call site's token decides the colour; the declared value only describes an
  untinted use, and the stroke-only rule is what keeps a single tint faithful.
- **No surface was restyled.** Scope, not omission. `UX-003` and `UX-004` own their rebuilds.

## Verdict

**Accept with fixes.** `FINDING-1` and `FINDING-2` should land before `/qa`; `FINDING-3` and
`FINDING-4` are cheap enough to take in the same pass. None of them touches the security property the
ticket exists to establish, which is sound.

## Resolution

All four landed as `TASK-FIX-1`..`4`. Two produced more than the finding asked for:

- **`FINDING-1`** — the pairing assertion's negative control (`onSurface = divider`) fails at 1.55
  light / 1.38 dark **while the membership assertion stays green**, which is the finding demonstrated
  rather than asserted. 14 pairs are checked, `inverseOnSurface`/`inverseSurface` included, with a
  floor so a renamed role cannot empty the scan.
- **`FINDING-3`** — the budget now counts **distinct icon names** rather than files. Scanning every
  `drawable*` directory would otherwise have made a legitimate `drawable-night` variant of an existing
  icon fail the budget, which is not what `C6` bounds. Both directions are demonstrated.
- **`FINDING-4`** — the code landed inside `TASK-FIX-3`'s commit rather than its own. Recorded in the
  tasklist rather than rewritten: the commit is already a pushed handoff checkpoint.

`FINDING-2`'s fix is verified with `:app:compileDebugAndroidTestKotlin`, since the JVM gate never
builds that source set. Its runtime effect — `BrowserFontScaleTest` measuring Webora's type scale
instead of Material's — needs a device and is recorded in QA as pending evidence, not as a gate.
