## Summary

An optional `presentation.dock` nominating up to three already-validated ids; a sealed slot
arrangement resolving them; a dock that renders it and a drawer that subtracts what it rendered; the
reference integration's five pinned copies moved together; and the hosted journey re-pointed at both
surfaces. Six commits across two repositories.

The structural claim worth checking is that **the field adds no capability**. Every id it can carry
already denotes an item the validator produced, so it introduces no action, URL, icon, label or
callback — and `presentation-dock-dropped-item.json` proves the strong form: an item security
validation refused cannot be resurrected by naming it.

## Findings

### FINDING-1 · High · the hardest invariant in the issue was unasserted (fixed, `TASK-FIX-1`)

The issue states it plainly: *"a SiteSkin manifest cannot make tab management inaccessible."* A
projection takes the dock's Tabs slot, and that is safe **only** because `browserMenuCommands()` has
carried `TABS` since `DEVX-003`. Nothing connected the two facts. A future edit to that list would
have removed the browser's tab switcher from integrated mode entirely, with a manifest as the
proximate cause and no test failing.

`a projection may take the Tabs slot only because the menu still offers Tabs` asserts both halves,
and both are needed: the membership check alone passes if projection stops dropping Tabs, the drop
check alone passes if the menu loses it. Verified — removing `add(BrowserMenuCommand.TABS)` fails it,
and re-adding Tabs to the projected arrangement fails three other cases.

### FINDING-2 · Medium · the app layer trusted core's cap (fixed in TASK-2)

`dockArrangement` did not bound the id list; core does, and the app was relying on it.
`SiteSkinChromeModel` already runs its own 5/5/20 caps over core's limits for exactly this reason —
the browser's dock is not where a disagreement between the two layers should first become visible.
Found by its own test rather than by reading. The assertion checks *which* three survive, since a cap
that kept the wrong ones would still satisfy a count.

### FINDING-3 · Medium · a negative control that found a missing fixture (fixed in TASK-1)

Control C — resolving dock ids against the raw manifest instead of the normalized collections —
**passed**. `SPEC.md` states the rule normatively and no fixture exercised it, because none named an
id that security validation had dropped. `presentation-dock-dropped-item.json` does: a `javascript:`
item is refused for its scheme, the dock names it, and it must resolve to nothing. With that fixture
the control fails two cases.

### FINDING-4 · Low · two scans needed scoping, not loosening (fixed in TASK-3)

`!source.contains("else ->")` matched `actionLift`'s unrelated lift table, so the check is sliced to
the slot loop. The de-duplication scan was anchored on `HubGroup(R.string`, which a line-wrap for
detekt split in two. Both are the repository's own recorded traps — scope a scan to its subject, and
anchor it on something a reformat cannot break.

## Security

| Property | Assessment |
|---|---|
| No new capability | The field carries ids. `presentation-dock-dropped-item` proves a refused item stays refused. |
| Browser slots unreachable | `Brand`, `Tabs`, `More` are objects with no fields; `Site` carries only the trusted item. Reflective inventory, with a control. |
| No fourth site slot | Bounded in core *and* in `dockArrangement`; both asserted. |
| Browser and site types stay apart | `UX-024`'s rule, now one surface lower. The shared-shape refactor fails two cases. |
| De-duplication hides, never deletes | Model untouched; `NavMatcher` still resolves a projected route; unprojected ids still listed. |
| Lifecycle | No new path — the arrangement is derived per composition from the active configuration, so existing teardown covers it. |

## Not findings

- **The dock grows to five slots at 56.0 dp each on a 320 dp host.** That is the measurement `UX-015`
  shipped and `UX-024` recorded moving away from; still above the 48 dp target contract.
- **Fewer than three ids still projects.** A site nominating one has expressed the same preference as
  one nominating three; falling back would silently ignore a valid request.
- **`home` and `call-shop` are not projected.** Deliberate in the manifest — a projection covering
  everything would make the de-duplication assertion vacuous.
