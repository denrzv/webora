# Review: CI-004
Date: 2026-08-14
Status: RESOLVED

## Summary

Three commits: a pure `AnrDismissalPolicy` with eight tests and two negative controls, a guard that
searches the classified window instead of `rootInActiveWindow` and records what it saw, and the
documentation. The gate is green, `:app:compileDebugAndroidTestKotlin` builds, and
`ScreenEvidencePolicyTest`'s 20 fixtures, `RenderedContentPolicyTest` and `CandidateVerdictTest` all
pass unedited — research §5's signal that the change did not reach too far.

The ticket's shape held up: the three-way verdict was right in the first plan and survived the
research revision that moved the *mechanism* from patience to reachability.

Two findings that matter, both fixed in `TASK-FIX-1`. **The sharper one is that implementation added
a security control and left it where this ticket's whole argument says a decision must not live** —
enumerating windows is itself a trust decision, and the check that keeps it honest sat in
`androidTest` with no test, which is the shape that let run 13's defect reach `main`. The other is
that the diagnostic tree walk ran on every poll to produce a list read once, on a device the harness
had just been taught to be more patient with.

## Findings

### FINDING-1 · Medium · load
**File:** `app/src/androidTest/java/app/webora/browser/visual/AnrDialogInspection.kt:75`

`inspect` computes `presentViewIds` eagerly on every observation, and only the *last* observation's
list is ever printed. A dialog that never becomes pressable is now polled ~40 times instead of
failing on the first look — that is the fix working — so the walk runs 40 times to produce one list.
Each walk dequeues up to 400 nodes and calls `getChild` for each of their children, all over the
accessibility IPC, on a device that is by construction already not responding.

This is the same class of self-inflicted load `CI-005` removed when it stopped the capture loop
dumping windows on every blank poll, and `CI-004`'s own research flagged the dump service as a
suspect in run 13's ANR. A diagnostic that is read once should be gathered once.

Current:
```kotlin
presentViewIds = presentViewIds(searched),
```

Fix: hand the observation a thunk and force it in `DismissalJournal.report`, so the walk happens at
most once per `requireAppOwnsScreen` call.
```kotlin
walkPresentViewIds = { presentViewIds(searched) },
// in AnrDialogObservation:
val presentViewIds: List<String> by lazy(LazyThreadSafetyMode.NONE, walkPresentViewIds)
```
The roots may be one poll stale when forced; a stale node yields fewer ids, which degrades the
diagnostic and cannot change a decision.

### FINDING-2 · High · untested security control
**File:** `app/src/androidTest/java/app/webora/browser/visual/AnrDialogInspection.kt:145`

Moving from `rootInActiveWindow` to enumerating `uiAutomation.windows` widens what the harness can
see, and `android:id/button2` is the negative button of every `AlertDialog` — including Webora's
first-use consent dialog, which the journey deliberately captures with a dialog focused. The only
thing standing between that enumeration and a harness that presses a Webora dialog is
`isSystemOwned`. TASK-2 implemented it correctly and `TASK-FIX-1` moved it into the gate.

**It has no test, and it is the newest security control in the change.** `PROJECT_RULES.md` requires
security-sensitive behaviour to carry explicit tests including negative cases, and the whole argument
of this ticket is that a capture-time decision living in `androidTest` is a decision nothing verifies
— the property that let run 13's defect reach `main` in the first place. Shipping the fix for that
while adding a fresh instance of it is the wrong trade.

It is a pure function already; only its parameter type is holding it in the wrong source set.

Current:
```kotlin
private fun isSystemOwned(root: AccessibilityNodeInfo): Boolean =
    root.packageName?.toString() in SYSTEM_PACKAGES
```

Fix: take the package name and move the decision beside `AnrDismissalPolicy`, exactly as that policy
takes `List<String>` rather than nodes. The guard keeps reading `packageName` off the node; the rule
about what that name permits becomes gate-testable.
```kotlin
// src/screenshotPolicy/java/.../AnrDismissalPolicy.kt
fun mayBeSearchedForWaitAffordance(windowPackage: String?): Boolean
```
Tests must include the negative cases that matter: Webora's package is refused, a null package is
refused, and a lookalike (`com.android.systemui.foo`, `android.evil`) is refused — with a negative
control that opens the check to any package and fails the Webora case.

### FINDING-3 · Low · tidiness
**File:** `app/src/androidTest/java/app/webora/browser/visual/AnrDialogInspection.kt:258`

`report` appends the `--- last observation ---` header before the null check that can return, so a
journal with no last observation would print a dangling header. Unreachable today — `hasSamples`
guarantees a recorded observation — but the two lines say different things about the same
invariant.

### FINDING-4 · Low · efficiency
**File:** `app/src/androidTest/java/app/webora/browser/visual/AnrDialogInspection.kt:113`

`window.root` is fetched twice per visible window per poll: once in the `systemOwned` filter, once in
`rootsOf`. `AccessibilityWindowInfo.getRoot()` builds a node each call. Fold the fetch into one pass
and carry the root alongside its window.

## Not findings

- **`AutomationFlags.interactiveWindows` never reaches a decision.** Deliberate. The policy's inputs
  are the plan's four fields; the interactive-windows flag explains *why* a lookup found nothing and
  belongs in the record, not in the verdict. If it were an input, a device without the flag would get
  a differently-shaped decision rather than an explained one.
- **`enableRequiredFlags` returns `Unit` and swallows a null `serviceInfo`.** It does not swallow it:
  `inspect` re-reads both flags on every observation, so the condition lands in
  `WaitAffordances.viewIdReportingEnabled` (making the zero a `NotYet`) and in the record. Failing at
  construction would turn a possibly-fine run red on a condition the framework may have satisfied
  already — the plan decided this explicitly.
- **Three identification rules where the plan named one.** The two additions sit *behind* the package
  check and only affect which system-owned window is found. `focused` is not a heuristic: this branch
  runs only because `dumpsys` already said the focused window is the System UI ANR dialog, so input
  focus and the classification are the same fact read through two APIs.
- **`WAIT_VIEW_IDS` is `val` rather than `const`.** It is a `List`, and its two entries are unchanged
  from `CI-002`.
- **A `Press` that finds the node by `decision.viewId` rather than `single()`.** With one candidate
  these are identical; selecting by the policy's answer makes the press provably the decision rather
  than a parallel selection that happens to agree.
- **The journal writes one file per `requireAppOwnsScreen` call and overwrites nothing.** Frames have
  distinct labels, so `dismissal-01-home.txt` and `dismissal-03-siteskin-integrated.txt` coexist.

## Verdict

**Sound, with two findings to fix before the hosted run is worth reading.** FINDING-2 is the one that
matters: the change added a security control and left it in the source set this very ticket exists to
move decisions *out* of. FINDING-1 changes how much work the harness does while the device is ANRing,
which is exactly the variable `CI-004`'s own research suspects in run 13. FINDING-3 and FINDING-4 are
tidiness and ride along.

All four went to `TASK-FIX-1` as a new commit, not by amending history. The package allow-list is
now `AnrDismissalPolicy.mayBeSearchedForWaitAffordance` with four tests; its negative control (any
non-null package searchable) fails the Webora and lookalike cases and leaves the null case passing,
which is the control working — the case the relaxed rule still gets right could never have stood in
for the two it does not.

Not fixed here, recorded for the backlog: the detekt/`androidTest` gap.
