# Review: UX-022

Status: REVIEW_COMPLETE

Issue: [#112](https://github.com/denrzv/webora/issues/112)
Reviewed at `80cf467` on `claude/bloom-flowers-reference-y5ybs7`, based on `origin/main` `14b8e3d`.

## Scope

An optional `presentation.hub` hint carried through validation as a closed enum; one browser-owned
policy resolving it to a surface; a start-side drawer presenting every trusted site item in three
headed groups; and the Brand Hub opening whichever surface the policy chose. Four commits, 32 files.

## Findings

### FINDING-1 — criterion 18 had no negative control (fixed, `TASK-FIX-1`)

The PRD asks for a control proving no `presentation` value changes the dock's order, the browser
security surface, or action validation. TASK-4 shipped without one; the only guards were structural
scans, and a scan asserts what a file *mentions*. The leak worth catching is a value reaching
somewhere it was never named.

`HubHintIsolationTest` is that control as a runtime sweep — `UX-002`'s `C2` shape. The same manifest
is validated once per spelling at the boundary (absent, `auto`, `bouquet`, `drawer`, `carousel`) and
every browser-owned projection is compared across the set: origin, home URL, the browser menu, every
normalized item, every *resolved* action, and every colour role in both projections. Compared, not
sampled — so it covers the fields nobody thought to check.

Its own guard is the load-bearing half. Deleting `presentation` from `SecurityValidator` makes every
configuration identical and the sweep green forever; a second case asserts the hint really does move
the surface. Both controls verified:

| Control | Result |
|---|---|
| `browserMenu` reversed when the hint is `DRAWER` | `no hub value moves any browser-owned projection` FAILED |
| `presentation` never normalized (`val presentation = null`) | `the sweep exercises a hint that really does select a surface` FAILED |

### FINDING-2 — the plan's TASK-4 control described a case that does not exist (fixed in TASK-4)

"Give the drawer its own visibility state → a tab-switch case must fail." There is no tab-switch
case: `siteActionsExpanded` is a `remember` inside `BrowserScreen`, and the JVM gate cannot drive a
composable. The rule became a source contract instead — exactly one hub visibility state, both
surfaces reading it under the names they use.

Worth recording because the naive control **does not compile**: declaring the second state in
`BrowserScreen` puts it out of scope for the reader in `RegularBrowser`. The control that compiles
declares it beside the call site, and that is the one the scan catches. A control that fails to
compile is not a passing control, and the difference is invisible in a grep for `FAILED`.

### FINDING-3 — the first policy rule was stated one level too coarse (fixed in TASK-2)

`the hint is read in exactly one file` failed on `InspectorSnapshot.kt`, which was correct code:
`DEVX-001`'s panel holds a `HubPresentation?` and prints its name, and showing a site owner what was
requested beside what was composed is the entire reason core's nullable holder exists. Displaying a
value decides nothing.

Restated at the mechanism — no file outside the policy may name a `HubPresentation` **constant** —
plus a second assertion that exactly one function maps a hint to a surface. A rule stated too coarse
fails honest call sites and teaches people to widen it; stated at the mechanism it has nothing to
widen. The original control (a `compiledHubDefault` appended to `SiteSkinDock.kt`) fails both.

### FINDING-4 — criterion 14 was unguarded until a control looked for it (fixed in TASK-3)

Only navigation rows may publish selection. Replacing `if (item.isNavigation)` with `if (true)`
compiled, ran, and passed the whole suite. The assertion added for it reads `HubRow`'s body rather
than the file, because a whole-file scan cannot tell an unconditional `selected` from a guarded one;
an instrumented case drives the semantics tree it produces. This is `BROWSE-009`'s lesson —
a guard being correct and a guard being evidenced are different facts.

### FINDING-5 — one written control could not be written, and the reason is stronger (no change)

`assertFalse("configuration." in source)` reads like a ban on re-deriving a group from the untrusted
configuration. Every attempt to violate it is a compile error: `HubDrawerContent` has no
`SiteSkinConfiguration` parameter, so `configuration` is unresolved. The assertion stays — it becomes
load-bearing the moment someone adds that parameter — but today the *type* forbids it and the scan is
documentation of intent. Recorded rather than deleted so nobody mistakes it for tested evidence.

## Decisions taken, for a reviewer to check first

**`CI-009`'s frame 04 changed subject, and `requirePageContent` was removed from it.** Bloom declares
no `presentation`, so `AUTO` resolves to the drawer and the hub frame now photographs a full-window
modal. `RenderedContentPolicy` asks whether `BROWSER_CONTENT_TAG`'s rectangle is non-uniform; the
drawer's window covers that rectangle, and a drawer is gloriously non-uniform. Keeping the check
would have measured the drawer and passed for the wrong reason — `CI-005`'s defect verbatim, arriving
through the ticket that changed the surface. The consent frame has been in this category since
`CI-001`.

This is the one place `CI-005`'s "may only ever refuse more" needs arguing rather than asserting.
Removing a check that has become meaningless is not weakening a check that still applies, and what
replaces it is stricter *for that frame*: the drawer's own tag displayed plus all five trusted action
ids present as rows. A blank or half-composed hub fails those; a fraction over a covered rectangle
could not. `ExpressiveBloomJourneyContractTest` now pins which check each frame carries, with the
modal frames named explicitly rather than derived from a predicate, so this is not a hole to opt out
through.

**Hosted acceptance must be re-taken.** `CI-009` was already pending two consecutive cold runs, and
frame 04 depicts a different surface now. This checkout has no emulator; that evidence is not
available here and is not claimed.

**`SPEC.md` §5's code block deliberately did not gain the field.** That block is the reference
integration's manifest field-for-field, and `DEMO-005` makes the fixture, the published copy and the
specification example one coordinated artifact. Adding `"hub": "drawer"` there would have made the
spec's canonical example describe something `bloom-flowers.json` does not publish, while criterion 5
requires that file byte-identical. The field is documented in §5 prose immediately below with its own
example and value table.

**The fixture went to `invalid/`, not `valid/` as the plan named.** `valid/` may carry warnings —
`forward-compat-1.1` does — but it is where exemplary documents live, and a typo'd hub is a document
with a mistake in it. It sits beside `icon-unknown`, whose argument it copies. A second fixture in
`valid/` pins the happy path and is what caught the `rootFields` control.
