# UX-006: Research
Status: RESEARCH_READY

## Question

The consent sheet must show what a manifest will change before it is applied. Three things have to
be decided before a plan can commit to a file list and a trust boundary:

1. Where the projection lives, given that the sheet is the one place untrusted branding is displayed
   **before** the user has agreed to it — so `HARDEN-002`'s "beside, never instead of" rule has to be
   restated for a surface it was not written for.
2. Which colour the swatch shows: the raw trusted value from `branding`, or `SiteSkinTheme`'s
   guarded projection — and what happens when the manifest supplied no colour at all.
3. How the counts are stated, given they must describe the chrome that would render rather than the
   manifest that was fetched.

Everything else the PRD asks for is already decided by existing code and needs mapping, not
deciding.

## Origins involved

- **The serving origin.** `SiteSkinCandidate.origin` is a canonical `SiteOrigin` and is already the
  key the decision persists under (`SiteConsentStore.consentKey()` base64-encodes
  `origin.canonical`). `HARDEN-002` requires the sheet to display that same complete canonical
  string — scheme, host, non-default port — so the visible grant matches its key.
  `BrowserScreen.kt:220` passes `candidate.origin.canonical` today and that is correct; this ticket
  must not "improve" it into a registrable domain.
- **No asset origin is involved, and that is a decision, not an omission.** Previewing the site's
  logo would mean fetching `branding.logoUrl` before the user has agreed to anything.
  `BrandAssetLoader` is only invoked from the `LaunchedEffect` keyed on
  `BrowserMode.Integrated.configuration` (`BrowserScreen.kt:148-157`), i.e. strictly after
  activation. Consent must not move that earlier: a user who presses **Never** would otherwise still
  have caused a second request to the site, which is exactly the "refusing costs nothing" property
  the sheet is supposed to have. The monogram path (`BrandAsset.Monogram(brandMonogram(...))`) is
  local and synchronous and is the only brand mark available pre-consent.
- **No third origin exists in this flow.** The configuration is already origin-bound —
  `candidateDisposition()` re-parses `configuration.origin` and compares it to `available.origin`
  before a candidate is ever constructed (`SiteSkinRuntime.kt:36-37`), so anything the sheet reads
  off the configuration is already proven to belong to the origin in its title.

## Manifest-controlled surface

If this ships as scoped, a website gains the ability to place the following inside the browser's
consent dialog, all of it already core-trusted, normalized and bounded:

| Value | Source | Core bound already applied |
|---|---|---|
| Site name | `site.name` | schema-required, non-empty |
| Short name | `site.shortName` | optional |
| Toolbar title | `toolbar.title` | clamped to `MAX_TITLE_LENGTH` = 64 |
| Toolbar subtitle | `toolbar.subtitle` | clamped to `MAX_SUBTITLE_LENGTH` = 128 |
| Primary colour | `branding.primaryColor` | canonical `#RRGGBB`, contrast-corrected downstream |
| Item counts | `bottomNavigation` / `quickActions` / `menu` | truncated to 5 / 5 / 20 |

Note what is **not** on that list and must not join it: `logoUrl` (no pre-consent fetch),
`homeUrl` and every `action` payload (the sheet describes, it does not offer navigation), and item
`label`s. Labels are tempting — listing the tabs by name is more informative than counting them —
but each one is up to 32 characters of attacker-chosen text, and five of them turn a consent dialog
into a five-line site-authored message directly above an **Allow** button. Counting is the version
that stays a description. `SiteSkinChromeModel.accessibleLabel` exists for the surface where labels
genuinely must render; the consent sheet is not that surface.

`site.name` is the one unbounded string in the table. The schema requires it and core never clamps
it — `SecurityValidator.kt:96` clamps the subtitle and `:165` clamps item labels, and nothing clamps
`site.name`. So the app layer must bound it here, and this is the single most load-bearing detail in
this research note.

## Browser-owned remainder

Everything that makes the sheet a decision rather than an advertisement:

- **The origin string and its position.** Browser-authored, non-editable, the dialog title, drawn
  from `SiteOrigin.canonical`. No manifest value may become the title or be concatenated into it.
- **The three choices, their labels, their order and their persistence.** `ADR-011` semantics are
  untouched: Allow persists + activates after rechecking origin and generation
  (`BrowserScreen.kt:229`), Not now is ephemeral, Never persists refusal.
- **The framing copy.** `strings.xml:38`'s statement that the address and security indicator stay
  under Webora control is a browser claim and stays compiled.
- **Attribution.** Which lines are Webora speaking and which are the site asking. Manifest text is
  rendered in separate `Text` nodes under a browser-authored heading, never blended.
- **Every bound.** Length, count, contrast, and the flattening of control and format characters.
- **Layout, emphasis, ordering and the button set.** No manifest field may reorder or restyle
  anything; the sheet's structure is identical for every site.
- **The dark/light choice.** `SiteSkinTheme.scheme(darkTheme)` reads `isSystemInDarkTheme()`; a
  manifest supplies colours and does not decide whether the user's preference applies.

## Prior art

- **`ADR-011`** decides that consent is asked at all, and — in its Consequences — that "the manifest
  supplies only the origin string and, optionally, the site name". The optional half was never
  implemented. This ticket implements it and must amend the ADR to say what "optionally" now covers.
- **`ADR-006` / `HARDEN-002`** decide the rule for active chrome: branding is presentation beside
  browser identity, never identity itself; the logo and its descendants are explicitly decorative;
  the complete canonical origin is shown at consent time. All three transfer directly; the third is
  already implemented and must be preserved rather than re-derived.
- **`A11Y-001`** decides that a visual bound is not a bound — assistive technology reads the string,
  not the layout — which is why the bound belongs in the model rather than in a `maxLines`.
- **`DEVX-001`** already solved "display untrusted website text inside browser-owned UI" once, in
  `inspectorValue`, including the two non-obvious parts (format characters, and why a regex is the
  wrong tool). Reusing it is strictly better than writing a second one.
- **`SKIN-001`** decides that manifest colours are parsed only by `SiteSkinTheme.from`, never in a
  composable. A swatch drawn by parsing `branding.primaryColor` inline would violate that.
- **`SKIN-003`** established the pure-model-plus-thin-composable split and the app-layer 5/5/20 caps
  as defense in depth over core's own truncation.

## Decisions this note makes for the plan

**1. The swatch shows the projected colour, and only when the manifest supplied one.**

`SiteSkinTheme.from` substitutes compiled Webora defaults for absent branding, so a swatch drawn
unconditionally from the projection would show Webora's own indigo and attribute it to a site that
asked for nothing — the sheet's one job is attribution, so that is disqualifying. The swatch is
therefore present only when `branding?.primaryColor != null`, and absent otherwise, per the PRD's
"absent renders as absent".

When it is present, it shows `SiteSkinTheme.from(configuration).scheme(darkTheme).primary` — the
guarded value — not the raw hex. `guardContainer` may move the colour before the chrome ever paints
it, so the raw value is a colour the browser has already decided not to use; previewing it would
make the sheet a less accurate promise than the chrome it describes. The swatch is a preview of the
outcome, and the outcome is the guarded colour.

**2. Counts are stated per surface, computed after the app-layer caps.**

`SiteSkinChromeModel.from` takes 5/5/20 before rendering, so counts must be taken from the same
capped lists or the sheet promises six tabs and five render. Per surface rather than one total:
"adds 4 navigation tabs and 1 quick action" is a description of a change, while "adds 5 items" is a
number. The extra strings are three plurals, which `strings.xml` handles.

The model computes counts from `configuration` directly using the same constants rather than calling
`SiteSkinChromeModel.from`, because that function also needs `currentPageUrl` to resolve an active
item — a concept with no meaning at consent time, and passing a URL in to discard the result would
be the kind of seam that later grows a reason to keep it.

**3. `site.name` is bounded by `MAX_TITLE_LENGTH`, and every displayed string goes through the
existing untrusted-text treatment.**

Core clamps the subtitle and the item labels; it does not clamp `site.name`. The sheet displays the
site's name as its primary site-supplied line, so the bound must exist somewhere, and the app layer
is the only place left. `MAX_TITLE_LENGTH` (64) is the right constant — it is the bound core applies
to `toolbar.title`, the field that plays the same role in the chrome — read from
`SiteSkinLimits`, never copied.

`inspectorValue`'s treatment (flatten, strip format characters, bound) is required for all of it,
not just the name. It currently lives in `app/.../inspector/InspectorText.kt` and is `internal` to
the same module, so it is reachable — but its name and KDoc are inspector-specific, and a consent
sheet depending on a debug tool's helper reads as an accident. The plan should move it to a
neutral home with the bound as a parameter, updating the inspector's call sites, and keep
`InspectorTextTest`'s cases pointed at the moved function. That is a rename plus a parameter, not a
rewrite; the character walk and its two comments must survive intact.

## Risks

- **The sheet becomes the impersonation surface it exists to guard.** A site named "Your Bank"
  rendered above an Allow button, before any chrome has changed, is worse than the same string in
  the top bar — the top bar at least sits beside a domain the user has already navigated to.
  → *Plan obligation:* the origin stays the dialog title; site text renders under a browser-authored
  attribution heading, in body typography, below the framing copy and above nothing but the buttons.
  A test must assert the origin is the title and that no manifest string can occupy that slot.
- **`site.name` shipping unbounded.** It is the one field with no core clamp and the one the sheet
  most wants to show. → *Plan obligation:* bound it in the model, and test it with an adversarial
  value plus a negative control that fails when the bound is removed.
- **Format characters reversing the sheet.** `U+202E` inside `site.name` reverses everything after
  it, including — depending on layout — text the browser authored. → *Plan obligation:* route every
  displayed manifest string through the moved `inspectorValue`, whose walk already strips
  `Character.FORMAT`. The negative control is a name containing `U+202E`.
- **Moving `inspectorValue` breaking the inspector's absence guarantee.**
  `assertInspectorAbsentFromReleaseVariants` walks release Kotlin output for the panel class; moving
  a helper out of `src/debug` into `src/main` is safe for that check but must not drag anything else
  with it. → *Plan obligation:* move only the function and its private `isDisplaySeparator`, leave
  every `SiteSkinInspectorPanel` reference in place, and run `:app:check` — not just `test`.
- **The `FlowRow` regression.** `BrowserScreen.kt:361` records that three buttons plus "Never for
  this site" already do not fit one line at large font scale. Adding a preview block above them
  consumes vertical space at 200% scale. → *Plan obligation:* the content area must scroll or wrap
  rather than pushing a button off-dialog; verify at 200% before the ticket closes.
- **Scope drift into `UX-004`.** The sheet is due a restyle. → *Plan obligation:* structure, bounds
  and tests only; no new colour, spacing or shape decisions beyond what the swatch needs.

## Open questions

Carried into `/plan` rather than resolved here:

- **Where the moved untrusted-text helper lives, and what it is called.** It is now shared between a
  debug-only panel and a security dialog, so neither package owns it. The plan picks the package and
  the name; the constraint is that the bound becomes a parameter and both call sites pass a constant
  read from `SiteSkinLimits`.
- **Whether `toolbar.title` or `site.name` is the primary site-supplied line when both exist.** They
  serve different roles — `site.name` identifies the site, `toolbar.title` is what the chrome will
  display — and the sheet is a promise about the chrome. Arguable either way; the plan decides and
  records why.
