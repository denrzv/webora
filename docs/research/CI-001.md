# CI-001: Research
Status: RESEARCH_READY

## Question

How can a private GitHub repository produce trustworthy screenshots of its APK against the deployed
SiteSkin integration without an owner-operated Android device, while keeping execution manual and
failure evidence downloadable?

## Origins involved

- `https://denrzv.github.io` is the only serving origin. It is compiled into `SuggestedSite.kt` and
  is the canonical origin the consent assertion must observe.
- `https://denrzv.github.io/.well-known/siteskin.json` is discovered by normal production code.
  Brand assets referenced by the manifest remain subject to the existing exact-origin policy; the
  automation adds no asset exception.
- GitHub-hosted Ubuntu executes the emulator and makes the ordinary outbound HTTPS requests. No
  loopback server, origin substitution, or cleartext `debugRelease` relaxation is appropriate.

## Manifest-controlled surface

Once the real manifest validates and the test grants consent, it can influence the already-defined
SiteSkin title/subtitle, guarded colours, bounded logo, navigation, menu, and quick actions. The
automation observes that production path; it must not inject a configuration or replace the live
manifest merely to make a screenshot deterministic.

## Browser-owned remainder

The canonical-origin consent heading, TLS/domain indicator, Allow decision, origin activation, URI
dispatch, emulator/API selection, screenshot timing/names, and artifact retention remain controlled
by Webora and the workflow. Success is gated on browser-owned SiteSkin semantics before the final
capture, so a web page rendering by itself cannot masquerade as integrated mode.

## Prior art

- Prior tasklists record successful local Pixel 6 API 33 connected tests and screenshots, so API 33
  is evidence-backed rather than an arbitrary matrix choice.
- Repository cloud policy forbids provisioning a software-only emulator in managed agent sessions;
  it does not prohibit GitHub's KVM-backed hosted runner, which is the intended runtime target.
- `ReactiveCircus/android-emulator-runner` documents the required `/dev/kvm` permission adjustment,
  AVD creation, boot wait, animations control, and execution of a caller-supplied script. Pinning its
  v2.34.0 commit avoids mutable third-party workflow code.
- Android `UiAutomation.takeScreenshot()` captures the full display, including the platform WebView,
  unlike a Compose subtree capture. App-specific external files need no storage permission and can
  be pulled with `adb` after the test.

## Risks

- Live Pages/manifest outage → gate each state with a bounded wait, retain test output and logcat,
  and describe live dependency in the workflow summary.
- Consent may already be persisted → instrumentation installs a fresh debug package on a fresh AVD;
  clear package data in the script as defense in depth.
- Splash/IME/animations pollute captures → disable animations, wait for stable semantic states, and
  capture only after Compose idleness.
- `UiAutomation.takeScreenshot()` or file output silently fails → assert the bitmap/write result in
  the test and separately fail the shell step if no pulled PNG exists.
- Private-repository minute use → `workflow_dispatch` only, one device, concurrency cancellation,
  and a job timeout.
- GitHub Pages is inaccessible from this managed environment → compile the instrumentation here;
  runtime evidence must be produced by the GitHub-hosted KVM runner the ticket adds.

## Open questions

None. A full-device instrumentation capture, API 33, debug APK, live origin and manual-only workflow
are the smallest design that answers the owner's request without weakening production boundaries.
