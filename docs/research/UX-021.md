# UX-021: Research

Status: RESEARCH_READY

## Question

What the plan needs decided before it can commit to a trust boundary and a file list:

1. Where does confirmed-secure transport state come from, given that `BrowserMode` carries an origin
   and an origin has no lifecycle?
2. Which layer writes it, so that `BROWSE-009`'s per-tab renderer ownership is not re-broken?
3. What ground does a browser semantic colour stand on inside a header a manifest paints?
4. What happens to `SITESKIN_SECURITY_TAG`, which carries `CI-009`'s pending hosted acceptance?
5. Does the shield need a new glyph, or is the existing `ic_lock`/`ic_warning` pair the answer?

## Origins involved

- **The committed main-frame origin.** The only origin that may produce a security presentation, and
  already the only one `securityPresentation` reads. Unchanged by this ticket.
- **The active integrated origin** (`BrowserMode.Integrated.origin`). Equal to the committed origin by
  construction — `BrowserState.forObservedOrigin` drops integrated mode on any exact-origin mismatch —
  so integrated chrome never displays a shield for an origin other than the page's.
- **No new origin is contacted.** This ticket adds no fetch, no asset and no certificate lookup. The
  brand-asset origin (`NET-003`) and the manifest origin (`NET-001`) are untouched.

The registrable domain shown in the accessible description continues to come from `SiteOrigin`, which
canonicalizes before it can be constructed and derives the registrable domain from the bundled Public
Suffix List (`ADR-004`).

## Manifest-controlled surface

What a website can influence if this ships as scoped:

| Influence | Mechanism | Bound |
|---|---|---|
| The header's background, and therefore what the shield sits *near* | `presentation.colors.background` from `ExpressiveSiteSkinPresentation` | Already contrast-guarded by `SKIN-001`; the shield does not read it |
| The title the shield sits after, and its length | `toolbar.title` / `site.name` | Bounded by `SiteSkinLimits`; ellipsized at one line; must not displace the shield |
| The subtitle above/below | `toolbar.subtitle` | Same bound; not on the shield's row |
| **Whether the shield is `SECURE`** | Only by *being served over HTTPS and completing* — i.e. by actually being secure | This is the mechanism working, not a leak |

What a website must not be able to influence, and cannot after this ticket:

- The shield's colour, glyph, size, position, presence or accessible description.
- The transport classification itself, including by redirecting, by failing, or by serving content
  that claims a state.
- Whether the shield renders at all — `TopChrome.PROTECTED_INTEGRATED` already makes
  `showsSecurityIdentity` a browser constant with no manifest input.

The one genuinely new surface is **adjacency**: a green shield next to a manifest-supplied title is a
browser trust mark beside site-authored text, and a site could pick a title that reads as part of the
mark ("Verified by"). This is the same class as `HARDEN-002`'s bounded-preview attribution and is
already bounded by the existing one-line ellipsized title plus the separately-attributed browser
sub-surface the plan will put the shield on.

## Browser-owned remainder

| Guarantee | Enforcing affordance |
|---|---|
| Transport state is derived only from browser-observed navigation results | The state lives in `BrowserState`, written only through `routeRendererEvent` from a `WebViewEvent` carrying its own `tabId` |
| The shield's colour is compiled | `WeboraColorScheme.secure` / `.notSecure`, and `BrowserTokenIsolationTest`'s two halves |
| The shield's colour has a measured contrast floor | The shield sits on a browser-owned `container` sub-surface; `WeboraColorSchemeTest` already measures `secure`/`notSecure` **on `container`** at 6.80/7.94 |
| Green requires positive confirmation | `SECURE` is written only by a successful main-frame completion observation, never by parsing a URL |
| Meaning is not colour-only | Two distinct glyphs, plus a browser-authored `contentDescription` |
| Integrated identity presence/absence stays assertable | `SITESKIN_SECURITY_TAG` moves onto the shield's security node, same value |
| One classification, two chromes | `securityPresentation` remains the single projection both `BrowserChrome` and `SiteSkinTopBarModel` read |

## Prior art

- **`ADR-006` — browser-owned chrome.** The registrable domain and TLS indicator are always visible in
  SiteSkin mode and no manifest field may suppress them. Deleting the *row* is legal; deleting the
  *indicator* is not. The shield plus its accessible description is what keeps the guarantee, and the
  plan owes an explicit argument that a 16–20 dp glyph plus screen-reader text satisfies "always
  visible" where a domain string used to be. **This is the ticket's one genuine tension with a
  standing decision** — the visible registrable domain leaves integrated chrome entirely.
- **`HARDEN-002` — brand impersonation.** Active chrome shows browser-derived domain and TLS through a
  *dedicated semantics node*, and the logo and its descendants are explicitly decorative. The shield
  inherits both halves.
- **`UX-014` — expressive integrated top chrome.** Already establishes that the identity and Back
  sub-surfaces use `WeboraTheme` tokens inside a header the manifest paints, and that a manifest
  cannot suppress, relabel, reorder, restyle, enable or dispatch them.
- **`UX-008`** — "The slot uses the Webora Material scheme even though its surrounding bar uses the
  validated SiteSkin scheme. Do not change it to a SiteSkin colour merely to blend the row — the
  visual boundary is the ownership boundary." Directly on point for the shield's sub-surface.
- **`UX-002` / `ADR-013`** — `secure` and `notSecure` were compiled into the palette and measured on
  `container` before any surface drew them that way. This ticket is the first consumer of that
  intent in integrated chrome.
- **`BROWSE-009`** — the routing contract, and the explicit statement that a cross-tab write corrupts
  `SecurityPresentation`. Also the source-scan rules: read executable lines, forbid the mechanism not
  a spelling.
- **`BROWSE-004`** — `isForMainFrame` filtering and the closed `LoadErrorKind` mapping, including
  `LoadErrorKind.TLS`.
- **`A11Y-001`** — the browser-authored security semantics node exists in both modes and is built only
  from the committed `SiteOrigin`; no origin yields no node rather than a blank one.
- **`CI-003` / `CI-009`** — `BROWSER_CONTENT_TAG` is the page measurement rectangle. The shield is
  inside the header, well outside it, so no exclusion rect changes. Frame acceptance reads
  `SITESKIN_SECURITY_TAG`.

## Findings that decide open design choices

**1. The four states map onto existing observations with no new event.**

| Issue state | Existing seam |
|---|---|
| `UNKNOWN` | `BrowserState()` default; `BrowserObservation.PageStarted` (fires on every main-frame start, resetting) |
| `SECURE` | `WebViewEvent.MainFrameCompleted` → `BrowserObservation.Page(isLoading = false)` **and** committed scheme `https` **and** no failure recorded |
| `NOT_SECURE` | same completion with committed scheme `http` |
| `TLS_ERROR` | `BrowserObservation.PageFailed(kind = LoadErrorKind.TLS)`, already produced by both `onReceivedError`'s `ERROR_FAILED_SSL_HANDSHAKE` and `mainFrameTlsFailure` |

`WebViewEvent` needs no new case, `HardenedWebViewClient` needs no new callback, and
`RendererEffect` needs no new effect. This keeps the change inside `BrowserState.observe` plus the
projection — the two places the JVM gate can drive directly.

**2. `onPageFinished` fires for failed navigations too**, which is why `HardenedWebViewClient` tracks
`failedMainFrameUrl` and suppresses `onMainFrameCompleted` for it. `MainFrameCompleted` is therefore
already the *successful*-completion signal, which is exactly what `SECURE` requires. `PageChanged`
(from `doUpdateVisitedHistory` and from `onPageFinished` unconditionally) is **not** — a rule written
on `PageChanged` would go green on a failed page. This is the single most load-bearing detail in the
mapping and the natural place to get it wrong.

**3. Non-TLS failures must not stay `UNKNOWN` by accident and must not become `TLS_ERROR`.** A
`CONNECTION`/`NETWORK`/`UNKNOWN` failure leaves no confirmed transport, which is `UNKNOWN` — the same
neutral pixel as `TLS_ERROR` under the two-colour mapping, but a different internal state, and the
issue asks for the internal distinction to survive for a later page-info surface.

**4. `securityPresentation` currently returns `null` for a null origin, and callers rely on it.**
`BrowserScreen:698` does `checkNotNull(security)` on the integrated path, which is safe because
`Integrated.origin` is non-null. `BrowserChrome:65` uses `security?.let`. Adding a state parameter
must not change the nullability contract or `A11Y-001`'s "no origin yields no node".

**5. The shield's ground is already solved and already measured.** `secure`/`notSecure` are documented
as "on `[container]`" and measured only against `container`, at 6.80 (light) and 7.94 (dark). Placing
the shield on a browser-owned `container` sub-surface — the same move `BrowserBack` makes with
`surfaceContainer` two rows up — needs no new token and no new measured pair. Placing it directly on
`presentation.colors.background` would put a compiled browser colour on a website-chosen ground with
no floor at all, and is the design error this ticket is most likely to make.

**6. The glyph question, and a real cost either way.** `ic_lock` and `ic_warning` exist and already
mean these two states in `BrowserSecurityIdentity`. Reusing them costs nothing and keeps one visual
vocabulary; the budget test's own comment warns that a duplicate icon "is one icon drawn twice". But
the issue asks for a *shield*, fifteen times, including in its title, and the two surfaces are not
doing the same job: in regular chrome the glyph sits beside the words `Secure · example.com`, so it
is supporting a label, while in integrated chrome it will be alone and must carry the whole visual
distinction by itself. **Recommendation for the plan: two new shield glyphs, budget raised 18 → 20,
recorded as a deliberate raise with `UX-005` as precedent.** Colour must not be the only
differentiator, so the two shields need distinct internal marks, and both must satisfy the viewport /
1.9 stroke / single-colour / no-fill contracts.

## Risks

- **A green shield is a stronger claim than the word `Secure`** → the plan sequences the state model
  before the visual, in separate tasks, so a partial implementation never ships an emphatic indicator
  over a scheme-only signal.
- **`SECURE` depends on a completion signal, and completion signals arrive late** → the plan must
  write transport state only inside `BrowserState.observe`, reached only from `routeRendererEvent`
  with the event's own `tabId`, and must carry a negative control re-pointing the router at
  `session.activeId` (`BROWSE-009`'s established control, which must fail on a transport case too).
- **`onReceivedSslError` cannot always identify the main frame** → `mainFrameTlsFailure` publishes
  nothing when unsure. The plan must ensure those cases land in `UNKNOWN`, never in a retained
  `SECURE`; concretely, `PageStarted` must clear the state on every navigation so "no news" is never
  the previous page's good news.
- **`SITESKIN_SECURITY_TAG` carries `CI-009`'s pending hosted acceptance** → the tag keeps its exact
  value and stays on a node that is displayed in integrated mode and absent otherwise. The plan owes
  a check of all five instrumented call sites, including the bounds assertion at
  `SiteSkinTopBarTest:90-92`.
- **`ADR-006` says the registrable domain is always visible in SiteSkin mode, and this removes it from
  the pixels** → the plan must either state this as a scoped amendment with the issue as its
  authority, or keep a domain affordance. It cannot be silently dropped; `ADR-006`'s argument is the
  suspension-grade one about `evil.example` rendering as a bank. Note the brand row still shows a
  manifest-supplied title and logo, so after this ticket the *only* contradicting signal in integrated
  chrome is a coloured glyph and a screen-reader string. **The plan must decide this explicitly and
  record it.**
- **A shield placed after a `weight(1f)` title will be pushed off-screen** → lay the shield out as a
  fixed sibling in the title row before the flexible text takes the remainder, and pin it with the
  existing bounds-style assertion at 320 dp.
- **A four-value enum with a two-value visible mapping invites a `when` that forgets a branch** → the
  mapping must be exhaustive over the enum with no `else`, so a fifth state is a compile error.
- **Unused strings and an unused separator** → `siteskin_security_separator` and possibly
  `siteskin_tls_secure`/`siteskin_tls_not_secure` become dead. Leave nothing behind that reads like a
  live contract.

## Open questions

Carried into `/plan` as explicit decisions, not resolved here:

1. **`ADR-006` amendment.** Does integrated chrome keep any visible registrable domain, or does the
   shield plus accessible description replace it outright? The issue's target layout says outright.
   The plan must record the decision and, if it amends `ADR-006`, say so in the ADR rather than only
   in the plan.
2. **Glyph budget.** Two new shield drawables (recommended, budget 18 → 20) versus reusing
   `ic_lock`/`ic_warning`.
3. **Where the transport state is stored.** A field on `BrowserState` versus a field on
   `BrowserMode.Regular`/`Integrated`. The former keeps `BrowserMode`'s equality semantics — which
   `forObservedOrigin` and `activateSiteSkin` compare — free of a lifecycle value, and is the
   expected answer; the plan must confirm nothing depends on transport participating in mode
   equality.
