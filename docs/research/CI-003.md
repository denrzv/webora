# CI-003: Research
Status: RESEARCH_READY

Input for `/plan`. Maps the capture path, what the browser already exposes, where a pixel check can
live so the JVM gate can fail it, and one correction the PRD needs.

## 1. The capture path, and why nothing in it waits for pixels

`LiveSiteScreenshotTest.capturesLiveBloomFlowersSiteSkinJourney` (`app/src/androidTest/.../visual/`):

```kotlin
composeRule.onNodeWithText(string(R.string.siteskin_allow)).performClick()
waitUntilNodeExists(hasTestTag(SITESKIN_SECURITY_TAG))
waitUntilNodeExists(hasTestTag(SITESKIN_BOTTOM_NAV_TAG))
composeRule.onNodeWithTag(SITESKIN_SECURITY_TAG).assertIsDisplayed()
composeRule.onNodeWithTag(SITESKIN_BOTTOM_NAV_TAG).assertIsDisplayed()
captureDeviceScreenshot("03-siteskin-integrated.png")
```

and inside `captureDeviceScreenshot`:

```kotlin
composeRule.waitForIdle()
guard.requireAppOwnsScreen(name.removeSuffix(".png"))
val bitmap = requireNotNull(instrumentation.uiAutomation.takeScreenshot()) { … }
```

Four gates, none of which is about drawn content:

| Gate | What it actually asserts |
|---|---|
| `waitUntilNodeExists(tag)` | a semantics node with that tag is in the tree |
| `assertIsDisplayed()` | that node has non-zero bounds inside the window — a **layout** claim |
| `waitForIdle()` | the Compose runtime has no pending work. The page is a `WebView`, an Android view; Compose does not track its paint |
| `requireAppOwnsScreen` | `CI-002`'s focus classification — *who* owns the window, never *what* is drawn in it |

So the capture fires as soon as the chrome's semantics exist. There is no signal anywhere in this
path that the renderer has produced a frame.

## 2. What run 9's frame already tells us, without the full-resolution PNG

Open question 1 asked whether the top bar is absent, drawn blank, or unpainted. One of the three is
**ruled out by evidence already in hand**:

`assertIsDisplayed()` on `SITESKIN_SECURITY_TAG` passed, and that tag sits inside `SiteSkinTopBar`
(`SiteSkinTopBar.kt:147`). A node absent from composition has no semantics entry, and one with zero
bounds fails the assertion. **The top bar therefore existed in the tree with real bounds at capture
time.** "The bar is missing from composition" is not the explanation.

That leaves *drawn blank* or *not yet painted*, and the frame as a whole favours the second: the page
region is empty too, while the bottom navigation and quick action — composed earlier, in the same
recomposition that replaced regular chrome — did draw. A capture landing between the new content's
layout and its draw produces exactly this picture.

**Still not settled, and the plan must not assume it:** whether the bar is unpainted or painted with
no visible content needs the full-resolution frame, which this session cannot download (artifact
access is blocked; `403 GitHub access is not enabled for this session`). The design below is chosen
so it does not depend on the answer — it waits for the page region, and if the bar turns out to be a
*product* defect it stays visible in the evidence rather than being papered over.

## 3. Signals the browser already publishes

| Signal | Where | Usable as a paint gate? |
|---|---|---|
| `state.isLoading` | `BrowserState.kt:10`, fed from `WebViewEvent.PageStarted`/finished | **No.** `onPageFinished` is a document-lifecycle event; it precedes first paint and says nothing about compositing |
| `BROWSER_STATUS_TAG` live region | `BrowserScreen.kt:663` | No — accessible text derived from `isLoading`, same limitation, one indirection further away |
| `SITESKIN_SECURITY_TAG`, `SITESKIN_BOTTOM_NAV_TAG` | already used | Semantics, per §1 |
| The captured `Bitmap` itself | `uiAutomation.takeScreenshot()` | **Yes.** It is the only artefact in the path that is made of pixels |

The last row is the finding that shapes everything: the harness already takes a bitmap, so a pixel
check costs one extra capture per poll and no new machinery. `DEVX-002` established the technique in
this repository for exactly this class of lie — a structurally perfect PNG with invisible labels
passes any "did it write a file" assertion, and only counting ink separates the two.

## 4. Where the decision has to live

Criterion 4 requires a JVM-gated rule. The repository has one worked precedent and one live
counter-example, both from this milestone:

- `app/src/screenshotPolicy/java/app/webora/browser/evidence/ScreenEvidencePolicy.kt` — a pure object
  over strings, shared into `test` and `androidTest` and into no variant. `ScreenEvidencePolicyTest`
  runs in `./gradlew test` with no emulator.
- `ScreenEvidenceGuard` (`androidTest`) holds *only* interaction: reading the dump, pressing a
  button, recording. The split is what lets a checkout with no `/dev/kvm` prove that a Webora ANR can
  never be dismissed.
- The counter-example: a compile error in `BrowserFontScaleTest` survived a green
  `scripts/pre-commit-check.sh`, because the gate never compiles `androidTest` at all.

So the new rule belongs beside `ScreenEvidencePolicy` as a pure function over **sampled pixel
statistics** — not over a `Bitmap`, which is an Android type and would drag the policy back into a
source set the gate cannot compile. The guard samples; the policy decides.

## 5. The region to measure

The page lives in an untagged `Box` at `BrowserScreen.kt:469`:

```kotlin
Box(Modifier.fillMaxWidth().weight(1f)) {
    HardenedWebView(…, modifier = Modifier.fillMaxSize())
    state.loadFailure?.let { failure -> BrowserErrorPage(…) }
}
```

Tagging that `Box` gives the test the page rectangle from the semantics tree
(`fetchSemanticsNode().boundsInWindow`), which is exactly the region a "the page rendered" claim is
about — and it excludes the chrome, so a frame cannot pass on the strength of its own navigation bar.
Test tags already live in `main` here (`BROWSER_SECURITY_TAG`, `SITESKIN_BOTTOM_NAV_TAG`, …), so this
is an established pattern rather than a new exception.

Note the second child: `BrowserErrorPage` renders **inside** the same box. A load failure therefore
fills the region with browser-owned content and would satisfy a naive non-blank check. Whether that
should count as "rendered" is a plan decision; the honest answer is that it is a legitimately
non-blank page region and the run's redness should come from the journey's own assertions, not from
this check pretending an error page is a blank screen.

## 6. Trust boundary — and a correction the PRD needs

`CI-002`'s focus classification reads window titles AOSP builds from a **process name**, so no
website text reaches it. That property does **not** transfer here, and the PRD overstates it:

> *"no manifest, page, or website-controlled value may influence the decision"*

A pixel check on the page region reads pixels **the website drew**. That is unavoidable — those
pixels are the thing being verified. The achievable property is directional, and the plan should
state it in these terms instead:

> **Website content can only make the check refuse, never permit.** A site that renders a blank page
> fails the capture and reddens the run; no page content can cause a capture that would otherwise be
> refused.

That is fail-closed in the same direction as every other guard in this pipeline, and it is honest
about what a pixel check can and cannot promise. The bounded consequence — a red run on a genuinely
blank page — is acceptable because the site under test is our own reference integration, and a
`bloomflowers` page that renders blank is a defect we want the run to catch anyway.

No new network access, no new permission, no change to what is captured or stored. The check reads a
bitmap the harness already holds.

## 7. Risks the plan must answer

1. **A legitimately white page.** The reference integration's pages have a near-white background
   (`#FFF7FA`), so "any non-background pixel" is the right shape and "mean brightness" is not. The
   threshold must be justified against the actual frames rather than tuned until green.
2. **Papering over a product defect.** If the top bar is genuinely drawn blank, no amount of waiting
   reveals it. The check must target the page region only, so a broken top bar stays visible in the
   evidence instead of being absorbed by a longer wait — the same refusal `CI-002` made when it
   declined an `else` branch that dismisses whatever is in the way.
3. **Flake on a slow emulator.** A bounded poll on an observed condition, per
   `scripts/android-emulator-ready.sh`, with every sample recorded so a failure explains itself.
4. **Cost inside the emulator step.** `CI-002` established that runner work during device life
   starves `system_server`. Sampling must be a strided read of an already-captured bitmap, not a
   per-sample file write or a full-image histogram.
5. **The error-page ambiguity** in §5.

## 8. Open questions for `/plan`

- Sampling shape: stride, and whether the statistic is "distinct colours" or "fraction differing from
  the modal colour". The latter is cheaper and matches `DEVX-002`'s ink counting.
- Threshold, and how it is justified rather than tuned.
- Whether the check applies to all three frames or only the ones whose evidence is a rendered page.
  Frame 01 is Home — Compose-only, no `WebView` — so the page region does not exist there.
- Whether `BrowserErrorPage` filling the region should be treated as rendered (§5).
