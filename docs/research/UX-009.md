# UX-009: Research
Status: RESEARCH_READY

## Question

Two, and only the second is open:

1. **What draws the circle?** Settled by reading, with every link verified against the artifact this
   build resolves rather than against recollection of Material's defaults. Recorded below so the plan
   does not re-derive it.
2. **Where does the fix belong, and what asserts it afterwards?** The token is shared between a
   control shape that is correct and a container shape that is not, so "change the number" and
   "change who reads it" are different fixes with different blast radii. And the defect survived a
   green androidTest suite, so the plan owes an assertion that would have failed.

## The mechanism, verified link by link

| Link | Evidence |
|---|---|
| `WeboraRadius.PILL = 999.dp` | `WeboraRadius.kt:23`, with the KDoc stating the intent: "large enough that any control this rounds becomes a pill at any height it can reach" |
| That value is Material's `extraLarge` role | `WeboraRadius.kt:34` |
| A dialog container resolves to that role | `androidx.compose.material3.tokens.DialogTokens.ContainerShape` is `ShapeKeyTokens.CornerExtraLarge` — read from `material3-android:1.4.0`'s `classes.jar` with `javap`, not from memory |
| An over-large corner is *scaled*, never rejected | `CornerBasedShape.createOutline` computes `Size.getMinDimension`, then for each adjacent pair whose sum exceeds it multiplies both by `minDimension / sum` — the `fdiv`/`fmul` pairs are visible in `foundation-android:1.10.6`'s bytecode |
| Material lays a dialog out between 280 dp and 560 dp wide | `DialogMinWidth = 280`, `DialogMaxWidth = 560` in `AlertDialogKt`'s static initialiser |
| The container clips its content | `AlertDialog` draws a `Surface(shape = …)`, and `Surface` clips to its shape |

**So the arithmetic is forced.** At any dialog width `w` the app can produce, `999.dp + 999.dp`
exceeds `w`, so every corner resolves to exactly `w / 2` — both vertical pairs are clamped, and the
height only matters if it is the shorter side. A `312 × 500` dp dialog gets four 156 dp corners,
which is a vertical stadium; the heading sits in the top band where the shape has collapsed to almost
nothing, and the `Surface` clip removes the characters rather than merely overlapping them. That is
exactly what frame `02-siteskin-consent.png` shows, down to the heading surviving as `ow`.

Nothing here is timing-dependent, which is consistent with runs 14 and 15 agreeing over a page that
had painted in the second.

## Blast radius: every `AlertDialog` in the app, not just consent

`extraLarge` is a default, so the defect is at the role and reaches every dialog that does not
override it. Enumerated by grep rather than by memory:

| Call site | Surface | Owner |
|---|---|---|
| `BrowserScreen.kt:354` | External-URL confirmation | browser |
| `BrowserScreen.kt:387` | **SiteSkin first-use consent** | browser (`ADR-011` enforcement point) |
| `BrowserScreen.kt:462` | External-navigation confirmation (`mailto`/`tel`/`geo`) | browser |
| `PrivacySettingsScreen.kt:134` | Clear-browsing-data confirmation | browser |
| `SiteSkinInspectorPanel.kt:37` | Inspector panel | browser, debug-only |

Four of the five are the surfaces where Webora asks before something irreversible or trust-granting
happens. The frame found one; the token broke all of them.

## Who else reads the role, and what must not move

Three shape mechanisms exist today, and only one is affected:

- **`MaterialTheme.shapes.extraLarge`, read explicitly — exactly one call site.**
  `HomeScreen.kt:48`, the Home address `OutlinedTextField`. `ADR-013` draws that as a pill, and a
  single-line text field is short enough that a 28 dp corner would visibly stop being one. This is
  the one place that must be re-pointed at `WeboraRadius.PILL` directly, or the fix trades a broken
  dialog for a broken address field.
- **`RoundedCornerShape(WeboraRadius.PILL)`, named directly — already correct.** `BrowserChrome.kt`
  lines 71, 107 and 141 (address pill, identity chip, dock). `UX-003` wrote them that way; they do
  not read the Material role and do not move.
- **Other Material roles.** `large` at `HomeScreen.kt:78`, `OnboardingScreen.kt:67`,
  `PrivacySettingsScreen.kt:62`; `medium` at `PrivacySettingsScreen.kt:113`. Untouched.

`SiteSkinTopBar.kt:82,101` clips the logo slot with a literal `RoundedCornerShape(8.dp)` — outside
this ticket, but worth noting as a hard-coded radius that the token system does not cover.

## Why the existing tests all pass

Three gates could plausibly have caught this and none can:

- `WeboraThemeTest.every shape corner comes from the compiled radii` asserts each corner is *one of*
  `WeboraRadius.ALL`. `999.dp` is in that list, so the assertion is satisfied by the defect. It
  constrains provenance, not fitness — there was never an assertion that a container role is a
  container-sized value.
- `WeboraDimensionsTest.every radius below the pill is a multiple of the same base` explicitly
  subtracts `PILL` from the set it checks, and correctly so.
- `SiteSkinConsentDialogTest` asserts `assertIsDisplayed()` on the heading and passes over a clipped
  one. Clipping happens in the parent's *draw*; the semantics tree carries the node's bounds and its
  full text either way. This is `CI-003`'s finding — semantics precede pixels — arriving one layer
  up, and it is why the frame was the first thing to notice.

**Consequence for the plan:** an assertion added to the androidTest suite in the same shape as the
existing ones would also pass over the defect. The gate assertion has to be about the *resolved
geometry* of the shape, not about node presence.

## The assertion that would have failed

`RoundedCornerShape.createOutline(size, layoutDirection, density)` is public API and pure Kotlin for
the all-corners-rounded case: it returns `Outline.Rounded(RoundRect(...))` with no `android.graphics`
type on the path, so a plain JUnit test can lay a shape out at a chosen size and read the corner radii
back. That measures the same code Compose runs, including the clamp — which is the property that
matters, since the defect is *not* visible in the token value alone (`999.dp` is a perfectly good
number until something 312 dp wide reads it).

Two risks with it, both for the plan to close:

- **Reachability.** `:app`'s unit tests compile against the AAR `classes.jar`, and Compose's
  inline-class returns (`Size`, `Dp`, `Density`) sometimes drag in stubs. If `createOutline` proves
  unreachable from `testDebugUnitTest`, the fallback is a token-level assertion (no Material role
  carries `PILL`, container roles bounded) — strictly weaker, because it tests the number rather than
  what the number does, and the plan should say so rather than quietly substituting it.
- **Where 280 dp comes from.** `DialogMinWidth` is `internal` to material3, so the test must carry
  its own constant. That is a transcribed value, which this repo distrusts on principle
  (`DEMO-001`'s checksum rule). It is acceptable here only because the assertion is
  *conservative in the safe direction*: a shape that is a rounded rectangle at 280 dp is a rounded
  rectangle at every larger width, since the corner is absolute and the clamp only ever shrinks it.
  The constant's provenance goes in a comment beside it.

## Origins involved

None. This is browser-owned chrome geometry with no network, no manifest and no origin comparison.
The origin string *displayed* in the consent heading comes from `SiteOrigin.canonical` and is what
the clipping destroys — the ticket is about that text remaining legible, not about how it is derived.

## Manifest-controlled surface

**Nothing, and that must remain true.** A shape token is compiled; `UX-002`'s `C2` — no manifest
value reaches a browser token — covers `WeboraRadius` already, and this ticket adds a value to that
same file rather than a new mechanism. The consent dialog's site-authored half stays confined to
`SiteSkinConsentModel`'s bounded projection inside the `text` slot; a website cannot influence the
container, the heading, or the actions.

## Browser-owned remainder

- The heading string, including the complete canonical origin `HARDEN-002` requires, so the visible
  grant matches the `SiteOrigin` persistence key. Clipping is a browser-owned security statement
  losing characters.
- `UX-007`'s action block: filled Allow, outlined Not now, text Never for this site, full width,
  stacked, outside dismissal means Not now. This ticket touches the container only, and the existing
  assertions passing *unmodified* is the evidence for that.
- The container shape itself, and the enforcement that it cannot become a control shape again.

## Risks

- **Fixing the call site instead of the role** → the plan changes `WEBORA_SHAPES.extraLarge` and
  leaves every dialog fixed at once; a `shape =` argument on `SiteSkinConsentDialog` is explicitly
  refused, since it would leave four dialogs stadium-shaped and the collision live.
- **Silently un-pilling the Home address field** → `HomeScreen.kt:48` is re-pointed at
  `WeboraRadius.PILL` in the same commit as the role change, never as a follow-up.
- **A new gate test that cannot fail** → the plan states the negative control explicitly: restore
  `extraLarge = RoundedCornerShape(WeboraRadius.PILL)`, confirm red, restore the fix, and record the
  result in the tasklist per `CLAUDE.md`'s rule.
- **A test that pins Material's internals** → assert only what Webora controls (the resolved corner
  radius of Webora's own shape at a chosen size). Do not assert on `DialogTokens`, which is a
  third-party implementation detail that may be re-keyed in a Compose upgrade.
- **Claiming the fix from the wrong artifact** → the closing frame cites run number and commit SHA.

## Open questions

- **28 dp or 20 dp for `extraLarge`.** Both are multiples of the 4 dp base and both produce a dialog.
  20 dp would reuse `LARGE` and add no token; 28 dp is Material's own extra-large and keeps the
  scale's roles distinct, which matters because a scale whose top two roles are equal invites the
  next person to collapse them. Decided in `/plan`, on the ordering argument rather than on cost.
- **Whether the instrumented heading assertion can be made to fail on the defect at all.** A pixel
  comparison would, and this repo has no Robolectric and no screenshot-diff harness; the honest
  outcome may be that androidTest documents the requirement while the JVM geometry test is the gate.
  `/plan` states which of the two is load-bearing rather than implying both are.
