# NET-004: Research
Status: RESEARCH_READY

## Question

Why does the reference integration's declared, correctly served logo render as a monogram, and what
must the plan commit to so the answer comes from evidence rather than from argument?

Two sub-questions, and they have different shapes:

1. **Which stage produces the monogram?** Currently unanswerable from anywhere — the pipeline records
   nothing, so this is a capability the ticket has to build before it can be used.
2. **What may change once it is known?** `NET-003`'s bounds are fixed by the backlog entry, so the
   answer space is: a defect in the app's own wiring, a defect in the harness, or a refusal that is
   correct and merely invisible.

## What reading the code already settles

Two of the backlog's four candidates fall to inspection, and recording that keeps the plan from
paying for them.

**The logo is declared and reaches the app.** The served manifest is byte-identical to the pinned
fixture — `sha256 ed0ca884…d2d96e1d` for
`https://denrzv.github.io/.well-known/siteskin.json`, `spec/fixtures/valid/bloom-flowers.json` and
`denrzv/bloom-flowers`'s working copy alike, verified by recomputation rather than transcription.
`bloom-flowers.expected.json` pins the normalized result, so `branding.logoUrl` arrives at the app as
an **absolute** same-origin URL (`https://<origin>/assets/siteskin/logo.png`), not the relative path
the manifest writes. `BrandAssetLoader.load`'s `configuration.branding?.logoUrl ?: return fallback`
is therefore not the path taken.

**Composition does recompose when the asset lands.** `BrowserScreen.kt:159` keys its
`LaunchedEffect` on `integrated?.configuration`, and `BrowserState.forObservedOrigin` returns *the
same* `BrowserMode.Integrated` instance for a same-origin page start
(`BrowserState.kt:85`), so the key is stable across the page's own load events and the effect is
neither restarted nor cancelled mid-flight. `brandAsset` is a `MutableState` written from the effect,
so the top bar recomposes when the bitmap arrives. `SiteSkinTopBar.BrandLogo` renders
`BitmapAsset` through `Image(bitmap = …, ContentScale.Fit)` in the same 40 dp slot, with no branch
that could prefer the monogram over a present bitmap.

**What the origin actually serves** (checked from this machine, not assumed):
`GET https://denrzv.github.io/assets/siteskin/logo.png` → `200`, `content-type: image/png`, no
redirect, 5,702 bytes; PNG signature valid, `IHDR 512 × 512`, bit depth 8, colour type 2, interlace
0. Every `NET-003` bound clears with room: 512 ≤ 1024 per axis, 262,144 ≤ 1,048,576 total, 5.7 KiB ≤
512 KiB, declared type matches signature, PNG rather than SVG.

**So the surviving candidates are all off this machine:** `BitmapFactory` on a real device, the
emulator's transport to GitHub's CDN, or the harness photographing before the asset arrives. No JVM
test can reach any of them, which is why this ticket's first deliverable is evidence capability
rather than a fix.

**One data point against the timing candidate, and it is not conclusive.**
`reports/qa/CI-003.md:28` records run **11**'s frame as "the top bar with monogram, title, subtitle
and `Secure · denrzv.github.io`", and run 15 shows the same monogram at `f1e81640`. Two runs eight
commits apart, both monogram, is weak evidence against a coin-flip race — but a race that
systematically loses looks exactly like a deterministic refusal, and nothing recorded so far can tell
the two apart.

## The tool built for this question cannot answer it

`DEVX-001` built the inspector precisely so a site owner is not left guessing between failures that
render identically, and the backlog entry directs reading it first. Doing so is what produces this
finding:

- `InspectorBrandAsset` is `NONE | DECODED_BITMAP | MONOGRAM` (`InspectorSnapshot.kt:95`). The panel
  prints `snapshot.brandAsset.name` (`SiteSkinInspectorPanel.kt:71`) and stops.
- `ManifestTraceRecord` covers manifest transport and validation only. There is no brand-asset
  section, so nothing about the asset survives the navigation.
- `BrandAssetFetchResult.Rejected` is a bare `data object` — it carries no reason, unlike
  `ManifestFetchResult.Rejected(reason: FetchRejection, httpStatus, redirects)`, which the manifest
  path has had since `DEVX-001`. The asymmetry is the gap.
- `BrandAssetLoaderTest` demonstrates the consequence directly: five distinct refusals — missing
  logo, signature/MIME disagreement, probe format disagreement, over-limit bounds, null decode,
  transport rejection, thrown exception — all assert the same `BrandAsset.Monogram("B")`. The tests
  are correct; there is simply nothing else to assert.

So "read the inspector before reading code" answers a different question than intended: it tells us
the instrument is missing a channel. The plan's first obligation is that channel.

## Origins involved

- **Serving origin:** `https://denrzv.github.io` at runtime (`SCOPE-001`'s Pages user site);
  `https://bloomflowers.example` in the corpus fixture. One manifest serves both because every URL in
  it is origin-relative.
- **Asset origin:** the same complete canonical origin, by construction. `OkHttpBrandAssetSource`
  re-parses the *resolved* logo URL and compares the full `SiteOrigin` tuple against the
  configuration's own origin before any request, and again for each of at most two redirect targets.
  Core has already origin-bound the URL during security validation
  (`SecurityValidator.kt:68`, `SS-E-ASSET-CROSS-ORIGIN`), so the app's check is the second of two
  independent ones. Neither may be relaxed.
- **No third origin exists or may be introduced.** No CDN, no image proxy, no cache host.

## Manifest-controlled surface

If this ships as scoped, a website continues to influence exactly what it influences today:

- Whether a logo is declared at all, and its same-origin path.
- The bytes served at that path, within `BrandAssetLimits` — 512 KiB, 1024 px per axis, 1,048,576 px
  total, PNG/WebP declared *and* signed.
- The monogram's letter, indirectly, through `site.shortName`/`site.name` (already bounded by core).
- The response's `Content-Type` and `Location` headers, which select a typed browser-owned enum
  value and are never displayed verbatim.

**New surface added by this ticket: none.** The reason vocabulary is browser-authored; a website can
cause a reason to be *selected* but cannot supply, extend, or phrase one. That distinction is the
same one `ScreenEvidencePolicy` relies on when it keys off an AOSP-constructed process name.

## Browser-owned remainder

| Guarantee | Enforcement |
|---|---|
| Reasons are a closed enum, never remote text | The enum has no `String` member; any URL or header that reaches the panel passes `inspectorValue`'s flatten-and-bound |
| The logo slot stays decorative | `BrandLogo`'s `clearAndSetSemantics { }` stays; the outcome must not become a semantics property of it (`HARDEN-002`) |
| The monogram remains the user-facing fallback | Reason data is debug-only; no user-visible surface changes |
| Recording never decides | The trace observes only, per `DEVX-001`; the published `BrandAsset` must be identical with and without recording |
| Domain and TLS stay non-suppressible | Untouched by this ticket, asserted in the same frame |
| Release variants gain nothing | `SITESKIN_INSPECTOR_AVAILABLE` from the variant source set, never `BuildConfig.DEBUG`; `assertInspectorAbsentFromReleaseVariants` still checks compiled output |
| No new capability, permission or network request | The asset fetch stays one request per activation |

## Prior art

- **`NET-003`** — the caps, the allow-list, the same-origin recheck, the monogram-on-any-failure rule.
  Fixed by the backlog entry; this ticket may make refusals *legible*, never *fewer*.
- **`DEVX-001`** — the trace's design: a sink defaulting to a discarding `None` rather than a nullable
  recorder, because a null check is a branch and a branch is where traced and untraced paths diverge.
  `SiteSkinTraceNeutralityTest` is the shape of the proof that recording changed nothing.
- **`DEVX-003`** — refused a screenshot mode outright: a frame is evidence *because nothing arranged
  the screen for the camera*. Bounds any harness change here.
- **`CI-003`** — the precedent for a harness waiting on a real state (pixels) that arrives on its own,
  and for recording the winning measurement on success rather than only on failure.
- **`CI-005`** — "this may only ever make the harness refuse more" is the constraint to check a
  harness diff against.
- **`HARDEN-002`** — the logo and its descendants are explicitly decorative.
- **`DEVX-002`** — artifact names carry the commit SHA because a stale artifact looks exactly like a
  current one. Every evidence claim in this ticket cites run number and SHA.
- **`DEMO-001`** — the reference integration is the artifact site owners copy, which is why a silent
  refusal here is a protocol-adoption problem and not a cosmetic one.

## Risks

- **Threading an outcome through the loader changes what publishes.** → The plan owes a neutrality
  test in `SiteSkinTraceNeutralityTest`'s shape: the same `BrandAsset` with recording on and off,
  across the whole refusal matrix, with a guard that the matrix is non-trivial.
- **The evidence convicts nothing and the ticket ships a nicer inspector.** → Acceptance requires a
  hosted frame with the logo, so a merely-better instrument does not close it. If the pipeline is
  exonerated, the defect is the harness's and the fix lands there.
- **A harness "fix" that stages the screen.** → Any wait must be for a state that occurs without the
  harness's help, and must record what it saw; nothing may be hidden, pre-seeded or suppressed.
- **androidTest changes bypass the gate.** → `:app:assembleDebugAndroidTest` runs as part of the
  task's own verification, and the workflow already builds it before the emulator boots.
- **Third-party host coupling.** → A journey that hard-fails on a missing logo makes GitHub Pages a
  build dependency. The plan decides between failing and recording; the PRD carries it as open.
- **Reason text drifting into remote content.** → No `String` in the enum; the panel keeps
  label/value as separate `Text` nodes.

## Open questions

Carried into `/plan` as explicit unknowns.

1. **Which candidate holds.** Decided by the device probe, not by the plan.
2. **Where the device probe lives.** Inside `LiveSiteScreenshotTest` (no workflow change, but couples
   a diagnostic to the journey) or beside it (needs `SCREENSHOT_TEST_CLASS` to accept a list).
3. **How the app's *actual* outcome — not a second copy's — reaches the diagnostics artifact.** The
   recorder is constructed per-composition (`remember { inspectorRecorder() }`), so instrumentation
   cannot read it today. A probe that runs its own loader instance measures the pipeline, not the
   running browser, and a second copy is a second thing that can disagree.
4. **Whether a missing logo should fail the screenshot job** once the pipeline is known-good.
