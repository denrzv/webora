# UX-018 research — Privacy settings modal ownership

Status: RESEARCH_READY

## Question

Where should modal ownership live so privacy settings fully isolate the current page and dismiss
before browser navigation without duplicating insets or changing privacy state?

## Origins involved

The observed page may have any HTTP(S) origin, including an authorized SiteSkin exact origin such as
`https://denrzv.github.io`. Privacy settings themselves have no serving or asset origin: all copy,
controls, colors, callbacks, and state are local to Webora. Stored decisions merely display canonical
origins as data and never grant those origins presentation control.

## Manifest-controlled surface

None. A validated manifest may affect integrated browser chrome while its exact-origin mode is
active, but it cannot style, open, dismiss, reorder, or receive input through privacy settings.

## Browser-owned remainder

`BrowserScreen` owns the visibility flag and callbacks. A Compose `Dialog` is the correct boundary:
it creates a modal window, intercepts outside/page input, routes system Back through
`onDismissRequest`, and can host an opaque full-size Material `Surface`. The dialog must apply safe
drawing insets internally instead of reusing `browserModifier`, which belongs to the underlying app
window.

## Relevant code

| Path | Why it matters |
|---|---|
| `app/src/main/java/app/webora/browser/browser/PrivacySettingsScreen.kt` | Current scrollable settings content lacks any opaque full-size/modal owner; also owns the nested clear-data `AlertDialog`. |
| `app/src/main/java/app/webora/browser/browser/BrowserScreen.kt` | Owns `settingsVisible`, opens settings from neutral and integrated menus, currently composes content as an overlapping sibling. |
| `app/src/androidTest/java/app/webora/browser/browser/PrivacySettingsScreenTest.kt` | Covers controls and can pin Close/system-Back dismissal of the new dialog boundary. |
| `app/src/androidTest/java/app/webora/browser/browser/BrowserFontScaleTest.kt` | Existing 200% reflow coverage for the settings content must remain valid. |

## Prior art

`SiteSkinConsentDialog`, external-navigation dialogs, `TabSwitcher`, and `SiteSkinInspectorHost` use
Compose modal windows rather than overlaying page content. `UX-017` preserves the exact-origin chrome
boundary; this ticket must temporarily cover that chrome without letting it enter settings.

## Risks

- A full-width dialog without an opaque `Surface` would preserve the visual bug → require both the
  modal window and a full-size Material background.
- Reusing the underlying `browserModifier` would double-consume safe insets → dialog content owns
  `WindowInsets.safeDrawing` once.
- Clear-data confirmation could dismiss settings accidentally → keep settings visibility independent
  and compose confirmation as a nested alert above it.
- A custom Back handler could compete with browser history → rely on `Dialog.onDismissRequest`, which
  receives Back before the underlying activity.
