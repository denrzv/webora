# UX-027 research — where the brand asset stops
Status: RESEARCH_READY

PRD: `docs/prd/UX-027.prd.md`
Issue: [#128](https://github.com/denrzv/webora/issues/128)
Measured at `7fe22ba`.

## F1 — What is already excluded, and how

The issue asks for the whole lifecycle to be traced. Four of its five sections can be closed before
writing any code, which is what narrows the ticket:

| Layer | Evidence | Verdict |
|---|---|---|
| The artwork | `assets/siteskin/logo.png`, 512 × 512 PNG, 5702 bytes, present on `origin/main` of the reference repo | fine |
| The origin | `curl -sI` → `HTTP/2 200`, `content-type: image/png`, `etag "6a8555fe-1646"` (0x1646 = 5702) | fine |
| URL resolution | core resolves `/assets/siteskin/logo.png` to an absolute same-origin URL during security validation; `bloom-flowers.expected.json` pins it | fine |
| Loader logic | `BrandAssetLoader`, `OkHttpBrandAssetSource` and `BitmapBrandAssetDecoder` are **unchanged since `NET-004`** (`git log` shows only `c9314af` and `cc5b334`), and their suite passes | fine in isolation |

`NET-004` recorded this pipeline working end to end: hosted runs 17 and 18 logged
`stage=DECODED httpStatus=200 pixels=512x512 attempts=1`, and run 18's frame showed the flower in the
40 dp slot.

So the defect is **after decode**: publication, or Compose propagation. Those are the issue's sections
3 and 4, and they are the layer with no automated coverage, because the whole of it lives inside a
`@Composable`.

## F2 — The effect itself is not the regression

`BrowserScreen`'s load effect is textually unchanged from `NET-004`, which is the last commit where
this demonstrably worked:

```kotlin
LaunchedEffect(integrated?.configuration) {
    val configuration = integrated?.configuration
    brandAsset = configuration?.let { … Monogram … }
    if (configuration != null) {
        val loaded = assetLoader.load(configuration)
        brandAssetSink.record(configuration.origin, loaded.trace)
        if (publishesBrandAsset(state.mode, configuration)) brandAsset = configuration to loaded.asset
    }
}
```

What *did* change is the state's type: `BrandAsset?` became `Pair<SiteSkinConfiguration, BrandAsset>?`,
and readers went through

```kotlin
brandAsset?.takeIf { it.first === configuration }?.second ?: Monogram(…)
```

That is `UX-012`'s configuration-identity association, and it is the one new way this can fail
silently: **if the pair's configuration is not identical to the one the reader holds, the reader
falls back to the monogram and nothing anywhere reports a problem.** The loader still says `DECODED`,
the trace still records success, and the screen still shows `B`. Every symptom in the issue matches
that shape.

`SiteSkinConfiguration` has no `equals`, so `===` and `==` are the same comparison here — `NET-004`
recorded that. The association therefore holds exactly as long as `BrowserState.forObservedOrigin`
keeps returning the same `Integrated` instance, which is a documented deliberate property and the
thing to verify rather than assume.

## F3 — Both identity surfaces now read through one value, and both are recent

`UX-025` (`4d8a3f0`) and `UX-026` (`7fe22ba`) both landed after `NET-004`'s evidence and both render
site identity:

```kotlin
val hubAsset = brandAsset ?: BrandAsset.Monogram(…)      // BrowserScreen, integrated branch
SiteSkinDock(brandAsset = hubAsset, …)                    // centre hub
SiteSkinHubHost(identity = SiteSkinHubIdentity.from(name, hubAsset), …)   // drawer header
```

So the dock and the drawer do already share one value rather than capturing independently — the
issue's section-4 worry about "each capturing an initial fallback" does not apply as written. But
`SiteSkinHubIdentity.from` is called during composition and produces a **`data class` holding the
asset by value**; a drawer that is already composed when the asset publishes must recompose for the
new identity to reach it. That is ordinary Compose behaviour and should work, and it is the second
thing to verify rather than assume.

## F4 — The gap that let this through

There is no test anywhere that drives *fallback → loaded*. `BrandAssetLoaderTest` proves the loader
returns a decoded asset; nothing proves the decoded asset reaches a consumer. Both halves can be
green while the transition is broken, which is precisely the state the issue reports.

That is also why the fix must land with a test the JVM gate runs (PRD criterion 1): a fix verified
only by looking at an emulator regresses the moment someone changes the association again.

## F5 — Reproduce before diagnosing further

Reading has excluded the transport half and narrowed the rest to an identity association that is
correct on paper. Continuing to read is the wrong next move; the cheap decisive experiment is an
end-to-end JVM reproduction:

- the **real** Bloom configuration, validated through `SiteSkinValidator` from the checked-in fixture;
- a `MockWebServer` serving the **real** 512 × 512 PNG bytes at the real path;
- the **real** `BrandAssetLoader`, `OkHttpBrandAssetSource` and `BitmapBrandAssetDecoder`;
- the **real** `publishesBrandAsset` guard, driven with the modes a session actually produces.

If that goes green, the pipeline and the guard are both sound and the defect is in composition alone
— which is a much smaller place to look, and the test is required coverage regardless.

`BitmapFactory` is an Android type, so a JVM test cannot decode. The decoder seam is
`BrandAssetDecoder`, so the reproduction uses the real loader and source with a decoder stand-in;
that keeps the URL resolution, origin recheck, redirect policy, caps and signature checks all real,
and stubs only the one call the JVM cannot make.

## F6 — The device answered the question, and it is not composition

An inspector reading from the affected emulator, on `main`:

```
Brand asset
  Slot shows        MONOGRAM
  Produced by       TRANSPORT_UNAVAILABLE
  Refused because   —
  HTTP status       —          ← no server answer at all
  Redirects         0
  Load took         32863 ms
  Attempts          3          ← NET-004's maximum, exhausted
Transport
  Outcome           CACHED
  Cache             FRESH_HIT  ← the manifest never touched the network
Validation          ACCEPTED
```

**The arithmetic identifies the failure exactly.** `CALL_TIMEOUT_SECONDS` is 10, `MAX_ATTEMPTS` is 3,
and the backoff is `RETRY_DELAY_MILLIS * attempt` — 1 s then 2 s. So a run in which every attempt
hits the full call timeout costs `3 × 10 + 1 + 2 = 33 s`, against the 32 863 ms recorded. Every
attempt timed out with no response: a blackholed connection, not a refusal (which returns fast) and
not DNS (which fails fast).

**And the manifest proves nothing about the network here.** `Outcome CACHED / Cache FRESH_HIT` means
`NET-002` served it from memory without a request. So SiteSkin activating is not evidence that the
network was reachable when the asset was fetched — the two are independent, and only one of them
made a call.

**This is `NET-004`'s defect at a longer timescale.** That ticket's diagnosis was that a transient
failure became permanent because *"nothing ever asked again"*: `BrowserScreen` keys the load on the
trusted configuration instance, and `forObservedOrigin` deliberately returns the same `Integrated`
instance for every same-origin page start, so the effect never re-runs. Its fix added three attempts
— which moved the boundary from 0 seconds to 33, and did not remove it. Past 33 seconds the burst is
spent and the origin shows a monogram for the rest of the visit, with the logo one request away, in
exactly the words `NET-004` used.

So TASK-1's green reproduction and this reading agree rather than conflict: the pipeline is sound,
and the browser stops asking too early.

**The fix is a later opportunity to ask, not a bigger burst.** Raising `MAX_ATTEMPTS` moves the
boundary a third time and lengthens a 33-second stall. What the browser lacks is a *natural* retrigger
— and same-origin main-frame page starts are one it already observes, is user-driven, needs no timer,
and cannot spin.

## F7 — Origins and trust boundary

Nothing about the boundary changes. The asset may come only from the validated configuration's own
canonical HTTPS origin, `NET-003`'s caps and allow-list stay, and publication stays guarded by
configuration identity. The risk in *this* ticket is the opposite of the usual one: the pressure is
to publish more eagerly, and a fix that relaxed the guard would trade this bug for `HARDEN-002`'s —
one origin's brand over another's page. Any change to `publishesBrandAsset` needs a control proving
a foreign configuration still cannot publish.

## F8 — Landing order

1. **Reproduce** end to end in the JVM gate, with the real fixture and real bytes.
2. **Fix** whatever that localises, with a negative control.
3. **Cover** the transition so it cannot regress silently again.
