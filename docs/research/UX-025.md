## F1 — The dock the ticket actually starts from

`SiteSkinDock.kt` after `UX-024`, in composition order:

| Slot | Content | Tag |
|---|---|---|
| 1 | `BrandHubCommand` — 52 dp asset circle | `SITESKIN_DOCK_HUB_TAG` |
| 2 | Tabs | `SITESKIN_DOCK_TABS_TAG` |
| 3 | More | `SITESKIN_DOCK_MORE_TAG` |

Three slots, hub **leading**. `ExpressiveSiteSkinDock` is a `Row` and each command wraps itself in
`Modifier.weight(1f)`, so slot width is `(rowWidth − 2 × 8 dp padding) ÷ n` and adding slots is
arithmetic rather than layout work. `UX-024` recorded 93.3 dp per slot at three, against 56.0 at
five on a 320 dp host — so a five-slot dock returns to a measurement `UX-015` already shipped and
`UX-024` moved away from for a different reason.

`browserMenuCommands()` has offered `TABS` since `DEVX-003`, so the More menu already exposes tab
management. The issue's "move Tabs into More" requirement is largely satisfied before this ticket
begins; what remains is proving it, and deciding whether the *dock* slot survives when there is no
projection.

## F2 — Two item types, deliberately not one

`UX-024` introduced `BrowserNavigationCommands.kt`:

- `BrowserNavigationCommand` — a closed enum (`BACK`, `FORWARD`, `REFRESH`).
- `BrowserNavigationAction` — that enum plus a `Boolean`.

and `SiteSkinItemModel` carries an icon, a label and a `NavigationItem`, because a website supplies
all three. `CLAUDE.md` records why they must not converge:

> the moment they shared an item type a manifest could publish something that renders identically to
> Back.

**This ticket puts both kinds in one row for the first time**, which is exactly where that pressure
appears. A shared `DockSlot(icon, label, onClick)` would be the natural refactor and would hand a
manifest the shape of a browser command. The slot model must stay closed: browser slots name an
enum, site slots carry the trusted `NavigationItem`, and no constructor accepts both.

`SiteSkinNavigationContractTest.fixedDock` currently asserts the ordered list
`["BrandHubCommand", "ic_tabs", "ic_more"]`. `UX-024` records that this list was **re-stated, not
shortened**, when it went from five to three, "because deleting two names from an ordered list is
indistinguishable from weakening the predicate". The same rule binds here: whatever the list becomes,
its control must prove a site-driven fourth slot is still refused.

## F3 — What Bloom actually declares, and the id the issue got wrong

`spec/fixtures/valid/bloom-flowers.json`:

- `bottomNavigation`: `home`, `catalog`, `cart`, **`profile`**
- `quickActions`: `call-shop`
- no `menu`, no `presentation`

The issue's example is `["catalog", "cart", "account"]`. **There is no `account` id.** The item
labelled Account has id `profile` and routes to `/account` — `DEMO-001` records that the label,
token, route and id "need not share a spelling". The issue anticipates this: *"Use the existing
action ids if they differ in the deployed manifest; do not create duplicate action definitions solely
for dock projection."* So the projection is `["catalog", "cart", "profile"]`, and inventing an
`account` id to match the issue's prose would be exactly the duplicate definition it forbids.

`home` and `call-shop` are not projected and remain the drawer's contents — which is what makes
criterion 11's de-duplication observable rather than vacuous.

## F4 — The deployment URL in the issue does not exist

The issue names `https://denrzv.github.io/apps/bloom/`. The reference repository has no `apps/`
directory; it serves `index.html`, `catalog/`, `cart/`, `account/` and `.well-known/siteskin.json`
at the **origin root**, and `LIVE_ORIGIN` in both hosted tests is `https://denrzv.github.io`.

That is not a detail to quietly correct — `DEMO-001` records it as a functional requirement:

> A GitHub Pages *project* site at `denrzv.github.io/bloom-flowers/` cannot host a SiteSkin
> integration at all: `/.well-known/siteskin.json` belongs to whatever owns the user-site root.

An `apps/bloom/` path could not serve a manifest at all. The plan should treat the origin as
`denrzv.github.io` and say so, rather than following the issue's URL into a shape the protocol
forbids.

## F6 — Where de-duplication belongs, and where it must not

`SiteSkinHubDrawer` renders three `HubGroup`s from `model.quickActions`, `model.bottomNavigation`
and `model.siteMenu`. `SiteSkinChromeModel.from` builds all three from the trusted configuration.

Criterion 11 is a **presentation** rule and criterion 12 depends on it staying one: if projection
filtered `SiteSkinChromeModel`'s collections, then

- `NavMatcher.activeItem` would stop seeing the projected item, so the drawer's active-route state
  would be wrong; and
- an item that resolved but could not be rendered would be absent from *both* surfaces, which is
  precisely what criterion 12 forbids.

So the model keeps every item, and the **drawer** subtracts the ids the dock actually rendered. That
also makes the fallback trivially correct: if the dock did not render it, the drawer still has it.

One thing research cannot settle and the plan must: an id appearing in more than one collection.
Bloom has none, so any rule is untestable against the reference integration and needs its own
fixture.

## F7 — Origins, and what the manifest can and cannot influence

| Concern | Site-controlled? |
|---|---|
| Which validated ids are nominated | **yes**, bounded to three |
| The action behind an id | no — already validated; the field carries no payload |
| Slot count, order, geometry, colour roles, targets | no |
| Brand Hub, More | no — browser-owned in the type |
| Icon | no — closed semantic map, `UX-005` |
| Label | bounded manifest text, already re-bounded by `accessibleLabel` |
| Selected state | no — `NavMatcher` over the browser-observed URL |

No new origin decision. Projection is a lookup from an id to an item the validator already produced,
so it cannot widen the action allow-list, the scheme allow-list or origin binding. Every existing
teardown — exact-origin departure, tab switch, configuration change — removes the dock wholesale,
so criterion 14 is met by adding no lifecycle path at all.

## F8 — Hosted evidence changes, again

`LiveSiteScreenshotTest` and `LiveSiteNavigationSmokeTest` assert `SITESKIN_DOCK_TAG`,
`SITESKIN_DOCK_HUB_TAG`, and reach site actions through `BloomReferenceContract.actionTag(id)`,
which `UX-022` re-pointed at the drawer's row prefix. If Bloom starts projecting, then `catalog`,
`cart` and `profile` are no longer drawer rows — so the hub frame's assertion that all five action
ids appear as rows breaks.

That is a real coupling and the plan must own it: either the journey addresses projected items by
their dock tag, or the contract's id list splits into projected and drawer sets. `CI-009`/`CI-010`
acceptance must be re-taken either way, and this checkout has no emulator.

## F9 — Landing order

1. **Protocol.** `presentation.dock` through schema, `ManifestStructure`, `UnknownFieldScanner`, the
   DTO, `SecurityValidator` normalization, the trusted model, fixtures, registry, `SPEC.md`. Nothing
   in the app.
2. **Resolution.** A pure `dockProjection(configuration, pageUrl)` producing a closed five-slot or
   three-slot arrangement. Gate-drivable.
3. **Composition.** `SiteSkinDock` consumes the arrangement; the drawer subtracts rendered ids.
4. **Reference integration.** Bloom's five copies, in one commit, with recomputed checksums.
5. **Hosted journey.** Re-point the contract, and re-take acceptance.

Steps 1–3 are independently green. Step 4 is a second repository. Step 5 cannot complete here.
