# UX-020 — Research

Status: RESEARCH_READY

## 1. What the surface is today

`app/src/main/java/app/webora/browser/browser/BrowserTabSummary.kt` holds both the pure model and the
composable. The model is fine and stays:

```kotlin
internal data class BrowserTabSummary(id, label, position, count, selected)
internal fun tabSummaries(session: BrowserSession): List<BrowserTabSummary>
private fun BrowserTab.browserLabel(): String   // "Home" | registrableDomain | "Page"
```

The presentation is what the ticket is about (`BrowserTabSummary.kt:45-97`):

- `AlertDialog`, so a 280 dp-wide box (`DialogMinWidth`) reading `WEBORA_SHAPES.extraLarge`.
- `title` = `Tabs: %1$d of %2$d`.
- `text` = a `Column` with `verticalScroll`, tagged `TAB_LIST_TAG`.
- Per tab, a `Row` carrying `semantics { selected = … }` and **two filled `WeboraButton`s**:
  - select, `weight(1f)`, visible label `Tab %1$d of %2$d, %3$s` — an accessibility sentence used as
    display copy;
  - close, visible label `Close %1$s tab` — a second full sentence, filled, beside the first.
- `confirmButton` = filled `New tab`; `dismissButton` = filled `Close`.
- `if (!session.canCreateTab)` renders `tab_limit_reached` as bare `Text`.

Eight tabs is therefore sixteen filled buttons plus two more, all in one emphasis, inside 280 dp.
There is **no visual** selected state at all — `selected` is a semantics property only.

## 2. What the other browser-owned modals do

`PrivacySettingsScreen.kt` after `UX-018` is the reference:

| | tab switcher (today) | privacy settings (`UX-018`) |
|---|---|---|
| Container | `AlertDialog`, 280 dp | `Dialog(usePlatformDefaultWidth = false)` + `Surface(fillMaxSize, background)` |
| Insets | none (Material owns them) | `Modifier.windowInsetsPadding(WindowInsets.safeDrawing)` inside the dialog |
| Heading | `title` slot | `Text(…, headlineLarge)` |
| Row | two filled buttons | `Surface(shape = shapes.medium, color = surface)` → `Text(weight(1f))` + `WeboraTextButton` |
| Primary action | filled, in `confirmButton` | filled `WeboraButton(fillMaxWidth())` |
| Dismiss | filled `Close` | `WeboraTextButton(fillMaxWidth())` |
| Back | dialog window | dialog window, pinned by `systemBackDismissesPrivacyDialog` |

`GlobalSiteSkinRow` additionally shows the tonal-row idiom: `Surface(shapes.large, surfaceVariant)`,
row padding `WeboraSpacing.LARGE`, a `Column(weight(1f))` of `titleMedium` + `bodyMedium`, trailing
control. That is the shape to reuse.

`AlertDialog` stays correct for the short confirmations — `ClearBrowsingDataDialog`,
`SiteSkinConsentDialog`, the external-URL and external-navigation prompts. Those are a sentence and
two decisions. A list of up to eight items with a per-item destructive action is the settings shape,
not the confirmation shape.

## 3. The selected-state colour, and the trap in it

`UX-003` recorded that an alpha multiplier is not an acceptable state mechanism, so the selected tab
needs a **colour role**. The obvious pairing — unselected `surfaceVariant`, selected `primaryContainer` —
**does not work**, and the palette is why:

```
LIGHT  chrome = 0xFFD3EBEA     container = 0xFFB4E5E3    ← different
DARK   chrome = 0xFF1F2C2C     container = 0xFF1F2C2C    ← identical
```

`materialColorScheme` maps `surfaceVariant ← chrome` and `primaryContainer ← container`
(`WeboraTheme.kt:73,88`). In dark theme those are the same 32-bit value, so a selected/unselected
distinction built from that pair is **invisible in dark mode** while passing every light-mode check.
This is exactly the class of defect `UX-009` describes: a value that is correct in one box and wrong
in another, satisfying a provenance assertion either way.

The pair that separates in both projections and is already measured is `primary` / `onPrimary`:

```
LIGHT  primary = 0xFF00696E   onPrimary = 0xFFFFFFFF
DARK   primary = 0xFF5CDBD8   onPrimary = 0xFF003736
```

`WeboraColorSchemeTest`'s measured table already carries `MeasuredPair("onPrimary", "primary", BODY)`
(line 133), so a filled-primary selected row introduces **no unmeasured colour**. Unselected rows take
`surfaceVariant` / `onSurface`, also in the table (`ink`/`chrome`, line 125).

A test must pin the separation itself rather than the two role names, or the next palette edit can
re-collapse them silently. That is a JVM assertion over `WeboraColors`, not a screenshot.

## 4. Ownership and the labelling boundary

`BROWSE-006` fixes what a row may say, and this ticket must not widen it. `browserLabel()` reads only
`BrowserMode`: `Home`, `mode.origin?.registrableDomain ?: "Page"`, `mode.origin.registrableDomain`.
`TabSwitcherModelTest` already pins the two attacks — a manifest `site.name` of `Remote Bank` and an
`addressText` of `attacker.test` both fail to reach the label. Those tests must keep passing
**unedited**; if a restyle needs them changed, the restyle crossed the boundary.

Two specific things the visual refresh must *not* reach for, both of which a "neater tab switcher"
naturally suggests:

- a **page title** on the row — that is document content, and `BROWSE-004` already keeps document
  content out of identity;
- a **favicon or thumbnail** — a remote asset per tab, which would be a second brand-asset pipeline
  outside `NET-003`'s caps, allow-list and same-origin recheck.

Both are explicit non-goals in the PRD, and the row's only decorative glyph should be a bundled
drawable.

## 5. What the visible label should become

Today the row's visible text *is* the accessibility sentence (`Tab %1$d of %2$d, %3$s`). Splitting
them is the actual readability fix:

- visible: the label alone (`shop.example`, `Home`, `Page`), plus a browser-authored ordinal line.
- accessible: the existing full sentence, kept as the row's `contentDescription`, so screen-reader
  output does not regress while the pixels stop repeating "Tab 1 of 8," on every line.

`A11Y-001`'s conventions scan (`accessible names resolve from resources`) means both must stay in
`strings.xml`; no literal may reach `Text(` or a `contentDescription`.

## 6. The close control

It becomes icon-only, using `ic_close.xml` (already bundled, `UX-002`'s ten-vector set — no new
drawable, so `UX-002`'s icon budget assertion is untouched). It must go through `WeboraIconButton`,
which:

- requires a non-null `contentDescription` at the **type** level, so the icon cannot ship nameless;
- applies `browserTouchTarget()` — the one 48 dp contract;
- sizes the glyph from `WeboraChrome.ICON_SIZE`.

`BrowserSurfaceConventionsTest`'s `browser controls use the touch target wrapper` scans for raw
Material button imports in any file declaring `@Composable`, so reaching for `IconButton` directly in
`BrowserTabSummary.kt` fails the gate. That is the enforcement, already in place.

## 7. Nested clickables

A clickable row containing a clickable close control is the one structural risk. Compose merges
descendant semantics into a node marked `mergeDescendants`, and `Modifier.clickable` sets it. If the
row is made clickable naively, `TAB_CLOSE_TAG`'s node can stop being separately addressable and
`TabSwitcherTest`'s tag lookups become ambiguous.

The existing tags are the contract (AC-5), so the safe shape is: keep the **select affordance** as the
tagged clickable (a `Surface(onClick = …)` carrying `TAB_SELECT_TAG` and the `selected` semantics),
and keep the close control a **sibling** of it inside an untagged layout `Row` — not a descendant.
That preserves both tags as leaf-ish nodes and keeps `assertIsSelected()` on the same node it targets
today.

## 8. Tests, and which layer can hold them

The gate is JVM-only and there is no Robolectric, so:

- **JVM (`app/src/test`)** — must carry the load-bearing assertions:
  - the palette separation from §3, with a negative control that collapses the two roles;
  - the source-structure contract, in the `BrowserChromeContractTest` idiom: the switcher declares no
    raw `AlertDialog`, the tags survive, and no filled `Button` is the row's select affordance. Each
    with its intentionally-broken counter-example, as that file already does three times.
  - `TabSwitcherModelTest` unedited.
- **Instrumented (`app/src/androidTest`)** — Compose behaviour, recorded as instrumented evidence and
  never promoted to a gate claim (`A11Y-001`'s rule): existing `TabSwitcherTest` plus close/back
  dismissal in the `PrivacySettingsScreenTest` idiom.

`:app:compileDebugAndroidTestKotlin` must be run explicitly — `scripts/pre-commit-check.sh` runs
`./gradlew test`, which never compiles `androidTest` (`CI-003`, `CI-004`).

## 9. Call sites and blast radius

`TabSwitcher` has exactly one production caller, `BrowserScreen.kt:451-469`'s private
`BrowserTabSwitcher`, which adapts session operations onto the four callbacks. That wrapper does not
change: the callback signatures are unchanged (AC-4).

`BrowserScreen` already consumes `WindowInsets.safeDrawing` once around the active surface
(`UX-012`). The dialog must own its own inset read inside its own window, as `PrivacySettingsDialog`
does; adding a second read in the shell would double-pad.

The switcher is reached from three places — `BrowserNavigationShell`'s direct Tabs slot, the regular
overflow (`BrowserMenuCommand.TABS`) and the integrated hub — and all three already funnel through
`tabsVisible = true`. No entry point moves.

## 10. Risks

1. **Dark-mode collapse (§3).** Highest. Mitigated by choosing `primary`/`onPrimary` and pinning the
   separation in a JVM test with a negative control.
2. **Semantics merging (§7).** Mitigated by sibling structure and by keeping the four tag constants.
3. **Full-window for a two-tab list.** A full-screen surface for two rows is more chrome than the
   content needs. Accepted: it is the same trade `UX-018` made for a settings screen that is often
   one toggle, and one modal language is worth more than per-surface fitting.
4. **`androidTest` is outside both gates.** `./gradlew detekt` does not analyse it (`CI-004`), and
   `./gradlew test` does not compile it. Compile it explicitly before every commit.
