# UX-007: Research
Status: RESEARCH_READY

## Current implementation

`SiteSkinConsentDialog` in `BrowserScreen.kt` uses Material `AlertDialog`. Allow is its
`confirmButton`; Not now and Never share a bare `FlowRow` in `dismissButton`. That arrangement
cannot express one coherent hierarchy because Material positions the two slots independently.
`WeboraButton` is a filled Material button with the repository's 48 dp minimum-target modifier;
`WeboraTextButton` provides the lower-emphasis browser-token text treatment.

The dialog body is already vertically scrollable. `BrowserFontScaleTest` exercises the current
labels at 200%, and `SiteSkinConsentDialogTest` covers the exact canonical origin, protected copy,
bounded preview, and three callbacks, but neither test pins action geometry/order or outside
dismissal.

## Origins and trust boundary

The involved origin is the candidate's complete canonical HTTPS origin, already compared with the
browser-observed committed origin before this dialog is composed. UX-007 does not read, compare,
store, or transform origins.

The manifest may influence only the existing bounded attributed preview (`SiteSkinConsentModel`):
title, optional subtitle, guarded colour, and capped surface counts. It must not influence action
labels, order, emphasis, placement, enabled state, callbacks, or dialog dismissal. Those remain
browser-controlled compiled policy. The protected origin title and Webora security explanation
remain outside SiteSkin styling.

## Implementation direction

Render one private consent-action column through `confirmButton` and leave `dismissButton` empty.
Use full-width controls: filled Allow, outlined/secondary Not now, and text Never. A vertical stack
is the most deterministic adaptive layout: it fits narrow screens and long translations without
producing split rows, while wide dialogs retain intentional alignment. Keep `onDismissRequest =
onNotNow`.

An internal overload accepting labels would widen the security surface merely to facilitate tests.
Instead, test production strings under constrained width and 200% font scale, plus source/runtime
ordering and target bounds. Existing localized-resource plumbing remains unchanged.

## Risks and evidence

- A scrollable body does not scroll AlertDialog actions; a full-width vertical stack bounds each
  label independently and avoids horizontal competition.
- Instrumentation tests compile in managed cloud, but Pixel 6 visual/runtime evidence requires a
  connected device or KVM. Do not create a software-only emulator.
- Negative controls: reverting to separate AlertDialog slots must fail the ordering/layout contract;
  routing dismiss to Never must fail callback coverage; using site styling in the action block must
  fail the browser-token/source convention checks.

## No migration

No protocol, storage, preference, manifest, or schema change is involved.
