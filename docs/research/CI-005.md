# CI-005: Research
Status: RESEARCH_READY

Input for `/plan`. Answers all four of the PRD's open questions; the second and third change what the
plan may do.

## 1. The seam, in two call sites

`LiveSiteScreenshotTest.captureDeviceScreenshot` does exactly this:

```kotlin
guard.requireAppOwnsScreen(label)            // returns when mCurrentFocus is Webora
guard.captureWhenRendered(label, region, excluded)   // polls up to 20s, re-screenshotting
```

`captureWhenRendered` then loops:

```kotlin
while (uptimeMillis() < deadline) {
    attempt++
    val bitmap = takeScreenshot(label)
    when (RenderedContentPolicy.verdict(sampleRegion(bitmap, region, excluded))) {
        is ContentVerdict.Rendered -> { record(...); return bitmap }
        is ContentVerdict.Blank -> samples.appendLine(...)
    }
    SystemClock.sleep(POLL_INTERVAL_MILLIS)
}
```

**Nothing in that loop consults ownership.** The bitmap returned — the one written to the artifact —
is validated for *content* only. Ownership was established once, before the loop, potentially
seconds earlier.

Run 14 is the seam firing: `focus-03-siteskin-integrated.txt` records
`mCurrentFocus=Window{f2c1917 u0 app.webora.browser.debug/app.webora.browser.MainActivity}` — clean —
and the frame saved 4143 ms later has a System UI dialog in it.

## 2. The arithmetic says the dialog *was* the measurement

Run 14's region is `Rect(0, 349 - 1080, 2127)` → 1080 × 1778 = **1,920,240 px**.

The ANR dialog's window, from run 13's `window-01-home.txt` (same dialog type, same device profile):
`Requested w=1024 h=514` → **526,336 px**, or **27.4%** of the region.

Measured: `PASSED differing=0.3047865285496029`.

27.4% of geometry against 30.5% of measurement, with the remainder explained by the dialog's shadow
and the rounded corners of the dim. **The page contributed approximately nothing**, which the first
three attempts state directly at `differing=0.0023` against `modal=#ffffffff`.

For contrast, run 12's genuinely rendered page measured `0.7530`. The check did not merely fail to
notice the obstruction — the obstruction *is* the number.

Note the shape of the failure: `RenderedContentPolicy` asks "is this region non-uniform?", and that
is the right question for *liveness*. A dialog is non-uniform. The policy is not wrong; it is being
asked about a region that something else owns.

## 3. PRD open question 3, answered — and it is a refusal

**No, ownership must not be inferred from the screenshot.** Detecting a system dialog by its pixels
is precisely the "recognise the obstruction by how it looks" heuristic `CI-002` refused when it built
the classification on `dumpsys window` titles derived from process names. Pixels cannot distinguish a
System UI ANR from a Webora crash dialog from a page that happens to render a grey rounded card, and
a website *can* influence the third. It would also drag `Bitmap` into a decision that must stay pure.

Ownership stays a `dumpsys window` read classified by `ScreenEvidencePolicy.focusVerdict`.

## 4. PRD open question 2, answered — and it constrains where the check goes

A `dumpsys window` read is a shell round trip. The loop polls every 500 ms for up to 20 s, so a naive
"check ownership every iteration" is up to 40 extra dumps per frame, 120 per journey.

That is not merely slow. `CI-004` research §10 recorded that the System UI ANR's reason on run 13 was
`executing service com.android.systemui/.dump.SystemUIAuxiliaryDumpService` — **System UI's own dump
service**. A harness that polls dumps harder may provoke the obstruction it exists to detect. This is
a lead rather than a proven mechanism, and it is more than enough reason not to multiply dump traffic
by forty.

**So the check belongs on the candidate that passes, not on every candidate.** A frame is only
returned once; verifying ownership at that moment costs *one* extra dump per successful capture —
three per journey — and leaves the blank-page polling exactly as cheap as it is today.

## 5. The residual window, stated rather than hidden

Verifying after the screenshot leaves a gap: the bitmap is taken, then ownership is read. If an
obstruction were present *during* the screenshot and gone by the read, a contaminated frame would be
accepted.

Two reasons that is acceptable, and both should be in the plan rather than discovered later:

- The gap is one shell round trip — tens of milliseconds — against a 500 ms poll.
- An ANR dialog does not vanish spontaneously. It is dismissed by an action, and the only actor
  permitted to dismiss one is the harness itself, which is not dismissing anything inside this loop.

The opposite ordering error — obstruction absent during the screenshot, present at the read — costs a
discarded candidate and another poll. That is the safe direction, and it is the one the design should
prefer whenever it must choose.

Bracketing the screenshot with two reads would close the gap entirely at twice the dump cost. The
plan should say why it is not doing that, or do it.

## 6. PRD open questions 1 and 4, answered

**Question 1 — does ownership move inside the loop and subsume `requireAppOwnsScreen`?** No.
`requireAppOwnsScreen` does more than classify: it owns the dismissal budget, the `MAX_DISMISSALS`
accounting and the `interference-*` records, and `CI-004` is actively changing it. Folding the two
would collide two tickets in one function. It stays as the precondition — ownership *before* we start
looking is still the right first question — and the candidate check is a second, cheaper assertion.

**Question 4 — one verdict or two?** One, and it composes the existing two rather than replacing
them:

```kotlin
sealed interface CandidateVerdict {
    data object Accept : CandidateVerdict
    data class Retry(val reason: String) : CandidateVerdict
}

fun candidateVerdict(focus: FocusVerdict, content: ContentVerdict): CandidateVerdict
```

`FocusVerdict.OwnedByApp` + `ContentVerdict.Rendered` → `Accept`. Everything else → `Retry` with a
reason naming which half failed. Pure, JVM-testable, and it leaves `focusVerdict` and
`RenderedContentPolicy.verdict` untouched so their fixtures pass unedited (criterion 7).

The absence of a `Reject` case is deliberate: the deadline already owns "give up", and a third case
would be a second place to decide the run is over.

## 7. What the fix must not disturb

| Property | Owner | How it stays |
|---|---|---|
| One process, one action may be dismissed | `ScreenEvidencePolicy` | untouched — this ticket adds a check, never a dismissal |
| The 1% liveness bar | `RenderedContentPolicy` | untouched; the threshold is not the defect |
| Ownership classification | `focusVerdict` | untouched and reused; 20 fixtures pass unedited |
| The frame saved is the frame validated | today: content only | extended to both, which is the ticket |
| Records on success as well as failure | `rendered-*.txt` | extended with ownership per attempt, not replaced |
| `CI-004`'s changes to `requireAppOwnsScreen` | that ticket | this ticket does not touch that function |

## 8. Risks the plan must answer

1. **Runs that used to pass will now fail.** Intended — they were passing on contaminated frames —
   but it will look like a regression the first time it happens. The failure message must say
   *ownership was lost during capture*, not something generic, or the next person will re-diagnose
   this from scratch.
2. **A discarded candidate must not consume the dismissal budget.** Same rule `CI-004` established
   for a different reason: budgets count actions, not observations.
3. **`Retry` must not become a silent infinite loop.** It is bounded by the existing deadline and
   must not extend it. The temptation to "give it a bit longer since we discarded some" is the
   `SETTLE_TIMEOUT_MILLIS` shortcut in a new costume.
4. **The negative control has to reproduce an interleaving, not a state.** A test that feeds a
   contaminated observation to a pure function proves the function; the defect was in *when* the
   function is called. The control should drive a sequence — blank, blank, obstructed-and-non-uniform
   — and assert the sequence is not accepted.
5. **Two tickets, one file.** `CI-004` edits `requireAppOwnsScreen`, `CI-005` edits
   `captureWhenRendered`. Same file, disjoint functions. Land whichever is ready; the other rebases.

## 9. Open questions for `/plan`

- Does `rendered-*.txt` gain an ownership column per attempt, or only on the accepted candidate? Per
  attempt would need a dump per poll, which §4 rules out — so the honest record is "ownership
  verified on the accepted frame", plus a line for each candidate discarded *because* of ownership.
- Should a candidate discarded for ownership be visible in the frame count, so a reader can tell a
  slow render from a contested screen?
- Does the guard expose the candidate check to `LiveSiteScreenshotTest`, or keep it internal? The
  journey currently calls two guard methods in sequence; keeping the composition inside
  `captureWhenRendered` means the journey does not change at all.
