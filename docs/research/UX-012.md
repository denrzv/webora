# UX-012: Research
Status: RESEARCH_READY

## Question

Where is chrome ownership currently inferred, and what minimum contract makes every mode transition
and tab selection render only the chrome authorised by the browser-observed active state?

## Origins involved

- The active main-frame origin is parsed into `SiteOrigin` by `BrowserState.observe`; an integrated
  mode survives only an exact scheme/host/port match.
- A SiteSkin candidate and its configuration are bound to that same exact origin. Same-origin brand
  assets are already validated and are presentation-only; they do not decide chrome ownership.
- Another tab may hold a different regular or integrated origin. Its state remains stored but is not
  authorised to contribute chrome while that tab is inactive.
- Home has no origin and therefore authorises no site-controlled chrome.

## Manifest-controlled surface

Only a trusted integrated configuration may supply the bounded SiteSkin title/subtitle/brand asset,
validated colour scheme, semantic navigation items, menu items, and quick actions. It may occupy the
bottom product slot and content action layer only while the selected tab is `BrowserMode.Integrated`.

## Browser-owned remainder

- `BrowserMode`, the selected tab, exact-origin comparison, consent decision, and global toggle decide
  whether integration exists; a manifest cannot select a chrome mode.
- Home and regular pages own the shared `BrowserNavigationShell` from `UX-011`.
- Integrated mode always owns a browser-protected top layer: `SiteSkinTopBar` includes the observed
  registrable domain/TLS presentation and fixed Back affordance from `UX-008`.
- Android system/predictive Back remains dispatched by `BrowserBackHandler`; the app does not draw
  Android Back/Home/Recents.
- Browser settings, tabs, inspector availability, error recovery, and external-navigation
  confirmation remain browser-owned.

## Prior art

- `ADR-004` defines complete origin equality; no subdomain inheritance.
- `ADR-006` requires an always-visible browser-owned domain/TLS identity in integrated mode.
- `ADR-011` requires consent before activation and regular mode after Not now/Never.
- `SKIN-004` implements origin-change deactivation; `UX-008` fixes integrated Back beside branding.
- `UX-011` supplies the one reusable Home/regular browser shell; this ticket must not fork it.
- `docs/BACKLOG.md` and `docs/DEVELOPER_PLAN.md` define the three navigation layers and M8 handoff gate.

## Risks

- Renderer conditionals drift independently → introduce one exhaustive pure projection of mode to
  visible chrome layers, then make rendering and tests consume it.
- Stale SiteSkin action/navigation after origin or tab change → project only the active state's
  current mode; clear transient site menu/consent state on tab selection as already done.
- A loaded brand asset accidentally becomes an activation signal → keep asset availability separate
  from ownership; integrated chrome must remain browser-protected even while the asset falls back.
- Tests merely restate enum types → assert the complete layer set across a multi-step journey and add
  mutated negative controls that would expose protected-layer suppression or cross-tab reuse.
- UI test runtime unavailable in managed cloud → compile instrumentation tests and report runtime
  evidence as an environment limitation; do not provision a software-only emulator.

## Open questions

None. Existing ADRs and predecessor tickets settle origin, consent, system Back, identity, and visual
ownership. This ticket needs a projection and integration tests, not a new architectural decision.
