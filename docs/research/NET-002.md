# NET-002 — Manifest cache research

Status: RESEARCH_READY

## Existing flow

`BrowserScreen` creates `OkHttpManifestSource` and a `ManifestDiscoveryCoordinator`. On each main-frame page start, the coordinator canonicalizes an HTTPS `SiteOrigin`, cancels prior discovery, fetches raw bytes, and passes them through `SiteSkinValidator`. The source currently collapses every HTTP, policy, and I/O outcome to nullable bytes, so it cannot distinguish conditional `304`, transport unavailability, or an authoritative HTTP failure. No cache implementation exists.

## Origins and trust boundary

- The observed main-frame HTTPS origin is browser-owned input after `SiteOrigin` canonicalization.
- Manifest bytes, `Cache-Control`, `ETag`, `Last-Modified`, response codes, and redirects are website-controlled.
- Cache identity must use the full canonical origin tuple plus the accepted manifest's exact schema version. Host suffixes, registrable domains, subdomains, and ports are never interchangeable.
- The manifest may influence only the already-validated `SiteSkinConfiguration`. It cannot choose cache keys, extend freshness beyond 24 hours, turn an HTTP rejection into offline reuse, or influence another origin.
- Cancellation, current-navigation matching, freshness calculation, conditional request construction, stale fallback policy, and all browser security chrome remain browser-controlled.

## Relevant contracts

- `spec/SPEC.md` requires a cached lifetime ceiling of `min(Cache-Control max-age, 24 hours)` and forbids applying cached configuration cross-origin.
- `SiteOrigin.canonical` provides collision-resistant origin identity.
- `SiteSkinValidationOutcome.Accepted.configuration.schemaVersion` is the trusted version value after validation.
- `ManifestSource` exposes only nullable bytes. NET-002 needs an app-layer metadata-aware transport contract while retaining `ManifestSource` compatibility where useful.

## File map

- `app/.../siteskin/OkHttpManifestSource.kt`: request/redirect/body transport; extend with conditional request metadata and closed response outcomes.
- `app/.../siteskin/ManifestDiscoveryCoordinator.kt`: cache policy orchestration and validation seam.
- New `app/.../siteskin/ManifestCache.kt`: exact-origin/version storage, active-version index, freshness policy, and clock seam.
- Corresponding app unit tests: cache isolation/freshness and coordinator conditional/offline behavior.
- `BrowserScreen.kt`: composition-root construction only if new dependencies require it.

## Risks and tests

- Cross-origin collision: test equal versions on two origins and remove the origin component as a negative control.
- Version collision: store successive accepted versions for one origin and assert exact keys remain distinct.
- Directive overflow/ambiguity: malformed, negative, duplicate, and huge `max-age` are stale; no exception or wraparound.
- Revalidation confusion: only `304` may reuse bytes as validated current content; status errors do not.
- Offline confusion: only a closed transport-unavailable outcome permits stale fallback.
- Lifecycle races: existing cancellation and stale-result tests remain required.

## Conclusion

Implement a small bounded in-memory cache in the app layer. This delivers same-session offline reuse without Android storage dependencies and deliberately leaves durable persistence and user clearing policy to `PRIV-001`. Split transport results into explicit success/not-modified/unavailable/rejected outcomes so cache policy is testable and fail-closed.
