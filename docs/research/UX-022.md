# UX-022: Research

Status: RESEARCH_READY

## Question

What the plan needs decided before it can commit to a trust boundary and a file list:

1. Where does an optional `presentation.hub` enter validation, given that the structural schema
   exists in **two** places — `spec/siteskin-1.0.schema.json` and `ManifestStructure` in
   `ManifestValidation.kt` — and the unknown-field walk in `ManifestParser` is a **third** list of
   known field names?
2. Is an unrecognised `hub` value a schema failure, a security-layer normalization, or silence? The
   three answers differ by "whole manifest rejected" versus "one warning".
3. Does the normalized value appear in the canonical result, and if so when? `SecurityConformanceTest`
   compares every reachable fixture's `result` byte-for-byte against a hand-written
   `canonicalJson()`, so the answer decides whether 30-odd `.expected.json` files change.
4. What shape carries the value into the app so that no Compose call site ever compares a string,
   and so a manifest that declared nothing is indistinguishable from one that declared nonsense?
5. Where does the drawer's open/closed state live, given that `siteActionsExpanded` is one
   `BrowserScreen` boolean today and `BROWSE-009` records what happens when site state is addressed
   by "whichever tab is selected now"?
6. How does Back close the drawer without disturbing `BROWSE-002`'s single Back precedence, which
   `BrowserBackHandler` and `navigateBrowserBack` currently own end to end?
7. What does the bouquet become, so that keeping it does not mean keeping it untested?

## Origins involved

- **The serving origin of the manifest**, already canonicalized by `OriginPolicy.parse` and carried
  as `SiteSkinConfiguration.origin`. `presentation.hub` is not a URL, not a resource reference and
  not resolvable, so it participates in **no** origin decision — the field is structurally incapable
  of naming an origin, which is the property to preserve when writing its grammar.
- **The committed main-frame origin**, which decides whether integrated mode survives a page start
  at all (`BrowserState.forObservedOrigin`). The drawer is composed only under
  `TopChrome.PROTECTED_INTEGRATED` / `BottomChrome.SITESKIN`, so exact-origin departure removes it
  with the rest of integrated chrome before any hint can be re-read.
- **The brand-asset origin** (`NET-003`), unchanged. The drawer header must consume the already
  published `BrandAsset` that `BrowserScreen` holds in `brandAsset`, keyed by configuration
  identity. It must not start a second load: `NET-004` records that the publication guard is
  `publishesBrandAsset(state.mode, configuration)` and that a second loader is precisely the
  `BrandAssetCoordinator` mistake — a tested class with no callers beside an untested inline copy.
- **No new origin is contacted.** No fetch, no asset, no storage, no permission.

## Manifest-controlled surface

What a website can influence if this ships as scoped:

| Influence | Mechanism | Bound |
|---|---|---|
| Which of two compiled hub components opens | `presentation.hub` → `HubPresentation` → browser policy | Closed three-value enum; the policy may override |
| Which items appear in either hub | `bottomNavigation` / `quickActions` / `menu` | Unchanged: 5 / 5 / 20, `SS-W-LIMIT-TRUNCATED` on overflow |
| Row labels | `NavigationItem.label` | Already clamped by core; re-bounded by `accessibleLabel` before display *and* before the accessibility tree |
| Row glyphs | `NavigationItem.icon` | Closed `SITE_SKIN_ICON_RESOURCES` map, unknown → `ic_siteskin_generic`, decorative semantics |
| Which row is active | `match` patterns via `NavMatcher` | Decoded HTTP(S) path only; no match selects nothing |
| What a row does when tapped | `NavigationItem.action` | `ActionResolver` → sealed `ResolvedAction`; external navigation still confirms |
| Drawer header text and colours | `site.name` / `site.shortName` / `branding.*` | Bounded strings; `SiteSkinColorScheme`'s six contrast-guarded roles |

What it explicitly cannot influence, **by construction rather than by review**: the value space is
three tokens, so there is no string, number, URL or structure through which a dimension, position,
duration, component name, resource name or callback could arrive. An unknown token is normalized to
`AUTO` at the validator, so by the time any UI sees the value it cannot tell a typo from an absence
— there is no channel for a site to smuggle a distinguishable fourth state.

## Prior art

- **`SPEC.md` §4.2(1) and (7)** — an optional field and an optional top-level section are both
  additive and must not bump the major. This is the clause that makes the ticket legal at all.
- **`SPEC.md` §4.2's minor semantics** — "a declaration of intent, not a request for permission".
  Recognition is therefore **not** gated on the declared minor: a `1.0` document carrying
  `presentation` is honoured, and a site that starts using it SHOULD bump to `1.1`.
- **`ADR-007` / `SS-E-ACTION-UNKNOWN` / `SS-W-ICON-UNKNOWN`** — the settled answer to "what happens
  to a value we do not recognise". Both are `pattern` in the schema with the closed vocabulary
  enforced in the security layer, both degrade, neither rejects. `icon-unknown.expected.json` and
  the schema's own `icon` description spell out the reasoning.
- **`SPEC.md` §4.3(7)** — the canonical result's shape is versioned where the change alters an
  already-valid document's result. This is the constraint behind decision 3.
- **`UX-015`** — established the browser-owned hub, typed `NavigationItem` dispatch, and the rule
  that only navigation rows publish selected/not-selected semantics. Its `CLAUDE.md` record already
  describes headed groups; this ticket restores that shape.
- **`UX-017`** — the branded dock, the single asset-bearing centre command, and the prohibition on
  "a second asset loader, raw resource lookup, component-specific manifest color, or generic command
  model".
- **`SKIN-003`** — the browser section that manifest entries cannot suppress or replace.
- **`SKIN-001`** — colours reach UI only through `SiteSkinTheme.from`, already WCAG-guarded.
- **`BROWSE-009`** — site-derived state addressed by tab id, never by "whichever tab is selected".
- **`UX-020`** — the two browser-owned modal shapes, and the finding that `surfaceVariant` and
  `primaryContainer` are the *same value* in dark theme, so a selected state built from them is
  invisible in one projection. Directly relevant to the drawer's active-route row.
- **`UX-002` C2** — no manifest value reaches a browser token, tested from both sides.
- **Issue #112 comment** — this is the canonical UX-022; #111 is closed as superseded for removing
  the bouquet; `CI-010` (#115) owns hosted cross-presentation acceptance.

## Findings

### F1. The structural contract exists three times, and all three must move together

`spec/siteskin-1.0.schema.json` (published), `ManifestStructure` in `ManifestValidation.kt` (the
executable validator), and `UnknownFieldScanner.rootFields` in `ManifestParser.kt` (the
diagnostic walk) each carry an independent list of known fields. The first two are cross-checked by
`ProductionSchemaConformanceTest`; the third is not checked against either. Missing it does not fail
any test and does not break validation — it silently emits `SS-W-FIELD-UNKNOWN` on `/presentation`
for every conforming manifest, which is the diagnostic drift `SPEC-003` exists to prevent.

### F2. Pattern, not enum — and the corpus already argues the case

`schemaDoesNotEnumerateActionTypesOrIcons` exists because an `enum` turns an unrecognised value into
`SS-E-SCHEMA-INVALID`, which rejects the **whole manifest**. A site that types `"drawr"` would lose
its entire integration — colours, navigation, actions — over a presentation preference. The
established shape is a `pattern` that carries the *structural* security property (a `hub` value
structurally cannot be a URL) with the closed vocabulary enforced in the security layer, exactly as
`normalizeIcon` does. A new `warn` code with a `/presentation/hub` pointer is the icon path with a
different name.

### F3. The canonical result must stay silent when the manifest was silent

`SecurityConformanceTest.canonicalJson()` emits `branding`, `toolbar`, `bottomNavigation`, `menu`
and `quickActions` only when non-null, and compares the whole object with `assertEquals`. If
`SiteSkinConfiguration` gains a **non-null** presentation field, every reachable fixture's
`.expected.json` needs a new key — including `bloom-flowers.expected.json`, whose body is pinned by
SHA-256 in two repositories. A **nullable holder** (null ⇒ the manifest declared no `presentation`
object) leaves every existing expectation byte-identical, and `"presentation": {}` still normalizes
to a declared-but-empty holder that emits `{"hub":"auto"}` — the same way an unknown icon emits
`"icon":"generic"`.

The consequence for the app is that `null` and `AUTO` are two spellings of one answer, which is a
drift surface. The plan should give the configuration **one** accessor that collapses them, so no
consumer writes `?: AUTO` twice.

### F4. `AUTO` is not a synonym for `DRAWER`, and the difference has to be structural

The issue reserves the browser's right to choose another presentation "when required by viewport,
accessibility, platform or future browser policy". If `AUTO` is mapped to the drawer at the call
site, the third token has no independent existence and the reservation is prose. A pure
`resolveHubPresentation(hint) : HubSurface` function, driven through all inputs by the JVM gate, is
what makes `AUTO → DRAWER` a *policy* that can change without touching either component. It is also
the only layer the gate can reach: everything downstream is inside a `@Composable`.

### F5. The bouquet is behaviour, not decoration

`actionBouquet()` has three pinned assertions in `SiteSkinChromeModelTest` (order, dedup, cap) and
`ActionPetal`'s `actionLift` table is a five-case layout contract. Keeping the bouquet "as an
option" must mean keeping those tests passing against the same function, not moving the code behind
a branch nothing exercises. The plan should isolate the compact projection rather than rewrite it,
and the drawer should consume the three lists directly from `SiteSkinChromeModel` — which is what
`from()` already produces, so no new projection of untrusted data is introduced.

### F6. Hub state is already tab-scoped, and the drawer must inherit that rather than restate it

`siteActionsExpanded` is reset by `LaunchedEffect(activeTabId, integrated?.configuration)` and by
`RendererEffect.DiscoverManifest` **for the owning tab only** — `BrowserScreen` carries a comment
recording that clearing it unconditionally let a background page start dismiss the foreground tab's
consent dialog. A second state object for the drawer would need the same three resets and would be
free to drift from them. One visibility state, with the resolved surface derived from the current
configuration at render time, keeps the existing lifecycle guarantees without restating them.

### F7. Back is a browser contract with one owner, and the drawer is the first transient overlay
inside it

`SiteActionBouquet` never needed this: a `Popup` with `dismissOnBackPress = true` consumes Back in
its own window before `BrowserBackHandler` sees it, and `IntegratedBrowserMenuSheet` gets the same
from `ModalBottomSheet` (asserted by `SiteSkinNavigationHubTest.systemBackDismissesBrowserSheetExactlyOnce`).
Whatever the drawer is built from must give the same guarantee **structurally** — a modal window
that consumes Back — rather than by adding a drawer branch inside `navigateBrowserBack`, which is
total over `BrowserMode` and has no business knowing about an overlay. A Compose
`ModalNavigationDrawer` is *not* a separate window and does not consume Back on its own; a
`Dialog(usePlatformDefaultWidth = false)` is, which is `UX-018`/`UX-020`'s established list-surface
shape and already carries the focus-containment behaviour the issue asks for.

### F8. The active-route row must not be built from `surfaceVariant` vs `primaryContainer`

`UX-020` found those two collapse to one value in dark theme. The drawer's selected state is a
SiteSkin-coloured surface, so the equivalent question is whether the chosen pair separates in both
of `SiteSkinTheme`'s projections. `SiteSkinColorScheme`'s `primary`/`onPrimary` against
`secondary`/`onSecondary` is the pair `ActionPetal` already uses for its primary/secondary
distinction, and both are contrast-guarded by `SKIN-001`. State must also not be colour-only —
`stateDescription` carries it for assistive technology, as `SiteSkinBottomNavigation` already does.

### F9. Only `:app` currently consumes the trusted model, so the protocol half can land first

`siteskin-lint` prints diagnostics generically from `diagnostic.code.value`, so a new code needs no
tooling change. `ManifestValidationTrace.diagnostics` is likewise a generic list. That makes a clean
task split: protocol + fixtures + spec, then resolver, then drawer, then wiring — each independently
green.

## Risks

- **A third copy of the field list is missed** → the plan must name `UnknownFieldScanner.rootFields`
  explicitly in the file list, and the fixture that proves it is a *valid* fixture carrying
  `presentation` whose expected diagnostics do **not** include `SS-W-FIELD-UNKNOWN`.
- **An enum reaches the schema** → whole-manifest rejection on a typo. The plan must state
  pattern-not-enum and add the fixture that proves a bad value warns rather than rejects;
  `securityLayerFixturesPassTheSchema` catches the reverse direction automatically.
- **The canonical result changes for documents that were already valid** → §4.3(7) breaking change,
  and `bloom-flowers.expected.json` is one of the five pinned copies. The plan must commit to the
  nullable-holder shape and state it in `SPEC.md` §12.
- **`AUTO` is hard-coded to the drawer** → the third token becomes decoration. Resolution must be a
  pure function with its own test over every input.
- **The bouquet becomes untested** → keep `actionBouquet()`'s existing assertions passing against
  the same function; a plan that rewrites it must carry the same three cases.
- **A second brand-asset load appears in the drawer header** → `UX-017` and `NET-004` both forbid it.
  The drawer takes the already-published `BrandAsset` as a parameter.
- **Back stops working, or works twice** → the drawer must consume Back in its own window, and the
  test for it is the one `SiteSkinNavigationHubTest` already writes for the sheet: dismissed
  **exactly once**.
- **`CI-009`'s pending frames change meaning** → changing the default hub changes what frame 07
  photographs. The plan must keep every browser-owned tag that hosted acceptance asserts, and must
  not silently redefine an assertion those runs depend on. `CI-010` owns the cross-presentation
  evidence; this ticket owes it stable tags, not new frames.
- **The instrumented suite compiles separately** → `:app:compileDebugAndroidTestKotlin` is not part
  of `./gradlew test`, and `UX-021` shipped two broken instrumented tests that way.
- **Menu rows at 20 items and 200% font scale** → the drawer's scroll container is load-bearing, not
  cosmetic; without it the extended section is exactly as unreachable as the bouquet made it.

## Open questions

Carried into `/plan` as explicit decisions, not resolved here:

1. **The diagnostic code's spelling.** `SS-W-PRESENTATION-UNKNOWN` mirrors `SS-W-ICON-UNKNOWN` and
   is the obvious choice, but the registry is a published artifact and the name is permanent.
2. **Where resolution lives** — a new `SiteSkinHubPresentation.kt` beside the drawer, or a field on
   `ExpressiveSiteSkinPresentation`. The latter keeps one projection but breaks that class's
   documented promise to contain colours and motion only.
3. **The drawer's container** — `ModalNavigationDrawer` reads as the platform answer and is named in
   the issue's own non-goals as an implementation detail the protocol must not expose; F7 argues a
   full-window `Dialog` is the shape that actually delivers Back and focus containment. Whichever is
   chosen must satisfy start-side placement under RTL without a physical constant.
4. **Whether the inspector gains a requested-vs-effective presentation row.** Cheap, matches
   `DEVX-001`'s divergence-indicator shape, and is where a site owner would look — but it is
   additive scope and the plan should decide it explicitly rather than let it arrive with the drawer.
5. **Whether `spec/versions.json` needs a row.** It is the version *decision* table, not a field
   table, so probably not — but `SPEC.md` §4.2's minor guidance needs to name the field.
