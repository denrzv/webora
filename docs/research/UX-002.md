# UX-002: Research
Status: RESEARCH_READY

## Question
`ADR-013` already decided the palette, geometry and type scale. What the plan still has to decide is
narrower and mostly mechanical:

1. **What shape the token layer has.** A Material `ColorScheme` is a ~30-role type; Direction A names
   eleven colours per theme. Roles the direction does not name have to come from somewhere, and
   "somewhere" must not be a Material default — acceptance criterion 1 forbids it.
2. **Which pairs the contrast test asserts, and how it knows it is asserting all of them.** The
   naive answer is a hand-written list, which is exactly the shape that silently stops covering a
   token someone adds later.
3. **How `C2` is tested so that it can fail.** Comparing two separately declared constants passes
   whether or not a path exists between them.
4. **Which icons, from which source, at what fidelity.** `C6` says there is none on the classpath and
   recommends `res/drawable` vectors.
5. **Where `contrastRatio()` lives once two palettes need it.**

None of these is an origin question, which makes this ticket unusual for the repository. The trust
boundary it touches is real but it is a *compile-time* one.

## Origins involved
- **Serving origin(s):** none. This ticket performs no fetch, parses no remote document and reads no
  URL. Nothing it adds is reachable from a network path.
- **Asset origin(s):** the icon set is **compiled into the APK** as `res/drawable` vector XML. There
  is no remote asset, so there is no same-origin question to answer — which is the point of `C6`
  preferring bundled vectors over anything fetched or over a large third-party artifact.

The absence is worth stating rather than skipping. `NET-003` exists because a *website's* logo is
remote input needing a signature check, a size cap and a bounded decode. A browser icon has none of
those risks precisely because it is not remote, and the way to keep that true is for the icon
mechanism to be `res/drawable` — a website cannot add a file to it.

## Manifest-controlled surface
**Nothing this ticket adds.** That is the ticket's security property, not an aside.

What a manifest can influence today is unchanged and stays unchanged: `SiteSkinTheme.from` maps
`configuration.branding`'s four colour fields into `SiteSkinColorScheme`'s six roles, guarded to
4.5:1 / 3:1. That surface is `SiteSkinTheme.kt:42` and it remains the entire website-influenceable
colour surface, exactly as `ADR-013` and the type's own documentation say.

The reason `C2` needs a test now rather than later is stated in `ADR-013` and is worth repeating in
the plan's own terms: **the invariant is currently maintained by an absence.** There is no browser
palette, so there is nothing for a manifest value to leak into. This ticket removes the absence.

The concrete leak this ticket must make impossible-and-detectable:

| Hypothetical path | What it would look like in code | Why it is not caught today |
|---|---|---|
| A browser token derived from branding | `WeboraColors.chrome = SiteSkinTheme.from(config).light.primary` | Nothing forbids the import |
| A browser token "themed" to the active site | `weboraColors(site = configuration)` | A plausible-looking convenience |
| The identity chip tinted by the site | `identityContainer = siteScheme.primary` | The most dangerous one: it repaints the exact element `ADR-006` makes browser-owned |

The third is the one with teeth. `ADR-013`'s `C1` mechanism is a chip carrying the registrable domain
and TLS state; a manifest-derived colour on that chip is a website influencing Webora's own identity
presentation, which is the `HARDEN-002` brand-impersonation surface arriving through colour instead
of through text.

## Browser-owned remainder
Everything in this ticket, enforced by four distinct mechanisms rather than by intent:

| Guarantee | Enforcing affordance |
|---|---|
| The browser palette is compiled and takes no input | `WeboraColorScheme` is built from `const` values; there is no factory taking a `SiteSkinConfiguration` |
| No path exists from core into the token layer | A source scan asserting the token sources import nothing from `dev.siteskin.core` or `app.webora.browser.siteskin` |
| No manifest value moves a browser token at runtime | A projection sweep asserting browser tokens are bit-identical before and after real manifests are projected, with the SiteSkin scheme proven to have moved |
| Every browser colour is measured | Reflection over the role model: every declared colour appears in the contrast table, as a measured pair or an explicitly justified decorative exemption |

The fourth is the anti-decay mechanism. A hand-written pair list is correct once; a reflected
completeness assertion is correct for tokens that do not exist yet, which is the same argument
`BrowserSurfaceConventionsTest` makes for discovering its scanned set rather than listing it, and
`SpecCorpusTest` makes for asserting registry completeness in both directions.

## Findings that changed the plan

**The measured table in `ADR-013` reproduces exactly.** Recomputing every pair from the published hex
values gives 12.44 / 6.80 / 7.65 light and 10.49 / 7.94 / 8.50 dark, and the chip-to-ground figures
land on 1.27 and 1.29 — the same numbers the ADR prints. The palette can be transcribed rather than
re-derived, and the contrast test will confirm the transcription rather than discover a problem.

**Every text and icon pair Direction A draws clears its threshold with margin.** Lowest measured body
pair is `onPrimary` on `primary` at 6.47:1 against a 4.5 target; lowest non-text pair is `primary` on
`chrome` at 5.19:1 against 3.0. Nothing in the direction needs adjusting to pass, so no value has to
deviate from the ADR.

**The only sub-threshold pairs are surface-against-surface.** `chrome` on `ground` is 1.15:1, `surface`
on `ground` 1.08:1, `divider` on `ground` 1.44:1, and the chip on ground 1.27:1. `ADR-013` already
ruled on the chip — a status display, not an interactive control, so WCAG 1.4.11 does not require its
boundary to carry contrast, and the identity is carried by text at 10.49:1 or better. The same
reasoning covers the rest: these are containment boundaries, and every one of them contains text or a
glyph that clears its own threshold. The plan must record them as **explicit** decorative exemptions
rather than omitting them, or the completeness assertion is worth nothing.

**Material's `outline` role wants the direction's `muted`, not its `outline`.** Material uses
`outline` for boundaries that must reach 3:1 and `outlineVariant` for decorative dividers. Direction A
uses tonal containers *instead of* outlines, so its `--f-outline` (`#C6D2D1` / `#2C3838`) is a hairline
divider — 1.44:1 on ground, correct for what it is and wrong for what Material will use it for. Mapping
Material `outline` → `muted` (7.73:1 light, 9.74:1 dark on ground) and `outlineVariant` → the
direction's hairline resolves it **without inventing a colour**, which matters for the closure
property below. The browser role is therefore named `divider`, since calling it `outline` would invite
exactly the wrong mapping.

**The closure property is what makes "no Material default" mechanical.** If every colour in the
derived Material `ColorScheme` must be a value that appears in the closed browser role model, then any
role left to a `lightColorScheme()` default fails the test by construction — no one has to remember to
pass all thirty arguments, and no one has to audit which ones Compose added in the last BOM bump. It
also means the error family cannot smuggle in a red: mapping Material `error` → `notSecure` and
`onError` → `identityContainer` reuses an already-measured pair with the roles swapped, and the
7.65:1 / 8.50:1 figures carry over unchanged.

**Both halves of the C2 test are needed, and neither is sufficient.** The runtime sweep proves values
do not move but would pass a design where the browser palette is *derived* from a manifest and happens
to be stable for the manifests tested. The source scan proves no path exists but would pass a design
that reaches core through reflection or through a third module. Together they are the same
belt-and-braces `:siteskin-core`'s Android-freedom uses: a classpath assertion **and** a CI job with
no SDK installed.

**`ColorScheme` and `ButtonDefaults` are readable in a plain JVM test.** `BrowserAccessibilityTest`
already asserts against `ButtonDefaults.MinHeight`, and `SiteSkinThemeTest` runs a 130-case colour
sweep with `Color` and a real `SiteSkinValidator`. No Robolectric, no emulator — so the contrast,
closure and isolation tests are all **Gate**-grade rather than Evidence.

**`unitTests.isReturnDefaultValues = true` is on.** `Color` and `ColorScheme` are pure Kotlin, but a
test that reached a real resource id or an `android.content.res` call would silently receive `0`
rather than failing. The tests here must therefore assert on Kotlin values, never on resource
resolution — a drawable's *existence* is proven by `assembleDebug` compiling `R.drawable.*`
references, not by a unit test asserting an int is non-zero.

**Ten icons, not eight, and the difference is evidence rather than preference.** `C6` listed eight
before a direction was chosen and named `stop`, which Direction A never draws. Enumerating the
`<use href="#i-…">` references inside the `dir-a` band gives exactly ten: `back`, `fwd`, `reload`,
`home`, `menu`, `more`, `lock`, `close`, `search`, `warn`. `search` sits in the address pill, `more`
in its trailing slot, `menu` in the dock, `warn` on the error page, `close` on the settings header,
and `lock` on the identity chip.

**The `warn` glyph has a second job the sketch does not draw.** Direction A only ever renders the
identity chip in its `Secure` state, but `SecurityPresentation` has two, and `NOT_SECURE` is the one
that matters. `ADR-013` measured a not-secure foreground for the chip (`#7A1B14` / `#FFB4AB`) without
naming a glyph. Shipping a lock for both states would be worse than no glyph; `warn` is the asset that
already exists in the set and it covers the second state. Which glyph the chip renders is `UX-003`'s
call — this ticket's obligation is that the asset and the colour pair both exist so `UX-003` is not
forced to choose between inventing one and reusing the lock.

**`values-night/themes.xml` is about the window, not about Compose.** `isSystemInDarkTheme()` reads
`Configuration.uiMode` and already returns the system setting regardless of the platform theme, so
the Compose half works the moment the theme selects on it. What does not work is the window
background behind Compose and the theme applied before the first frame: `android:Theme.Material.Light`
is light in every configuration. The night resource is what makes the pre-composition frame and the
system-bar regions agree with the palette.

## Risks
- **Transcription error in a hex value** → the contrast test asserts every pair rather than a sample,
  and the ADR's published ratios are reproduced in the plan so a wrong digit shows up as a changed
  number rather than as a still-passing test.
- **The completeness assertion becomes decoration** → it must fail when a token is added without a
  table entry. The tasklist records that as a negative control: add a role, watch it go red.
- **The `C2` test passing vacuously** → it has to project a real manifest through the real validator
  and assert the SiteSkin scheme *did* move, so a test that silently stopped exercising anything
  fails. Plus its own negative control: wire a manifest value into a browser token.
- **Decorative exemptions growing quietly** → each is a named entry with a written reason, reviewed
  like any other code. A future ticket adding one is visible in the diff; omitting a token entirely
  is not possible, because the completeness assertion is reflected.
- **`RAW_BUTTON_IMPORT` turning the build red for a plausible-looking change** → `WeboraIconButton`
  must land in `BrowserAccessibility.kt`. Recorded in the tasklist as an acceptance note, because the
  failure surfaces as an unrelated-looking convention test.
- **Repainting surfaces this ticket does not own** → supplying a palette necessarily changes every
  screen's appearance. Structure stays untouched, values stay `ADR-013`'s, and the instrumented
  suites (`BrowserFontScaleTest`, `PrivacySettingsScreenTest`, `SiteSkinChromeTest`) are semantics
  assertions that a repaint does not disturb.
- **`Typography` and `Shapes` quietly falling back** → same closure treatment as colour: every text
  style's size comes from the compiled scale, every shape corner from the compiled radii, asserted by
  reflection rather than by argument count.

## Open questions
None blocking. Two judgements are recorded so `/plan` commits to them rather than discovering them:

1. **The token layer is a closed browser role model with a Material `ColorScheme` derived from it**,
   mirroring `SKIN-001`'s projector, rather than a `ColorScheme` authored directly. Direct authoring
   would make the closure and completeness assertions run over a 30-role Material type whose shape
   changes with the BOM, which is a test that breaks on upgrades for reasons unrelated to Webora.
2. **The intermediate shape and spacing steps are derived from the direction's own base unit**
   (4 dp) rather than invented. `ADR-013` names 20 dp cards, 999 dp pills, a 4 dp base and a 20 dp
   gutter; the steps between them are multiples of the base. This is recorded because "derived from
   the stated base" and "chosen to look right" are indistinguishable in the resulting numbers, and
   only the first is reviewable.
