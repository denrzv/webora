# Research: UX-015 — Branded browser dock & SiteSkin navigation hub
Status: RESEARCH_READY

## Scope and current behavior

`RegularBrowser` projects protected integrated mode through `chromeHandoff()`: UX-014 supplies the
expressive top header, but `BottomChrome.SITESKIN` still renders `SiteSkinBottomNavigation` and the
content overlay still renders `SiteSkinQuickActions`. The `open_menu` action sets
`siteMenuExpanded`; `BrowserScreen` then renders `SiteSkinMenu`, whose site section is followed by a
separate browser section. Tabs/settings/inspector state and the active controller live in
`BrowserScreen`. UX-015 must replace only this integrated bottom/content placement with the UX-013
dock and hub; regular/Home `BrowserNavigationShell` remains unchanged.

## Origins, tabs, and lifetime

- The only site origin involved is the active tab's trusted `BrowserMode.Integrated.origin`, already
  canonicalized and exact-origin bound by core/activation. No hub code should parse or compare an
  origin.
- The browser-observed page URL enters `SiteSkinChromeModel.from` only for `NavMatcher` active-route
  selection and `ActionResolver.resolve`; it is not manifest authority.
- `activeTabId` selects both state and `BrowserWebViewController`. WebView observations are addressed
  to their originating tab id. Tab switching already closes `siteMenuExpanded` in the switcher
  session-change callback, while conditional composition requires an active integrated mode.
- A stronger, pure authorization seam should make hub visibility depend on the same active
  protected projection/configuration identity that supplied its model. Dismiss before dispatch and
  use callbacks created from the current `RegularBrowser` composition; do not store a raw URL,
  controller, tab id, or action in the hub state.

## Manifest-controlled surface

Only trusted, normalized and bounded values already present in `SiteSkinChromeModel` may enter the
hub: navigation/action labels, semantic icon tokens, typed `NavigationItem` values, active-route
state, site title/short name, and the six contrast-guarded presentation colour roles. Existing model
caps are 5 bottom navigation items, 5 quick actions, and 20 site-menu items. The hub must continue to
emit the original trusted item to the existing typed resolver; it must not manufacture a URI or
intent and must not accept raw DTOs.

## Browser-controlled remainder

- Dock order is exactly Back, Forward, brand hub, Tabs, More. Icons, localized labels, enabled
  states, 48 dp targets, geometry, semantics, and callbacks are compiled browser policy.
- Back uses the existing browser/native-Home behavior; Forward uses the active controller's observed
  `canGoForward` state and `goForward`. Tabs opens the existing tab switcher. More opens the existing
  browser-owned command surface. A manifest cannot add, remove, imitate, reorder, or style these.
- Hub attribution, open/dismiss state, section headings, browser menu items, favourite state, and
  browser command callbacks remain browser-owned. Website colours may paint the branded container
  but not browser control sub-surfaces.
- UX-014's canonical domain/TLS identity, header Back, loading/error regions, global safe-drawing
  inset, reduced-motion platform input, and brand-asset publication guard remain unchanged.

## Relevant decisions and specification

- `ADR-004` requires exact `(scheme, host, port)` origin binding; no registrable-domain or suffix
  comparison belongs in this UI.
- `ADR-006` requires browser security chrome and overflow/settings to remain visible and
  browser-owned.
- `ADR-013` establishes compiled Webora geometry/tokens and a floating dock without deriving
  browser tokens from SiteSkin values.
- SPEC action resolution defines `open_menu` as opening the browser-owned SiteSkin menu and keeps
  resolved actions closed data rather than generic native execution.
- UX-012/BROWSE-006 make the active tab projection and addressed controller the isolation boundary.
  UX-013 owns dock geometry/inset; UX-014 owns the expressive protected header.

## Recommended implementation direction

1. Introduce a focused `SiteSkinNavigationHub` beside existing SiteSkin chrome. Reuse
   `SiteSkinChromeModel`, menu headings/items, bounded labels, local icon mapping and typed callbacks;
   render trusted navigation plus quick actions in site-attributed sections and retain a distinct
   browser section.
2. Introduce an expressive integrated dock composable that calls `ExpressiveSiteSkinDock` and fills
   five equal browser-owned slots. Keep its API explicit (`canGoBack`, `canGoForward`, five named
   callbacks/model input), not a list/map supplied by a site.
3. In `RegularBrowser`, compute the model once for protected integrated mode, remove persistent
   bottom navigation and quick-action overlay, render the dock, and lift hub-open state/callbacks
   through `BrowserScreen` so existing Tabs/More destinations stay authoritative.
4. Keep `open_menu` routed to that same hub. Close before every site/browser dispatch. Ensure active
   mode/configuration loss makes composition and remembered visibility fail closed.
5. Add pure/source negative controls plus Compose instrumentation for fixed order, enabled states,
   section separation, selected route, callbacks, compact width/large font, and disappearance.

## Risks and mitigations

- **Stale hub after tab/origin change:** authorize composition from current integrated mode and close
  on active session changes/page start; add negative tests for non-integrated projection.
- **Site/browser command mixing:** separate composables/headings and typed callback parameters; never
  flatten into a generic item list.
- **Five controls overflow:** equal weighted 48 dp slots inside the 12 dp-inset primitive; icons carry
  semantics while visible long labels remain in hub/menu, not below each compact dock icon.
- **Duplicate site navigation:** delete integrated bottom navigation and overlay calls in the same
  task that wires the hub; source contract asserts they are absent from integrated composition.
- **Callback targets wrong tab:** callbacks are derived from the current active controller and model,
  hub stores only visibility; dispatch receives the trusted item selected from the current model.
- **More loses browser destinations:** reuse `BrowserMenuCommand`/browser-owned labels and existing
  state setters instead of inventing a new menu authority.

## Open questions resolved for planning

- The central brand control opens the hub; `open_menu` opens the identical surface.
- The hub owns site navigation, quick actions, favourite, page information, settings, and debug-only
  inspector via existing closed command vocabulary. Tabs has a fixed dock entry and need not be
  duplicated in the hub, though the existing command model may remain shared where changing it
  would widen ticket scope.
- Header Back remains because UX-014/UX-008 require it; the dock Back is the M9 essential browser
  command specified by UX-015. Neither is manifest-controlled.
