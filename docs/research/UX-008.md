# UX-008: Research
Status: RESEARCH_READY

## Question

Where can integrated mode expose browser Back without handing its presentation to the manifest or
weakening SiteSkin's identity and navigation hierarchy?

## Runtime map

- `BrowserScreen.kt`'s `RegularBrowser` selects integrated presentation when `BrowserMode.Integrated`
  has both a security presentation and a loaded brand asset. It replaces `BrowserChrome` with
  `SiteSkinTopBar`, then replaces the regular `BrowserNavigationDock` with
  `SiteSkinBottomNavigation`.
- The same `BrowserState.canGoBack` and `BrowserWebViewController.goBack()` already drive regular
  chrome and the activity-level `BrowserBackHandler`. No controller or state change is needed.
- `SiteSkinTopBar` is an 80 dp minimum-height row: bounded logo, manifest title/subtitle, then the
  browser-authored `SecurityIdentity` tagged `SITESKIN_SECURITY_TAG`. Its outer surface and text use
  the validated SiteSkin colour scheme.
- `WeboraIconButton` supplies the closed `ic_back` drawable, required browser-authored content
  description, 48 dp target, and enabled state. Browser navigation therefore has an existing
  accessible primitive and resource vocabulary.

## Origins and trust boundary

- The committed top-level WebView origin selects the active `BrowserMode.Integrated`; history may
  contain same-origin or cross-origin pages, but Back remains a browser history command rather than
  a manifest action.
- A trusted `SiteSkinConfiguration` for the active exact origin may influence the bounded logo,
  title, subtitle, SiteSkin colour scheme, site navigation, quick actions, and site menu.
- The manifest must not influence whether Back exists, its icon, accessible label, enabled state,
  placement, ordering, callback, touch target, container colour, or icon colour. `canGoBack` comes
  only from the observed WebView state and activation calls only `BrowserWebViewController.goBack()`.
- The registrable domain, TLS description, Back control, and browser menu remain browser-owned.

## Placement findings

1. A second bottom dock would compete directly with SiteSkin navigation, consume substantial page
   height, and violate the requirement not to spend the site's chrome budget.
2. A floating Back control in `BROWSER_CONTENT_TAG` would cover page content and would need explicit
   exclusion from CI-003's rendered-content measurement. It would also compete with quick actions.
3. A leading Back control in the existing top-bar row is visible before site branding, does not
   disturb the bottom site's primary navigation, and preserves the security row within its existing
   title column. To keep ownership visually and structurally explicit, the control must use
   `WeboraIconButton` on a browser-token container rather than SiteSkin colours.
4. Matching regular chrome, Back should remain present and disabled when history is unavailable.
   Hiding it would make layout and discoverability depend on history state.

## Test seams and negative control

- Extend the instrumentation-level `SiteSkinTopBarTest` to assert Back is displayed, enabled/disabled
  from browser state, labelled from `R.string.back`, and invokes its callback.
- The negative control should render two deliberately different hostile SiteSkin colour schemes and
  assert the tagged Back container retains the same browser-owned background while branding changes.
  This fails if the control is moved onto `colors.background` or otherwise adopts manifest styling.
- Preserve the existing `SITESKIN_SECURITY_TAG` assertions so moving/removing the identity row fails.
- Add a source contract in JVM tests if needed to prove `SiteSkinTopBar`'s navigation inputs are only
  `canGoBack` and `onBack`, not configuration-derived labels/styles. Runtime hostile colours cover
  the highest-risk visual leak; the closed signature covers suppression and relabelling.

## Risks

- Inheriting `SiteSkinTheme` Material locals or passing SiteSkin colours to the button would blur
  ownership even if the icon resource stays local.
- A 48 dp leading control plus 40 dp logo reduces title width. Existing one-line ellipsis bounds the
  remote strings; font-scale instrumentation should compile, and a narrow-width test should confirm
  identity remains displayed.
- Runtime instrumentation cannot run in this checkout without KVM/device; compile it and report the
  environment limitation rather than provisioning a software emulator.
