# UX-024: Research
Status: RESEARCH_READY

## Question

What the plan needs decided before it can commit to a trust boundary and a file list:

1. What the header actually costs today, and what removing `BrowserControlRow` returns.
2. Whether the integrated dock keeps Back and Forward, measured rather than preferred.
3. What the collapsed hub draws, and what that does to the icon budget.
4. Where the bouquet expands, and whether it can reach the trust chip, the title or `CI-003`'s
   measurement rectangle.
5. Which state variable owns it, given `UX-022` already recorded what a second flag costs.
6. Whether reduced motion gains its first real reader here.

## Origins involved

- **Serving origin** — the committed `SiteOrigin` of the integrated page. It supplies exactly two
  things this ticket touches: the `SiteSkinColorScheme` painting the header the hub sits inside, and
  the registrable domain feeding `headerIdentityPlacement`. Neither reaches a hub command.
- **Asset origin** — same-origin by `NET-003`, and irrelevant here. The hub draws no `BrandAsset`.
  `UX-017` deliberately made the *dock's* centre command the sole asset-bearing control; the
  navigation hub must not become a second one.
- **No new origin, no new request.** Nothing in this ticket fetches, decodes or caches anything.

## Manifest-controlled surface

If this ships as scoped, a website can influence:

- the header's background, and therefore the ground *behind* the hub's tile — as today;
- the `secondary`/`onSecondary` roles painting the dock pill the hub is *not* in;
- nothing else.

A website cannot influence: which commands the hub contains, their order, their count, their icons,
their labels, their enabled state, their callbacks, the hub's own icon or label, whether the hub
composes, or whether the bouquet opens. Every one of those is a compiled value or a
browser-observed fact.

**The specific new risk this ticket creates.** The browser bouquet and `UX-015`'s site bouquet will
share a visual vocabulary — circular bubbles, a `Popup`, an anchor in browser-owned chrome — by
design, because the issue asks for exactly that. The moment they share an *item model* a manifest
can publish an item that renders identically to Back. `SiteSkinItemModel` carries `icon`, `label`,
`isActive` and a `NavigationItem`; a browser command carries none of those and needs none. Two
types, not one type with a flag, and a source scan is what can see the difference.

## Browser-owned remainder

| Thing | Enforced by |
|---|---|
| Hub composes unconditionally in `PROTECTED_INTEGRATED` | `ChromeHandoff`'s exhaustive projection; no model field gates it |
| Exactly three commands, in compiled order | a pure `browserNavigationActions(...)` returning a closed enum list, drivable by the JVM gate |
| Icons and labels | bundled `R.drawable` / `R.string`, asserted by a source scan |
| Enabled state | `state.mode.canNavigateBack()`, `state.canGoForward`, `refreshAction(state)` — all browser-observed |
| Ground | `BrowserControlTile`'s `MaterialTheme.colorScheme.surfaceContainer`, per `UX-014` |
| Dispatch | `navigateBrowserBack`, `controller::goForward`, `dispatchRefresh` — no `ActionResolver` |
| Only one overlay open | one closed state value, so exclusion is structural rather than a pair of assignments |
| Teardown | the same projection that removes integrated chrome removes the hub with it |

## Findings

### F1 — The control row costs 40 dp of page, and the minimum height absorbs its removal

`ExpressiveSiteSkinHeader` is `heightIn(min = 96.dp)` with a 20 dp top gutter and 20 dp of reserved
curve depth below content.

| Band | Today | After |
|---|---|---|
| top gutter | 20 | 20 |
| `BrandRow` | 48 | 48 |
| `BrowserControlRow` | 48 | — |
| curve depth | 20 | 20 |
| content total | 136 | 88 |
| **rendered** (min 96) | **136** | **96** |

**40 dp returned to the WebView.** On the hosted emulator (360 dp, density 3) that is 120 px off a
~1757 px content region — about 7%. With `UX-023`'s wrapped identity row present the saving is the
same 40 dp, and the header goes 168 → 128.

This is the ticket's measurable goal, and it is why criterion 10 pins a *reduction* rather than a
new row count: an assertion that the header has two rows would also pass on a header that had
grown a different second row.

### F2 — The hub's collapsed footprint is Back's, so `headerIdentityPlacement` needs no new arithmetic

`HEADER_FIXED_WIDTH = 116.dp` is documented as *"Back 48 + 8, logo 40 + 12, and the 8 dp before the
chip."* A hub occupying the same 48 dp `BrowserControlTile` in the same leading slot leaves all
three terms unchanged, so `UX-023`'s table, its budget and its wrap threshold all still hold. Only
the KDoc's naming of the first term changes.

That is a reason to put the hub *in* the leading slot rather than beside it. Any other footprint
re-opens a measurement `UX-023` closed three commits ago.

### F3 — Three dock slots are wider than five and the centre command still fits

`ExpressiveSiteSkinDock`: a `Box` with 12 dp horizontal inset around a `Row` with 8 dp horizontal
padding. On the 320 dp floor:

```
320 − 2×12 (inset) − 2×8 (padding) = 280 dp of slot width
```

| Slots | Each | ≥ 48 dp target | 52 dp centre circle |
|---|---|---|---|
| 5 (today) | 56.0 | yes | fits, 2 dp each side |
| 3 (after) | 93.3 | yes | fits, 20.6 dp each side |

Removing Back and Forward makes every remaining slot *wider*, keeps Brand Hub in the centre
position it already occupies, and changes no dimension, radius, height or colour in
`ExpressiveSiteSkinDock`. `EXPRESSIVE_DOCK_MIN_HEIGHT` stays 60 dp.

**The honest cost, recorded rather than argued away.** Integrated Back goes from two one-tap
affordances to zero: the hub, then the bubble. Android system and predictive Back are unchanged and
remain a single gesture, and `BROWSE-002`'s precedence is untouched — but the visible affordance is
one interaction further away, and the issue directs this explicitly ("simplify redundant navigation
affordances where possible"). The alternative — hub in the header *and* Back/Forward in the dock —
is the duplicate-controls outcome the same paragraph forbids.

**What the collapsed hub may not do about it.** Surfacing Back's availability on the collapsed
control — a disabled hub at history root, say — is exactly criterion 2's failure: a control that
looks disabled when Back is unavailable *is* a Back button, and a user who cannot open it cannot
reach Forward or Refresh either. The hub is always enabled. Its three children carry state.

### F4 — The bouquet expands downward, in its own window, and clears everything

Anchor: the collapsed hub's 48 dp tile, at x = 20 dp (the header gutter), y = 20 dp.

`SiteActionBouquet`'s pattern inverted — `Alignment.TopStart` with a positive y offset instead of
`TopCenter` with a negative one. `TopStart` resolves against layout direction, so RTL is correct
with no physical constant, per `UX-022`.

| Constraint | Measurement | Verdict |
|---|---|---|
| horizontal fit at 320 dp | 20 gutter + 3 × 60 dp slots = 200 dp | 120 dp spare |
| the trust chip | trailing end of the brand row, y = 20…68 | bouquet starts at y ≈ 76 — no overlap |
| the site title | same row | no overlap |
| status bar / cutout | `BrowserScreen` consumes `safeDrawing` once; expansion is *downward* | never crosses it |
| 200% font scale | bubbles are icon-only and fixed at 52 dp; no text grows | unchanged |

**It overhangs `BROWSER_CONTENT_TAG` by design, and that is a capture constraint, not a layout
one.** The bouquet spans roughly y = 76…136 while the header ends at 96, so ~40 dp of it is drawn
over the top of the page region. A `Popup` is its own window and contributes nothing to the
header's layout, but `CI-003` measures *pixels* inside that rectangle from a device screenshot. So:
**no frame may be captured with the navigation bouquet open under `requirePageContent = true`.**
None of `CI-009`'s six canonical frames opens it, so nothing changes today; the rule needs writing
down before someone adds a seventh.

### F5 — One closed overlay state, because `UX-022` already paid for the alternative

`siteActionsExpanded` is a single boolean serving both site surfaces, reset in three places:

| Reset | Site |
|---|---|
| tab switch / active configuration change | `LaunchedEffect(activeTabId, integrated?.configuration)` |
| page start on the owning tab | `RendererEffect.DiscoverManifest` |
| tab-switcher session change | `onSessionChange` |

plus incidental clears in `onHome`, `onOpenBrowserMenu` and `dispatchSiteItem`'s `OpenMenu` arm.

`UX-022` recorded the finding directly: *"a drawer with its own flag would need all three again, and
the failure is silent and specific: a tab switch tears down the dock while a drawer nobody reset
stays composed over the next origin's page."* A second boolean for the navigation bouquet is that
same bet taken a second time, and it additionally makes criterion 13's mutual exclusion a pair of
assignments that can be forgotten in one direction.

**So: replace the boolean with a nullable closed enum.**

```kotlin
internal enum class IntegratedOverlay { SITE_HUB, BROWSER_NAVIGATION }
```

Exclusion becomes structural — a variable holds one value — and every existing reset becomes
`= null` with no new site. Parameter arithmetic is favourable too: `RegularBrowser` loses
`siteActionsExpanded`, `onSiteActionsToggle` and `onSiteActionsDismiss` (3) and gains `overlay` and
`onOverlayChange` (2).

`SiteSkinTopBar`'s parameter list stays at seven if the three commands arrive as one list plus one
dispatcher, replacing `canGoBack`/`onBack`/`canRefresh`/`onRefresh`. `LongParameterList` allows 6
and the function already carries `@Suppress`; not growing it is still worth doing.

### F6 — The commands are a pure list, which is where the gate can reach them

The repository's established shape for *"a closed browser-owned list that a manifest must not be
able to reach"* is `browserMenuCommands()` (`DEVX-003`): one expression, read by two surfaces, with
availability as a parameter so the JVM gate can drive the branch a debug-only build cannot reach.

The same shape applies:

```kotlin
internal enum class BrowserNavigationCommand { BACK, FORWARD, REFRESH }
internal data class BrowserNavigationAction(val command: BrowserNavigationCommand, val enabled: Boolean)
internal fun browserNavigationActions(
    canGoBack: Boolean, canGoForward: Boolean, canRefresh: Boolean,
): List<BrowserNavigationAction>
```

Total, compiled, ordered. The gate can then assert the count, the order, and each enabled flag's
source, none of which a Compose-free test could reach if the list were built inline in the
composable — the same argument `BROWSE-009` makes for `routeRendererEvent` and `BROWSE-010` for
`rendererMountAction`.

The negative control writes itself: a version taking `List<SiteSkinItemModel>` must fail.

### F7 — The collapsed hub needs a glyph the set does not have, and the budget is at its ceiling

`res/drawable/` holds exactly 20 icons and `BrowserIconContractTest.BUDGET` is 20. Every candidate
for reuse is wrong:

| Candidate | Why not |
|---|---|
| `ic_back` | criterion 2 — it *is* the misleading direct-Back reading |
| `ic_more` | already the dock's More; two controls, one glyph, one surface |
| `ic_menu` | means menu, and the integrated menu exists |
| `ic_search`, `ic_home`, `ic_tabs` | say something else |

The issue names the answer: *"a browser-authored navigation/history icon"*. Back, Forward and
Refresh are the history family, so a **history** glyph — a clock face with a counter-clockwise
arrow — names the group rather than any member of it.

That is a budget raise, 20 → 21, and the budget exists so a raise is a decision. `UX-005` and
`UX-021` are the precedents; both recorded the argument at the constant. The new drawable must
match the contract the test enforces: 24 dp / 24-unit viewport, `strokeWidth="1.9"`, round caps and
joins, **no** `fillColor`, one declared colour, real `pathData`.

### F8 — Reduced motion gains no reader here, deliberately

`ExpressiveSiteSkinPresentation` carries a closed `STANDARD`/`REDUCED` policy that `UX-013` and
`UX-014` both left unread, recording that *"the first downstream ticket adding a real decorative
transition must map `REDUCED` to an immediate state change."*

The issue permits this ticket not to be that one: *"reduced-motion settings should use a
minimal/fade/instant transition rather than requiring radial animation."* Choosing instant for
**both** policies satisfies it, and is the right trade here — the browser has no animation anywhere
today, and the first one should not be introduced inside a security-relevant overlay whose
behaviour no local gate can observe. The bouquet composes and decomposes immediately.

This is a deferral, and it should be written down as one rather than left to look like an omission.

### F9 — What a manifest could reach if the wiring is careless

Three concrete paths, each with the guard that closes it:

1. **A site colour on a browser command.** `presentation.colors.*` is in scope throughout
   `SiteSkinTopBar`. `BrowserControlTile` is the shared ground and
   `SiteSkinTopBarContractTest`'s `FORBIDDEN_IN_CHIP` list is the existing scan; the hub's
   declaration must be added to it.
2. **A site item in the browser bouquet.** Prevented by type, per the trust-boundary section.
3. **A site hint choosing the browser surface.** `UX-022`'s `presentation.hub` is read in exactly
   one place (`HubSurface.kt`) and that rule is already asserted — *"no file outside the policy may
   name a `HubPresentation` constant."* The new code must not become the second reader.

## Risks

- **A shared bouquet composable.** `ActionPetal` and `actionLift` are right there, and reusing them
  is the direct route to a shared item model → the plan must give the browser bouquet its own
  composable and its own model type, and a scan must prove the browser one names neither
  `SiteSkinItemModel` nor `NavigationItem`.
- **A second flag creeps back in.** The easy diff is `var navigationExpanded by remember { … }` →
  the plan must convert `siteActionsExpanded` to the closed overlay value in the same task that adds
  the hub, so the two never coexist as separate booleans even transiently.
- **`fixedDock`'s list gets *edited* rather than re-stated.** Deleting two names from an ordered
  list is indistinguishable from weakening it → the plan must pair the edit with a negative control
  that fails when a manifest-derived command is added to the three that remain.
- **The 40 dp is given back.** A bouquet that participates in the header's layout, or a collapsed
  hub taller than the tile it replaces → criterion 10's assertion must be a comparison, and the
  bouquet must be a `Popup`.
- **Hosted evidence.** No emulator here. Every hosted test edit is unverifiable locally beyond
  `:app:compileDebugAndroidTestKotlin` → the plan must state the residue as pending hosted
  acceptance, as `CI-009` and `CI-010` each did, and must not present a compiled instrumented suite
  as evidence the journey passes.
- **Ergonomics.** Back moves one interaction away in the mode where sites are most app-like → not
  mitigable in code beyond keeping system Back untouched; recorded in the PRD and to be re-checked
  against the first hosted frames.

## Open questions

Carried into `/plan` as explicit unknowns:

- **Does the collapsed hub show any state at all?** F3 argues it must always be enabled. Whether it
  may carry a *decoration* — a dot when Forward is available, say — is undecided; it is a
  browser-derived fact, so it is legal, but it is also scope the issue did not ask for. The plan
  should either commit to it or refuse it in one sentence.
- **Does `SITESKIN_BACK_TAG` keep its value on the new control?** Keeping it means the hosted tests
  need smaller edits and `assertDoesNotExist` teardown proofs keep working unchanged; it also means
  a tag named `back` identifies a control that is not Back, which is the kind of quiet lie
  `UX-020`'s "assert the application, not the constant" exists to catch. The plan must choose, and
  the choice changes how many hosted lines move.
- **One frame or none for the open bouquet?** `CI-009`'s inventory is pinned at six and is
  cardinality-independent in production. Adding a seventh frame is a `CI-*` ticket's decision, not
  this one's — but the plan should say so explicitly rather than leave it ambiguous.
