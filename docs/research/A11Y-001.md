# A11Y-001: Research
Status: RESEARCH_READY

## Question
Which accessibility guarantees are currently unowned, which component actually causes each gap, and
where the resulting affordance must live so that it cannot be omitted by the next screen. The plan
also needs to decide whether accessible text is a second channel for manifest content — because
assistive technology reads the semantics tree, not the pixels, so every visual bound `ADR-006` and
`HARDEN-002` place on manifest content has to have a semantics-tree counterpart or it is not a bound.

## Origins involved
- **The committed main-frame origin.** Already canonicalized into `SiteOrigin` and projected by
  `securityPresentation(BrowserMode)`. It is the only permitted source of accessible identity and
  transport-security text, in both regular and integrated mode. Address-bar text is user-editable
  and page content is attacker-controlled; neither may reach a security semantics node.
- **The manifest origin.** Identical to the committed origin by construction — `SKIN-004` publishes
  a candidate only when its canonical origin still equals current browser state. This ticket adds no
  new fetch and therefore no new origin.
- **Asset origins.** None new. `NET-003` already resolved brand artwork to a bounded decoded bitmap
  or a browser-generated monogram, and `SiteSkinTopBar` already clears semantics on that slot.

No network work, no new storage, and no new origin comparison is introduced by this ticket.

## Manifest-controlled surface
Unchanged in extent, but newly explicit in the accessible channel:

- **Site item labels** (`NavigationItem.label`, ≤ `SiteSkinLimits.MAX_LABEL_LENGTH` = 32 after core
  normalization) may name a bottom-navigation item, quick action, or menu row — and nothing else.
  `SiteSkinChrome.kt` already promotes `item.label` into `contentDescription`, which is the single
  place manifest text enters the accessibility tree today.
- **Toolbar title and subtitle** (≤ 64 / ≤ 128) are read as ordinary text nodes in the top bar.
- **Branding colours**, already normalized by `CORE-004` and guarded again by `SiteSkinTheme`.

A manifest gets **no** control over: any browser control's name, role, or state description; the
security node's text; the announcement of loading or failure; the touch-target minimum; the font
scale; the light/dark selection; or the order in which the security node is reached.

## Browser-owned remainder
| Guarantee | Enforcing affordance |
|---|---|
| Every browser control ≥ 48 dp | One browser-owned modifier, applied at the call site of each control; `Button` does not supply this itself (see below). |
| Operable at 2.0x font scale | Reflowing/scrolling containers in browser-owned screens. |
| Identity and transport security are announced | A dedicated semantics node built only from `SecurityPresentation`, which is built only from `SiteOrigin`. |
| State never colour-only | Textual `stateDescription` alongside every colour treatment. |
| AA contrast in both projections | `SiteSkinTheme.guardContainer`, now exercised on the dark projection and an adversarial corpus. |
| Manifest text cannot narrate security | Accessible manifest text is bounded and used only as an item name, never concatenated with browser security wording. |

### Verified framework behaviour (Compose Material3 1.4.0, from the resolved sources jar)
These were read out of the artifact rather than assumed, because each one decides whether a fix is
needed at all:

- `Button` applies `defaultMinSize(ButtonDefaults.MinWidth, ButtonDefaults.MinHeight)` where
  `MinHeight = ButtonSmallTokens.ContainerHeight = 40.dp`, and does **not** call
  `minimumInteractiveComponentSize()`. Every plain `Button` in this app is a 40 dp target. **Real gap.**
- `Switch` *does* call `minimumInteractiveComponentSize()` and `toggleable(role = Role.Switch)`. Its
  size and role are fine; it has no name because the label is a sibling. **Name-only gap.**
- `NavigationBarItem` uses `selectable(role = Role.Tab)`, so selection state is already exposed, and
  clears the icon's semantics when a label is shown. Selection is therefore *not* colour-only to
  TalkBack today; a `stateDescription` makes it explicit but is an improvement, not a repair.
- `NavigationBar` uses `defaultMinSize(minHeight = …)`, so it grows with font scale rather than
  clipping. **Not a gap.**
- `DropdownMenuItem` already applies `sizeIn(minHeight = 48.dp)`, so `SiteSkinChrome`'s explicit
  `heightIn(min = 48.dp)` on menu rows is redundant but harmless.

## Prior art
- `ADR-006` — the registrable domain and TLS indicator are never suppressible. The accessible
  channel is in scope for that rule, which is what makes item 4 of the PRD a security requirement
  and not a nicety.
- `ADR-011` / `HARDEN-002` — consent shows the complete canonical origin; consent controls are
  browser-owned. The consent dialog's buttons are in the 48 dp sweep.
- `SKIN-001` — the WCAG guard (4.5:1 body, 3:1 UI) and the closed six-role model already exist.
  This ticket does not re-derive them; it proves them on the projection nobody consumed.
- `SKIN-002` / `SKIN-003` — bounded logo slot, decorative icon suppression, one-line ellipsized
  labels, 48 dp SiteSkin targets, and the 1.5x font-scale instrumented tests to extend to 2.0x.
- `CORE-004` / `SiteSkinLimits` — label, title, and subtitle truncation already happened before any
  string reaches the app.
- `CLAUDE.md` testing section — no Robolectric, so composable behaviour is proven by splitting a
  pure function out and testing that; instrumented tests are QA evidence, not gate coverage.

## Risks
- **Semantics merge rather than replace** → adding a description to a node that already publishes
  one produces a doubled announcement. The plan must put each new description on a node whose
  resulting text is asserted, and must not add one to `Switch` and its label both.
- **48 dp applied blindly worsens 2.0x layout** → the button row grows past the viewport. The plan
  must pair the target minimum with a reflowing container, and must not resolve the conflict by
  shrinking the target.
- **A copied label limit silently diverges from core** → the app-layer bound must read
  `SiteSkinLimits.MAX_LABEL_LENGTH`, so a core change cannot leave the app enforcing a stale number.
- **Dark selection changes what ships today** → it must be driven only by the system setting, must
  not add a colour role, and must not become manifest-influenceable. `SiteSkinTheme.from` stays the
  only constructor.
- **Live-region announcements can become chatty** → loading is a frequent transition; announcing
  every progress change would be worse than silence. Only start/finish and failure are announced.
- **Instrumented tests are not gate coverage** → any guarantee stated as an acceptance criterion
  needs a JVM-provable counterpart, or it is documentation. The security-relevant ones (accessible
  security identity, bounded manifest text) must be pure functions tested with a negative control.

## Open questions
None blocking. One deliberate deferral: an in-app font-size or high-contrast preference is a
non-goal here, so Webora follows the platform. If `PLAY-001` finds a store requirement for an
in-app control, it gets its own ticket rather than widening this one.
