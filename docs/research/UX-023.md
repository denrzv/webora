## F1 — The row, exactly as it is today

`SiteSkinTopBar.kt:95` `BrandRow`, unchanged in contents by `BROWSE-011` (which only lifted it into
its own declaration to stay under detekt's `LongMethod` ceiling):

| Child | Width | Owner |
|---|---|---|
| `BrowserBack` | 48 dp (`MINIMUM_TOUCH_TARGET`) | browser |
| `Spacer` | 8 dp | browser |
| `BrandLogo` | 40 dp (`LOGO_SLOT_SIZE`) | browser slot, site pixels |
| `Spacer` | 12 dp | browser |
| title `Column` | `weight(1f)` | site text |
| `Spacer` | 8 dp | browser |
| `SiteSkinSecurityChip` | unweighted, `widthIn(max = 160.dp)` | browser |

`ExpressiveSiteSkinChrome.kt:114` `EXPRESSIVE_GUTTER = 20.dp`, applied start and end. So on a 320 dp
host the row has **280 dp**, fixed children take **116 dp**, and title + chip share **164 dp**.

The chip is `Row(spacedBy(4.dp), padding(horizontal = 8, vertical = 4))` containing a 16 dp shield
(`SECURITY_SHIELD_SIZE`) and 12 sp Medium text. Its non-text width is therefore
`16 + 4 + 8 + 8 = 36 dp`, and the text gets whatever remains.

**Where the numbers come from.** The ~117 dp / ~198 dp figures for `example.co.uk` at 100% / 200%
are `UX-021`'s, recorded at `SiteSkinTopBar.kt:314` and in `docs/BACKLOG.md`. This ticket does not
re-derive them — no emulator here — and treats them as the measured baseline. Anything this ticket
*adds* must therefore be justified structurally rather than by a new number nobody ran.

## F2 — The app has no responsive layout anywhere, and this is the first

`grep -rn 'BoxWithConstraints|fontScale|LocalConfiguration|maxWidth' app/src/main/java` returns
**nothing**. Every Webora surface today is a fixed composition that happens to fit, and the two
places that came closest — `UX-016`'s six equal dock slots and `UX-021`'s chip cap — both solved
their problem with arithmetic at a constant rather than a runtime branch.

That matters more than it sounds. Whatever ships here becomes *the* pattern for responsive layout in
this codebase, and the next surface that needs one will copy it. So the decision wants the same
shape the repository already uses for platform-touching logic: **a pure function the JVM gate can
drive, plus a thin composable wrapper that reads the platform value** — `rendererMountAction`,
`routeRendererEvent`, `refreshAction`, `resolveHubPresentation`, and `UX-014`'s animator-duration
read are all this shape, and `CI-003` records what happens when a decision lives where
`./gradlew test` cannot reach it.

## F3 — What the manifest can influence in this row, and why that is the whole risk

| Input | Site-controlled? | Reaches layout how |
|---|---|---|
| `model.title` | **yes**, bounded to 32 chars | length of the weighted column's content |
| `model.subtitle` | **yes**, bounded, nullable | whether a second line exists |
| `model.brandAsset` | pixels only | slot is fixed at 40 dp; `extremeAspectRatioBitmapCannotResizeLogoSlot` pins it |
| `presentation.colors` | yes, contrast-guarded | colour only, no dimension |
| `model.security` | **no** — browser-derived | the chip's content |

So the site controls **two** things that a naive responsive rule would read: title length and
subtitle presence. A trigger phrased as *"wrap when the title is long"* or *"drop the subtitle when
crowded"* lets a website decide the browser's layout — and the specific reachable outcome is a
manifest choosing a title that pushes the trust chip onto a second row, or off. That is
`HARDEN-002`'s impersonation surface arriving through layout instead of text, and it is the sharpest
thing in this ticket.

**The trigger must therefore be width and/or font scale only.** Both are platform facts a site
cannot influence. `LocalDensity.current.fontScale` and `BoxWithConstraints`'s `maxWidth` are the two
candidates, and neither has any manifest input.

## F4 — Three candidates, measured against the 164 dp budget

The backlog names three and rules only that browser identity may never be what yields.

**(a) Drop the subtitle at large scale.** Frees a *vertical* line, not horizontal width. The chip
and title still share 164 dp. **Does not solve the stated problem** — it is a height remedy for a
width failure. Also the subtitle is the site's, so dropping it is a content decision made on the
site's behalf.

**(b) Shrink the logo slot.** 40 dp → 24 dp frees 16 dp, taking the budget to 180 dp against a chip
that wants ~198 at 200%. **Insufficient on its own**, and it degrades the site's brand presence to
buy the browser room — a trade the browser should not need to make. `LOGO_SLOT_SIZE` is also pinned
by `extremeAspectRatioBitmapCannotResizeLogoSlot`, which asserts the slot is *fixed* regardless of
bitmap intrinsics; a scale-dependent slot weakens the guarantee that assertion exists for.

**(c) Wrap the chip onto its own row.** Removes the chip from the horizontal budget entirely: the
title column then has the full 280 − 116 + 8 = **172 dp**, and the chip gets a row where it can take
up to its 160 dp cap without competing. Both criteria 1 and 2 are satisfiable, and neither element
yields to the other. **This is the only candidate that satisfies the acceptance criteria.**

Cost: the header grows by roughly one chip-height row (~28 dp at 100%, more at 200%) *when the rule
fires*. `EXPRESSIVE_HEADER_MIN_HEIGHT` is a **minimum** (96 dp), not a fixed height, so the header
already grows with content and no constant needs changing.

## F5 — Where a wrapped chip should go, and the row that is already there

`BROWSE-011` added `BrowserControlRow` as a sibling below `BrandRow`, trailing-aligned via
`Arrangement.End`, currently holding only Refresh. A wrapped chip could join that row instead of
adding a third.

**Measured against it: it fits.** The control row holds one 48 dp tile against 280 dp, so ~224 dp is
free — more than the chip's 160 dp cap. Leading-aligned chip plus trailing-aligned Refresh is a
natural pairing, and both are browser-owned, which is exactly the grouping the row's KDoc already
describes ("the browser's controls, on their own line inside a header the site paints").

**But it collides with a live assertion.** `SiteSkinTopBarContractTest` has
`the browser control row does not compete with the brand row for width`, and its KDoc explains the
mechanism: the contract test locates the brand row's flexible title column by **the first
`Modifier.weight(1f)` in the file**, so the control row deliberately uses `Arrangement.End` rather
than a weighted spacer. Putting the chip there with any weighted arrangement breaks that locator.
A leading-aligned chip with `Arrangement.SpaceBetween` and no weight does not — but the plan must
check that assertion explicitly rather than assume it.

Adding a **third** row avoids the collision entirely at the cost of more height. The plan chooses;
research's finding is that the two-row option is viable and cheaper, and that the constraint on it
is a named test with a stated mechanism rather than a guess.

## F6 — What must not move, with the assertion that pins each

| Guarantee | Pinned by | Consequence if broken |
|---|---|---|
| Chip declared after the weighted title, unweighted | `the security identity is laid out after the flexible title` | a long title pushes the trust mark out |
| `SITESKIN_SECURITY_TAG` value and placement | `CI-009`, `CI-010`, `LiveSiteScreenshotTest`, `SiteSkinTopBarTest` | hosted teardown assertions stop meaning anything |
| Chip grounds on `primaryContainer` | `the security chip grounds on the container role its colours are measured against` | an unmeasured colour under the trust mark |
| No manifest colour in the chip | `no manifest colour reaches the security chip` | `UX-002` `C2` violation on the trust surface |
| Tag applied to a node, not merely declared | `the security tag is applied to a node rather than merely declared` | a scan passes over a chip that lost its tag |
| Instrumented identity floor 140 dp | `SiteSkinTopBarTest.SECURITY_CHIP_FLOOR` | a chip showing one character passes |
| 48 dp targets for Back and Refresh | `SiteSkinTopBarTest` | `A11Y-001` regression |
| Logo slot fixed at 40 dp regardless of bitmap | `extremeAspectRatioBitmapCannotResizeLogoSlot` | site pixels resize browser chrome |
| Control row does not compete for width | `the browser control row does not compete with the brand row for width` | the title-column locator breaks |
| Full-width `Secure · domain` row stays deleted | `the full-width security row and its separator are gone` | `UX-021`'s reversal |

## F7 — Origins and trust boundary

No origin decision changes. The chip's content is `SecurityPresentation`, derived only from the
committed `SiteOrigin` and `BrowserState.transportSecurity` — `UX-021`'s four states, one owner
(`transportLabel`), no manifest input. This ticket moves *where the chip is drawn* and touches
neither what it says nor how it is classified.

Nothing in discovery, consent, activation, the renderer, event routing, capture policy or `spec/` is
implicated. Criterion 10 should be met by not editing those files at all, which makes it verifiable
from the diff rather than from a test.

## F8 — Evidence the JVM gate can and cannot hold

**Can:** the decision as a pure function over (width, fontScale) → layout choice, driven through
every input; a source scan that the decision reads no manifest value; the declaration-order and
tag/colour contracts above, which are existing tests that must keep passing unedited.

**Cannot:** that a 13-character domain actually renders without ellipsis at 200% on a 320 dp host.
That is a text-measurement fact requiring a device, and this checkout has none. Criterion 1 is
therefore instrumented evidence, recorded and never promoted to a gate claim — `A11Y-001`'s rule and
the posture `CI-002`–`CI-005` each took.

This asymmetry is the reason F2's shape matters: the more of the ticket that lives in the pure
decision, the more of it the developer machine can defend. A responsive layout written entirely
inside a composable would be a ticket with no gate coverage at all.

## F9 — Landing order

1. **The decision.** Pure function plus its tests, wired to nothing. Gate-drivable from the start.
2. **The layout.** Consume the decision in `SiteSkinTopBar`, keeping every F6 assertion passing
   unedited where possible; where one must change, its negative control changes with it.
3. **Evidence.** Instrumented cases at 320 dp × 200%, and the default-scale case that proves the
   large-scale path is *not* taken at 100% (criterion 7) — the anti-vacuity guard, since a rule that
   always fires would satisfy criterion 1 while breaking the layout everyone else sees.
