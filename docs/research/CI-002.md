# CI-002: Research
Status: RESEARCH_READY

## Question

Three things the plan cannot decide without evidence:

1. **What actually produced the `System UI isn't responding` dialog** on the green `CI-001` run, so
   the fix removes a cause rather than a symptom.
2. **What the device can be asked** that means "ready to be photographed", given that
   `sys.boot_completed=1` demonstrably does not.
3. **How an automated dismissal can be narrow enough to be safe** — how the harness tells a
   system-owned dialog from a Webora-owned one, from the device, without a locale-dependent or
   version-fragile guess, and where the deciding code can live so a JVM test with a negative control
   can reach it.

## Observed evidence

Run [`31491580516`](https://github.com/denrzv/webora/actions/runs/31491580516) — the first green
screenshot run, `ci/fix-android-emulator-disk` @ `328bd08d`, conclusion `success`, three PNGs
collected. Its own step timings are the finding:

| Time (UTC) | Event |
|---|---|
| 12:30:59 | `Run live SiteSkin screenshot journey` step starts — AVD creation, then emulator boot |
| ~12:33 | Emulator reports booted; `scripts/android-screenshot-ci.sh` starts Gradle |
| 12:33–12:41:43 | **72 Gradle tasks execute** — Kotlin compilation, D8, `packageDebugAndroidTest` |
| 12:41:54 | `Starting 1 tests on emulator-5554` |
| 12:42:23 | `Finished 1 tests`; `BUILD SUCCESSFUL in 8m 39s` |

So for **eight and a half minutes** a full Android build ran on the same 4-vCPU hosted runner as a
freshly booted emulator, and only then did the journey start. `system_server` and `com.android.
systemui` finish their own start-up work — package scanning, JIT, launcher inflation — inside that
window, at whatever CPU share the Kotlin daemon and D8 leave them. An ANR is the *expected*
consequence of that arrangement, not an emulator defect: Android's ANR timers are wall-clock, and
the watchdog does not care that the delay came from the host.

`BACKLOG.md` §M7 records the visible outcome from the artifact: `System UI isn't responding`
overlays covered all canonical frames. Both facts point at the same cause and the same first fix —
**build before boot, so the emulator's start-up is not competing with a compiler.**

This is also why the current `png_count == 3` guard passed: the pipeline's only evidence assertion
is that three files exist. Nothing in it can look at a frame.

## Origins involved

None. `CI-002` adds no network path, no origin, and no manifest handling. The journey continues to
use exactly one origin — `https://denrzv.github.io`, the live Bloom Flowers deployment reached over
ordinary HTTPS discovery, inherited unchanged from `CI-001`.

## Manifest-controlled surface

**Nothing.** No production source changes, and no website can influence the readiness gate, the
capture, or the dismissal decision — none of them read manifest content. The one adjacent risk is
worth naming so the plan does not create it: if the interference guard were ever keyed on *page or
manifest text* ("dismiss the dialog whose text mentions the site"), a website would gain a lever on
the harness. It is keyed on the window's owning **process name**, which only the OS supplies.

## Browser-owned remainder

This ticket's trust boundary is not an origin boundary — it is **evidence integrity**, and it runs
the same direction as the product's rules.

| Must hold | The affordance that enforces it |
|---|---|
| The harness may remove system-owned interference | Allow-list of exactly one process, `com.android.systemui` |
| The harness may never remove product-owned interference | Any other owner is a test failure carrying the observed window; the allow-list has no wildcard and no "unknown → dismiss" branch |
| A dismissal is never silent | Every dismissal is written to the run artifact with the window title it acted on |
| An unreadable device state is not a pass | The focus check fails closed when it cannot identify the focused window at all |

This mirrors `PROJECT_RULES.md`'s allow-list rule one layer up: an unknown dialog is treated exactly
as an unknown action type is — refused, not guessed at. The failure mode this prevents is concrete:
a generic "dismiss the top dialog" loop would clear a Webora crash dialog and photograph the
launcher behind it, and the job would stay green.

## What the device can be asked

`sys.boot_completed=1` fires when `ACTION_BOOT_COMPLETED` is dispatched. It says nothing about
System UI having settled. Signals that are actually observable over `adb`, all cheap and all
poll-friendly:

| Signal | Command | Means |
|---|---|---|
| Boot broadcast | `getprop sys.boot_completed` → `1` | the current, insufficient gate |
| Boot animation gone | `getprop service.bootanim.exit` → `1` | the display is no longer owned by bootanim |
| Package manager live | `pm path android` returns a `package:` line | `system_server` is answering binder calls |
| A window is focused | `dumpsys window` → `mCurrentFocus=Window{… u0 <title>}` | something is actually on screen |
| Nothing has crashed | that title is not an error-dialog title | System UI (or anything) is not already in ANR |

The gap the plan must close is that any one sample can be lucky. A **settle window** — the same
verdict on N consecutive samples, under an overall deadline — is the difference between "ready" and
"ready at the instant we happened to look", and unlike a fixed `sleep` it is an observation with a
record.

## How the OS names an error dialog

AOSP titles these windows from the framework, not from a resource string, which makes them
locale-independent and greppable:

- `AppErrorDialog` (crash) — `attrs.setTitle("Application Error: " + processName)`
- `AppNotRespondingDialog` (ANR) — `attrs.setTitle("Application Not Responding: " + processName)`

So `dumpsys window`'s `mCurrentFocus` line carries both *that* an error dialog is up and *whose
process* it belongs to. `com.android.systemui` and `app.webora.browser.debug` are distinguishable
without reading a single translated word, which is what makes a one-package allow-list implementable
rather than aspirational.

The buttons are a weaker contract and the plan must treat them as such. The ANR dialog is an
`AlertDialog` built by `BaseErrorDialog`, so `Wait` is the *negative* button — `android:id/button2`
— while the crash dialog uses a custom layout with `android:id/aerr_*` ids. Neither id is public
API. The harness therefore verifies the button it is about to press and fails closed with the
observed node tree when it cannot, rather than clicking whatever is at a coordinate.

The instrumentation can reach these nodes because `UiAutomation` runs with a shell-privileged
accessibility connection; `LiveSiteScreenshotTest` already uses it for `takeScreenshot()`.

## Where the deciding code can live

The dismissal decision is the security-relevant part of this ticket, so it needs a test that fails
when it is widened. That rules out both obvious homes:

- **`src/main`** would make it JVM-testable and would ship test-harness policy inside the browser.
  Not acceptable for a screenshot ticket.
- **`src/androidTest` alone** keeps it out of the APK but puts it where `./gradlew test` cannot see
  it — and this checkout has no `/dev/kvm`, so "the test exists" would mean "the test has never
  run".

There is a third option with precedent in this repository. `app/build.gradle.kts` already shares one
source directory between source sets that AGP would otherwise keep apart:

```kotlin
getByName("debugRelease") {
    java.srcDir("src/release/java")
    kotlin.srcDir("src/release/java")   // AGP 9 needs both; java.srcDir alone is not compiled
}
```

The same mechanism can give the policy a home that **both** `test` (JVM, runs here) and
`androidTest` (device, runs in CI) compile, while `main` does not — so the JVM gate proves the
decision and the device consumes the same code, with no second copy to drift.

## Risks

- **The dismissal path may never execute in CI once contention is removed** → the proof of the
  decision must live in JVM tests with negative controls, not in "the hosted run went green".
- **A `dumpsys` parser that matches nothing turns the focus check into a no-op** → parse failure and
  an unidentifiable focus are failures, and the raw dump is written to the artifact so the recorded
  fixtures can be checked against a real device.
- **Button ids are not public API** → verify before pressing, fail closed with the node tree.
- **Pre-building outside the emulator step could silently re-build inside it** if a task is
  considered out of date → assert both APK files exist before Gradle runs, so a rebuild is a loud
  precondition failure rather than eight quiet minutes.
- **Scope creep into `DEVX-002`** → artifact files may be *added*, but the existing names, paths and
  upload globs stay put.
- **The settle window lengthens every run** → it is bounded, sampled in seconds, and cheap compared
  with the eight minutes the pre-build moves out of the emulator step.

## Open questions

Carried into `/plan` rather than resolved here:

1. Does the System UI ANR still occur once the build no longer overlaps boot? Unknowable without a
   hosted run, and the design is deliberately correct either way — the guard is defence in depth, not
   the fix.
2. Do the recorded `dumpsys window` fixtures match API 33 byte for byte? The hosted run's diagnostics
   answer it; until then the parser is written to accept the documented shape and fail closed on
   anything else.
