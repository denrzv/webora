# UX-005: Research
Status: RESEARCH_READY

## Question
How can integrated SiteSkin chrome replace prototype glyphs with semantic vectors without allowing
manifest input to address browser resources, weakening accessibility, or drifting from validation?

## Origins involved
- The committed page origin supplies the already-validated manifest during existing discovery.
- Navigation/action destinations remain governed by the existing exact-origin and action-resolution
  rules; this ticket adds no destination or origin capability.
- No asset origin is involved. Every trusted-chrome icon is compiled into the app. Logo fetching is
  unchanged and is not part of this icon path.

## Manifest-controlled surface
A site may choose an optional icon **token** on each navigation/menu/quick-action item. Core accepts
only its closed vocabulary and normalizes any unknown token to `generic` with
`SS-W-ICON-UNKNOWN`. A trusted `NavigationItem.icon` can therefore influence which browser-owned
decorative shape is displayed, but not its resource id, bytes, tint, size, semantics, or behavior.

## Browser-owned remainder
The browser owns the token-to-`R.drawable` mapping, bundled vector bytes, tint, geometry, selected
indicator, content descriptions, state descriptions, touch targets, fallback, and action dispatch.
There must be no `getIdentifier`, URI parsing, file lookup, font/glyph rendering, or network fetch in
the selection path. Item labels remain the accessibility names and icons clear their own semantics.

## Prior art
- `ADR-006` requires browser-owned, unsuppressible security identity in integrated chrome.
- `ADR-007` establishes forward-compatible unknown-name handling and allow-list validation.
- `ADR-013` and `UX-002` establish bundled 24 dp stroke vectors, browser-owned tint, and a counted
  icon budget instead of an external icon dependency.
- `SKIN-003` establishes trusted model projection, defense-in-depth limits, selected semantics, and
  decorative icon semantics.
- The schema deliberately treats `icon` as a bounded string rather than an enum; the security layer
  is authoritative so a future name does not reject the entire manifest.

## Risks
- UI/core vocabulary drift → define one explicit mapping test and update conformance output with core.
- Dynamic Android lookup sneaks in later → source-reading negative control forbids it in the icon seam.
- Added vectors violate the established optical system → expand `BrowserIconContractTest` and budget.
- A launcher icon misrepresents multiple quick actions → use the first trusted bounded action as a
  preview while retaining the browser-authored plural accessibility label and full expanded menu.
- Large text crowds bottom navigation → retain Material `NavigationBarItem`, ellipsized one-line labels,
  and instrumentation coverage at 200% font scale.

## Open questions
None. `catalog` is the generic storefront/catalog cue, `flower` is the domain-specific cue, and
`grid_view` remains supported for compatibility while Bloom Flowers moves to `flower`.
