# UX-011: Research
Status: RESEARCH_READY

## Question

How can Home and ordinary pages share the existing browser-owned dock while preserving active-tab,
system-navigation, accessibility, and manifest trust boundaries?

## Current surface and state ownership

- `BrowserScreen.kt` is the composition root. It derives `state` and `controller` from the active
  `BrowserSession` tab. Home currently returns early after rendering `HomeScreen`; regular pages
  continue into `RegularBrowser`, whose non-integrated branch alone renders
  `BrowserNavigationDock`.
- `HomeScreen.kt` owns its scrolling content, editable search field, records, and an additional
  full-width Tabs button. It accepts no WebView controller or manifest state. The separate Tabs
  affordance is the discontinuity this ticket should remove.
- `BrowserChrome.kt` defines the only browser dock. It presents Back, Forward, Reload, Home, and
  More; Tabs is currently reachable only through the overflow menu even though `BROWSE-006` already
  wires the callback to the real switcher.
- `BrowserState` holds the active tab's observed Back/Forward flags and load state.
  `BrowserWebViewController` remains per-tab. Home has no loaded renderer, so Back, Forward, and
  Reload must be disabled rather than routed to a detached or background controller.
- `MainActivity` enables edge-to-edge. `BrowserScreen` applies `WindowInsets.safeDrawing` to its
  root modifier, so navigation/status/cutout insets are already consumed once for Home, regular,
  and integrated surfaces. The dock must remain inside that padded root rather than add its own
  navigation-bar padding.
- `BrowserBackHandler` registers with `OnBackPressedDispatcher` and delegates to the active
  controller only when `state.canGoBack`. This is the existing system/predictive-back-compatible
  boundary; this ticket need not draw or intercept Android Home/Recents.

## Origins and manifest-controlled surface

Home has no origin. An ordinary page has the active tab's browser-observed `SiteOrigin`. A trusted
manifest may affect integrated top/bottom site chrome only after activation; it is not accepted by
`HomeScreen`, `BrowserNavigationDock`, or their callbacks. Regular shell labels, icon resources,
order, Material colours, enabled states, tabs/settings/inspector dispatch, and layout must remain
browser-authored.

The strongest negative control is structural: keep the dock signature limited to browser-observed
booleans and browser-owned callbacks, and assert that the shared Home/regular call sites do not pass
`SiteSkinConfiguration`, `BrowserMode.Integrated`, theme values, or manifest-derived content. This
also prevents a future manifest field from silently acquiring shell authority.

## Layout and accessibility

- `WeboraIconButton` requires a non-null accessible name and enforces `MINIMUM_TOUCH_TARGET` of
  48 dp. Adding a direct Tabs icon through this wrapper preserves both properties.
- The dock has a fixed 60 dp height and currently five 48 dp action targets. Adding Tabs creates six
  targets (288 dp), which fits the project's compact pixel profile within the 320 dp-wide screen
  after 40 dp of gutters only if the dock is allowed to occupy the full width and distributes
  targets without extra fixed gaps.
- Icon-only semantic labels do not scale with font size, so 200% text does not widen the dock. Home
  content should use `weight(1f)` above the same dock, allowing its lazy list to scroll independently
  without clipping the persistent shell.
- Compose instrumentation can assert displayed/enabled semantics, direct Tabs dispatch, and 48 dp
  minimum width/height for all six controls. The existing double-font harness should cover Home as
  well as regular chrome.

## Proposed seam and likely files

- Change `BrowserNavigationDock` to accept `canReload`, render direct Tabs before More, and keep the
  existing browser-owned overflow command for compatibility.
- Introduce a small `BrowserNavigationShell` layout composable in `BrowserChrome.kt` that owns the
  full-width gutter/padding once. Both Home and `RegularBrowser` call that same shell/dock rather
  than duplicating modifiers.
- Change the Home branch in `BrowserScreen.kt` to a `Column`: `HomeScreen(weight(1f))` followed by
  the shared shell with disabled history/reload callbacks and the real tab switcher callback.
  Remove Home's separate Tabs button and parameter.
- Update `BrowserChromeTest.kt`, `HomeScreenTest.kt`, `BrowserFontScaleTest.kt`, contract tests,
  strings, and add a tabs vector if the closed browser icon set lacks one.
- After implementation update `CLAUDE.md`, `docs/ROADMAP.md`, and ticket reports. No core, protocol,
  network, permission, persistence, or ADR change is expected.

## Risks and verification

- A fixed-height six-action row can overflow if padding is duplicated; pixel-size Compose tests are
  required.
- Reload must be disabled on Home and should track whether the active regular tab has a committed
  page rather than remain an always-enabled no-op.
- Moving the direct Tabs action must not remove overflow access or alter integrated SiteSkin chrome;
  `UX-012` remains responsible for mode handoff.
- The full pre-commit gate proves JVM tests, lint/detekt, APK assembly, and instrumentation source
  compilation. With no `/dev/kvm` or attached device, runtime gesture/three-button checks and a
  screenshot are environment-limited rather than replaced with a software emulator.
