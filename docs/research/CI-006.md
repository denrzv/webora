# CI-006: Research
Status: RESEARCH_READY

## Question
What observable condition distinguishes a boot-complete emulator from one quiet enough to run the
canonical screenshot journey, without weakening capture-time evidence.

## Origins involved
- The live page and manifest use `https://denrzv.github.io`; the logo is same-origin under the
  already-trusted configuration.
- This ticket does not fetch, compare, or alter any origin. It runs before the app/test APKs start.

## Manifest-controlled surface
Nothing. The readiness script observes Android boot services, PackageManager, window focus, and
kernel CPU counters before instrumentation. Remote page and manifest bytes have not been consumed.

## Browser-owned remainder
The harness owns readiness and evidence acceptance. `ScreenEvidencePolicy` and the instrumented guard
remain the sole capture-time classifiers; readiness must not classify/dismiss windows, and a website
cannot extend the deadline, change the quiet threshold, or cause a contested frame to be saved.

## Prior art
- `CI-002`: boot completion alone is not visual readiness; use repeated observable samples.
- `CI-004`: only the allow-listed System UI ANR may be cleared, by its Wait affordance.
- `CI-005`: the ownership verdict must be sampled at the instant of capture and may only refuse more.
- `NET-004`: runs 16 and 17 show five system processes timing out; run 18 captures immediately on a
  quiet device. The brand-asset wait took under one second and is not causal.

### Candidate observations

Package/dexopt log strings are implementation-specific and retrospective: absence of a selected
message does not prove the device has capacity. Process-specific checks also miss run 17's central
fact, which is contention across System UI, phone, keyboard, intelligence services, and search.
Android's aggregate `/proc/stat` counters instead measure the shared resource implicated by all of
them. Two successive samples yield a percentage without locale or wall-clock parsing. Because the
gate already requires consecutive samples, a busy observation naturally resets settling rather than
adding a second retry mechanism.

The first counter observation has no preceding interval and therefore cannot prove quiet. It must be
reported distinctly and rejected. Counter parse failures and resets also fail closed. The arithmetic
belongs in a pure function so CI can pin boundary behavior without `/dev/kvm`.

## Risks
- Guest CPU can be briefly busy for legitimate work → use repeated samples and the existing bounded
  deadline, not a single observation or unbounded wait.
- Integer arithmetic can misclassify a boundary → test exact below/at/above-threshold fixtures.
- `/proc/stat` format/counters can be missing or reset → distinct fail-closed verdicts and samples.
- Adding a new signal without artifact detail repeats the original diagnosis gap → log raw previous
  and current totals plus derived percentage on every sample.
- A readiness change could drift into capture policy → touch no Android source or timing constants.

## Open questions
The initial quiet threshold needs hosted confirmation. This is validation, not permission to weaken
the capture guard or lengthen its deadline.
