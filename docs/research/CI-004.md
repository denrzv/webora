## 1. The guard's own KDoc states the contract that `dismissSystemAnr` breaks

`ScreenEvidenceGuard`'s class documentation, written by `CI-002`:

> The bounded poll exists because a dialog dismissal is asynchronous: for a moment after `Wait` the
> focused window can legitimately be nothing at all. So **a blocking verdict is retried until the
> deadline** and only then fails — with the last reason and the dump that produced it.

That is the design intent, and `requireAppOwnsScreen` implements it faithfully for two of the three
verdicts:

| Verdict | Loop behaviour | Retried? |
|---|---|---|
| `OwnedByApp` | records focus, returns | — |
| `Blocked` | stores `lastReason`, sleeps, re-dumps | **yes**, until the deadline |
| `DismissableSystemAnr` | calls `dismissSystemAnr`, which throws on 0 candidates | **no** |

**The verdict that means "this is clearable" is the only one that cannot be retried, and the verdict
that means "this is unrecoverable" is retried patiently for 20 seconds.** That inversion is the
defect in one sentence. A `Blocked` screen gets forty polls; a dialog we are explicitly permitted to
clear gets one look at the accessibility tree.

## 2. The single-look lookup, and the three ways it reads zero

```kotlin
val candidates = WAIT_VIEW_IDS.flatMap { viewId ->
    val root = uiAutomation.rootInActiveWindow ?: return@flatMap emptyList()
    root.findAccessibilityNodeInfosByViewId(viewId)
        .filter { it.isClickable && it.isVisibleToUser }
        .map { viewId to it }
}
if (candidates.size != 1) { throw evidenceFailure(...) }
```

| Cause | Why it yields 0 | Distinguishable today? |
|---|---|---|
| **a. Node tree lags the window** | `dumpsys window` reads WindowManager, which names `mCurrentFocus` the moment the window is added. The accessibility node tree is a different pipeline and populates later — more so on 2 cores under `swiftshader`. | No |
| **b. `rootInActiveWindow` is null** | Transient; the `?: return@flatMap emptyList()` reports it as an absent button. Also re-fetched *inside* the `flatMap`, once per id, so the two lookups can see different trees. | No |
| **c. `FLAG_REPORT_VIEW_IDS` not in effect** | `findAccessibilityNodeInfosByViewId` returns nothing at all without it. `enableViewIdReporting()` returns silently when `serviceInfo` is null, and nothing records whether the flag took. | No |

All three produce the identical message the run printed twice. The code already anticipated (c) — the
KDoc on `enableViewIdReporting` says the failure is *"indistinguishable from a dialog with no Wait
button — a recoverable run failing as an unrecoverable one."* That sentence describes what happened,
and the guard it motivated covers only one of the three routes to it.

**On (c) specifically:** assigning `uiAutomation.serviceInfo` reconnects the accessibility service,
so the flag is not necessarily in effect the instant `init` returns. The guard is constructed well
before frame 01, which makes (c) the least likely of the three here — but the silent `?: return` is
still a hole worth closing, and cheap to close.

## 3. PRD open question 3, answered — and it decides the file list

**Yes, the dismissal decision is expressible as a pure function, and it is currently the only
capture-time decision that is not one.**

Today the split is:

| Decision | Where | JVM-testable |
|---|---|---|
| What is the focused window? | `ScreenEvidencePolicy.focusVerdict` | yes |
| Is the page drawn? | `RenderedContentPolicy.verdict` | yes |
| **Do these candidates justify a press?** | `if (candidates.size != 1) throw` inside the guard | **no** |

The third is the same *kind* of decision as the other two — a total classification of an observation,
fail-closed on ambiguity — and it sits in `androidTest`, where `./gradlew test` never compiles it and
managed checkouts with no `/dev/kvm` never run it. That is precisely the shape `CI-002` and `CI-003`
both refused, for the reason `CI-003` recorded: an Android type in the signature drags the decision
into a source set the gate cannot reach.

The observation it needs is a `List<String>` of view ids that matched and were clickable and visible.
No Android type is required to decide on it, so the function belongs beside its two siblings in
`src/screenshotPolicy/java`, already wired into both `test` and `androidTest`
(`app/build.gradle.kts:124-125`, `java.srcDir` **and** `kotlin.srcDir`).

The three-way shape the PRD fixed maps onto a sealed verdict exactly as `FocusVerdict` does, which
means the "no `else` branch that dismisses" property is inherited rather than re-argued.

## 4. What `MAX_DISMISSALS` counts, and why the fix must not conflate it

`dismissals++` happens **before** the attempt, and the exhausted-budget message reads
`"${verdict.title} survived $MAX_DISMISSALS dismissals"`. That sentence is only true if a press
actually occurred: a dialog cannot *survive* a dismissal that never pressed anything.

So a retry for "not queryable yet" must **not** consume the budget. `MAX_DISMISSALS = 2` bounds how
many times the harness may clear a dialog that keeps coming back — a different question from how
patiently it waits for one dialog's button to become pressable. Conflating them would reintroduce the
same bug with a larger constant: two polls instead of one.

## 5. What the fix must not disturb

| Property | Owner | How it stays |
|---|---|---|
| One process, one action | `ScreenEvidencePolicy.DISMISSABLE_ANR_PROCESS`, `WAIT_VIEW_IDS` | untouched; this ticket changes *when we conclude*, not *what may be cleared* |
| Ambiguity fails closed | `candidates.size != 1` | preserved as an explicit branch; ≥2 must stay immediate |
| No `else` that dismisses | the sealed `FocusVerdict` | mirrored by the new sealed verdict |
| Every refusal keeps its dump | `evidenceFailure` writes `window-<label>.txt` | unchanged |
| `ScreenEvidencePolicyTest` fixtures | 20 recorded cases | must pass **unedited**; needing to edit one is the signal the change reached too far |

## 6. The diagnostic gap, which is why this cost two runs to understand

The failure message names the ids the harness **looked for** and never the ids that were **present**:

```
0 Wait affordances were found among android:id/button2, android:id/aerr_wait
```

From that line alone, (a), (b) and (c) are indistinguishable — which is why two hosted runs and a log
download produced no more information than the first assertion did. The guard already holds the
focused window's node tree at that moment and can enumerate its ids cheaply. Recording them turns the
next occurrence into a one-line diagnosis, and is the difference between this ticket fixing the
symptom and fixing the blindness.

This is the same lesson `CI-003` recorded as *record the measurement on success, not only on
failure*, arriving from the other direction.

## 7. On the emulator, and why it is not the fix

`cores: 2`, `-gpu swiftshader_indirect`, `Boot completed in 99925 ms`. Readiness settled in 13 s
against a 180 s deadline and the ANR appeared **after** it, during the run — so the readiness gate is
not the gap, and `CI-002`'s host-side ordering held (the log shows both APKs prebuilt before the
emulator step).

Raising `cores` would make the ANR rarer and leave a harness that cannot clear its one permitted
obstruction. The slow guest is what made a latent race reproducible; it is evidence, not the cause.

## 8. Risks the plan must answer

1. **Retrying inside `dismissSystemAnr` versus returning to the outer loop.** The outer loop already
   sleeps, waits for idle and re-dumps. A second retry loop inside the helper would be a second
   place for the deadline to be interpreted, and the two could disagree. Prefer making the helper
   *report* "not yet" and letting the existing loop own patience.
2. **The dump is re-read on each pass, so the verdict is re-derived.** If the dialog goes away
   between passes the verdict changes to `Blocked` or `OwnedByApp` on its own, which is correct and
   already handled — the plan must not add state that remembers "we were dismissing".
3. **A test that cannot fail.** The new pure function must have a negative control that fails when
   the three-way distinction collapses back to `size != 1`. Without it this ticket ships the same
   class of untested decision it exists to remove.
4. **`isClickable && isVisibleToUser` is part of the observation, not the decision.** Keep the filter
   in the guard; a policy that took nodes rather than ids would need Android types and would land
   back in `androidTest`.
5. **The unread dump.** If `window-01-home.txt` later shows a Wait button under an id outside
   `WAIT_VIEW_IDS`, that is an *additional* fix — a verified id, never a guessed one — and does not
   invalidate this one. Causes (a) and (b) are defects regardless of what that file says.

## 9. Open questions for `/plan`

- Does the pure verdict take `List<String>` (ids found) or a richer record that also carries the
  count of nodes seen before filtering? The second would diagnose "nodes present but not clickable"
  without another round trip.
- Should "not yet" be distinguishable in the *final* failure message from "never appeared"? The last
  reason today is whatever the loop stored last; a dismissal that timed out waiting for a button is a
  different story from a window nobody could identify.
- Does `enableViewIdReporting` gain a recorded outcome, or a hard failure when `serviceInfo` is null?
  The PRD requires it be reported rather than swallowed; whether an unavailable `serviceInfo` should
  fail the run immediately is a judgement the plan should make explicitly.


## 10. What the diagnostics artifact says, and what it costs the plan

The owner supplied `webora-screenshot-diagnostics-d830cac8…` after `/plan` was approved. It answers
the PRD's first and fourth open questions and **invalidates the mechanism the plan chose**.

### The timeline kills the race

| Time | Event | Source |
|---|---|---|
| 12:16:22 | readiness settles, 3 consecutive ready samples | `artifacts/readiness.txt` |
| 12:16:27.465 | `ANR in com.android.systemui` — the dialog appears | `logcat.txt:18297` |
| 12:17:30.485 | the test process starts | `logcat.txt:29624` |
| 12:17:47.864 | `Refusing to capture 01-home` | `logcat.txt:31130` |

**The dialog had been on screen for 63 seconds before the test began, and 80 seconds before the
lookup ran.** It was not assembling. Combined with two attempts failing byte-identically, the zero is
**deterministic**, not transient.

That is fatal to the plan's headline mechanism. Under a deterministic cause, making every zero
`NotYet` produces forty identical failures across the 20-second deadline and then fails the run
anyway — no frames, same outcome, later. Patience cannot fix a lookup that is looking in the wrong
place or at nothing.

### What the window dump does and does not show

`window-01-home.txt` confirms the classification was correct — `mCurrentFocus`, `mFocusedWindow` and
`mNavBarColorWindowCandidate` all name
`Window{3aaa129 u0 Application Not Responding: com.android.systemui}`, and the window is real:
`mHasSurface=true isReadyForDisplay()=true isVisible=true`, `ty=SYSTEM_ALERT`, `pfl=SYSTEM_ERROR`,
`package=android`, `mOwnerUid=1000`.

It carries `mAnimationIsEntrance=true`, which looks like the race — and is not, given the 63 seconds.
Treat it as a stale attribute, not evidence of an animation in progress.

**`dumpsys window` describes windows, not view hierarchies.** It cannot say whether the dialog has a
Wait button, which is exactly the blindness §6 identified. The artifact does not close that gap; it
proves the gap is the thing worth fixing first.

### Two lines that point at reachability rather than absence

```
12:17:39.747  V UiAutomation: Init UiAutomation@55c0959[id=1, flags=0]
12:17:47.306  W WindowManager: Cannot find window which accessibility connection is added to
```

The second lands **0.5 seconds before the refusal**. Read carefully: it is a WindowManager warning
that an accessibility connection references a window it cannot resolve. That is *suggestive* of
`rootInActiveWindow` being unable to reach a `SYSTEM_ALERT` window owned by uid 1000, and it is not
proof — neither line names the guard's call. Recorded as the strongest available lead, not a
conclusion.

The candidate causes now rank:

| Cause | Standing after the artifact |
|---|---|
| The lookup cannot reach the dialog's window at all | **leading** — deterministic, and the WM warning fits |
| The dialog genuinely has no Wait button | **live and unexcluded** — a system-process ANR dialog may not offer one, and if so the current refusal is *correct* behaviour |
| `FLAG_REPORT_VIEW_IDS` not in effect | still possible, still deterministic, still cheap to rule out by recording it |
| Node tree lagging the window | **refuted** by 63 seconds |

### Webora is not implicated, and my earlier speculation is refuted

Six ANRs in 32 seconds, none of them the app:

```
2  ANR in com.android.phone
1  ANR in com.android.systemui
1  ANR in com.google.android.apps.youtube.music
1  ANR in com.google.android.googlequicksearchbox:interactor
1  ANR in com.google.android.youtube
```

`app.webora.browser` appears in no ANR. The suggestion that the M6/M7 design refresh's heavier first
frame contributed is **refuted**, not merely unconfirmed. The device was broadly thrashing.

### A lead worth its own ticket, not this one

The System UI ANR's reason is `executing service com.android.systemui/.dump.SystemUIAuxiliaryDumpService`
— System UI's *dump* service. The harness polls `dumpsys window` every 500 ms and
`android-emulator-ready.sh` samples it too. `dumpsys window` targets `system_server` rather than
System UI, so this is not a direct accusation; but a harness whose evidence-gathering may provoke the
obstruction it then refuses to photograph is worth investigating separately. Do not fold it into
`CI-004`.

### What this means for the plan

1. **The diagnostic comes first, and is the deliverable that does not depend on being right.** Until
   the failure records the dialog's actual node ids, the window list, and whether view-id reporting
   is in effect, every fix is a guess — including the one this research originally proposed.
2. **Reachability, not patience, is the likely fix.** The plan should treat "search the right
   window" as the primary mechanism and retry as secondary robustness.
3. **The three-way verdict survives.** `Press` / `Ambiguous` / `NotYet` is still the right shape, and
   the fail-closed half is still required. What changes is that `NotYet` stops being the headline.
4. **A correct outcome remains possible.** If the dialog has no Wait button, today's refusal is right
   and `CI-004` becomes a diagnostics-and-clarity ticket rather than a behaviour fix. The plan must
   not be written so that only "make it press the button" counts as success.


## 11. Run 14 eliminates one branch, and confirms the direction

Run **14** (`31706775744`, same commit) captured all three frames, and its diagnostics settle a
question this research left open. Frames 01 and 02 each carry an `interference-*` record:

```
window=Application Not Responding: com.android.systemui
process=com.android.systemui
pressed=android:id/aerr_wait
label=Wait
click_accepted=true
```

**The Wait button exists, at `android:id/aerr_wait`, and the guard pressed it — twice, in one run.**

Consequences for the plan:

1. **"The dialog genuinely has no Wait button" is eliminated.** §10 listed it as live and unexcluded,
   and the plan was deliberately written so that a refusal could still be a correct outcome. That
   branch is now closed: when the lookup can see the dialog, the sanctioned affordance is there.
2. **Run 13's zero was reachability, confirmed rather than inferred.** The same code, on the same
   image, with the same ids, succeeded here and failed there. Whatever differed, it was not the
   dialog's contents.
3. **No new view id is needed.** `WAIT_VIEW_IDS` already contains the one that works. The plan's
   out-of-scope note about a possible additional id can be dropped rather than carried.
4. **`FLAG_REPORT_VIEW_IDS` was in effect in run 14**, since the lookup returned ids at all. That
   does not clear it for run 13 — the flag is set per `UiAutomation` instance and both runs built
   their own — but it does move it below reachability in the ranking.

The ticket gets smaller and better-aimed: observe the right window, record what was seen, keep the
three-way verdict. Nothing in §1, §3, §4 or §6 changes.
