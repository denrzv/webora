# CI-004: The one permitted dismissal must actually execute
Status: PRD_READY

## Context / Problem

`CI-002` established that the screenshot harness may clear exactly one obstruction — an
`Application Not Responding: com.android.systemui` dialog — and only by pressing **Wait**. That
allow-list of one is correct and is not in question here.

**The dismissal cannot execute.** Hosted run **13** on `main` (`31697590198`, `d830cac8`) failed
twice, on both attempts, with a byte-identical assertion:

```
Refusing to capture 01-home: Application Not Responding: com.android.systemui is dismissable
but 0 Wait affordances were found among android:id/button2, android:id/aerr_wait.
```

So the harness identified the one obstruction it is permitted to clear, and then could not press it.
It refused to capture — correctly — and the run produced **zero frames**. Two attempts on the same
commit make this reproducible, not a flake.

**The defect is in the mechanism, and it is visible without the dump.**
`ScreenEvidenceGuard.requireAppOwnsScreen` is a patient loop: a 20-second deadline, a 500 ms poll, a
`waitForIdle` between passes, and `MAX_DISMISSALS = 2`. It is built to tolerate a screen that has not
settled. `dismissSystemAnr` then defeats that patience — it inspects the accessibility tree **once**
and throws if it finds zero candidates:

```kotlin
val candidates = WAIT_VIEW_IDS.flatMap { viewId ->
    val root = uiAutomation.rootInActiveWindow ?: return@flatMap emptyList()
    ...
}
if (candidates.size != 1) { throw evidenceFailure(...) }
```

Three transient conditions are indistinguishable from "this dialog has no Wait button", and each
kills the run on first contact:

1. **The window is focused before its nodes are queryable.** `mCurrentFocus` names the ANR dialog as
   soon as the window is added; the accessibility tree for it can lag.
2. **`rootInActiveWindow` returns null**, which yields zero candidates via the `?: return@flatMap`
   and is reported as a missing button.
3. **`FLAG_REPORT_VIEW_IDS` was never set.** `enableViewIdReporting()` bails silently on
   `serviceInfo == null`, and its own KDoc names the consequence: without the flag,
   `findAccessibilityNodeInfosByViewId` returns nothing, which is *"indistinguishable from a dialog
   with no Wait button — a recoverable run failing as an unrecoverable one."*

The code already knew this failure mode and guarded one instance of it. The guard is incomplete.

**The environment is the aggravating factor, not the cause.** The AVD runs `cores: 2` with
`-gpu swiftshader_indirect` and reported `Boot completed in 99925 ms`. The readiness gate settled
cleanly in 13 s and the ANR appeared *afterwards*, during the run — so readiness is not the gap, and
`CI-002`'s host-side ordering still holds (both APKs were prebuilt; the log shows the precondition
passing). A slow guest makes the race easy to hit; it does not make a one-shot lookup correct.

## Goals

- The harness can press **Wait** on the one dialog it is permitted to dismiss, on this emulator.
- "Not queryable yet" and "not present" stop being the same outcome.
- A dismissal that genuinely cannot be performed still fails the run, with a diagnostic that names
  what was actually on screen.
- The screenshot journey produces its three frames again on `main`.

## Non-goals

- Widening **what** may be dismissed. The allow-list stays one process and one affordance.
- Any change to `ScreenEvidencePolicy.focusVerdict`, `RenderedContentPolicy`, the readiness gate, the
  artifact layout, or the contact sheet. This ticket is about executing a decision already made
  correctly.
- Tuning the AVD (`cores`, GPU mode) to make the ANR less likely. That may be worth doing, but it
  would hide this defect rather than fix it, and the defect would return on any slow runner.
- Investigating why System UI ANRs at all. Related, unproven, and separable — see Open questions.
- Any product change. No frame has been captured of the M6/M7 design refresh yet, so nothing about
  the app's appearance is in scope here.

## The mechanism this ticket must not choose

**Pressing whatever button is on the dialog.** The existing comment states the rule and the reason —
*"the button ids are not public API, so 'press whatever looks like Wait' is not a thing this may do —
a wrong press on an error dialog can close an app."* A retry loop that ends in a relaxed match is the
same violation with extra steps.

The asymmetry to preserve, stated so the plan cannot blur it:

| Candidates found | Meaning | Behaviour |
|---|---|---|
| 0 | possibly not queryable **yet** | retry within the existing deadline, then fail |
| exactly 1 | the sanctioned affordance | press it |
| 2 or more | genuine ambiguity | fail closed **immediately**, never guess |

Only the first row changes. Making ambiguity retryable would be a different and worse bug.

## User stories

- As someone reviewing demo evidence, a run that hits a recoverable System UI hiccup still produces
  the three frames instead of nothing.
- As a maintainer, a run that fails tells me which nodes were actually on screen, so the next fix is
  informed by data rather than by a second guess.
- As a reviewer of the harness, the set of dismissable obstructions is exactly what `CI-002` defined,
  and I can see that it did not grow.

## Acceptance criteria

1. Zero candidates is a **retryable** condition bounded by the existing settle deadline, not an
   immediate failure.
2. Two or more candidates still fails immediately and is never resolved by choosing one.
3. The allow-list is unchanged: one process (`com.android.systemui`), one action (Wait), and
   `MAX_DISMISSALS` still bounds how many times a dialog may be cleared.
4. `rootInActiveWindow` returning null is treated as "look again", not as "no button exists".
5. `FLAG_REPORT_VIEW_IDS` is established before any lookup can conclude a button is absent, and a
   failure to establish it is reported rather than silently swallowed.
6. A dismissal failure records what was on screen — the view ids actually present on the focused
   dialog — so the diagnostic distinguishes "wrong id" from "no nodes at all".
7. The decision remains a pure function in `src/screenshotPolicy/java`, testable by
   `./gradlew test` with no emulator, in keeping with `CI-002` and `CI-003`. The guard reads and
   retries; the policy decides.
8. Negative control: with the fix reverted, the new test fails.
9. A hosted run on `main` captures three frames and the owner confirms `preview.png`.
10. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Integrity:** nothing here may make a contaminated screen photographable. The change buys patience
  before refusing, never permission to capture.
- **Reliability:** the retry must be bounded by the deadline that already exists; no new unbounded
  wait, and no increase to `SETTLE_TIMEOUT_MILLIS` as a substitute for fixing the lookup.
- **Diagnosability:** every refusal keeps writing the full `dumpsys` output it writes today.
- **Testability:** the JVM gate must be able to fail on this defect. An emulator-only fix is not
  acceptable — it is the shape that let this reach `main` in the first place.

## Risks

- **Retrying a genuine absence wastes the deadline.** Acceptable: the run fails either way, and the
  20 s is already the budget for a screen that will not settle.
- **Masking a real System UI failure.** A dialog that never becomes clickable still fails the run.
  The change alters when we conclude that, not whether we do.
- **Scope creep into the ANR's cause.** The pull to "fix the emulator so it stops ANRing" is strong
  and out of scope; a harness that cannot clear its one permitted obstruction is a defect regardless
  of how often the obstruction appears.

## Open questions

For `/researcher`, before the plan commits to a mechanism:

1. `diagnostics/window-01-home.txt` from run 13's diagnostics artifact
   (`webora-screenshot-diagnostics-d830cac8…`) has not been read. Which of the three transient
   conditions was it — no nodes at all, a null root, or a Wait button under an id not in
   `WAIT_VIEW_IDS`? The fix direction is the same for the first two; the third would additionally
   require a verified id.
2. Is `FLAG_REPORT_VIEW_IDS` actually set on this device? `enableViewIdReporting()` returns silently
   when `serviceInfo` is null, and nothing records whether the flag took effect.
3. Can the dismissal decision be expressed as a pure function over a list of found view ids, so it
   joins `ScreenEvidencePolicy` in the shared source set rather than staying inside the
   emulator-only guard?
4. Does the logcat show `am_anr` for `com.android.systemui` alone, or is `app.webora.browser` also
   implicated? This does not change this ticket's fix, but it decides whether a separate ticket is
   warranted for the app's cold-start cost on a 2-core software-rendered device.
