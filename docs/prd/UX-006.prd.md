# UX-006: Informed first-use consent — show what the manifest will change
Status: PRD_READY

## Context / Problem

`ADR-011` requires the user to agree before a validated manifest restyles the chrome, and
`SKIN-004` implements it: `candidateDisposition()` returns `Ask` when an origin carries no stored
decision, `BrowserScreen` shows `SiteSkinConsentDialog`, and the chrome changes only on **Allow**.
Deny — either spelling of it — leaves the page rendering in regular mode. That part is done and
this ticket does not reopen it.

What the sheet actually shows is the problem:

> **Allow bloomflowers.example to customise Webora?**
> The site can customise navigation and appearance. The address and security indicator stay under
> Webora control.

Both strings are compiled (`strings.xml:37-38`). The only variable is the origin. So the user is
asked to approve a *specific* manifest and is shown nothing from it — the decision is made against
a generic description of the feature, not against the thing being granted. Every input needed to do
better is already in hand at that moment: `SiteSkinCandidate.configuration` is a
`SiteSkinConfiguration`, which is core-trusted, normalized and bounded by construction, and the
dialog already holds it — it currently reads one field off it and discards the rest.

That is a real gap in `ADR-011`'s own terms. The ADR justifies the interruption by saying the trust
boundary must be *legible*; a sheet that describes the feature rather than the grant makes the
boundary visible without making it informative. `ADR-011` even anticipates the fix — "the manifest
supplies only the origin string and, optionally, the site name" — and the optional half was never
built.

The tension this ticket exists to resolve is that the obvious fix and `HARDEN-002` point in
opposite directions. Showing what the site asks for means rendering **site-supplied branding inside
the dialog that decides whether to trust that site** — the exact surface where a manifest reading
"Your Bank" with a bank-blue swatch does the most damage, because the user has not yet had a chance
to refuse it. `HARDEN-002` settles the question for active chrome (branding is presentation *beside*
browser identity, never identity itself); this ticket has to settle it for the consent sheet, where
the stakes are higher and no precedent exists.

## Goals

1. Show, in the consent sheet, what the manifest will actually change if allowed — drawn from the
   trusted configuration the browser is being asked to apply, not from compiled prose.
2. Keep the sheet's own identity claim browser-owned: the complete canonical origin stays the
   dominant, non-editable, browser-typography element, and no manifest value can displace, restyle
   or outrank it.
3. Make the preview's untrusted half unmistakably attributed to the site, so a user reading the
   sheet can tell which text Webora is asserting and which text the site is asking for.
4. Bound every manifest-supplied value the sheet displays — length, count, and colour contrast —
   at the app layer, on the same terms `SiteSkinChromeModel` already applies to active chrome.
5. Leave the decision semantics of `ADR-011` untouched: Allow persists and activates, Not now is
   ephemeral, Never persists refusal, and every Allow still rechecks origin and generation.

## Non-goals

- Changing when consent is asked. First-use per origin stays; this is not per-navigation
  confirmation, which would supersede `ADR-011` and `PRIV-001`'s decision store.
- Changing the three choices, their persistence, or the global SiteSkin switch.
- Rendering the integrated chrome itself, or replacing `SiteSkinChrome.kt`'s placeholder glyphs.
  That is `UX-005`, descoped.
- A settings-side preview of a stored decision. `PrivacySettingsScreen` lists origins; making those
  rows expand into previews is a separate ticket.
- Introducing `WeboraTheme` tokens. `UX-002` owns the browser palette; this sheet uses what exists
  and is expected to be restyled by `UX-004` afterwards.
- Any change to `:siteskin-core`. The configuration is already trusted, normalized and bounded; the
  work is entirely in how the app layer projects it.

## User stories

- As a user seeing an unfamiliar site ask to customise the browser, I can see what it wants — its
  name, its colours, how many navigation entries and quick actions it will add — before I decide.
- As a user, I can tell at a glance which line of the sheet is Webora speaking and which is the
  site, so a site calling itself something familiar cannot borrow the browser's voice.
- As a user with a screen reader, I hear the origin and the browser's framing before any site text,
  and the site's text is announced as the site's.
- As a security reviewer, I can point at one function that decides everything the sheet shows about
  a manifest, and one test that proves an adversarial manifest cannot exceed those bounds.
- As the implementer of `UX-004`, I can restyle this sheet without needing to know which of its
  parts are security-load-bearing, because a test tells me when I have broken one.

## Acceptance criteria

1. A pure, app-layer model — no Compose, no `Context` — projects a `SiteSkinConfiguration` into the
   closed set of values the consent sheet may display. It is the only path from a configuration
   into that sheet, and `SiteSkinConsentDialog` takes it plus the origin rather than a
   configuration.
2. The sheet displays, from that model: the site name, the subtitle if present, the brand colour as
   a swatch, and the counts of bottom-navigation entries, quick actions and menu entries the site
   would add. Absent optional values render as absent, never as a blank row or a placeholder.
3. Manifest-supplied text in the sheet is bounded at the app layer by the corresponding
   `SiteSkinLimits` constant read from `:siteskin-core`, and flattened to a single line with format
   and bidirectional control characters removed — the treatment `inspectorValue` already applies to
   untrusted strings. A test drives an adversarial name (over-length, newline-bearing,
   `RIGHT-TO-LEFT OVERRIDE`) through the model and asserts the bound, with a negative control.
4. Counts are computed after the same 5/5/20 caps `SiteSkinChromeModel` applies, so the sheet
   promises what the chrome would actually render rather than what the manifest asked for.
5. The complete canonical origin — scheme, host, and a non-default port — remains present and
   browser-authored, per `HARDEN-002`. A test asserts the origin string the sheet displays is
   exactly `SiteOrigin.canonical`, with a negative control proving the test detects its removal.
6. No manifest-supplied string is rendered as the sheet's title or concatenated with browser-authored
   text; site text and browser text are separate `Text` nodes, and the site's are attributed to the
   site in the visible copy and in their accessible names.
7. The brand swatch is a bounded decorative shape with cleared accessibility semantics — it can
   never be the sheet's only carrier of meaning, and colour is not the sole channel for any
   information the sheet conveys.
8. `ADR-011` gains an amendment section recording what the sheet shows, why the manifest half is
   attributed rather than blended, and what would constitute violating that.
9. Decision behaviour is unchanged: existing `SiteSkinConsentDialogTest` and the `SKIN-004` /
   `HARDEN-002` consent tests pass without modification to their assertions.
10. `docs/ROADMAP.md`, `docs/BACKLOG.md` and `docs/DEVELOPMENT_PLAN.md` carry `UX-006` as an M6
    ticket, distinct from the descoped `UX-005`.
11. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Security/privacy:** the consent sheet is a security surface and gains untrusted content in this
  ticket, so every bound that exists for active chrome must exist here. No new network work may
  happen before consent — in particular the brand logo is **not** fetched to preview it; the sheet
  uses the trusted colour and a browser-generated monogram, so refusing costs the site nothing it
  did not already get from discovery. No manifest field may influence the sheet's layout, ordering,
  emphasis or button set.
- **Reliability/fallback:** a configuration missing every optional field still produces a complete,
  legible sheet. The model cannot throw on any trusted configuration; failure to project a value
  means omitting it, never failing the consent flow — refusing to ask is not a safe default, because
  it would silently activate or silently drop.
- **Performance:** projection is pure and synchronous over already-parsed data, run in composition
  at dialog time only. No I/O, no decode, no main-thread blocking.
- **Accessibility:** the sheet keeps `WeboraButton`'s 48 dp targets and remains usable at 200% font
  scale with all three choices reachable — the `FlowRow` comment at `BrowserScreen.kt:361` records
  why, and adding content above the buttons must not regress it. Every string comes from
  `strings.xml`; the swatch carries no accessible name and the colour information it conveys is also
  present as text.

## Risks

- **The preview becomes the identity.** A large site name over a small origin is a better
  impersonation vector than today's sheet. Mitigation is criterion 2 plus 6: the origin is the
  title, site text is attributed and subordinate. This is the risk that decides the ticket, and the
  reason for the `ADR-011` amendment.
- **Untrusted text escaping its bound in the accessible channel.** Exactly the `A11Y-001` finding —
  clipping pixels is not bounding a string. Criterion 3 applies the bound in the model, before
  either channel.
- **Scope drift into `UX-004`.** The sheet will be restyled by the design refresh; investing in its
  appearance now is wasted. Structure and bounds are the deliverable, not visual polish.
- **Weakening a passing test to fit new content.** The consent tests encode `HARDEN-002`; new
  content that makes one awkward is a signal about the content, not the test.

## Open questions

None blocking. Two decisions are delegated to `/researcher` and recorded in the plan:

- Whether the brand-colour swatch shows the raw trusted colour or the `SiteSkinTheme`-projected
  pair. The projection applies the WCAG guard, so a swatch drawn from the raw value could display a
  colour the chrome would never use — but the projection is a six-role scheme built for chrome, not
  a swatch. Research decides which is the honest preview.
- Whether counts are stated per surface ("3 tabs, 1 quick action") or as one total. The per-surface
  form is more informative and more strings; the total is one string and less useful.
