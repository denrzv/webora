# UX-003: Browser-owned chrome rebuild
Status: PRD_READY

## Context / Problem
`UX-002` supplied the compiled browser palette, typography, geometry and bundled icons, but the
regular browser chrome still presents five filled, text-labelled controls in a wrapping row and an
address field whose surrounding structure predates the selected design direction. The result is
functional but visually heavy, consumes page area unpredictably at large font scales, and does not
express Direction A's deliberate separation between an editable address and browser-authored site
identity.

This ticket rebuilds only browser-owned browsing surfaces: the address pill, separate security
identity chip, regular-mode navigation dock and overflow menu, persistent progress/error status, and
browser error page. It consumes `WeboraTheme`; no website value may influence these surfaces.

The security requirement is structural, not cosmetic. The visible identity chip and its
`BROWSER_SECURITY_TAG` semantics derive from `securityPresentation(state.mode)`, whose origin is the
committed `SiteOrigin`. They remain present while the address field is focused or edited, even when
the address text visibly disagrees with the committed origin.

## Goals
1. Implement Direction A's 52 dp address pill, separate tonal identity chip and floating navigation
   dock using the browser-owned tokens and bundled vector assets from `UX-002`.
2. Replace the five-button regular-mode control row with clear back, forward, reload/stop, home and
   menu affordances without losing any command or enabled-state behaviour.
3. Keep the browser-owned menu, progress and error status reachable and understandable, including
   the persistent live-region contract.
4. Restyle `BrowserErrorPage` as part of the same browser-owned visual system while preserving retry
   behaviour and useful diagnostics.
5. Preserve the security and accessibility boundaries with focused unit and instrumentation tests,
   including negative controls for the identity node.

## Non-goals
- SiteSkin integrated top bar, bottom navigation, quick actions or menu styling; `UX-005` owns those
  manifest-themed surfaces and `UX-008` owns integrated-mode navigation controls.
- Home, onboarding or privacy/settings screen redesign; `UX-004` owns them.
- New manifest fields, protocol behaviour, origin rules, network behaviour or persisted state.
- Replacing `WebView`, changing navigation history semantics, or adding browser capabilities.
- Adding an icon library or allowing remote icons into browser-owned chrome.

## User stories
- As a user browsing a regular site, I can navigate, reload or stop, go home and open the browser
  menu from a compact, recognisable control set.
- As a user deciding whether to trust a page, I always see the committed registrable domain and TLS
  state separately from the editable address, including while editing it.
- As a screen-reader or large-text user, I receive named controls, persistent loading/failure
  announcements and usable 48 dp targets without load-bearing labels being truncated.
- As a user whose page fails, I see a coherent browser-owned error surface and can retry.
- As a reviewer, I can prove that removing or rebasing the browser security identity makes a test
  fail rather than relying on visual inspection.

## Acceptance criteria
1. Regular mode renders Direction A's browser-owned address pill, a distinct identity chip and a
   floating navigation dock; the prior five filled text-button `FlowRow` is gone.
2. Back, forward, reload/stop, home and overflow-menu commands preserve their existing behaviour and
   disabled states, and the existing browser menu commands remain reachable.
3. `BrowserSecurityIdentity` derives its visible and semantic presentation from the committed
   origin through `securityPresentation(state.mode)`, publishes `BROWSER_SECURITY_TAG`, and remains
   composed while the address field enters, remains in and leaves edit focus.
4. A negative-control test demonstrably fails if the tagged security identity is removed or sourced
   from editable address text.
5. The persistent status live region remains present: progress is polite, failure is assertive, and
   browser errors expose a retry action.
6. Every interactive chrome control has a minimum 48 dp touch target and remains usable at 200% font
   scale without truncating a load-bearing string.
7. Unselected enabled navigation controls use an explicit browser-owned colour role, not reduced
   alpha that makes them appear disabled or fall below the 3:1 non-text contrast target.
8. Browser-owned chrome uses only `WeboraTheme` tokens, bundled local vectors and string resources;
   no manifest value, Material default, remote icon or new icon dependency reaches it.
9. `BrowserErrorPage` uses the browser token layer and bundled warning icon while preserving error
   detail, retry semantics and accessibility.
10. Relevant JVM/unit tests, Android compilation and instrumentation-test compilation pass; runtime
    instrumentation is captured when a connected device is available.
11. `bash scripts/pre-commit-check.sh` passes.

## NFR
- Security/privacy: committed-origin identity is always visible and browser-authored; no website or
  editable field can suppress, restyle or replace it; no new telemetry or URL logging.
- Reliability/fallback: visual restructuring must not change WebView navigation, menu dispatch,
  loading, error or retry behaviour.
- Performance: no new dependency or remote asset load; recomposition must not trigger navigation or
  network work.
- Accessibility: named controls, 48 dp targets, non-colour TLS meaning, persistent live-region
  semantics, deterministic traversal, and 200% font-scale resilience.

## Risks
- Compact icon controls can become ambiguous or inaccessible; mitigate with mandatory resource-backed
  names, state descriptions where needed and command-level tests.
- Moving the identity into the editable pill would save height but violate `ADR-006`; enforce the
  distinct tagged node and edit-state negative control.
- Direction A's sketch uses 38% opacity for unselected dock slots, which reads as disabled and can
  miss non-text contrast; use a measured opaque role instead.
- Overflow refactoring can silently lose debug-only inspector availability or regular browser menu
  commands; keep the existing closed command model and test both availability branches.
- Font scaling can turn a compact dock into clipped semantics or inaccessible labels; compile and
  exercise the existing large-font instrumentation suite and add focused coverage where absent.

## Open questions
None. Direction A and its identity mechanism were decided by `ADR-013`; command scope and acceptance
are fixed by the roadmap and backlog.
