# UX-024: Replace the integrated standalone navigation controls with a compact navigation bouquet
Status: PRD_READY

## Context / Problem

Integrated SiteSkin chrome spends two rows and five dock slots on browser navigation, and the
commands are scattered across three surfaces that do not read as related.

**What the header costs today.** `SiteSkinTopBar` composes a brand row and then `BROWSE-011`'s
`BrowserControlRow`, which holds exactly one 48 dp control:

| Band | Height |
|---|---|
| `EXPRESSIVE_GUTTER` (top) | 20 dp |
| `BrandRow` — Back, logo, title/subtitle, trust chip | 48 dp |
| `BrowserControlRow` — Refresh, trailing-aligned | 48 dp |
| `EXPRESSIVE_CURVE_DEPTH` (reserved below content) | 20 dp |
| **Total** | **136 dp** |

`EXPRESSIVE_HEADER_MIN_HEIGHT` is 96 dp, so the control row is not absorbed by the minimum — it is
40 dp of real page, taken from the WebView, for one command. On the hosted emulator's 360 dp × 3
density that is 120 px off a ~1757 px content region.

**`BROWSE-011` was right and its placement is what this ticket revisits.** That ticket measured the
brand row and found it could not take a sixth child: 280 dp of content width, of which Back, the
logo and three gaps take 116, leaving 164 dp for the weighted title and the unweighted trust chip.
A 48 dp control plus its gap takes that to 108 while the chip alone wants ~121 for
`denrzv.github.io`, so the chip truncates and the site's title measures to zero. Its conclusion —
*a browser command needed a row of its own* — was correct given that the row already held a
single-purpose Back button. This ticket removes that premise instead of arguing with the
arithmetic.

**Three surfaces, one command family.** Back is a leading tile in the brand row (`UX-008`,
`UX-014`). Refresh is alone on its own row (`BROWSE-011`). Forward exists only as a dock slot
(`UX-015`), at the other end of the screen. Back is therefore in *two* places — header tile and
dock slot — while Refresh is in neither of the places the other two are. They are one family
presented as three unrelated controls.

**Source of record.** GitHub issue [#122](https://github.com/denrzv/webora/issues/122). Its
acceptance criteria are normative and are carried into the numbered list below; where this PRD
tightens one it says so.

## Goals

- Integrated chrome offers Back, Forward and Refresh as one compact, browser-owned **Navigation
  Hub** whose collapsed footprint is the 48 dp slot Back occupies today.
- `BrowserControlRow` and its 40 dp of header height are returned to the page.
- Every browser navigation command has exactly one visible integrated home, so no two controls
  compete for the same semantics.
- The hub is browser chrome in the same structural sense the dock is: no manifest field, count,
  label, colour, icon, action or hint can add to it, remove from it, reorder it, rename it, restyle
  its semantics, or dispatch through it.
- The commands themselves are untouched. Back is `navigateBrowserBack`, Forward is the active tab's
  `goForward`, Refresh is `refreshAction`. This ticket moves affordances, not behaviour.

## Non-goals

- Changing regular/Home chrome. `UX-016`'s six-slot dock keeps its Reload exactly where it is.
- Changing `BROWSE-002`'s Back contract, `BROWSE-011`'s `refreshAction` decision, or any
  history/tab semantics. `RefreshAction.Retry` remains the failed-page path and `reload()` still
  must not rewrite `hostedUrl`.
- Merging the browser navigation bouquet with `UX-015`'s site-action bouquet or `UX-022`'s drawer.
  Two bouquets, two models, two dispatch paths; the visual language is shared and the action model
  is not.
- Letting `presentation.hub` — or any other manifest value — select, populate or style the browser
  bouquet. `UX-022`'s hint chooses among the browser's own *site* surfaces and has no reader here.
- Removing the registrable domain, the trust chip, or `ADR-006`'s guarantee. The brand row's
  identity half is not edited.
- Adding pull-to-refresh, auto-reload, or any new history capability.
- Re-taking `CI-009`/`CI-010` hosted acceptance as part of this ticket's local gates. The frames
  change and must be re-taken; that is recorded, not performed here.

## User stories

- As a user reading a branded site, I get more page and less chrome, because the browser stopped
  spending a whole row on one button.
- As a user who wants to go back, forward or reload, I reach all three from one control in a fixed
  place, instead of hunting one in the header, one at the bottom and one nowhere.
- As a user at the start of history, the hub still opens and tells me Back is unavailable, rather
  than the browser hiding the command or the hub refusing to open.
- As a user with TalkBack, I discover all three actions by traversal, with their own labels and
  their own enabled state, without needing to know where the bubbles are drawn.
- As a site owner, nothing I publish changes which browser commands exist or what they do.

## Acceptance criteria

1. Integrated top chrome composes a browser-owned Navigation Hub in the leading slot of the brand
   row, in place of the standalone Back tile, at the same 48 dp target and the same
   `BrowserControlTile` browser-owned ground.
2. The collapsed hub carries a browser-authored accessible name meaning *browser navigation* — not
   `R.string.back` — so it does not read as a direct Back button.
3. Activating the hub opens exactly three actions, in the fixed compiled order Back, Forward,
   Refresh. The count and the order come from a compiled list with no model, count, index or
   configuration input.
4. Each action is a ≥48 dp target with a bundled drawable and its own localized label:
   `R.string.back`, `R.string.forward`, `R.string.reload` — the same names the same commands carry
   in regular chrome, per `DEVX-003`'s one-command-one-name rule.
5. Selecting an action closes the bouquet and then dispatches, in that order, through the existing
   callback the corresponding regular-chrome control already uses.
6. A tap outside the bouquet closes it and performs no navigation.
7. Android system/predictive Back while the bouquet is open closes the bouquet and does not reach
   `BrowserBackHandler`; the next Back follows the unchanged browser policy.
8. Back's and Forward's enabled state come only from the selected tab's browser-observed history
   (`state.mode.canNavigateBack()`, `state.canGoForward`) and Refresh's from `refreshAction(state)`.
   Disabled state is exposed semantically, not by colour alone.
9. `BrowserControlRow` and `SITESKIN_REFRESH_TAG`'s standalone row are removed; no second visible
   Refresh control is introduced anywhere in integrated chrome to preserve the old layout.
10. At default font scale the integrated header composes one fewer row than before this ticket, and
    a test pins the reduction rather than asserting the new row count alone.
11. The integrated dock no longer exposes Back or Forward, and keeps Brand Hub, Tabs and More as
    equal browser-owned slots. `UX-017`'s single branded pill, its 52 dp asset-bearing centre
    command, and its teardown behaviour are otherwise unchanged.
12. Browser navigation actions and site actions remain separate models end to end: the hub's items
    are a compiled browser enum, never `SiteSkinItemModel` or `NavigationItem`, and they never reach
    `ActionResolver`.
13. Exactly one of the browser navigation bouquet and the SiteSkin hub (bouquet or drawer) can be
    open at a time; opening either closes the other.
14. The navigation bouquet's visibility is reset by the same three events that reset the SiteSkin
    hub — tab switch, active-configuration change, and a page start on the owning tab — and is
    structurally unreachable once `PROTECTED_INTEGRATED` authorization is lost.
15. A source scan proves no manifest-derived value reaches the hub or any of its three actions,
    with a negative control that fails when one is introduced.
16. A negative control proves criterion 3's fixed list is a real guard: replacing it with a
    model-driven list fails a test.
17. `headerIdentityPlacement`'s inputs, arithmetic and `HEADER_FIXED_WIDTH` remain correct for the
    new leading slot, and `UX-023`'s wrap still triggers on width and scale alone.
18. `SITESKIN_SECURITY_TAG`, `SITESKIN_BRAND_TAG`, `SITESKIN_LOGO_TAG` and `SITESKIN_DOCK_TAG` keep
    their exact values; `CI-009` and `CI-010` assert on them, including `assertDoesNotExist` proofs
    of `UX-012`'s teardown.
19. The hosted journey and smoke tests reach integrated Back through the hub rather than through a
    tag that no longer exists, and still assert the browser-owned prerequisite before invoking it,
    per `CI-008`.
20. Nothing in the renderer, event-routing, discovery, consent, cache, capture or protocol layers is
    edited.
21. `./gradlew :app:compileDebugAndroidTestKotlin` compiles.
22. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Security/privacy:** the hub sits inside a header a manifest paints, so its ground, its icons,
  its labels, its order, its enabled state and its callbacks must all be compiled browser values —
  `UX-014`'s *"the visual boundary is the ownership boundary"*. The sharpest risk is not a wrong
  colour but a **site action reaching the browser bouquet**: the two clusters will look alike by
  design, and a shared item model would let a manifest publish something that renders exactly like
  Back. The models must be different types, not one type with a flag.
- **Reliability/fallback:** the bouquet is visibility state only. Losing integrated authorization,
  switching tabs or starting a page must remove it before another projection can dispatch through
  it; a stale overlay over a new origin is the failure mode `UX-022` records for a drawer with its
  own un-reset flag.
- **Performance:** no new measurement pass, no new platform read. The bouquet is a `Popup` composed
  only while open, and the header keeps `UX-023`'s single `BoxWithConstraints`.
- **Accessibility:** three actions behind one control is a discoverability trade the issue accepts,
  and the mitigations are contractual: the collapsed hub is never disabled (it always opens and
  reports state), each bubble carries its own label and `disabled` semantics, targets stay at
  `MINIMUM_TOUCH_TARGET`, and the cluster stays operable at 320 dp and 200% font scale without
  overlapping the trust chip or the title.

## Risks

- **Back becomes a two-tap command in integrated mode.** Today it is one tap in the header *and*
  one in the dock; after this ticket the visible affordance is behind the hub. The issue directs
  this explicitly and the system/predictive Back gesture is unchanged and still one gesture, but it
  is a real ergonomic cost and it is worth stating rather than discovering. `/researcher` should
  check whether the collapsed hub can usefully surface Back's *availability* without becoming a
  direct Back button (criterion 2 forbids the latter).
- **`UX-008` and `UX-014` are amended, not ignored.** Both require a leading Back affordance before
  site branding in integrated top chrome. Their purpose — SiteSkin may not replace the browser's
  history contract — is preserved by a hub whose only contents are browser commands, but the wording
  changes and the change must be recorded in `CLAUDE.md` rather than left to be rediscovered.
- **`UX-015`'s five-command dock is reduced to three.** That ticket's text says the five are fixed
  compiled browser policy; criterion 11 reverses part of it deliberately, on the issue's explicit
  direction. `SiteSkinNavigationContractTest.fixedDock` encodes the five-name order and will need to
  encode the new one — a test edit that must be a *deliberate* re-statement, not a relaxation.
- **Two bouquets that look alike.** `SiteActionBouquet` already exists with petals, lifts and a
  `Popup`. Reusing its composables would be the obvious economy and is the direct route to a shared
  action model; reusing only the *visual vocabulary* while keeping the models apart is the
  requirement, and the line needs to be drawn where a test can see it.
- **Hosted evidence changes and cannot be verified here.** `LiveSiteScreenshotTest` and
  `LiveSiteNavigationSmokeTest` both click `SITESKIN_BACK_TAG` directly, and `CI-009`'s frames
  photograph a header one row shorter. This checkout has no emulator, so the JVM gate must carry as
  much of the proof as possible and the residue must be declared as pending hosted acceptance.
- **The 40 dp saving could be spent on the bouquet.** A cluster that needs vertical room inside the
  header would give the height straight back. The bouquet is a `Popup` in its own window precisely
  so it does not participate in the header's layout, and criterion 10 pins the reduction.

## Open questions

- **Does the dock keep Back and Forward?** The issue states a preference, not a requirement, and
  criterion 11 commits to removal. `/researcher` must measure the alternative honestly: three equal
  slots in `UX-017`'s pill versus five, and what a 3-slot dock does to the 52 dp centre command's
  geometry at 320 dp.
- **What does the collapsed hub draw?** There is no compiled icon for *browser navigation* today;
  `UX-002`'s budget was 18 and `UX-021` raised it to 20. Research decides between an existing glyph
  and a new bundled vector, and the budget moves deliberately if a new one is added.
- **Where does the bouquet expand?** The header anchor is at the top of the screen, so `UX-015`'s
  upward `ACTION_BOUQUET_OFFSET` inverts. Research measures downward expansion against the trust
  chip, the title, the status-bar inset and `BROWSER_CONTENT_TAG`'s measurement rectangle —
  `CI-003` records that anything drawn into that rectangle must be excluded or kept out, and a
  `Popup` in its own window is the mechanism that keeps it out.
- **Which state variable owns the bouquet?** `siteActionsExpanded` is one flag serving two site
  surfaces with three resets. A second flag needs all three resets and the mutual exclusion of
  criterion 13; a single tri-state would make exclusion structural. Research decides and the plan
  commits.
- **Does reduced motion need a real branch here?** `ExpressiveSiteSkinPresentation` carries a closed
  motion policy that `UX-013` records as having no reader yet. A radial expansion would be the first
  real decorative transition in the browser, which makes this the ticket that must map `REDUCED` to
  an immediate state change — or deliberately ship no animation and leave the policy unread.
