# NET-004: The reference integration's logo never reaches the top bar
Status: PRD_READY

## Context / Problem

`spec/fixtures/valid/bloom-flowers.json` declares `branding.logoUrl: "/assets/siteskin/logo.png"`,
core resolves it to `https://denrzv.github.io/assets/siteskin/logo.png`, and the origin serves it:
`HTTP 200`, `content-type: image/png`, 5,702 bytes, a valid PNG signature, `512 × 512`, 8-bit
truecolour, non-interlaced. Every `NET-003` bound is satisfied with room to spare.

The hosted integrated frame nevertheless shows the browser-generated `B` monogram — in run **15**
(`31714792338`, `f1e81640`), and, per `reports/qa/CI-003.md`, in run **11** as well. Two runs eight
commits apart agreeing rules out a one-off.

`NET-003` makes the monogram the *correct* output of every non-cancellation failure. That is right
for the user and useless for the site owner: one glyph stands for "no logo declared", "refused by the
MIME allow-list", "refused by the bounds", "the server never answered", and "it has not arrived yet".
The reference integration is the artifact site owners copy, so whatever is happening here will happen
to them, and they will have exactly as little to go on.

**The tool built for this question cannot answer it.** `DEVX-001`'s inspector reports
`Brand asset: MONOGRAM` and stops — `InspectorBrandAsset` is `NONE | DECODED_BITMAP | MONOGRAM`, an
outcome with no reason. `ManifestTraceRecord` covers manifest transport and validation and says
nothing about the asset. Reading the panel first, as the backlog entry directs, is what establishes
that: the trace is silent about the one pipeline under investigation.

Nothing in the repository can currently close the question either. Local inspection eliminates two of
the backlog's four candidates by reading (the served manifest is byte-identical to the pinned
fixture, so the logo *is* declared; `BrowserState.forObservedOrigin` returns the same `Integrated`
instance for a same-origin page start, so the effect key is stable and composition does recompose
when the asset lands). The remaining candidates are on-device or in the network — `BitmapFactory`,
the emulator's transport, or the harness capturing before the asset arrives — and no JVM test can
reach any of them.

## Goals

1. Give the brand-asset pipeline a closed, typed outcome that names *which* stage produced the
   monogram, recorded in the trace and displayed by the inspector in one line.
2. Obtain device evidence that identifies which candidate holds, rather than choosing one by
   argument.
3. Fix what that evidence convicts, so a hosted integrated frame shows the declared logo.

## Non-goals

- Widening `NET-003`'s caps, MIME/signature allow-list, redirect budget or same-origin recheck. If
  the asset is legitimately refused, the refusal stays and the *reason* becomes visible.
- Removing the monogram fallback, or making a failed asset visible to the user. The monogram remains
  the user-facing behaviour; the reason is developer-facing and debug-only.
- Persisting or caching decoded assets, and any general-purpose image loader.
- Changing what `CI-002`/`CI-003`/`CI-005` allow to be photographed. Nothing here may make the
  harness accept a frame it rejects today.

## User stories

- As a site owner following the integration guide, when my logo does not appear I can open the
  inspector and read the reason in one line, instead of guessing between five failures that render
  identically.
- As a Webora maintainer, when a hosted frame shows a monogram I can tell from the diagnostics
  artifact whether the pipeline refused the asset, never received it, or simply had not finished.
- As a user, an unreachable or refused logo still leaves me browsing with a monogram and the
  registrable domain and TLS state intact.

## Acceptance criteria

1. `BrandAssetLoader` returns a closed outcome carrying both the asset and a browser-owned reason;
   every path that yields a monogram names its stage, and no reason is derived from remote text.
2. The transport distinguishes "no answer" from "the server answered and the browser refused it",
   with the refusal reason typed, mirroring `FetchRejection` for manifests.
3. The inspector displays the brand-asset outcome and its reason on one line, bounded and
   browser-authored, in debug variants only; release variants are unchanged and the compiled-output
   absence check still passes.
4. Device evidence recorded into the screenshot job's diagnostics artifact states the outcome, the
   reason, and the elapsed time for the reference integration's logo on a real emulator.
5. That evidence identifies which of the backlog's candidates holds, and the finding is recorded —
   including if it exonerates the pipeline.
6. A hosted integrated frame (`03-siteskin-integrated.png`) shows the manifest's logo in the 40 dp
   slot, from a run whose commit SHA matches the branch head being judged.
7. `NET-003`'s caps, allow-list, same-origin recheck and monogram fallback are unchanged, proven by
   the existing tests continuing to pass unmodified.
8. The registrable domain and TLS state remain present and non-suppressible in the same frame.
9. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Security/privacy:** the reason vocabulary is a closed browser-owned enum; no response header,
  server message, URL or manifest string becomes display text without passing `inspectorValue`'s
  bound. The trace stays in-memory, debug-only, cleared by `BrowsingDataCleaner`, never logged or
  transmitted. The logo slot stays decorative in the semantics tree — the outcome must not become an
  accessibility-visible property of it.
- **Reliability/fallback:** every failure still ends in a monogram and a rendering page. Recording an
  outcome may not change any outcome; the trace observes and never decides, as `DEVX-001` requires.
- **Performance:** no additional network request per navigation, no main-thread decode, and
  cancellation behaviour unchanged.
- **Accessibility:** the inspector's new line follows the existing label/value split — browser-authored
  label as its own `Text` node, never concatenated with a value.

## Risks

- **A fix that only moves the race.** If the evidence says the asset arrives after the frame is
  taken, the harness must wait for a state that occurs on its own — never suppress, pre-seed or stage
  anything for the camera. `DEVX-003` refused a screenshot mode on exactly those grounds.
- **A trace that changes behaviour.** Threading an outcome through the loader touches the path that
  publishes the asset. `SiteSkinTraceNeutralityTest`'s shape is the precedent for proving it did not.
- **Evidence read from the wrong run.** `DEVX-002` records that stale frames were once read as
  current. Every claim cites a run number and commit SHA.
- **Diagnosing by argument.** Four candidates are plausible and cheap to argue for. The ticket is
  only allowed to fix what the evidence convicts.

## Open questions

- Which candidate holds — carried into `/researcher` and `/plan` as the thing the evidence decides,
  not resolved here.
- Whether the device probe belongs in the existing journey class or beside it: the screenshot job
  filters instrumentation to one class, so a second class costs a workflow change.
- If the pipeline is exonerated, whether a missing logo should fail the screenshot job or only be
  recorded. Failing couples the job to a third-party host; recording risks the finding being ignored.
