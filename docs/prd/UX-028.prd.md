# UX-028: Copy the inspector's diagnostics as JSON
Status: PRD_READY

Issue: [#130](https://github.com/denrzv/webora/issues/130)

## Context / Problem

`DEVX-001` built the inspector because the browser computed everything a site owner needs and then
discarded it — a rejection's diagnostics, the HTTP status of a refused response, which of `NET-002`'s
cache paths served the navigation. `NET-004` widened it again when one monogram turned out to stand
for five different failures. The panel now answers those questions, and it answers them **only to a
pair of eyes**: the data is a scrolling grid of browser-authored labels beside bounded values, on a
phone, in a dialog.

Getting it anywhere else means transcribing it or photographing it. That is exactly the position the
inspector was built to end, one layer out: the browser knows, and the person who has to act on it
cannot get at what the browser knows.

The issue calls the surface **Site Scan Inspector**; in this tree it is the **SiteSkin inspector**,
`SiteSkinInspectorPanel` behind `browserMenuCommands()`'s `INSPECTOR` entry. Same surface, and this
PRD uses the repository's name.

**The issue's mock-up shows JSON in the modal, and the modal does not render JSON.** It renders
`InspectorRow(label, value)` pairs. The issue anticipates this — *"The ticket does not require
changing the Inspector schema to match this example; copy the actual current diagnostic model"* — and
lists redesigning the inspector UI as a non-goal. So the single-source-of-truth requirement is not
"share a JSON renderer with the display"; it is that the clipboard document and the visible rows are
**projections of one already-assembled `InspectorSnapshot`**, and that the JSON carries no value the
panel does not show.

That last clause is the security half. The panel bounds every website-controlled value through
`inspectorValue` — `untrustedText` at `SiteSkinLimits.MAX_SUBTITLE_LENGTH`. A serializer reading the
snapshot's raw fields would put *more* on the clipboard than the surface it claims to mirror, which
is the widening the issue's privacy section forbids, arriving through the back door of a format
change rather than through a new field.

## Goals

- One tap in the inspector puts the current diagnostic snapshot on the Android clipboard as a
  complete, valid, pretty-printed JSON document.
- The document is a total projection of the `InspectorSnapshot` the panel is rendering — same
  instance, same bounded values, nothing added.
- Types survive: nested objects, arrays, booleans, numbers and `null` are JSON types, not display
  strings. `—` is a display convention and must not reach the clipboard as a value.
- Field order is deterministic, so two captures of one origin diff cleanly.
- The panel stays open and says, visibly and to assistive technology, that the copy happened.
- A field added to the snapshot later cannot be silently missing from the copy, and a field of a new
  *kind* — a header map, a cookie, a page string — cannot be added to the snapshot without failing a
  test.

## Non-goals

- Rendering JSON inside the panel, or any other redesign of the inspector's layout.
- A share sheet, a file, an upload, or any automatic transmission to an external service. The
  clipboard is the whole transport, and the user's tap is the whole trigger.
- Widening the diagnostic model. No cookie, credential, authorization header, WebView storage value,
  form value or page DOM content becomes collectable because an export exists.
- Re-running discovery, re-validating, re-fetching a brand asset, or touching any browser state to
  produce the payload.
- Making the inspector reachable in a release variant, or letting the serializer compile into one.
- A general-purpose JSON library on `:app`'s classpath. `:siteskin-core` keeps kotlinx.serialization
  as an `implementation` dependency deliberately, and a debug-only tool is not the reason to add one
  to the browser.

## User stories

- As a site owner debugging a rejected manifest, I copy the inspector's output and paste it into an
  issue, a terminal, or a Claude/Codex prompt, and everything the panel told me is in it.
- As a Webora developer, I paste two captures side by side and diff them, because the field order is
  the same both times.
- As a user of a release build, none of this exists — no button, no serializer, no clipboard write.

## Acceptance criteria

1. The inspector panel exposes a browser-owned copy control with a resource-resolved label and
   accessible description, reachable without scrolling the diagnostics body.
2. Activating it places a single JSON document on the Android system clipboard as plain text, with no
   surrounding label, prose or Markdown fence.
3. The document parses as JSON, and its content is not truncated by the panel's scrolling viewport —
   the payload is built from the model, never from what is laid out.
4. The document is produced by a pure function of exactly one `InspectorSnapshot`, and the panel
   passes the snapshot it is currently rendering. Signature and call site are both asserted.
5. Every website-controlled string in the document is bounded by the same `inspectorValue` the panel
   applies to the corresponding row; a raw over-limit value fails a named test.
6. Booleans, numbers, `null`, arrays and nested objects are emitted as JSON types. An absent value is
   `null`, never the `—` the panel displays.
7. Field order is deterministic for a given snapshot shape: serializing the same snapshot twice
   yields byte-identical output, and the order is declared rather than derived from a hash map.
8. Every declared property of `InspectorSnapshot` appears in the emitted document; adding one without
   serializing it fails a test.
9. The reachable type graph of `InspectorSnapshot` is closed over a browser-owned allow-list of
   primitives, enums and inspector data classes; introducing a type outside it fails a test.
10. Copying leaves the panel open, performs no navigation, no discovery, no validation and no asset
    load, and mutates no browser state other than the clipboard and the panel's own feedback flag.
11. Repeated activation is safe and replaces the clipboard with the current snapshot's document.
12. Confirmation is visible without dismissing the panel and is published as a polite live region.
13. Neither the copy control, the clipboard write nor the serializer compiles into the `release` or
    `debugRelease` variants, asserted against compiled output.
14. String escaping is correct for `"`, `\` and every character below `U+0020`, proven by a test that
    feeds them in.
15. `./gradlew :app:compileDebugAndroidTestKotlin` compiles.
16. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Security/privacy:** the clipboard is OS-visible user data and this feature is an explicit,
  user-initiated export of a model that already exists. The payload's ceiling is the snapshot's
  ceiling; the serializer may narrow it and may never widen it. Website text stays bounded and
  flattened by the existing walk before it is JSON-escaped, so neither a newline nor a
  `RIGHT-TO-LEFT OVERRIDE` reaches the document.
- **Reliability/fallback:** a snapshot with no record, no configuration and no brand-asset trace
  still serializes to a valid document describing that state. There is no failure path that produces
  half a document — the writer is total over the model or the build does not compile.
- **Performance:** the document is built once per snapshot, off the composition's hot path, and the
  clipboard write is the only side effect. No network, no disk, no decoding.
- **Accessibility:** 48 dp minimum target through the existing wrapper; operable at 320 dp and 200%
  font scale, where the dialog's action row wraps rather than clipping; confirmation announced
  politely; light and dark unchanged.

## Risks

- **Serializing the raw model instead of the displayed one.** The obvious implementation reads
  `snapshot.origin` and `transport.manifestUrl` directly and exports unbounded website text. The
  negative control is a snapshot carrying an over-limit hostile string.
- **A second diagnostic representation.** A serializer that enumerates its own idea of the fields
  drifts from the panel the first time a row is added. Criterion 8 is the guard, and it has to be
  reflective — a hand-listed field table is correct on the day it is written.
- **Reading live state in the callback.** `rememberInspectorSnapshot` recomputes as the browser
  moves; a copy handler that reaches for the recorder, the mode or the active tab instead of its
  `snapshot` parameter is how one origin's transport joins another's applied chrome. The signature is
  the fix, and it is the same shape `hubDrawerHeight` and `rendererMountAction` already use.
- **Shipping the capability.** Anything placed in `src/main/java` compiles into every variant. The
  existing absence check names only `SiteSkinInspectorPanel`, so a serializer in a differently named
  file would pass it while compiling into `release`.
- **A JSON dependency for one debug screen.** Adding kotlinx.serialization to `:app` puts a parser on
  the browser's release classpath to serve a tool that cannot run there.
- **Confirmation that scrolls away.** The panel's body scrolls; feedback placed inside it can be off
  screen at the moment it appears, which is confirmation the user never sees.

## Open questions

None. The three that needed answering were resolved before this PRD was set `PRD_READY`:

- *Does the panel render JSON today?* No — it renders label/value rows, and the issue's non-goals
  keep it that way. The single-source rule binds the **snapshot**, not a renderer.
- *Where does the serializer live?* `src/debug/java`, beside the panel, so criterion 13 is a property
  of the source set rather than of R8's willingness to strip dead code. The JVM gate compiles that
  source set — `SiteSkinChromeModelTest` already imports `SITESKIN_INSPECTOR_AVAILABLE` from it — so
  the decision stays testable.
- *Which clipboard API?* Compose UI 1.10.6 ships `LocalClipboard` with a suspending `setClipEntry`;
  `LocalClipboardManager` is the deprecated predecessor. The panel uses the current one.
