# CI-006: The emulator ANRs its way out of frame 03
Status: PRD_READY

## Context / Problem

Hosted screenshot runs 13, 16, and 17 reached a rendered integrated page but could not capture it:
for the full 20-second capture deadline an Android process-ANR window, usually System UI's, owned
the display. Run 17 recorded five different system processes timing out in sixteen seconds. The
capture guard is correctly refusing contested evidence; the emulator readiness gate is declaring a
newly booted device ready while package work and device-wide CPU contention are still in progress.

Run 18 captured the same frame on its first attempt after 478 ms when the device was quiet. Extending
the capture deadline or dismissing from the capture loop would hide the failure rather than make the
device photographable.
## Goals
- Make emulator readiness include an observable, bounded device-quiet condition.
- Record that condition for every readiness sample so a hosted failure is diagnosable.
- Preserve the capture guard's fail-closed ownership rule and existing deadline.
## Non-goals
- Dismissing any dialog from the capture loop.
- Lengthening the 20-second capture deadline.
- Changing SiteSkin, browser UI, manifest handling, or screenshot acceptance policy.
## User stories
- As a reviewer, I receive three uncontested canonical frames rather than losing a run to boot churn.
- As a maintainer, I can see why each readiness sample was accepted or rejected.
## Acceptance criteria
1. Readiness rejects a device whose sampled CPU use exceeds the documented quiet threshold and
   resets the consecutive-ready count.
2. Every readiness sample records the raw CPU counters, derived busy percentage, and verdict.
3. Missing, malformed, or non-monotonic CPU counters fail closed with a distinct diagnostic.
4. The pure readiness self-test covers quiet, busy, missing, malformed, and counter-reset cases and
   runs in regular CI without an emulator.
5. The capture loop, its timeout, and its one-dialog allow-list remain unchanged.
6. Two consecutive hosted runs produce all three canonical frames without a contested capture.
7. `bash scripts/pre-commit-check.sh` passes.
## NFR
- Security/privacy: readiness consumes browser-independent kernel counters only; no page or manifest
  data is logged.
- Reliability/fallback: unavailable or invalid observations delay/fail readiness rather than silently
  passing it.
- Performance: sampling reuses the existing three-second loop and performs one small `/proc/stat`
  read per sample.
- Accessibility: no product UI or accessibility behavior changes.
## Risks
- A threshold that is too strict can exhaust the readiness deadline; one that is too loose admits the
  same startup churn. Pin the arithmetic and boundary in the pure self-test and validate hosted.
## Open questions
None. Hosted validation determines whether the initial threshold needs a follow-up task; it must not
be tuned by weakening capture evidence.
