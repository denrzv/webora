# UX-020 — The tab switcher joins the browser-owned modal language

Status: PRD_READY

## Context / Problem

`TabSwitcher` is the last browser-owned list surface that never received the design refresh. It is
an `AlertDialog` whose body is a stack of rows, and each row is **two filled `WeboraButton`s** — a
full-width one carrying the accessible sentence `Tab 1 of 3, example.com` as its *visible* label, and
a second filled one carrying `Close example.com tab`. Eight open tabs therefore draw sixteen filled
Material buttons inside a 280 dp-wide dialog, with the primary action (`New tab`) and `Close`
rendered in that same filled emphasis at the bottom. Nothing in the surface distinguishes the
selected tab except a semantics property no sighted user can read.

Every other browser-owned surface already speaks a different language. `UX-004` and `UX-018` give
privacy settings a headline, tonal `Surface` rows with text on the left and a compact text action on
the right, and one full-width primary button above a text `Close`. `UX-016` gives the dock six equal
slots of icon controls. `UX-009` fixed the shape role every dialog reads. The tab switcher predates
all of it, and it is the surface a user reaches most often after the address field.

## Goal

Present the tab switcher in the same browser-owned modal language as privacy settings — an opaque
full-window surface with a headline, tonal selectable rows, a visible selected state, an icon close
affordance per row, and one primary action — without changing `BrowserSession`, tab identity,
labelling policy, or the eight-tab limit.

## Non-goals

- Changing `BrowserSession`'s reducer, tab identity, ordering, selection, close or limit semantics.
- Changing what a tab row is allowed to display. `BROWSE-006`'s labelling policy stands: Home/Page
  fallbacks or the browser-observed registrable domain, and nothing else.
- Adding page thumbnails, favicons, document titles, or any per-tab remote asset.
- Moving the tab entry point, adding a second tab authority, or touching `BrowserNavigationShell`.
- Restyling the short confirmation dialogs (consent, clear data, external URL); `AlertDialog`
  remains correct for those.

## User stories

- As a user, opening Tabs shows a list I can read at a glance and tells me which tab I am on.
- As a user, closing a tab is a small distinct control, not a button with the same weight as the tab
  itself.
- As a user, Android Back dismisses the tab switcher and returns me to the unchanged page.
- As a user at 200% font scale with eight tabs open, every row and both actions remain reachable.

## Acceptance criteria

1. The tab switcher opens as an opaque full-window browser-owned modal surface built from the same
   `Dialog` + `Surface` + safe-drawing structure as `PrivacySettingsDialog`; page content cannot show
   through or receive input while it is open.
2. Each tab is one tonal row carrying its browser-derived label as ordinary text plus a compact
   icon-only close control; neither is a filled `Button`.
3. The selected tab is distinguishable **visually** — by a browser-owned colour role, not by opacity
   — in addition to the existing `selected` semantics, and the semantics property is retained.
4. Row selection, close, new-tab and dismissal invoke exactly the existing `onSelect`, `onCloseTab`,
   `onNewTab` and `onDismiss` callbacks with the same tab ids; `BrowserSession` is unchanged.
5. `TAB_LIST_TAG`, `NEW_TAB_TAG`, `TAB_SELECT_TAG` and `TAB_CLOSE_TAG` keep their current values and
   the same nodes they identify today, so existing instrumentation is not silently invalidated.
6. The disabled `New tab` action and the visible eight-tab limit message both survive; the limit is
   never communicated by hiding the action.
7. Android system Back dismisses the switcher before browser history or Home navigation.
8. Every control keeps the one 48 dp `MINIMUM_TOUCH_TARGET` contract; the close control does not
   introduce a smaller target to make a row fit.
9. No website, manifest value, SiteSkin palette, brand asset, page title or editable address text can
   influence any part of the surface.
10. The list scrolls and reflows at 200% font scale with eight tabs open.
11. `bash scripts/pre-commit-check.sh` passes, and `:app:compileDebugAndroidTestKotlin` compiles.

## NFR

- Security/privacy: the row's visible text remains a browser-derived label. A restyle must not become
  a seam through which a document title or manifest string reaches the switcher.
- Reliability/fallback: presentation only. No change to the session reducer, the saved snapshot, or
  controller/renderer lifecycle.
- Performance: no new I/O, network request, decoding or retained state.
- Accessibility: localized labels, `selected` semantics on the row, an accessible name on the
  icon-only close control naming the tab it closes, and 48 dp targets throughout.

## Risks

- The close control becomes icon-only, so its accessible name is the *only* thing naming it. An icon
  with no `contentDescription` is invisible to assistive technology; `WeboraIconButton` makes that a
  compile-time requirement, and the ticket must use it rather than a raw `IconButton`.
- Making the row itself clickable while it contains a second clickable control can merge or swallow
  semantics. The two must remain separately addressable by their existing tags.
- A full-window surface consumes safe-drawing insets; `BrowserScreen` already consumes them once, so
  the dialog must own its own inset handling exactly as `PrivacySettingsDialog` does, and not add a
  second read inside the browser shell.
- A visual selected state chosen as an alpha multiplier would repeat the mistake `UX-003` recorded:
  it reads as disabled and can fall below 3:1 whatever token sits underneath.
