# UX-009: Consent dialog renders as a circle and clips its own heading
Status: PRD_READY

## Context / Problem

Hosted screenshot run **14** (`31706775744`, `d830cac8`), frame `02-siteskin-consent.png`, shows the
first-use consent surface drawn as a large vertical stadium rather than a dialog. Its content
overflows the shape: the browser-authored heading
`Allow https://denrzv.github.io to customise Webora?` is clipped on the left to `ow`. Run **15**
(`31714792338`, `f1e81640`) reproduced it over a page that had fully painted, so — unlike `UX-010`,
which closed as a paint-timing artefact from the same pair of frames — this is a composition defect.

**The mechanism is fully determined by reading, and every link is checked rather than inferred:**

1. `WeboraRadius.PILL` is `999.dp`, deliberately "large enough that any control this rounds becomes a
   pill at any height it can reach" (`WeboraRadius.kt:22`).
2. `WEBORA_SHAPES` assigns that value to Material's `extraLarge` role (`WeboraRadius.kt:34`).
3. Material 3 `1.4.0` resolves a dialog container to that role: `DialogTokens.ContainerShape` is
   `ShapeKeyTokens.CornerExtraLarge`, confirmed by disassembling the artifact this build resolves.
4. `CornerBasedShape.createOutline` does not reject an over-large corner, it *scales adjacent corners
   down proportionally* to fit the shorter side. On a dialog roughly `312 × 500` dp all four corners
   resolve to half the width, which is a stadium.
5. `AlertDialog` draws that shape on a `Surface`, which clips its content to it — so the heading is
   not merely overlapped, it is removed from the frame.

`UX-002` asserted that every shape corner comes from the compiled radii, and it does. What nothing
asserted is that a *container* role never carries the pill. The token is correct for the address
pill and the dock slots it was drawn for; it reached the dialog because `extraLarge` is one Material
role serving both.

**The blast radius is larger than the frame that found it.** Every `AlertDialog` in the app takes
that default: SiteSkin consent, external-URL confirmation, external-navigation confirmation, the
clear-browsing-data confirmation, and the debug inspector panel. Four of the five are browser-owned
confirmations — the surfaces where Webora asks before something irreversible or trust-granting
happens.

**Why this is P1 and not cosmetic.** `ADR-011` makes the consent dialog the enforcement point of the
entire SiteSkin trust boundary, and `HARDEN-002` requires the complete canonical origin to be
displayed there so the visible grant matches the `SiteOrigin` persistence key. A clipped heading is
that security statement losing text — on the one screen a user reads before granting a website
control of the browser chrome. `UX-007`'s action hierarchy underneath is correct and unaffected.

## Goals

1. Give the Material container roles a radius that produces a dialog, so no browser-owned
   confirmation clips its own text.
2. Keep the pill where it was drawn for — the address field and the dock slots — by making that an
   explicit choice at the call site rather than a side effect of a shared Material role.
3. Add a gate test that fails when a container role can round a confirmation into a stadium, so the
   next value that collides is caught before a hosted run photographs it.

## Non-goals

- Changing `UX-007`'s action order, emphasis, full-width stack or dismissal behaviour.
- Changing what the consent dialog *says*, which strings it reads, or `SiteSkinConsentModel`'s
  bounding of manifest text.
- Restyling dialogs beyond their container shape — no new colour, elevation, padding or typography.
- Reworking `WeboraRadius` into a different scale. `ADR-013`'s named numbers stand.
- Anything about what the screenshot harness will photograph. `CI-002`/`CI-003`/`CI-005` are
  untouched, and nothing here may make a frame acceptable that is rejected today.

## User stories

- As a user deciding whether to let a site customise the browser, I read the complete origin Webora
  is asking about, with no character of the question missing.
- As a user confirming an external app launch or clearing my browsing data, the confirmation is a
  dialog with its text intact.
- As a maintainer, a radius that would clip a confirmation fails `./gradlew test` rather than
  appearing in a screenshot artifact three runs later.

## Acceptance criteria

1. The Material shape scale's container roles resolve to a rounded rectangle: at the narrowest
   dialog width Material will lay out, every resolved corner radius is at most a quarter of that
   width, so no side of the container is fully rounded.
2. No Material shape role in `WEBORA_SHAPES` carries `WeboraRadius.PILL`, and a JVM test fails if one
   does — verified with a negative control that restores the current value.
3. The corner values in `WEBORA_SHAPES` still all come from `WeboraRadius`, and every non-pill radius
   is still a multiple of the stated base — `UX-002`'s existing assertions pass unmodified.
4. The address field on Home and the dock slots remain pills, by naming `WeboraRadius.PILL`
   explicitly rather than by reading a Material role.
5. An instrumented assertion drives the consent dialog at 360 dp and requires the complete
   browser-authored heading, including the full canonical origin, to be displayed.
6. The consent dialog's actions remain filled *Allow*, outlined *Not now*, text *Never for this
   site*, full-width and stacked in that order; `SiteSkinConsentDialogTest`'s existing assertions
   pass unmodified.
7. A hosted `02-siteskin-consent.png`, from a run whose commit SHA matches the branch head being
   judged, shows a rounded-rectangle dialog with the heading complete.
8. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Security/privacy:** the heading is browser-authored and carries the complete canonical origin
  per `HARDEN-002`; no manifest value gains a path into the container shape, and the site-authored
  preview stays separately attributed. A shape token is compiled — `UX-002`'s rule that no manifest
  value reaches a browser token applies here unchanged.
- **Reliability/fallback:** a shape change cannot alter consent outcomes. Allow/Not now/Never keep
  their persistence semantics, and outside dismissal remains Not now.
- **Performance:** none — `WEBORA_SHAPES` is a compile-time constant built once.
- **Accessibility:** clipping is invisible to the semantics tree, which is why this survived a green
  androidTest suite. The visual bound and the spoken string must agree, so the new assertion is about
  what is *displayed*, not only about what a node reports.

## Risks

- **A test that cannot fail.** `assertIsDisplayed()` and `assertTextEquals()` both pass over a
  clipped heading, because clipping happens in the parent's draw and semantics precede pixels —
  `CI-003`'s lesson in a different layer. The gate assertion must therefore be about the resolved
  geometry, not about node presence.
- **Fixing the frame and not the class of defect.** Setting a shape on the consent dialog alone
  leaves the other four dialogs stadium-shaped and the token collision live. The fix belongs at the
  role.
- **Losing the pill where it is correct.** The address field and dock slots are drawn as pills by
  `ADR-013`; changing `extraLarge` moves anything that reads that role. Each such call site is
  enumerated and re-pointed at the token explicitly.
- **The evidence being read from the wrong run.** `DEVX-002` records that stale frames were once read
  as current. Any claim about the fixed frame cites a run number and commit SHA.

## Open questions

- Whether `extraLarge` should be a new declared radius or an existing one. The scale's largest
  non-pill value is `LARGE` at 20 dp, and Material's own extra-large is 28 dp; both are multiples of
  the 4 dp base, so `/plan` decides on which produces a dialog that reads as one rather than on which
  is cheaper.
- Whether any surface other than the address field and the dock slots reads `extraLarge` today —
  enumerated in `/researcher`, since a missed call site silently changes shape.
