# UX-018 — Make privacy settings a dismissible modal surface

Status: PRD_READY

## Context / Problem

Selecting Settings currently composes `PrivacySettingsScreen` as a transparent sibling after the
browser content. The WebView remains visible beneath the settings copy, so both surfaces visually
collide and the result does not establish a modal boundary. Because the settings layer is not a
dialog, system Back remains owned by browser navigation instead of dismissing settings first.

## Goal

Present privacy settings in an opaque, full-window, browser-owned modal surface that blocks the page
and dismisses predictably from both Close and Android Back without changing stored preferences,
consent decisions, or browsing state.

## Non-goals

- Redesigning privacy controls, consent storage, or clear-browsing-data behavior.
- Allowing websites or SiteSkin manifests to style, open, close, or otherwise influence settings.
- Changing SiteSkin discovery, consent, browser navigation, or WebView content.

## User stories

- As a user, Settings is visually separate from the current website and never overlaps its text.
- As a user, Close or Android Back dismisses Settings and returns me to the unchanged page.
- As a privacy-conscious user, the website cannot receive taps while Settings is open.

## Acceptance criteria

1. Settings opens in a full-window opaque browser-owned modal surface; WebView content cannot show
   through or receive input while it is open.
2. The existing privacy controls, stored exact-origin decisions, and clear-data confirmation remain
   available and behaviorally unchanged.
3. The Close action dismisses the modal and reveals the unchanged browser page.
4. Android system Back dismisses the settings modal before browser history or Home navigation.
5. The modal respects safe drawing insets, remains scrollable, and keeps controls reachable at 200%
   font scale.
6. No website, manifest value, brand palette, or remote asset can influence the modal's presentation
   or lifecycle.
7. Automated Compose coverage proves Close and Back dismissal and retains existing privacy-control
   coverage.
8. `bash scripts/pre-commit-check.sh` passes.

## NFR

- Security/privacy: settings remain app-owned and modal input isolation prevents page interaction.
- Reliability/fallback: dismissal does not mutate browsing, consent, or preference state.
- Performance: no new I/O, network request, or long-lived state.
- Accessibility: full-screen reflow, scrolling, localized labels, and standard Back semantics remain.

## Risks

- A nested clear-data confirmation must remain above the settings dialog and return to it on cancel.
- Applying safe insets both in the browser and dialog could double-pad content; the dialog must own
  its own window inset handling.

## Open questions

None.
