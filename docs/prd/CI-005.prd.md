# CI-005: The frame that is saved must be the frame that was validated
Status: PRD_READY

## Context / Problem

`CI-002` exists because three frames covered by `System UI isn't responding` passed every assertion
and shipped as product evidence. It made that impossible by refusing to photograph a screen Webora
does not own.

**It happened again, on run 14 (`31706775744`, `d830cac8`), and the job was green.**
`03-siteskin-integrated.png` shows the `System UI isn't responding` dialog over a blank page. The
harness's own diagnostics explain how, and the sequence is worse than a contaminated picture:

```
region=Rect(0, 349 - 1080, 2127)
attempt=1 elapsed=1013ms differing=0.0023084800967043298 modal=#ffffffff samples=119126
attempt=2 elapsed=1943ms differing=0.0023084800967043298 modal=#ffffffff samples=119126
attempt=3 elapsed=2961ms differing=0.0023084800967043298 modal=#ffffffff samples=119126
PASSED differing=0.3047865285496029 after 4143ms
```

Three seconds of a **99.77% uniform white** page region — nothing drawn. Then the fraction jumps to
30% and the check passes. What changed in that interval was not the page: it was the arrival of the
ANR dialog. Run 12's genuinely rendered page measured `0.7530`.

**So the obstruction supplied the pixels that certified the page as rendered.** `CI-003` built a
check to catch a blank page and the thing covering the page satisfied it.

The second half is how it got past `CI-002`. `focus-03-siteskin-integrated.txt` records the screen at
ownership-check time:

```
mCurrentFocus=Window{f2c1917 u0 app.webora.browser.debug/app.webora.browser.MainActivity}
```

Webora owned the screen when `requireAppOwnsScreen` looked. The dialog arrived during the 4.1 seconds
of content polling that followed. **Ownership is a point check; capture is a polling loop; nothing
re-asserts ownership on the bitmap that actually wins.** `CI-003` recorded "ownership first, content
second" and got the order right — it did not notice that the frame validated and the frame saved are
different frames.

Both halves have the same root cause and the same fix point, which is why they are one ticket.

## Goals

- The bitmap written to disk is one that satisfied **both** checks, at the moment it was taken.
- A screen obstruction can never contribute to the rendered-content measurement.
- A run that cannot obtain a clean rendered frame fails, loudly, with the evidence.
- `CI-002`'s and `CI-003`'s existing guarantees survive intact; this is a gap in their seam, not a
  disagreement with either.

## Non-goals

- Raising `MINIMUM_DIFFERING_FRACTION`. The blank page measured 0.23% and would still fail any sane
  bar; the dialog measured 30% and would still pass one. The threshold is not the defect and
  `CI-003` already refused to tune it.
- Changing what may be dismissed. That is `CI-004`, and its allow-list of one is untouched here.
- Fixing why System UI ANRs on this emulator, or tuning the AVD.
- The missing top bar (`UX-010`) or the circular consent dialog (`UX-009`). Both were found in the
  same frames and neither is a harness defect.

## The mechanism this ticket must not choose

**Masking the obstruction out of the measured region.** Excluding the dialog's rectangle so the
remaining pixels can be scored would let the check pass on a page that is still blank, still covered,
and now measured selectively. The rule stays what `CI-002` set: an obstruction is a reason to refuse,
never a region to work around.

Equally refused: **capturing the bitmap early and validating it late**, or validating a fresh
screenshot and saving a different one. The frame saved must be the frame that passed, or the check is
a claim about a picture nobody kept — the property `CI-003` already stated when it explained why
`captureWhenRendered` re-screenshots on every poll.

## User stories

- As someone reviewing demo evidence, a frame in the artifact is a frame that was verified clean at
  the instant it was taken.
- As a maintainer, a green screenshot job means the journey rendered, not that something was in the
  way of the camera.
- As a reviewer of the harness, ownership and content are both properties of the saved bitmap, and I
  can see which check rejected which candidate.

## Acceptance criteria

1. Ownership is re-asserted for the bitmap that satisfies the content check, not only before polling
   begins. A candidate taken while Webora does not own the screen is rejected.
2. A rejected candidate does not end the run on its own: the existing deadline still governs, so a
   transient obstruction is retried like any other unsettled screen.
3. The content check cannot be satisfied by a screen Webora does not own — under no ordering of
   arrival can an obstruction's pixels count toward `differing`.
4. When the deadline expires, the failure states which condition was unmet on the last candidate —
   ownership, content, or both — and keeps the existing `window-*` and `rendered-*` records.
5. `rendered-<label>.txt` records ownership alongside each attempt, so a future reader can see that
   the winning frame was clean rather than infer it.
6. The decision stays a pure function in `src/screenshotPolicy/java`, testable by `./gradlew test`
   with no emulator, in keeping with `CI-002` and `CI-003`.
7. `ScreenEvidencePolicyTest` and `RenderedContentPolicyTest` pass **unedited**. Needing to change an
   existing fixture is a signal the change reached further than the seam.
8. Negative control: with the fix reverted, a test reproducing run 14's sequence — blank region, then
   an obstruction, then a passing fraction — must fail.
9. A hosted run produces three frames and the owner confirms none carries a system dialog.
10. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Integrity:** this ticket may only ever make the harness refuse *more*. If any change here could
  cause a frame to be accepted that is rejected today, it is the wrong change.
- **Reliability:** no new unbounded wait. The 20-second deadline already exists and is the budget.
- **Diagnosability:** every rejected candidate is accounted for in the record, so "it took 4 seconds"
  and "it took 4 seconds because three candidates were obstructed" are distinguishable.
- **Testability:** the JVM gate must fail on this defect. An emulator-only fix is not acceptable —
  this is the second time a capture-time property has been provable only on hardware, and both times
  the property was wrong for months.

## Risks

- **Interleaving two checks invites a subtle ordering bug.** The failure being fixed *is* an ordering
  bug; the fix must not introduce a second one. Prefer one function that decides a candidate over two
  that each decide half of it.
- **A flaky device could now fail runs that previously passed.** Correct and intended: those runs
  were passing on contaminated frames. Say so in the ticket rather than discovering it as a surprise.
- **Scope pull toward `CI-004`.** Both touch `ScreenEvidenceGuard`. They are separable: `CI-004` is
  about clearing an obstruction, `CI-005` about never photographing one. Land them independently.

## Open questions

For `/researcher`, before the plan commits to a mechanism:

1. Does `captureWhenRendered` re-check ownership per candidate, or does the ownership check move
   *inside* the polling loop and subsume `requireAppOwnsScreen`? The second is simpler and changes
   the guard's public shape.
2. Is a `dumpsys window` read per poll affordable? It is a shell round trip every 500 ms, and
   research §10 of `CI-004` notes the System UI ANR's reason was its own dump service — a harness
   that polls harder may provoke what it is trying to avoid.
3. Can ownership be established from the screenshot itself rather than a second syscall — and if so,
   is that a decision that can stay pure and JVM-testable, or does it drag Android types in?
4. Should the two verdicts combine into one `CandidateVerdict`, or stay separate with the guard
   sequencing them? Criterion 6 requires whatever decides to be pure.
