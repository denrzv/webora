# UX-021 — Replace the SiteSkin security row with a compact inline trust shield

Status: PRD_READY

Issue: [denrzv/webora#104](https://github.com/denrzv/webora/issues/104)

## Context / Problem

Integrated SiteSkin chrome spends a whole row on transport identity. `SiteSkinTopBar` composes
`SecurityIdentity(model.security)` beneath the Back/brand row, drawing a full-width
`surfaceContainer` pill reading `Secure · denrzv.github.io` at 12 sp. It is the heaviest element in a
header whose brand row already identifies the site, and hosted frame `03` shows it consuming roughly
a third of the expressive header.

Underneath the visual complaint there is a correctness one, and it is the more important half.
`securityPresentation(mode)` classifies transport from one fact:

```kotlin
transportSecurity = if (origin.scheme == "https") SECURE else NOT_SECURE
```

The committed origin's *scheme*. Not whether the navigation completed, not whether a certificate was
accepted, not whether the browser is mid-load with nothing confirmed. `BROWSE-009` gave
`onReceivedSslError` a way to settle the page through `mainFrameTlsFailure`, and the resulting
`BrowserLoadFailure(kind = TLS)` lands in `BrowserState.loadFailure` — where `securityPresentation`
never looks. A tab whose certificate was rejected keeps `mode = Regular(https://…)` and therefore
still reports `SECURE`. Today that renders the word `Secure` next to a domain, which is wrong but
textual. This ticket wants to render it as a **green shield**, and a green shield is a positive trust
claim in a way a 12 sp word is not. Making the indicator more emphatic without first making the
signal honest would ship a worse defect than the one being fixed.

The gap is structural, not a missed condition: `BrowserMode` carries an origin, and an origin has no
lifecycle. Nothing in the type can distinguish *this HTTPS page loaded and its certificate was
accepted* from *this HTTPS URL is what we are currently attempting*. That distinction has to be
observed and stored, which is why this ticket adds browser-owned transport state rather than adding a
branch to the projection.

The two chrome variants must keep agreeing. `BrowserChrome` derives its identity chip from the same
`securityPresentation`, so a second classification for integrated mode alone would be a second place
for the two to drift — `UX-020` records what that costs when a mapping has two copies.

One constraint the issue does not state and the harness does: `SITESKIN_SECURITY_TAG` is the tag
`LiveSiteScreenshotTest` and `LiveSiteNavigationSmokeTest` use as the *authority* for whether
integrated identity is present, including the `assertDoesNotExist` that proves `UX-012`'s teardown
after leaving the origin. `CI-009` is pending hosted acceptance on exactly those assertions. The tag
therefore moves to the shield; it does not disappear.

## Goals

- Remove the full-width textual security row from integrated SiteSkin chrome, replacing it with a
  compact browser-owned shield immediately after the visible site title.
- Introduce a browser-owned transport state that distinguishes confirmed-secure from unknown,
  not-secure and TLS-failed, and derive both chrome variants' security presentation from it.
- Emit the green state only from a positively confirmed successful HTTPS main-frame navigation.
- Keep transport meaning, colour and semantics entirely browser-owned, on a browser-owned ground,
  inside a header the manifest paints.

## Non-goals

- A certificate viewer, certificate details, or EV/company-name display.
- Making the shield interactive, or building the page-information surface the richer internal states
  are being kept for.
- A visible three- or four-way colour mapping. `SECURE` is green; `UNKNOWN`, `NOT_SECURE` and
  `TLS_ERROR` are all the same neutral in this ticket.
- Redesigning the regular address bar or its identity chip beyond the state it reads.
- Mixed-content or subresource-level security signalling. The hardened WebView already blocks mixed
  content; per-subresource state is not modelled.
- Persisting transport state across process death. `BROWSE-006` requires a restored tab to
  re-traverse discovery and activation, and a persisted `SECURE` would be a way to skip the
  observation that earns it.

## User stories

- As a user on an integrated site, the header shows me the brand and one small trust mark instead of
  a banner repeating a domain I can already see.
- As a user whose page is still loading, the browser does not tell me the connection is secure before
  it knows.
- As a user on a site whose certificate was rejected, nothing green remains on screen.
- As a user switching between a secure tab and a failed one, each tab shows its own trust state
  immediately.
- As a screen-reader user, removing the visible text costs me nothing: the transport state and the
  canonical domain are still announced.

## Acceptance criteria

1. Integrated SiteSkin chrome renders no full-width textual `Secure · domain` row; the header is the
   Back/brand row plus title, subtitle and shield.
2. A shield is rendered immediately after the visible site title in the browser-owned title row,
   separated by a deterministic compiled gap.
3. A committed HTTPS main frame that completed successfully with no TLS failure renders the secure
   (green) shield.
4. A committed HTTP main frame renders the neutral shield.
5. A navigation in progress, a new tab, and any state with no confirmed main-frame result render the
   neutral shield — the secure state is never claimed before confirmation.
6. A TLS/certificate failure renders the neutral shield and clears any previously confirmed secure
   state for that tab; no green survives the failure.
7. A redirect that changes scheme in either direction resolves to the final committed main frame's
   state, not the originally requested URL's.
8. Switching tabs immediately shows the selected tab's own transport state, and an event from a
   background tab cannot change the selected tab's shield — `BROWSE-009`'s routing remains the only
   path.
9. Leaving an integrated origin removes the header and the shield with the rest of integrated chrome;
   `SITESKIN_SECURITY_TAG` identifies the shield's security node and its
   `assertIsDisplayed`/`assertDoesNotExist` instrumented contract is preserved.
10. A title long enough to ellipsize cannot push the shield out of the header at 320 dp.
11. The shield's colour comes only from compiled `WeboraColorScheme` roles and sits on a browser-owned
    sub-surface; no manifest colour, title, icon or action can change the shield's colour, glyph,
    presence, position or meaning. A source contract test rejects a SiteSkin colour reaching it.
12. Regular chrome consumes the same transport state rather than a scheme-only classification, and
    the two variants cannot classify one page differently.
13. The shield exposes a browser-authored state description carrying both the transport meaning and
    the browser-derived registrable domain; meaning is never carried by colour alone.
14. Light and dark projections, 320 dp width and 200% font scale all remain operable, and every new
    colour pair is measured by `WeboraColorSchemeTest`'s reflected table.
15. `bash scripts/pre-commit-check.sh` passes, and `:app:compileDebugAndroidTestKotlin` compiles.

## NFR

- **Security/privacy:** the shield is a trust claim, so it fails closed — anything the browser has not
  positively confirmed is neutral, never green. The state is derived only from browser-observed
  navigation results and the committed origin; page content, document title, editable address text
  and every manifest field are excluded by construction. The colour is a compiled browser token on a
  browser-owned ground, because a browser semantic colour drawn straight onto a manifest-painted
  background has no contrast floor a site cannot move.
- **Reliability/fallback:** presentation and state derivation only. No change to discovery, consent,
  activation, the session reducer, the renderer lifecycle or the saved snapshot. An unobserved or
  unrepresentable transport degrades to neutral, never to an error.
- **Performance:** no new I/O, allocation per frame, or retained state beyond one enum per tab.
- **Accessibility:** the security node keeps a browser-authored `contentDescription` naming transport
  state and registrable domain; the shield's pixels stay decorative; the indicator is not colour-only;
  the 48 dp target contract is untouched because a status indicator is not a control.

## Risks

- **A green shield is a stronger claim than the word `Secure`.** Ship the visual before the state
  model and the ticket has made an existing inaccuracy louder. The state model lands first.
- **`SECURE` requires a *completion* signal, and completion signals are the ones that arrive late.**
  `BROWSE-009` documents terminal callbacks arriving after a tab switch; the state must be written
  through `routeRendererEvent` for the owning tab, never at delivery time, or the fix reintroduces
  exactly the cross-tab identity leak that ticket removed.
- **`onReceivedSslError` does not identify the main frame.** `mainFrameTlsFailure` narrows it and
  publishes nothing when the answer is not a clear yes. A TLS state that only appears when that
  function publishes will therefore miss some failures — which is the fail-closed direction only if
  those cases land in `UNKNOWN`, never in a retained `SECURE`.
- **`SITESKIN_SECURITY_TAG` carries `CI-009`'s pending hosted acceptance.** Dropping or renaming it
  silently invalidates the frames that ticket is waiting on.
- **The shield sits inside a manifest-painted header.** Contrast has to be established against a
  browser-owned sub-surface; deriving it from the SiteSkin palette instead would be `UX-002`'s C2
  violation arriving through the one element whose whole job is to be trustworthy.
- **A shield after a `weight(1f)` title can be pushed off-screen** if the title row's constraints are
  written in the obvious order. The shield must be laid out before the flexible title consumes the
  remaining width.

## Open questions

None. The four-state vocabulary, the two-colour visible mapping and the deferred page-information
surface are all fixed by the issue.
