# A11Y-001: Accessibility
Status: PRD_READY

## Context / Problem
Webora's chrome is functionally complete through `PRIV-001`, but its accessibility guarantees are
uneven and, in places, only incidental. `SKIN-002`/`SKIN-003` gave SiteSkin chrome bounded touch
targets, decorative-icon suppression, and a browser-authored security description; every
browser-owned surface built before them did not get the same treatment. Concretely:

- `HomeScreen` and `OnboardingScreen` carry hard-coded English literals, so they are outside the
  reviewed browser-owned copy in `strings.xml` and cannot be localized or audited.
- Regular-mode chrome renders the security identity as an interpolated `"%1$s · %2$s"` string with
  no dedicated semantics node, while `HARDEN-002` requires exactly that node in integrated mode.
  The same guarantee should not depend on which mode the user is in.
- Material 3 `Button` has a 40 dp minimum height and does not receive
  `minimumInteractiveComponentSize`. Every regular-chrome, error-page, onboarding, home, and
  privacy-settings control is therefore below the 48 dp target that SiteSkin chrome already meets.
- `AddressBar`'s five-button `Row`, `OnboardingScreen`'s `Column`, and `PrivacySettingsScreen`'s
  `Column` are fixed, non-scrolling layouts. At large font scale their content is clipped rather
  than reflowed, and clipped controls are unreachable rather than merely ugly.
- `PrivacySettingsScreen` renders a bare `Switch` whose label is a sibling `Text`, so assistive
  technology announces a toggle with no name, and it repeats an identically labelled
  "Reset decision" button once per stored origin with nothing to distinguish them.
- `RegularBrowser` always selects `SiteSkinTheme.from(...).light`. The guarded dark projection is
  computed on every activation and then discarded, so a user who has chosen a dark system theme for
  accessibility reasons is served the light projection regardless.
- Loading and page-failure state changes are visual only; neither is announced.

Accessibility is also a security surface in this product. Assistive technology consumes the
semantics tree, not the pixels, so every bound the browser places on manifest content in the
*visual* chrome — bounded logo slot, one-line ellipsized labels, non-suppressible domain — must have
a counterpart in the *accessible* chrome, or a manifest regains through the semantics tree exactly
the impersonation surface `ADR-006` and `HARDEN-002` closed off visually.

## Goals
1. Give every browser-owned interactive control a minimum 48 dp touch target from a single
   browser-owned source, rather than per-call-site `sizeIn` that a new screen can silently omit.
2. Keep every browser-owned surface operable and unclipped at a 2.0x font scale by making its
   containers reflow or scroll.
3. Move all user-visible and accessible browser copy into `strings.xml` so it is reviewable,
   localizable, and cannot be authored inline in a composable.
4. Give regular-mode security identity the same dedicated, browser-authored semantics node that
   integrated mode already has, and announce loading and failure state changes.
5. Convey every state that is currently colour-only — navigation selection, toggle state, transport
   security — through text or a state description as well as colour.
6. Honour the system dark-theme preference when projecting SiteSkin colours, and prove the WCAG AA
   guard holds for the dark projection and for an adversarial colour corpus, not only for the
   defaults.
7. Bound what manifest-supplied text can contribute to the accessibility tree, so the semantics tree
   cannot carry impersonation content that the visual chrome refuses.

## Non-goals
- Accessibility of web page content inside the `WebView`. That is renderer-owned; Webora hardens
  the host and does not inject into the document (`addJavascriptInterface` remains forbidden).
- A user-facing font-size, high-contrast, or reduced-motion preference screen. Webora follows the
  platform settings; introducing a competing in-app control is separate product scope.
- Making an accessibility service, TalkBack itself, or gesture navigation a tested dependency of the
  build gate. Instrumented evidence is recorded in QA; the JVM gate covers the pure decisions.
- Changing the SiteSkin manifest schema. No new manifest field, and no accessibility-related field
  becomes website-controlled.
- Retrofitting Robolectric or any other Android-in-JVM harness to test composables.

## User stories
- As a TalkBack user, I can reach and identify every browser control, and I hear which site I am on
  and whether the connection is secure without inspecting colours.
- As a user with a 200% display font size, every browser control remains on screen and tappable,
  and no label overlaps another.
- As a user with a motor impairment, every browser control is at least 48 dp in both axes.
- As a user with low vision who has selected the system dark theme, integrated chrome is projected
  dark and still meets WCAG AA.
- As a security reviewer, I can confirm that a hostile manifest gains no accessible text it is
  denied visually — in particular that it cannot narrate its own security state.

## Acceptance criteria
1. A single browser-owned minimum-touch-target modifier is applied to every browser-owned
   interactive control in regular chrome, the error page, onboarding, home, privacy settings, and
   the clear-data and consent dialogs, and it resolves to at least 48 dp on both axes.
2. Onboarding, privacy settings, and the regular-chrome control row reflow or scroll rather than
   clip at a 2.0x font scale, and every control in them remains reachable.
3. `HomeScreen` and `OnboardingScreen` contain no user-visible string literal; all browser copy is
   resolved from `strings.xml`.
4. Regular-mode chrome exposes the registrable domain and transport-security state through a single
   browser-authored semantics node whose description is built from the committed `SiteOrigin`, never
   from address text, page content, or manifest fields.
5. Loading start/finish and main-frame load failure are announced through an assertive live region
   with browser-owned copy.
6. Navigation selection, the SiteSkin global toggle, and transport security each expose a textual
   state description in addition to any colour treatment.
7. `SiteSkinTheme` selects its light or dark projection from the system dark-theme setting, and both
   projections satisfy 4.5:1 for body pairs and 3:1 for UI pairs across an adversarial colour
   corpus, with a negative control proving the corpus test fails when the guard is removed.
8. Manifest-supplied text reaching the accessibility tree is bounded to the same length the visual
   chrome enforces and can never be combined with browser security wording, proven by a test whose
   negative control fails when the bound is removed.
9. `docs/accessibility/CONFORMANCE.md` maps each of these guarantees to the code and test that
   enforces it.
10. `bash scripts/pre-commit-check.sh` passes.

## NFR
- Security/privacy: accessible copy for identity and security is browser-authored and derived from
  the trusted `SiteOrigin`; manifest text may name a site item and nothing else. No accessibility
  work introduces telemetry, a new permission, or a new manifest field.
- Reliability/fallback: an absent or unparseable origin yields no security semantics node rather
  than an empty or guessed one; theme projection failure is impossible because the guard is total.
- Performance: all added work is pure Compose semantics and layout. No new network, no new disk
  read, no main-thread decode, and no recomposition keyed on anything that changes per frame.
- Accessibility: this ticket is the accessibility contract — WCAG 2.2 AA for contrast (1.4.3,
  1.4.11), 2.5.8 target size, 1.4.4 resize text to 200%, 1.4.1 use of colour, 4.1.2 name/role/value.

## Risks
- Applying a 48 dp minimum indiscriminately can push dense rows off-screen at large font scale;
  the fix must be reflow, not a smaller target.
- `Modifier.semantics` merges rather than replaces, so adding a description to a component that
  already publishes one can produce a doubled or contradictory announcement. Each added node needs
  a test asserting the exact resulting description.
- Bounding manifest text in the semantics tree duplicates a bound `:siteskin-core` normalization
  already applies. Duplication is intended as defense in depth, but the app-layer bound must not be
  written so that it silently diverges from the core limit.
- Selecting the dark projection changes what users see today. It must not alter which colour roles
  exist or let a manifest influence the choice.
