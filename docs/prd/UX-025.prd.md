# UX-025: Let SiteSkin project primary actions into the integrated bottom dock
Status: PRD_READY

Issue: [#123](https://github.com/denrzv/webora/issues/123)

## Context / Problem

The integrated dock is browser-owned space that a site cannot reach, and after `UX-024` it spends
that space on two commands the browser already offers elsewhere. A site with real app-like
destinations — Bloom's Catalog, Cart and Account — can only surface them behind the Brand Hub, one
interaction away, while the persistent surface beside it shows a tab switcher.

`UX-025` lets a manifest **nominate up to three already-validated action ids** for the dock's
non-central slots. It nominates; it does not define. Every action it can name has already passed
origin binding, the scheme allow-list, the action allow-list and limit clamping — so the new field
carries no payload, no URL, no icon and no callback, only a reference to something the browser has
already decided is safe.

## Three assumptions in the issue that the code has since overtaken

The issue was filed at 12:48 on 2026-08-18, before `UX-024` merged. Its product model describes a
dock that no longer exists, and the differences change what this ticket has to build:

| Issue assumes | Actual, at `90b5d7f` |
|---|---|
| Five slots: `Back / Forward / Brand Hub / Tabs / More` | **Three**: `Brand Hub / Tabs / More` — `UX-024` moved Back and Forward into the header's navigation hub |
| Brand Hub is already centre | Brand Hub is **leading**, in slot 1 |
| Tabs must be *moved* into the More menu | `browserMenuCommands()` has offered `TABS` since `DEVX-003`; the More menu already exposes it |

So this ticket does not remove Back and Forward from the dock — `UX-024` already did — and the
"Tabs remains reachable" requirement is largely met before it starts. What it must actually do is
grow the dock from three slots to five *when a projection exists*, move the Brand Hub from leading
to centre in that arrangement, and take Tabs out of the dock in favour of the More menu that already
carries it.

The issue's acceptance criteria are carried below unchanged in intent, restated against the dock
that exists.

## Goals

- An optional, bounded `presentation.dock` naming up to three existing validated action ids.
- A browser-owned projection step that resolves those ids to trusted `NavigationItem` values, or to
  a deterministic fallback, before anything reaches composition.
- The centre Brand Hub and the trailing More remain browser-owned and unreplaceable.
- Items successfully projected into the dock are not *also* drawn in the drawer — presentation
  de-duplication only, never removal from the validated model.
- Tabs stays reachable from browser-owned UI at all times.

## Non-goals

- Any new action type, URL, payload, icon source or callback reachable through `presentation.dock`.
- Site-defined slot count, order, geometry, colour roles or touch targets.
- Replacing the Brand Hub or More with a site action.
- Changing regular/Home chrome, or `UX-024`'s navigation hub and its three commands.
- Removing an action from the validated model because it was projected — route matching, dispatch
  and every other browser-owned projection must still see it.
- Android/Compose vocabulary in the protocol: no `leftSlot`, no coordinates, no dp, no component
  names. The field names *ids*, and the browser decides where they land.

## User stories

- As a Bloom user, Catalog, Cart and Account are one tap away on a persistent native surface,
  instead of two taps behind the Brand Hub.
- As a site owner, I choose which of my *already-declared* destinations deserve that space, and I
  cannot accidentally break the browser's own controls doing it.
- As a user, the browser's Tabs, history and settings remain reachable no matter what a site asks
  for.

## Acceptance criteria

1. `presentation.dock` is an optional array of at most three strings, each matching the existing id
   grammar, constrained by **pattern rather than enum** so an unknown value never rejects the
   manifest.
2. Ids that do not resolve to a validated navigation, quick-action or menu item are dropped with a
   registered `warn` diagnostic; the manifest is otherwise unaffected.
3. Duplicate ids are de-duplicated deterministically, first occurrence winning, with a diagnostic.
4. More than three ids is bounded to the first three with `SS-W-LIMIT-TRUNCATED`, never rejected.
5. The trusted model exposes the resolved projection as ordered ids only — no second copy of an
   action, and no raw manifest string reaches Compose.
6. A browser-owned resolver maps the trusted configuration plus the current page URL to an
   exhaustive five-slot arrangement; the centre and trailing slots are browser-owned in the type,
   not by convention.
7. With no `presentation.dock`, the dock is exactly `UX-024`'s three slots — Brand Hub, Tabs, More —
   unchanged in order, tags and callbacks.
8. With a valid projection, the dock is `site / site / Brand Hub / site / More`, and Tabs is
   reachable through the More menu.
9. A projected item dispatches through the existing `ActionResolver` path, emitting the original
   trusted `NavigationItem`; no raw URI, intent or generic command is introduced.
10. Projected items carry `NavMatcher`'s selected state, exposed semantically and never by colour
    alone.
11. Items successfully projected are absent from the drawer's visible rows, while remaining present
    in the validated model and reachable by route matching and dispatch.
12. An id that resolves but cannot be projected remains reachable in the drawer — nothing disappears
    from every surface.
13. A manifest cannot replace the Brand Hub or More, change slot count or order, or add a fourth
    site slot; a negative control proves each.
14. Projection is torn down by exact-origin departure, tab switch and configuration change through
    the existing guards, with no new lifecycle path.
15. Every slot keeps its 48 dp target and a browser-authored or validated-bounded accessible label;
    320 dp width and 200% font scale remain operable.
16. The Bloom fixture, its `.expected.json`, `BLOOM_FLOWERS_SHA256`, the served copy and that
    repository's `.sha256` move together, or three independent guards go red.
17. `./gradlew :app:compileDebugAndroidTestKotlin` compiles.
18. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Security/privacy:** the field references ids and nothing else. It cannot introduce an action,
  widen one, or reach a browser command. The sharpest risk is a projected site action rendering
  indistinguishably from a browser one in the same row — `HARDEN-002`'s impersonation surface at
  slot granularity — so the browser and site slots must not share an item type.
- **Reliability/fallback:** every failure — unknown id, unresolvable item, too many, duplicates —
  degrades to a dock that still works and a drawer that still lists the item. No failure may empty
  the dock or hide a valid destination from every surface.
- **Performance:** resolution is pure and runs with the existing chrome-model projection; no new
  network, storage or asset path.
- **Accessibility:** 48 dp targets, semantic selected state, accessible labels bounded by
  `SiteSkinLimits.MAX_LABEL_LENGTH`, operable at 320 dp and 200%, correct under RTL.

## Risks

- **The dock becoming a site-controlled surface by increments.** Today it is three ids; the natural
  next asks are a label override, an icon override, a fourth slot. The type must make each of those
  a visible widening rather than a small edit, which means the slot model is closed and the site
  never supplies anything but an id.
- **Two item types converging.** `UX-024` records that the browser cluster and the site cluster
  "look alike *by design*", and that the moment they shared an item type a manifest could publish
  something rendering identically to Back. The same trap is now one surface lower.
- **De-duplication deleting rather than hiding.** Criterion 11 is a *presentation* rule. If it is
  implemented by filtering the validated model, route matching and dispatch lose the item and
  criterion 12's fallback becomes unreachable.
- **The cross-repository artifact.** Bloom's manifest is pinned in five places across two
  repositories. `DEMO-001` records that transcribing a checksum is how four copies agree and the
  fifth does not.
- **Hosted evidence.** `CI-009`/`CI-010` photograph this dock. Their frames change, and this
  checkout has no emulator.

## Open questions

- Does the fallback dock keep Tabs in slot 2, or drop to two slots? Criterion 7 says keep `UX-024`'s
  three; research should confirm nothing else depends on that shape.
- Should a projected item be removed from the drawer's *navigation* group only, or from quick
  actions and menu too? The issue says "not duplicated"; research decides what "the same item"
  means when an id appears in more than one collection.
- Is `denrzv.github.io/apps/bloom/` — the URL in the issue — reachable at all? `DEMO-001` records
  that discovery is origin-rooted and a project *path* cannot host an integration. Research must
  check what the reference integration actually serves before the ticket plans a manifest change.
