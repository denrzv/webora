# NET-002 — Manifest cache

Status: PRD_READY

## Problem

Manifest discovery currently downloads and validates the same document on every navigation. This wastes network and battery, cannot revalidate with HTTP validators, and makes a previously integrated site unavailable during a transient offline period. A cache must improve resilience without ever allowing one origin's website-controlled chrome to appear on another origin.

## Scope

- Cache accepted manifest bytes under the exact canonical origin and declared schema version.
- Respect freshness for at most `min(Cache-Control max-age, 24 hours)`.
- Revalidate stale entries with `ETag` and `Last-Modified` and refresh metadata on `304 Not Modified`.
- Reuse a previously accepted entry when transport is unavailable, while never treating an HTTP rejection or newly invalid body as offline.
- Integrate cache lookup and update into the non-blocking manifest discovery lifecycle.

## Out of scope

Brand assets, cache persistence across app process death, eviction beyond bounded per-origin replacement, user cache controls, SiteSkin consent, and applying SiteSkin chrome are reserved for later tickets.

## User stories

- As a returning visitor, I can reuse a fresh validated manifest without another download.
- As a site owner, my HTTP caching validators are used when the manifest becomes stale.
- As a user with a transient network failure, I can reuse the last accepted manifest for that exact site.
- As a user navigating between sites, I never see cached configuration from a different canonical origin.

## Acceptance criteria

1. Accepted manifests are cached by exact canonical `origin + schemaVersion`, with the active version recorded independently for each origin.
2. A fresh entry avoids transport; freshness is capped at 24 hours and a missing, invalid, negative, or overflowing `max-age` makes the entry immediately stale.
3. A stale entry sends available `ETag` and `Last-Modified` validators; `304` refreshes its freshness metadata without replacing its validated bytes.
4. A transport-unavailable result may reuse the stale accepted entry for the same canonical origin, while HTTP errors and invalid replacement manifests return regular-browser behavior.
5. Cache writes occur only after `SiteSkinValidator` accepts the bytes and the declared schema version used in the key is taken from that trusted outcome.
6. Automated tests include negative controls proving distinct origins and schema versions cannot collide, the 24-hour ceiling is enforced, conditional validators are sent, and non-offline failures do not trigger stale reuse.
7. Discovery remains cancellable, ignores stale jobs, and never blocks WebView rendering.
8. `bash scripts/pre-commit-check.sh` passes.

## NFR

- Security/privacy: cache keys contain only canonical origins and versions; bodies and page URLs are never logged.
- Reliability/fallback: cache failure or invalid input degrades to regular browsing.
- Performance: cache access is bounded and does not add main-thread network work.
- Accessibility: no user-facing UI changes.

## Risks

- Ambiguous transport failures could incorrectly preserve maliciously removed or invalid manifests; stale reuse is therefore limited to explicit transport unavailability.
- HTTP date and cache directives are attacker-controlled and require overflow-safe parsing and a browser-owned lifetime ceiling.
