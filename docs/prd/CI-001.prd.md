# CI-001: Automated Android screenshots in GitHub Actions
Status: PRD_READY

## Context / Problem

The owner has no Android device and wants to see the GitHub-built Webora APK render the live Bloom
Flowers integration at `https://denrzv.github.io/`. The repository compiles instrumentation tests
but has no device job, so visible regressions and the deployed SiteSkin path currently require
someone else's local emulator.

## Goals

- Provide a manually triggered GitHub Actions workflow that runs Webora on a hardware-accelerated
  Android emulator.
- Exercise the live Bloom Flowers flow through first-use consent into integrated SiteSkin mode.
- Capture useful full-device screenshots and logcat and retain them as downloadable artifacts.
- Make failures diagnostic rather than silently uploading an empty artifact.

## Non-goals

- Pixel-perfect golden-image comparison or automatic visual approval.
- Running an emulator on every push or pull request and consuming private-repository minutes.
- Replacing the existing release workflow, Firebase Test Lab, or physical-device compatibility
  testing.
- Weakening HTTPS, origin binding, consent, or any browser-owned security affordance for automation.

## User stories

- As the owner without an Android device, I can select a Webora commit, run one workflow, and
  download screenshots showing Home, consent, and the integrated live site.
- As a reviewer, I can identify the commit, device/API and live origin represented by the artifact.
- As a maintainer, I get the instrumentation result and logcat when navigation or the live site
  fails instead of a misleading empty screenshot bundle.

## Acceptance criteria

1. A `workflow_dispatch` workflow builds the debug app and Android-test APK, starts a KVM-backed
   API 33 emulator, runs only the live screenshot instrumentation class, and uploads its output.
2. The instrumentation flow launches the real `MainActivity`, captures Home, opens the compiled
   Bloom Flowers suggestion, verifies the canonical `https://denrzv.github.io` consent heading,
   captures consent, selects Allow, waits for SiteSkin's browser-owned security indicator and bottom
   navigation, then captures the integrated screen.
3. Screenshots are full-device PNGs written to app-specific external storage with stable ordered
   names, and the workflow pulls them using `adb` before artifact upload.
4. The workflow always uploads screenshots, instrumentation output and logcat, fails if no PNG was
   produced, serializes emulator jobs, and has an explicit timeout.
5. The job is manual-only, uses least-privilege read permissions, pins third-party actions to
   immutable commit SHAs, and documents that it depends on the live GitHub Pages origin.
6. The existing release APK workflow remains unchanged; screenshots use the debuggable APK because
   the production release build requires signing credentials and the owner asked to inspect the app.
7. `bash scripts/pre-commit-check.sh` passes.

## NFR

- Security/privacy: the workflow grants no write permission, stores no credential, and captures only
  the public demo origin; the SiteSkin consent and browser-owned identity remain real.
- Reliability/fallback: bounded waits, one emulator at a time, `if: always()` diagnostics, and an
  explicit missing-PNG failure make environmental/live-site failures visible.
- Performance: manual execution and a single API/device matrix limit Actions-minute consumption.
- Accessibility: the automation locates browser-authored semantics/text and screenshots include the
  same security identity presented to a user.

## Risks

- GitHub Pages or manifest availability can make the live test fail independently of app code.
- Hosted emulator cold starts and WebView network loading can be slow or occasionally flaky.
- Screenshots are evidence, not assertions about every pixel or Android version.

## Open questions

None. API 33 matches the repository's prior emulator evidence and a manual workflow fits the
private-repository Actions budget.
