# CI-007: Canonical regular-browsing evidence
Status: PRD_READY

## Context / Problem
Webora's canonical hosted evidence currently stops at Home, first-use consent, and the Bloom Flowers
SiteSkin integration. Ordinary browsing is therefore accepted indirectly through implementation and
state tests even though it is the browser's default mode. Reviewers cannot see, in the same cold
journey, that leaving an integrated origin restores Webora's regular address/security identity and
navigation shell without retaining SiteSkin navigation or actions.

## Goals
- Add one canonical, uncontested frame of a deterministic non-integrated HTTPS page to the hosted
  screenshot journey.
- Exercise the integrated-to-regular handoff so the frame proves SiteSkin chrome was removed.
- Include the fourth frame in the human-facing contact sheet and job-summary accounting while
  retaining all existing canonical frames and separate diagnostics.
- Preserve the existing frame-ownership, rendered-page, clean-device, and live-integration gates.

## Non-goals
- Changing browser chrome, SiteSkin activation, consent, origin binding, or action resolution.
- Weakening or staging the screenshot acceptance policy to obtain a frame.
- Depending on volatile third-party page decoration for acceptance.
- Adding a second screenshot workflow or changing artifact retention and diagnostic separation.

## User stories
- As a reviewer, I can see Webora operating as an ordinary browser without inferring that experience
  from SiteSkin screenshots or unit tests.
- As a maintainer, I can tell from one cold journey that integrated chrome is removed when navigation
  crosses to a regular origin.
- As a developer diagnosing a hosted failure, I retain the same ownership, rendering, readiness, and
  per-frame diagnostics for the new frame as for the existing three.

## Acceptance criteria
1. A hosted cold run produces the existing three M7 canonical frames plus one clean regular-browsing
   frame reached by leaving the Bloom Flowers integrated origin for a deterministic HTTPS fixture.
2. The regular frame visibly contains Webora's address/security identity and regular navigation shell.
3. The regular frame contains neither SiteSkin bottom navigation nor SiteSkin quick actions, and the
   journey asserts the prior integrated state before crossing origins.
4. The fourth frame passes the unchanged Webora-window ownership and rendered-page acceptance gates,
   with diagnostics retained separately from canonical images.
5. The contact sheet and job summary account for four canonical frames without dropping or renaming
   the existing three.
6. `bash scripts/pre-commit-check.sh` passes.

## NFR
- Security/privacy: fixture content cannot supply evidence captions or alter browser-owned identity;
  assertions use the observed HTTPS origin and closed browser/SiteSkin semantics.
- Reliability/fallback: the ordinary page and its acceptance signal are deterministic and do not rely
  on mutable third-party decoration; any ownership or rendering ambiguity fails closed.
- Performance: retain the existing per-frame capture deadline and avoid adding emulator provisioning
  or an additional hosted job.
- Accessibility: verify the regular browser controls through their stable semantics while the saved
  full-device frame remains visual evidence rather than an accessibility substitute.

## Risks
- A public page can change or become unavailable. Prefer a repository-controlled, stable HTTPS asset
  already available on the Bloom deployment origin only if it is provably non-integrated; otherwise
  use a deterministic browser-controlled fixture compatible with the hosted WebView boundary.
- A same-origin destination could legitimately retain SiteSkin mode and fail to exercise the handoff.
  Research must choose a distinct origin and pin the transition assertion.
- New waiting or dismissal logic could manufacture a passing picture. Reuse the existing capture
  gates unchanged and wait only for app-observable destination state.

## Open questions
Research must decide the stable non-integrated HTTPS origin/fixture and the exact semantic evidence
that distinguishes restored regular chrome from integrated chrome before the file list is committed.
