# CI-003: Capture must wait for rendered content
Status: PRD_READY

## Context / Problem

`CI-002` established that a screenshot must show what a person would see, and enforced it against one
failure mode: something Webora does not own covering the screen. `DEVX-002` then made the frames easy
to review — and the first contact sheet it produced immediately exposed a second failure mode of the
same class.

In run **9** (`31570493622`, `c3ae985f`) the third canonical frame,
`03-siteskin-integrated.png`, shows the SiteSkin bottom navigation and the quick action over an
**empty page**, with no visible branded top bar. The job was green. Every assertion in
`LiveSiteScreenshotTest` passed.

They passed because they are all **semantics** assertions, and semantics exist before pixels:

```kotlin
waitUntilNodeExists(hasTestTag(SITESKIN_SECURITY_TAG))
waitUntilNodeExists(hasTestTag(SITESKIN_BOTTOM_NAV_TAG))
composeRule.onNodeWithTag(SITESKIN_SECURITY_TAG).assertIsDisplayed()
…
composeRule.waitForIdle()
```

`assertIsDisplayed()` asserts a node exists with non-zero bounds inside the window. It is not a claim
about drawn pixels. `waitForIdle()` waits for Compose, and the page is a `WebView` — an Android view
whose paint Compose does not track. So the capture fires as soon as the chrome's semantics tree is
populated, which can be before the renderer has drawn anything.

**This is `CI-002`'s failure repeated through a different mechanism.** There, three frames passed
every assertion while covered by an ANR dialog. Here, a frame passes every assertion while showing an
empty page. Both are a green job with worthless evidence. `CI-002` taught the harness to refuse a
screen Webora does not *own*; nothing yet teaches it to wait for a screen that has been *drawn*.

**Working hypothesis for why it surfaced now, to be confirmed in research rather than assumed:** in
run 5 the build ran *inside* the emulator step for 8m39s, so everything downstream was slow and the
page had long since painted by capture time. `CI-002` moved the build before boot, which made the
journey fast enough to outrun the renderer. The fix would then have exposed a pre-existing race
rather than caused it.

One observation is deliberately **not** explained yet: `SITESKIN_SECURITY_TAG` passes
`assertIsDisplayed()`, and the top bar region still renders blank. Whether the bar is absent, drawn
empty, or simply not yet painted changes the fix, and a 360 px contact-sheet tile cannot settle it.
Research must look at the full-resolution frame before the plan commits to a mechanism.

## Goals

- A canonical frame is captured only once the content it is evidence *of* has actually been drawn.
- The check is on **pixels**, not on the semantics tree — the same technique `DEVX-002` used to catch
  a font-less host writing structurally perfect PNGs with invisible labels.
- A page that genuinely never renders makes the run **red**, with a diagnostic naming what was
  observed. It must not silently produce a blank frame, and must not be papered over with a longer
  fixed wait.
- The existing `CI-002` guarantees stay exactly as they are.

## Non-goals

- Changing which frames are captured, their names, or the journey's steps.
- Any change to `ScreenEvidencePolicy`, the readiness gate, or the prebuilt-APK precondition. This
  ticket adds a condition; it relaxes none.
- Changing the artifact split, the contact sheet, or the summary (`DEVX-002`, shipped).
- Fixing whatever the integrated chrome's own visual defects turn out to be. If research finds the
  top bar is genuinely missing rather than unpainted, that is a **product** defect and belongs to a
  SiteSkin ticket — this one is about the harness photographing too early.
- Removing the SiteSkin inspector overlay (`DEVX-003`).
- Any pixel-level golden-image comparison. Evidence review stays human.

## User stories

- As a reviewer, when a canonical frame reaches me, the page is drawn — so what I am judging is the
  integration, not the harness's timing.
- As someone diagnosing a red run, a capture refused for an unrendered page tells me what it measured
  and what it expected, in the diagnostics artifact, rather than leaving me to compare screenshots.
- As a maintainer, I can trust that a green screenshot job means the frames are worth looking at, in
  the same way `CI-002` made it mean nothing was covering them.

## Acceptance criteria

1. Before each canonical capture, the harness verifies that the region the frame exists to show has
   actually been drawn, by examining pixels rather than the semantics tree.
2. The check has a bounded deadline. A page that never renders fails the run; it never yields a
   captured frame.
3. A refusal writes a diagnostic to the connected-test additional output — what was measured, what
   was expected, and for which frame — reaching the diagnostics artifact alongside `CI-002`'s
   `focus-*`, `interference-*` and `window-*` files.
4. The decision logic is a pure function over values, exercised by JVM tests that run in
   `bash scripts/pre-commit-check.sh` with no emulator, following `ScreenEvidencePolicy`'s precedent.
   A rule reachable only from `androidTest` is not acceptable: the gate never compiles that source
   set.
5. The rule carries a negative control — a frame that is blank where content is required must fail
   the check, and the test proving it must fail when the check is removed.
6. No `CI-002` behaviour changes: the prebuilt-APK precondition, the readiness gate, the focus
   classification and its one permitted dismissal all keep their current semantics and their tests.
7. `03-siteskin-integrated.png` from a hosted run shows the rendered page, verified by a human
   opening it. Recorded as instrumented evidence, not promoted to a gate claim.
8. Whatever the blank top bar turns out to be is stated explicitly in the QA report — harness timing
   or product defect — and if it is a product defect it is filed as its own ticket rather than fixed
   here.
9. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Security/privacy:** no manifest, page, or website-controlled value may influence the decision, by
  the same rule `CI-002` set for focus classification — the check reads only pixels the harness
  itself captured and bounds the harness supplies. No new network access, no new permission, and no
  change to what is captured or where it is stored.
- **Reliability/fallback:** the check must not become a flake generator. A bounded poll on an
  observed condition, never a fixed `sleep`, per `CI-002`'s readiness precedent; and its samples must
  be recorded so a failure explains itself instead of requiring a rerun to understand.
- **Performance:** polling happens inside the emulator step, where `CI-002` established that runner
  work starves `system_server`. The check must be cheap — sampling an already-captured bitmap, not
  compositing or writing files per sample — and must not extend the journey materially on a healthy
  run.
- **Accessibility:** N/A to the app. No Compose surface, string resource or semantics node changes.
  The harness gains a check; the browser is untouched.

## Risks

- **Asserting the wrong region.** A naive "is the screen non-blank" test passes on a page that is
  legitimately white. The check must target the region the frame exists to prove, and its threshold
  must be justified rather than tuned until green.
- **Turning a product defect into a harness workaround.** If the top bar is genuinely absent, waiting
  longer will never show it, and a check tuned until it passes would hide a real bug — the precise
  mistake `CI-002` refused when it declined an `else` branch that dismisses whatever is in the way.
- **Flake.** Too strict a threshold on a slow emulator turns a working pipeline red intermittently,
  which erodes trust in the evidence as surely as a blank frame does.
- **Scope drift into SiteSkin rendering.** The temptation to "fix the frame" by touching integrated
  chrome. This ticket changes the harness only.

## Open questions

To be closed by `/researcher`, before the plan commits to a mechanism:

1. Is the top bar absent, drawn blank, or merely unpainted at capture time? The full-resolution
   `03-siteskin-integrated.png` from run 9 settles it; the contact-sheet tile does not.
2. Does the `WebView` expose a signal the test can wait on — progress, `onPageFinished`, or a
   test-only tag — or must the check be purely pixel-based?
3. Is the timing hypothesis right? Comparing run 5's frame (page rendered, slow journey) with run 9's
   (blank, fast journey) is the available evidence.
