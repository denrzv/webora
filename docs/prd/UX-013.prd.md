# UX-013: Expressive SiteSkin chrome primitives & ownership model
Status: PRD_READY

## Context / Problem

The current integrated SiteSkin experience is secure and functional, but it reads as a recoloured
Material shell around a WebView. M9 needs a deliberately native-like, branded composition based on
the Bloom Flowers direction: curved integrated chrome and a floating browser dock. Before UX-014
and UX-015 build those surfaces, Webora needs reusable browser-owned primitives and an explicit
projection boundary that prevents richer styling from widening manifest control.

## Goals

- Define reusable curved and floating Compose primitives whose geometry, layout order, elevation,
  insets, and motion are compiled into Webora.
- Define a small presentation projection from an already-trusted `SiteSkinConfiguration`, limited
  to existing normalized brand roles.
- Provide deterministic light/dark projections and usable compact-width, large-text, and
  reduced-motion behavior for downstream integrated chrome.
- Pin the ownership boundary with executable negative controls before UX-014 and UX-015 consume it.

## Non-goals

- Replacing the current integrated top bar or bottom navigation; UX-014 and UX-015 own integration.
- Adding a manifest appearance preset, dimensions, paths, layout order, motion values, remote
  SVG/CSS, Compose definitions, or executable UI.
- Changing discovery, parsing, validation, consent, origin activation, action dispatch, or asset
  acceptance.
- Changing regular browsing chrome or Android system navigation.

## User stories

- As a person using an integrated site, I want branded chrome that feels intentionally composed in
  light and dark themes without losing the distinction between site and browser controls.
- As a person using large text or a compact device, I want the expressive chrome foundations to
  remain readable, reachable, and unclipped.
- As a security reviewer, I want source and behavioral evidence that a manifest cannot control
  geometry, browser identity, browser navigation, motion, or layout order.
- As a Webora developer, I want UX-014 and UX-015 to share one typed projection and one set of
  primitives rather than inventing separate trust seams.

## Acceptance criteria

1. A pure, typed presentation projection consumes only an already-trusted SiteSkin configuration
   and exposes no raw manifest DTO, arbitrary dimension, path, layout-order, animation, remote
   resource, or callback field.
2. Site-influenceable presentation values are restricted to the existing validated/normalized
   SiteSkin brand roles; browser geometry, elevation, insets, motion, controls, and security
   identity remain compiled browser values.
3. Reusable curved-header and floating-dock primitives provide deterministic browser-owned geometry
   suitable for UX-014 and UX-015 without yet replacing the shipped integrated surfaces.
4. The primitives handle 320 dp width, 200% font scale, light and dark theme projection, system
   insets, and reduced-motion mode without clipping required content or shrinking interactive
   targets below 48 dp.
5. Motion is decorative, bounded, and replaceable with an immediate state change when reduced
   motion is requested; it never delays security identity, origin teardown, or input availability.
6. Automated negative controls fail if website-controlled data gains a path into arbitrary
   geometry, browser-owned palette/tokens, browser command order, security identity, or motion.
7. Existing regular and integrated chrome behavior remains unchanged until the downstream UX-014
   and UX-015 integration tickets.
8. `bash scripts/pre-commit-check.sh` passes.

## NFR

- Security/privacy: Preserve exact-origin activation and ADR-006 identity ownership; introduce no
  new remote input, logging, persistence, telemetry, or native capability.
- Reliability/fallback: Projection is total for every trusted configuration and expressive motion
  has a deterministic no-motion path.
- Performance: Primitives avoid bitmap/vector generation, reflection, remote resources, and
  allocation-heavy work during recomposition.
- Accessibility: Required content wraps or reflows at 200% font scale, interactive targets remain
  at least 48 dp, semantics keep browser and site ownership distinguishable, and meaning does not
  depend on color or motion.

## Risks

- A generic theming abstraction could accidentally become a second, less constrained manifest
  surface; keep the projection closed and app-owned.
- Curved clipping could remove text or semantics at compact widths; test resolved geometry and
  representative Compose layouts rather than token provenance alone.
- Sharing primitives could blur browser/site ownership; APIs must accept content in explicitly
  named slots while browser controls and identity remain outside site-projected models.
- Animation could create transiently absent controls or flaky evidence; keep it optional,
  deterministic, and non-blocking.

## Open questions

- The exact primitive API, curve construction, projection role names, and motion mechanism require
  repository research before the implementation plan commits to files.
