# NET-003 — Brand asset pipeline

Status: PRD_READY

## Context / Problem

A validated SiteSkin configuration may name a logo, but the app has no bounded asset transport or
decode pipeline. Loading that remote input directly in UI code would let a site choose an
untrusted origin, content type, payload size, decode cost, or failure mode. The browser needs a
closed, cancellable pipeline that can provide a safe bitmap or an immediate browser-generated
monogram without delaying page or chrome rendering.

## Goals

- Fetch a validated branding logo only from the manifest's exact canonical HTTPS origin.
- Accept only PNG and WebP after checking response metadata and decoded content; refuse SVG and all
  other formats.
- Bound redirects, transfer bytes, decoded dimensions, and decode work before an image reaches UI.
- Perform transport and decoding off the main thread and support cancellation when navigation is
  superseded or the composition is disposed.
- Return a browser-generated monogram fallback for missing, rejected, malformed, oversized,
  unavailable, or cancelled asset work.

## Non-goals

Rendering the SiteSkin top bar, applying dynamic theme colours, persistent on-disk asset caching,
animated images, SVG support, cross-origin/CDN assets, consent, and SiteSkin mode transitions are
reserved for later tickets.

## User stories

- As a user, I see only bounded, same-origin site artwork in browser chrome.
- As a user on a site with a broken or unsafe logo, I receive a stable monogram rather than a crash,
  blank identity slot, or stalled browser.
- As a site owner, I can publish a PNG or WebP logo without blocking the page or browser chrome.

## Acceptance criteria

1. Asset requests accept only canonical same-origin HTTPS URLs and follow at most two redirects,
   each remaining on that exact origin; subdomains and origin changes are rejected.
2. Only `image/png` and `image/webp` responses whose bytes decode as an allowed format are accepted;
   SVG, mismatched, absent, ambiguous, or unsupported media types are refused.
3. A browser-owned byte ceiling aborts an oversized response without consuming an unbounded body,
   and browser-owned width, height, and decoded-pixel ceilings reject oversized images before a
   full bitmap allocation.
4. Network and decode work run off the main thread, remain cancellable, and a superseded request
   cannot publish an asset for a later navigation.
5. Every missing logo and every fetch, redirect, type, size, decode, or cancellation failure yields
   a deterministic browser-generated monogram result without crashing or blocking chrome.
6. Accepted bitmap data and fallback content expose no general-purpose remote URI or executable
   content seam to later UI code.
7. Automated tests include negative controls for cross-origin and subdomain redirects, SVG and
   content-type spoofing, transfer and dimension limits, cancellation/stale results, and fallback.
8. `bash scripts/pre-commit-check.sh` passes.

## NFR

- Security/privacy: asset URLs and bodies are never logged; remote input cannot select a decoder,
  bypass origin policy, or become executable content.
- Reliability/fallback: all failures are closed outcomes and retain a usable monogram identity.
- Performance: bounded streaming and metadata-first decode prevent unbounded memory use; no network
  or image decoding occurs on the main thread.
- Accessibility: the bitmap is decorative identity only; later UI owns a browser-derived content
  description and must not depend on remote metadata.

## Risks

- Android decoders may recognize content independently of HTTP metadata, so both declared MIME type
  and decoded format need enforcement.
- Image dimension probing can still allocate or read too much if the decoder seam is chosen poorly;
  research must identify an API that bounds work before full decode.
- A reusable image loader could silently enable cross-origin redirects, disk persistence, or format
  support outside this contract; the pipeline therefore needs an explicit browser-owned boundary.

## Open questions

- Which Android decode API provides the smallest testable seam for format and dimension checks?
- What byte, per-axis, and decoded-pixel ceilings balance branded-logo fidelity with bounded memory?
