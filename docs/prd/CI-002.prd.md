# CI-002: Deterministic clean Android screenshot capture
Status: PRD_READY

## Context / Problem

`CI-001` proved the journey: the hosted Pixel 6 / API 33 emulator boots, `LiveSiteScreenshotTest`
drives Home → consent → integrated SiteSkin mode against the live `https://denrzv.github.io`
deployment, and three PNGs come back. The instrumentation passed. The **evidence did not**: the
canonical frames were covered by Android's `System UI isn't responding` dialog.

That gap is the ticket. A Compose assertion answers "is the right node in the tree"; a screenshot is
supposed to answer "is this what a person sees". A run can satisfy the first and fail the second, and
today nothing in the pipeline can tell the two apart — the workflow reports green and uploads
contaminated evidence.

Two specific weaknesses produced it:

- **`sys.boot_completed=1` is treated as visual readiness.** It means the boot broadcast fired, not
  that `system_server` has stopped being saturated. The emulator-runner's `script:` step then starts
  a full Gradle build — Kotlin compilation, D8, packaging — on the same 4-vCPU runner that is still
  finishing boot. The System UI ANR is the predictable result of that contention, not a mystery.
- **There is no capture-time check that Webora owns the screen.** `captureDeviceScreenshot` calls
  `waitForIdle()` and then screenshots whatever the display holds. Compose idleness says nothing
  about a system dialog composited above the activity.

The fix has a sharp edge, which is why this is a ticket and not a patch: the obvious remedy — dismiss
whatever dialog is in the way — would also dismiss a Webora crash dialog, an ANR in Webora itself, a
permission prompt or a TLS warning. That would turn the screenshot job from evidence into
decoration, and it would do so silently.

## Goals

- Remove the known cause of System UI contamination rather than papering over its symptom.
- Replace implicit readiness with an **observable, bounded, diagnosed** post-boot gate.
- Verify at every capture point that the application under test actually owns the focused window.
- Where a system-owned ANR dialog can still appear, dismiss **only** that one, by an allow-list of a
  single package, preferring `Wait` over restarting System UI, and record what was dismissed.
- Make any other interference — including anything owned by Webora — fail the run loudly.

## Non-goals

- Golden-image comparison or automated visual approval. Screenshots stay human-reviewed evidence.
- Artifact packaging, contact sheets and job-summary presentation — `DEVX-002` owns those.
- Removing the SiteSkin Inspector overlay from canonical frames — `DEVX-003` owns that.
- Pixel-level determinism of the status bar (clock, battery, signal glyphs). `BACKLOG.md`'s
  acceptance defines this ticket's determinism as *readiness* determinism — an observable condition
  instead of a chosen delay. System UI demo mode is a reasonable later ticket and is deliberately not
  smuggled in here, where it would add a second System UI interaction to a ticket about System UI
  interference.
- Running the emulator on push or pull request. The workflow stays `workflow_dispatch`.
- Any change to production `src/main` behaviour, the trust boundary, or the live-origin nature of the
  journey.

## User stories

- As the owner reviewing a design change, I download the screenshots and see Webora, not an OS
  dialog on top of Webora.
- As a maintainer, when a run *is* red I can tell from the artifact whether the emulator misbehaved
  or Webora did, without re-running anything.
- As a reviewer of this pipeline, I can point at the line that decides what may be dismissed and see
  that it is an allow-list of one system package, not a "close whatever is on screen" loop.

## Acceptance criteria

1. The debug APK and the Android-test APK are built **before** the emulator is launched, so no
   compilation competes with a booting `system_server`; the in-emulator step installs and runs, and
   fails if either APK is missing rather than silently rebuilding.
2. A post-boot readiness gate polls observable device conditions — boot completion, boot animation
   exit, package-manager responsiveness and a focused window existing at all — requires them to hold
   for a **settle window of consecutive samples**, is bounded by an explicit deadline, and writes
   every sample it observed into the run artifact. It records the focused window's title without
   classifying it: deciding what a window *is* belongs to one owner (criteria 5 and 6), and a second
   copy of that knowledge in shell would be free to drift.
3. The readiness verdict is computed by a function that can be exercised without a device, and is
   covered by tests including a **negative control** in which a recorded contaminated sample is
   wrongly accepted once the guard is removed.
4. Before each canonical capture, the test asserts that the focused window belongs to the
   application under test, read from the device rather than assumed.
5. When the focused window is the known System UI application-error dialog, and only then, the test
   presses `Wait`, records the dismissal with the window it saw, and re-verifies focus before
   capturing. Bounded attempts; exhaustion fails the test.
6. Any other window over the app — including an application-error dialog owned by Webora — fails the
   test with the observed window description in the failure message. The dismissal decision is an
   allow-list of exactly one package, and is unit-tested with a Webora-owned dialog as its negative
   control.
7. A fresh cold hosted run returns `01-home.png`, `02-siteskin-consent.png` and
   `03-siteskin-integrated.png` with no `System UI isn't responding` overlay, and the readiness and
   interference diagnostics are present in the artifact whether the run passed or failed.
8. `docs/SCREENSHOTS.md` states what the pipeline may dismiss, what it will never dismiss, and where
   to look when a run is red.
9. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Security/privacy:** no production source changes, no new permission, no workflow write scope, no
  secret. Consent is still granted by clicking the browser-owned `Allow`, never by writing preference
  storage. Any new third-party action stays pinned to an immutable commit SHA.
- **Reliability/fallback:** every wait is bounded and every bound is diagnosed. A failure of the gate
  itself must fail the job, never skip the capture.
- **Performance:** pre-building outside the emulator step reduces wall-clock contention; the job
  keeps its 40-minute timeout and remains manual-only.
- **Accessibility:** the journey continues to locate browser-authored semantics and `strings.xml`
  copy; no test-only affordance is added to production UI to make automation easier.

## Risks

- **The dismissal path is the dangerous one.** Written loosely it hides exactly the failures the
  screenshots exist to reveal. Mitigated by the single-package allow-list, the positive focus
  assertion, and a negative control that fails when the allow-list is widened.
- **The System UI ANR may not reproduce once contention is removed,** leaving the dismissal path
  unexercised in the hosted run. That is a good outcome for the product and a weak one for evidence;
  the unit tests must therefore carry the proof of the decision, not the hosted run.
- **`dumpsys` output is a device-format dependency.** A parser that silently matches nothing would
  turn the focus assertion into a no-op. The gate must fail closed when it cannot identify the
  focused window at all, and the raw dump must reach the artifact so the recorded fixtures can be
  reconciled with a real device.
- The live origin remains a shared dependency with `CI-001`: a GitHub Pages outage still fails the
  run, correctly and visibly.

## Open questions

None blocking. Whether the System UI ANR persists after the contention fix is answered by running
the workflow, and the ticket is designed to be correct either way.
