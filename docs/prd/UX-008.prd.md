# UX-008: Browser navigation controls in integrated mode
Status: PRD_READY

## Context / Problem
When SiteSkin activates, its branded top bar replaces the regular address bar and its site navigation
occupies the bottom chrome. The resulting integrated surface has no visible browser back control,
leaving system back as the only route through WebView history. This gap became visible in CI-003's
first trustworthy rendered screenshot; it was never an intentional SiteSkin capability.
## Goals
- Give users a visible, reachable browser-owned back affordance in integrated mode.
- Place browser navigation without displacing the SiteSkin security identity row or making browser
  controls compete with the site's primary navigation.
- Preserve the existing controller/history contract and browser-owned visual/accessibility system.
## Non-goals
- Adding new browser capabilities, manifest fields, action types, or history semantics.
- Letting manifests hide, label, reorder, recolour, or otherwise configure browser navigation.
- Redesigning SiteSkin top-bar identity, site navigation, quick actions, or regular-mode chrome.
- Treating forward or reload controls as required scope when the observed accessibility gap is back.
## User stories
- As a user in an integrated site, I can visibly discover and activate Back without relying on a
  system gesture.
- As a keyboard, switch, or TalkBack user, I can reach a correctly labelled browser Back control.
- As a user, I continue to see the committed site's browser-authored domain and TLS state in their
  established identity row.
## Acceptance criteria
1. Integrated mode renders a visible browser-owned Back affordance that invokes the existing browser
   back callback and reflects whether back navigation is available.
2. The control has a stable browser-authored accessibility label and satisfies the repository's
   minimum touch-target convention.
3. The SiteSkin security identity row retains its position and browser-authored semantics contract.
4. No manifest value can suppress, relabel, reorder, or restyle the Back affordance; a negative
   control proves the boundary.
5. SiteSkin bottom navigation remains the primary integrated navigation and no new manifest field or
   native capability is introduced.
6. `bash scripts/pre-commit-check.sh` passes.
## NFR
- Security/privacy: navigation remains browser-owned and consumes no untrusted manifest value.
- Reliability/fallback: unavailable history disables the affordance rather than invoking a false
  action; regular mode and system-back behaviour remain unchanged.
- Performance: the control adds no I/O, persistence, or manifest processing.
- Accessibility: expose a stable role/label/state and preserve at least the 48 dp touch target.
## Risks
- Placing the control inside manifest-themed chrome could visually imply site ownership or permit
  inherited SiteSkin colours to restyle it.
- Adding a second bottom bar could crowd the site's navigation and shrink content unnecessarily.
- Tests that use only a friendly manifest may fail to prove independence from manifest values.
## Open questions
- Which existing integrated surface can host Back while remaining visibly browser-owned and leaving
  the security identity and site navigation hierarchy intact?
- Should the affordance remain visible-but-disabled at the root, matching regular chrome, or be
  hidden when unavailable? Research and surrounding conventions must decide before planning.
