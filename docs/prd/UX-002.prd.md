# UX-002: Design system foundations
Status: PRD_READY

## Context / Problem
`UX-001` decided what Webora should look like. `ADR-013` records the decision — **Direction A,
"Soft instrument", unamended** — with its palette, geometry, type scale and icon budget written down
as numbers. Nothing has been built from it. `MainActivity.kt:38` still composes a bare
`MaterialTheme {}`, so every browser-owned surface still renders in Material 3's default baseline
purple, in the default type scale, light-only regardless of the system setting.

The inversion `docs/design/AUDIT.md` §1.6 named is therefore still true: a site that publishes a
manifest gets `SiteSkinColorScheme` — six roles, a dark projection, and a WCAG guard that runs
before any colour reaches the screen — and the browser rendering it gets nothing.

This ticket builds the foundation and only the foundation. `UX-003` rebuilds the chrome against it
and `UX-004` does Home, onboarding and settings; `UX-005` reuses its icon mechanism for the
integrated SiteSkin chrome, which is why `DEVELOPER_PLAN.md` orders that ticket behind this one —
"introducing a second ad-hoc icon mechanism would recreate the inconsistency M6 is meant to remove."

Two constraints make this more than a styling ticket.

**`C2` stops being free the moment this lands.** `ADR-013` states the rule that survives whichever
direction won: Webora's palette, typography and shape scale are compiled into the app, with no path
from a manifest value into them. That invariant is currently maintained only by the accident that
there is no browser palette at all. Creating one is exactly when the accident stops protecting it,
so the test asserting it belongs in this ticket rather than after it — `ADR-013`'s consequences
section hands it over explicitly.

**`C6` says the icons do not exist.** `res/` contains no `drawable/` directory; the only icons in
the product are the Unicode glyphs at `SiteSkinChrome.kt:135` (`⌂ ▦ ▣ ● ☎`). No browser-chrome
control can be icon-only until something supplies the assets, and `C3` means the control wrapper has
to land in `BrowserAccessibility.kt` or the build turns red.

## Goals
1. Compile `ADR-013`'s Direction A tokens — colour in both themes, typography, shape, spacing — into
   a browser-owned `WeboraTheme` that replaces the bare `MaterialTheme {}`, so no browser surface
   renders a Material default.
2. Prove the browser palette against WCAG in a JVM test, using the same `contrastRatio()` the
   SiteSkin projection is already guarded by, lifted somewhere both palettes reach.
3. Prove `C2`: no manifest value can reach a browser token, with a negative control showing the test
   fails when the separation is removed.
4. Supply the bounded browser-owned vector icon set Direction A draws, as `res/drawable` vectors with
   no new dependency, plus the `WeboraIconButton` that `C3` requires an icon-only control to use.
5. Make the system bars follow the same setting the Compose palette does, so `C7`'s edge-to-edge
   regions are not the one surface still light-only.

## Non-goals
- Restyling any surface. `BrowserScreen`, `HomeScreen`, `OnboardingScreen`, `PrivacySettingsScreen`
  and `BrowserErrorPage` keep their current structure; `UX-003` and `UX-004` own the rebuild. The
  only visual change this ticket makes is the one that follows from the theme itself.
- The identity chip and the address pill. `ADR-013`'s `C1` mechanism is `UX-003`'s deliverable; this
  ticket supplies the colour pairs it will consume and nothing else.
- The SiteSkin integrated chrome and its placeholder glyphs. `UX-005` owns that surface and will add
  its semantic icons to the same `res/drawable` mechanism this ticket establishes.
- Adding `material-icons-extended` or any other icon dependency. `C6` rejected it: large, and
  deprecated upstream.
- Touching `SiteSkinTheme`'s projection behaviour. Its colours, its guard and its dark derivation
  stay exactly as they are; only the shared contrast helper moves.

## User stories
- As the implementer of `UX-003`, I read the token layer and find every value `ADR-013` specifies —
  including the identity-chip and TLS pairs from the measured table — without going back to the ADR
  to translate hex strings.
- As the implementer of `UX-005`, I add a semantic icon by dropping a vector into `res/drawable` and
  naming it in `strings.xml`, because that mechanism already exists and is already gated.
- As a reviewer, I can see a test that fails if someone routes a manifest colour into a browser
  token, so `C2` is enforced rather than asserted.
- As a user who has selected a dark system theme — often for accessibility reasons — I get dark
  browser chrome and dark system bars, not a light browser with a dark status bar over it.
- As a user relying on high contrast, every browser-owned colour pair has been measured at 4.5:1 for
  body text and 3:1 for non-text before it reaches me.

## Acceptance criteria
1. `WeboraTheme` supplies a compiled `ColorScheme`, `Typography` and `Shapes` to `MaterialTheme`, and
   `MainActivity` composes it instead of the bare `MaterialTheme {}`. No browser-owned surface reads
   a Material default palette or type scale.
2. The light and dark colour values are `ADR-013`'s Direction A palette, including the identity-chip
   text, TLS-secure and TLS-not-secure pairs from its measured table.
3. `WeboraTheme` selects its projection from `isSystemInDarkTheme()`, and `res/values-night/themes.xml`
   exists so the platform theme behind the system bars follows the same setting.
4. A JVM test asserts every browser-owned colour pair at 4.5:1 for body text and 3:1 for non-text UI,
   using the shared `contrastRatio()` — which is lifted out of `SiteSkinTheme.kt` to a location both
   palettes reach, with `SiteSkinThemeTest` still passing against the moved function.
5. A JVM test proves no manifest value can reach a browser token: a `SiteSkinConfiguration` whose
   branding requests distinctive colours produces a `SiteSkinColorScheme` carrying them and leaves
   every `WeboraTheme` token unchanged. A negative control is recorded in the tasklist — the test
   fails when a manifest value is wired into a browser token.
6. The vector drawables Direction A draws exist in `app/src/main/res/drawable/`, added as vector XML
   with no new Gradle dependency, and each has a `strings.xml` accessible name or is marked
   decorative.
7. `WeboraIconButton` is declared in `BrowserAccessibility.kt` — the file declaring
   `fun WeboraButton(` — takes a non-optional accessible name, and applies `browserTouchTarget()`.
   `BrowserSurfaceConventionsTest` stays green, including its `RAW_BUTTON_IMPORT` rule.
8. `docs/accessibility/CONFORMANCE.md` records the browser-palette contrast guarantee with its code
   and its test.
9. `bash scripts/pre-commit-check.sh` passes.

## NFR
- **Security/privacy:** `C2` is the security property of this ticket. `SiteSkinColorScheme` remains
  the entire website-influenceable colour surface; `WeboraTheme` is separately compiled and a
  manifest cannot read, reach or influence it. The identity-chip pairs are browser tokens
  specifically because `ADR-006` makes the domain and TLS state browser-owned — a manifest-derived
  colour on that chip would be a path from a website into Webora's own identity presentation.
- **Reliability/fallback:** none — no network, no parsing, no remote input. A theme cannot fail
  gracefully because it cannot fail; the values are compiled constants.
- **Performance:** the token layer is compiled constants and immutable data. No allocation per
  recomposition beyond what `MaterialTheme` already does, and no decode, parse or IO on the main
  thread.
- **Accessibility:** `A11Y-001` holds unchanged. 48 dp minimum targets — `WeboraIconButton` is the
  new way to violate that and so routes through `browserTouchTarget()` like its siblings; 4.5:1 body
  and 3:1 non-text, now asserted for the browser palette as well as the SiteSkin one; no meaning
  carried by colour alone; a type scale that survives 200% font scale. `C4` still holds: an icon
  without a `strings.xml` name fails the build rather than review.

## Risks
- **The palette is transcribed rather than measured.** `ADR-013`'s table gives ratios to two decimal
  places; retyping a hex digit yields a plausible colour that quietly misses 4.5:1. The contrast test
  is what catches it, which is why it asserts every pair rather than a sample.
- **`C2` tested as a tautology.** A test that compares two separately declared constants passes
  whether or not a path exists between them. It has to exercise the real projection with real
  manifest input, and it needs the negative control to prove it can fail.
- **The theme changes surfaces this ticket does not own.** Supplying a palette necessarily repaints
  every screen — that is the point — but a token whose value only looks right against `UX-003`'s
  rebuilt chrome can look wrong against today's. The mitigation is to keep the values `ADR-013`'s
  rather than tuning them against unrebuilt surfaces, and to leave structure alone.
- **`RAW_BUTTON_IMPORT` has a sharp edge.** A `WeboraIconButton` in a new file turns the build red;
  it belongs in `BrowserAccessibility.kt`. Named here because the failure looks like an unrelated
  convention test breaking.
- **The icon set grows past its budget.** `C6` bounds it deliberately: an icon a direction needs is
  an icon someone has to draw and check at 200% font scale. The set is the one Direction A draws,
  and additions belong to the ticket that needs them.

## Open questions
None. `ADR-013` decided the direction, the palette, the geometry and the type scale; `C3`–`C7` decide
where the wrapper lands, how icons are sourced and what the tests must assert.

One judgement is recorded here rather than left implicit: the icon set is the **ten** glyphs
Direction A actually draws across its four surfaces — back, forward, reload, home, menu, more, lock,
close, search and warning — not the eight `C6` listed illustratively. `C6`'s list was written before
a direction was chosen and names `stop`, which Direction A does not draw; the drawn set adds
`search`, `more` and `warning`. Deriving the set from the selected direction rather than from the
pre-selection estimate is the point of having selected one.
