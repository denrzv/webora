# UX-015: Branded browser dock & SiteSkin navigation hub
Status: PRD_READY

## Context / Problem

Integrated mode still dedicates its persistent bottom surface to website navigation and places
browser-owned Tabs and More inside a secondary menu. M9 requires a clearer ownership hierarchy: a
fixed floating dock for essential browser commands, with the already-validated SiteSkin navigation
and quick actions moved into a separately attributed native hub. This must be a placement change,
not a wider manifest capability or a second action-dispatch path.

## Goals

- Fill the UX-013 floating primitive with fixed Back, Forward, brand-hub, Tabs, and More controls.
- Move trusted, bounded SiteSkin navigation and quick actions into a branded hub while preserving
  active-route matching and typed item dispatch.
- Preserve exact-origin activation, active-tab isolation, browser-owned callbacks, and immediate
  teardown when the active projection leaves protected integrated mode.
- Keep all controls usable at compact width, large font scale, light/dark theme, and reduced motion.

## Non-goals

- Adding or changing SiteSkin schema fields, action types, validation, consent, or discovery.
- Allowing a manifest to alter dock command labels, icons, order, enabled state, geometry, or
  callbacks, or to imitate browser commands inside the hub.
- Changing regular/Home chrome, Android system navigation, or the UX-014 identity header.
- Adding new navigation destinations or generic URI/intent dispatch.

## User stories

- As a browser user, I can always reach Back, Forward, Tabs, and More from integrated mode.
- As a SiteSkin user, I can open one clearly branded hub to reach the site's validated navigation
  and quick actions without confusing them with browser commands.
- As a keyboard, switch, or screen-reader user, I can identify and operate every dock and hub
  control at compact width and large text.
- As a security reviewer, I can prove that tab/origin changes remove stale site content and that a
  manifest cannot control the fixed browser dock.

## Acceptance criteria

1. Protected integrated mode renders a floating dock in the fixed order Back, Forward, brand hub,
   Tabs, More; each control has a browser-authored label/icon, at least a 48 dp target, and an
   explicit browser/controller callback.
2. Back and Forward enabled states come only from the active tab's observed WebView history; Tabs
   and More reuse the existing browser-owned surfaces and the dock remains present regardless of
   manifest navigation/action count.
3. The central brand control opens a separately attributed SiteSkin hub containing only the active
   trusted configuration's bounded navigation and quick-action items, preserving active-route
   semantics and typed `NavigationItem`/`NormalizedAction` dispatch.
4. The hub preserves a separately labelled browser-owned section and cannot be used to suppress,
   replace, reorder, restyle, or dispatch any fixed dock command.
5. Leaving the exact origin, changing the selected tab, or otherwise leaving protected integrated
   projection dismisses/invalidates the hub and removes all site-branded dock/hub content before
   regular or Home chrome is rendered; stale callbacks cannot target a newly active tab.
6. At 320 dp and 200% font scale, in light and dark themes and reduced-motion mode, all five dock
   controls and all hub content remain reachable, distinguishable, and unclipped; decorative motion
   never delays dismissal, identity teardown, or input availability.
7. Automated positive and negative controls cover fixed dock ownership/order, history state,
   active-route selection, typed dispatch, browser-section separation, and tab/origin invalidation;
   existing security, regular-mode, and release boundaries remain green.
8. `bash scripts/pre-commit-check.sh` passes.

## NFR

- Security/privacy: Only trusted bounded models enter the hub; browser commands and callbacks remain
  compiled and active-tab addressed; no new telemetry or remote capability is introduced.
- Reliability/fallback: A missing/empty site item set still leaves the complete browser dock; loss
  of integrated authorization closes the hub and falls back to ordinary chrome.
- Performance: Hub projection remains pure/bounded and does not add network, parsing, or WebView
  work; recomposition is scoped to active browser and trusted configuration state.
- Accessibility: Browser-authored content descriptions, selected semantics, 48 dp targets, logical
  traversal, scalable text, and reduced-motion behavior are mandatory.

## Risks

- A generic menu refactor could accidentally mix site and browser commands or erase attribution.
- Capturing the active controller in a stale hub callback could violate tab isolation.
- Five compact dock controls may clip or shrink below target size at 320 dp or 200% font scale.
- Retaining the old persistent site navigation would duplicate destinations and obscure ownership.

## Open questions

- Research must choose the narrowest reuse seam for the existing SiteSkin menu/model and browser
  Tabs/More surfaces without introducing a second source of truth.
- Exact hub presentation and dismissal mechanics should follow existing Compose patterns while
  keeping browser and site sections structurally distinct.
