# UX-022 — Add SiteSkin hub presentation hints and drawer navigation

Status: PRD_READY

Issue: [denrzv/webora#112](https://github.com/denrzv/webora/issues/112)

## Context / Problem

`SiteSkinChromeModel` already keeps the manifest's three item sources apart. It projects
`bottomNavigation` with a `NavMatcher` active id, `quickActions` and `menu` — three bounded lists
with three different meanings, at three different caps (5 / 5 / 20).

`actionBouquet()` then throws all of that away:

```kotlin
internal fun SiteSkinChromeModel.actionBouquet(): List<SiteSkinItemModel> =
    (bottomNavigation + quickActions + siteMenu)
        .distinctBy(SiteSkinItemModel::id)
        .take(MAX_BOUQUET_ITEMS)
```

Concatenate, dedupe, keep five. `SiteActionBouquet` renders the survivors as circular petals in a
`Popup` above the dock. That is the entire native hub `UX-015` promised and `UX-017` branded, and it
has two defects that are not stylistic:

1. **It is lossy in the direction that matters.** A twenty-item `menu` is legal, normalized and
   trusted, and nineteen of its entries can be unreachable from the browser — not truncated with a
   diagnostic, but silently outranked by navigation that happened to be listed first. The browser is
   the only thing standing between a valid manifest and the user, and here it drops trusted content
   with no signal at all.
2. **It flattens a semantic distinction the protocol spent three fields establishing.** A route, a
   one-shot action and an overflow entry become the same circle. `isNavigation` survives into
   `SiteSkinItemModel` and reaches only `stateDescription`, so the distinction exists for assistive
   technology and nowhere in the pixels.

`UX-015`'s own record in `CLAUDE.md` describes a hub that "projects the current trusted, bounded
`SiteSkinChromeModel` into separately headed navigation and quick-action groups and then a distinct
Webora-controls section". The bouquet is not that; the headed-groups surface survives only as
`IntegratedBrowserMenuSheet`, which carries browser commands and no site content at all. This ticket
builds the structured surface and keeps the bouquet as an explicit choice.

The protocol half is where the care goes. Issue #112 asks the manifest to express a preference,
which means adding a field to a format whose free-change window `SPEC.md` §4.5 closed. It is legal:
§4.2(1) and §4.2(7) make an optional top-level section additive by definition, so this is a minor
bump and no existing manifest needs migration. What it is not is free — the field arrives with a
disposition decision, a fixture, a registry entry and a canonical-result question, and getting the
disposition wrong is how a typo'd presentation value discards a whole integration.

## Goals

- Add one optional, bounded, top-level `presentation.hub` hint to the manifest, carried as a closed
  normalized enum through validation into `SiteSkinConfiguration`.
- Resolve that hint through one browser-owned policy function, with the current policy
  `AUTO → DRAWER`, and never re-decide it from a raw string at a Compose call site.
- Build a browser-owned start-side drawer that presents quick actions, primary navigation and the
  extended menu as three separately headed groups, with the whole trusted `menu` reachable.
- Keep the bouquet as the presentation an integration gets by asking for it, with its compact cap
  and ordering unchanged.
- Keep every browser-owned guarantee that `UX-015`, `UX-017` and `HARDEN-002` established: the five
  dock commands, their order, their callbacks, the identity treatment and the lifecycle teardown.

## Non-goals

- Any manifest control over geometry, dimensions, position, animation, component names or native
  resources. The hint's whole value space is three tokens.
- A new action type, a new icon token, or a new asset-loading path. The drawer consumes the existing
  `BrandAsset`, the existing closed icon map and the existing `ActionResolver`.
- Raising `MAX_MENU_ITEMS`, `MAX_NAVIGATION_ITEMS` or `MAX_QUICK_ACTIONS`. The drawer makes the
  existing twenty-item menu bound *reachable*; it does not change what the bound is.
- Removing the bouquet, or making `AUTO` a permanent compiled alias of one component.
- Redesigning `BrowserNavigationShell`, regular chrome, or the `IntegratedBrowserMenuSheet` browser
  section.
- Hosted cross-presentation screenshot acceptance. Issue #115 (`CI-010`) owns that.
- Publishing the hint on `denrzv/bloom-flowers`. That is a separate cross-repository change with its
  own five-copy digest discipline, and it must follow browser support rather than lead it.

## User stories

- As a user of an integrated site with a large menu, every entry the site published is reachable
  from the hub instead of the first five in concatenation order.
- As a user, quick actions still read as prominent, branded, tappable circles rather than becoming a
  row of text in a list.
- As a user, the drawer tells me which navigation entry is the page I am on, and tells my screen
  reader the same thing.
- As a user with the drawer open, Back closes the drawer instead of leaving the site.
- As a user who switches tabs or leaves the origin, no site's actions remain on screen or remain
  dispatchable.
- As a site owner, omitting `presentation` costs me nothing and mistyping it costs me nothing beyond
  a warning in the inspector.
- As a site owner who wants the compact hub, `"hub": "bouquet"` still gets it.

## Acceptance criteria

1. The manifest accepts an optional top-level `presentation` object with an optional `hub` string;
   `siteskin-1.0.schema.json` constrains it by **pattern, not enum**, so an unrecognised value is
   never `SS-E-SCHEMA-INVALID`.
2. `auto`, `bouquet` and `drawer` normalize to the corresponding closed enum value; an absent
   `presentation`, an absent `hub`, and an unrecognised or wrongly-cased value all normalize to
   `AUTO`.
3. An unrecognised `hub` value produces a registered `warn` diagnostic with a pointer to
   `/presentation/hub`, and the manifest is otherwise unaffected — nothing is dropped and nothing is
   rejected.
4. The new diagnostic code is registered in `spec/diagnostics.json` and has a conformance fixture in
   the same commit; `SpecCorpusTest`'s both-directions completeness assertion passes.
5. Every existing fixture's expected result is unchanged except where a fixture deliberately
   exercises the new field, and `spec/fixtures/valid/bloom-flowers.json` stays byte-identical to its
   pinned SHA-256.
6. `SPEC.md` documents the field, its value space, its disposition and its minor-version status
   under §4.2, and `versions.json`/`layerOrder` semantics are unchanged.
7. Executable browser UI reads the normalized enum from `SiteSkinConfiguration`; no Compose code,
   model or resolver compares a raw manifest string.
8. One browser-owned resolution function maps the normalized hint to an effective presentation, with
   `AUTO → DRAWER` under the current policy, and it is a pure function the JVM gate can drive
   through every input.
9. The dock's centre Brand Hub opens the resolved presentation: the drawer when resolved `DRAWER`,
   the existing bouquet when resolved `BOUQUET`.
10. The drawer opens from the layout **start** side and is correct under RTL without a physical
    left/right constant.
11. The drawer header renders the validated site identity and the already-published `BrandAsset`,
    with the existing monogram fallback and no second remote fetch.
12. The drawer renders quick actions as compact branded icon actions with visible labels, primary
    navigation as a separate headed group carrying `NavMatcher`'s active state, and the extended
    menu as a third headed group.
13. All twenty permitted `menu` entries are reachable in the drawer; content longer than the
    viewport scrolls rather than truncating.
14. Only navigation rows publish selected/not-selected semantics; quick actions and menu rows do
    not, and active state is never carried by colour alone.
15. Selecting any drawer item closes the drawer and dispatches through the existing `ActionResolver`
    path; no raw URI, intent or generic command is introduced.
16. Back with the drawer open closes the drawer and does not reach WebView or browser Back.
17. A page start within the origin re-projects the drawer's active route; a tab switch,
    configuration change, SiteSkin deactivation or loss of `PROTECTED_INTEGRATED` authorization
    closes the hub before another projection can dispatch, and site A's hint cannot affect site B or
    regular browsing.
18. The dock remains exactly Back, Forward, Brand Hub, Tabs, More in that fixed order with unchanged
    callbacks, and a negative control proves no `presentation` value changes that order, the browser
    security surface, or action validation.
19. The drawer is operable at 320 dp width and 200% font scale; every interactive row meets the one
    48 dp `MINIMUM_TOUCH_TARGET` contract; every icon-only affordance carries an accessible name;
    colours come only from the guarded `SiteSkinColorScheme` and `WeboraTheme`.
20. `bash scripts/pre-commit-check.sh` passes, and `:app:compileDebugAndroidTestKotlin` compiles.

## NFR

- **Security/privacy:** the hint selects among compiled browser components and can do nothing else.
  It has no path into origin binding, action validation, scheme allow-listing, limits, contrast
  correction, consent, the dock's command set or the browser trust surface, and the value space is
  closed at the validator so an unknown token is indistinguishable from an absent one by the time UI
  sees it. Drawer content is the same trusted `NavigationItem` values the bouquet already dispatches;
  labels stay re-bounded by `accessibleLabel`. No new network, storage or permission surface.
- **Reliability/fallback:** a manifest with no hint, a malformed hint or an unsupported one degrades
  to the browser's own default with the page still rendering — `ADR-010` unchanged. The resolver may
  return a different presentation than requested, and callers must treat that as normal rather than
  as an error path.
- **Performance:** one enum on the configuration, one pure resolution per projection, no I/O and no
  additional decode. The drawer composes only while open.
- **Accessibility:** headed groups are the accessibility structure, not decoration. Active route is
  a `stateDescription`, quick-action circles carry labels rather than relying on the decorative icon,
  focus is contained while the drawer is open and restored to the Brand Hub when it closes, and the
  drawer scrolls at 200% font scale on a 320 dp host.

## Risks

- **Disposition is the sharp edge.** An `enum` in the schema would make `"hub": "drawr"` reject the
  entire manifest, dropping a working integration over a typo — the outcome `ADR-007` refuses for
  action types and `icon` already refuses by construction. The pattern-plus-security-normalization
  shape is the one the corpus already pins for `icon`; deviating from it is the likeliest way to
  ship a whole-manifest rejection by accident.
- **The canonical result's shape is versioned.** `SPEC.md` §4.3(7) makes a change to the canonical
  result breaking *where it alters the result for a document that was already valid*. Emitting
  `presentation` unconditionally would rewrite every existing `.expected.json`; the field must
  appear only when the manifest declared one, and that decision needs to be stated in `SPEC.md` §12
  rather than left implicit in a serializer.
- **The bouquet is not dead code and must not become untested.** `MAX_BOUQUET_ITEMS`, the
  `distinctBy` order and the petal lift table are existing behaviour with existing coverage;
  isolating the compact projection must not quietly relax any of them.
- **`AUTO` must stay a hint.** Hard-coding `AUTO` to the drawer component rather than routing it
  through the policy function makes the third token meaningless and forecloses the viewport and
  accessibility overrides the issue explicitly reserves.
- **Back interception is a browser contract with existing owners.** `BrowserBackHandler` and
  `navigateBrowserBack` implement `BROWSE-002`'s single Back precedence; adding a drawer-closing
  step in the wrong place either swallows Back for the whole app or fails to close the drawer at
  all. `BROWSE-010`'s navigation and mount semantics must survive untouched.
- **Hub state is not tab state.** `siteActionsExpanded` is a single `BrowserScreen` boolean today and
  is already reset by tab and configuration change; a drawer with its own state object is a second
  place for a stale site's actions to survive a switch, which is `BROWSE-009`'s cross-tab leak
  arriving through a new door.
- **The frames are pending acceptance.** `CI-009` is waiting on hosted runs asserting
  `SITESKIN_DOCK_*` and `SITESKIN_SECURITY_TAG`; changing what the centre command opens must not
  change those tags or the dock's structure.

## Open questions

None blocking. Two decisions are recorded above as constraints rather than questions — pattern over
enum for the schema, and a canonical result that carries `presentation` only when the manifest
declared it. The exact diagnostic code spelling, the section labels and the drawer's own geometry
are `/plan` decisions.
