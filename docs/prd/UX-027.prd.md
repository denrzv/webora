# UX-027: Restore the SiteSkin brand asset transition from monogram to logo
Status: PRD_READY

Issue: [#128](https://github.com/denrzv/webora/issues/128)

## Context / Problem

The reference integration's centre Brand Hub renders the deterministic monogram `B` and never
transitions to Bloom's logo, on a locally installed debug APK. `UX-017` requires that slot to carry
the validated `BrandAsset` and to use the monogram only while loading or after a genuine failure, so
a permanent `B` is a regression against an accepted contract.

`NET-004` is the ticket that made this pipeline diagnosable, and it recorded the working state:
hosted runs 17 and 18 logged `stage=DECODED httpStatus=200 pixels=512x512 attempts=1`, with run 18's
frame showing the flower in the 40 dp slot. So this pipeline demonstrably worked, and something has
since stopped it reaching the screen.

**Three things are already excluded before the ticket starts**, which is what makes it a state
problem rather than a transport one:

| Checked | Result |
|---|---|
| The declared asset exists | `/assets/siteskin/logo.png`, 512 × 512 PNG, 5702 bytes |
| The live origin serves it | `HTTP/2 200`, `content-type: image/png`, `etag` size matching |
| The loader's own logic | `BrandAssetLoader` and its sources are unchanged since `NET-004` and its suite passes |

So `logoUrl` resolution, transport, MIME handling and decoding are all working in isolation. What
remains is publication and Compose state propagation — the issue's own sections 3 and 4 — and that
is the layer with no automated coverage, because it lives inside a `@Composable`.

## Goals

- A successful load reaches the screen: the monogram gives way to the decoded asset without a
  navigation, a menu reopen or an app restart.
- Every native surface that shows site identity consumes **one** browser-owned asset state, rather
  than each capturing a fallback at its own first composition.
- The transition is covered by something the JVM gate can drive, so it cannot silently regress again
  — which is the gap that let this one through.
- Failure stays on the fallback and stays diagnosable through `NET-004`'s existing trace.

## Non-goals

- Weakening any part of `NET-003`'s asset policy — the caps, the allow-list, the exact-origin
  recheck, the signature match — to make Bloom pass.
- A general-purpose image loader, or remote images for any browser-owned control.
- Changing Bloom's artwork, the 40 dp slot, the 52 dp hub circle, or any geometry.
- Re-opening `NET-004`'s retry policy. `TRANSPORT_UNAVAILABLE` is retried and nothing else is; that
  decision stands unless the diagnosis implicates it.
- New diagnostics vocabulary. `BrandAssetStage` and `BrandAssetRejection` already name every stage
  the issue's Diagnostics section asks for.

## User stories

- As a Bloom visitor, the shop's flower appears in the branded chrome shortly after the page loads,
  instead of a letter that never changes.
- As a site owner, a logo I serve correctly is the one users see, and when it fails I can find out
  why from the inspector rather than guessing.
- As a Webora developer, a future change that breaks this transition fails a test on my machine.

## Acceptance criteria

1. With a configuration whose logo loads successfully, the published asset observed by native chrome
   transitions from the monogram to the decoded bitmap, and the transition is asserted by a test the
   JVM gate runs.
2. The centre Brand Hub and the drawer header render the *same* published asset — one state, not two
   independently captured fallbacks.
3. Opening or closing the SiteSkin drawer does not revert a loaded asset to the monogram.
4. A configuration with no `logoUrl` still yields the deterministic monogram, unchanged.
5. A genuine transport, rejection or decode failure keeps the fallback, keeps the rest of the
   integration working, and records its stage in the existing trace.
6. A load completing after a tab switch cannot publish into the newly selected tab; returning to the
   owning tab still shows its own asset.
7. A configuration change while a load is in flight discards the obsolete result.
8. Exact-origin departure removes the asset with the rest of integrated chrome.
9. `NET-003`'s caps, allow-list, signature matching and same-origin recheck are unchanged, and
   `BrandAssetLoaderTest` passes **unedited**.
10. Whatever defect the diagnosis finds has a negative control: reverting the fix fails a named test.
11. `./gradlew :app:compileDebugAndroidTestKotlin` compiles.
12. `bash scripts/pre-commit-check.sh` passes.

## NFR

- **Security/privacy:** the asset may come only from the validated configuration's own origin, and
  publication must remain guarded by configuration identity — a fix that publishes more eagerly must
  not publish into the wrong tab, origin or generation. The 40 dp slot stays decorative in the
  semantics tree; the load's outcome must not become an accessibility-visible property of it.
- **Reliability/fallback:** every failure path still ends at a monogram and a working integration.
  No failure may blank the slot or deactivate SiteSkin.
- **Performance:** one load per configuration. A fix must not re-fetch on every recomposition —
  which is the obvious over-correction if the cause turns out to be a key that never changes.
- **Accessibility:** unchanged. The slot is decorative and the identity contract is the browser's
  domain/TLS chip, not the logo.

## Risks

- **Fixing the symptom at the render site.** The issue warns against patching only the centre button.
  A monogram rendered where an asset exists is a state problem, and a local `remember` in the button
  would hide it while leaving the drawer wrong.
- **Over-correcting the effect key.** If the cause is an effect that does not re-run, the naive fix
  keys it on something that changes constantly and re-fetches per recomposition. `NET-004` recorded
  that `forObservedOrigin` returns the *same* `Integrated` instance for every same-origin page start
  precisely so this effect is stable.
- **Weakening the publication guard.** `NET-003`'s identity check is what stops one origin's brand
  appearing over another's page. A fix that publishes unconditionally would trade this bug for
  `HARDEN-002`'s.
- **Diagnosing from a green CI.** Hosted runs 17/18 recorded `DECODED`; if the current hosted run
  still does, the defect is between publication and pixels, and no amount of loader testing finds it.

## Open questions

- Does the load succeed and fail to publish, or fail to run at all? `NET-004`'s trace answers this
  directly and the inspector already displays it — research should read the stage before theorising.
- Is `publishesBrandAsset`'s `===` comparison still satisfied at publication time? It compares the
  configuration instance captured when the effect launched against the one in the mode; anything that
  reconstructs the `Integrated` mode mid-load would break it silently.
- Does `UX-025`'s dock or `UX-026`'s drawer capture the asset at their own first composition rather
  than reading the shared state? Both landed after `NET-004`'s evidence and both render identity.
- Is this reproducible in the hosted journey, or only on a locally installed APK? If only local, the
  difference is the variant or the network path, not the code.
