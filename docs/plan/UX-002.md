# UX-002: Implementation plan
Status: PLAN_APPROVED

## Overview
Build the browser-owned token layer `ADR-013` specified, in the shape `SKIN-001` already established
for the website-owned one: **a closed role model, with the Material type derived from it**, not a
`ColorScheme` authored by hand.

The two layers end up as mirror images, which is the point:

| | `SiteSkinColorScheme` (`SKIN-001`) | `WeboraColorScheme` (this ticket) |
|---|---|---|
| Input | a trusted `SiteSkinConfiguration` | **nothing** |
| Roles | six, closed | fourteen, closed |
| Guard | runs over every newly formed pair at runtime | runs over every declared pair in a JVM test |
| Who may change a value | the website, within the guard | a commit |

`SiteSkinTheme` has an input and therefore needs a runtime guard. `WeboraTheme` has no input, so its
guard can run once, at build time, over every pair that exists — which is strictly stronger, and is
what `C5` asked for when it said the browser palette should be asserted "in a JVM test".

Everything else follows from that spine: typography, shape and geometry get the same closed-model
treatment; the Material `ColorScheme`/`Typography`/`Shapes` handed to `MaterialTheme` are derived by
an explicit mapping that may introduce no value of its own; and `C2` gets a two-sided test because
neither side alone can fail for the right reasons.

## Flow
There is no runtime flow. Nothing here is discovered, validated or normalized, and that absence is
the ticket's security property rather than a gap in the plan.

- **discovery** — none. No fetch, no URL, no remote document.
- **validation** — none at runtime. The palette's validation is a JVM test that runs before the code
  can be committed, over values that cannot change after compilation.
- **normalization** — none. `SiteSkinTheme` corrects remote colours because remote colours can fail;
  a compiled constant that fails contrast is a bug to fix, not an input to correct. Adding a runtime
  guard to the browser palette would be worse than useless: it would let a failing token ship,
  silently corrected, instead of failing the build.
- **UI state** — `WeboraTheme(darkTheme = isSystemInDarkTheme())` selects a projection and supplies
  `MaterialTheme`. `darkTheme` is a **parameter with the framework read as its default**, the same
  thin-wrapper-over-pure-function shape `DEVX-003` used for `SITESKIN_INSPECTOR_AVAILABLE` and
  `SiteSkinTheme.scheme(darkTheme)` uses for the same selection: a test that cannot pass the other
  value cannot tell a correct implementation from one that ignores the setting.

## Data
### Trust boundary
The boundary this ticket defends is **compile-time and one-directional**: `app.webora.browser.design`
must not depend on `dev.siteskin.core` or on `app.webora.browser.siteskin`. Nothing in the design
package may take a `SiteSkinConfiguration`, a `SiteSkinColorScheme`, or a `String` that came from one.

There is no DTO and no domain model here because there is no untrusted input. The analogous
statement is the negative one, and it is the thing worth testing: **`WeboraColorScheme` has no
factory that takes an argument.** `SiteSkinTheme.from(configuration)` exists because a website
supplies colours; the browser equivalent would be a defect.

`SiteSkinColorScheme` remains the entire website-influenceable colour surface, unchanged in values,
roles and guard behaviour. The only edit to `SiteSkinTheme.kt` moves `contrastRatio`,
`relativeLuminance` and the two WCAG thresholds out of it; the projection itself is untouched.

### Storage / cache keys
None. Nothing is persisted, nothing is keyed, nothing is cached. The token layer is `const` data and
immutable `data class` instances.

## Security
### Origin binding
Not applicable, and stated rather than skipped: this ticket introduces no origin-scoped state, no
per-site behaviour and no code path that reads an origin. The identity-chip **colours** it defines
are consumed by `UX-003`, whose `BrowserSecurityIdentity` derives its *content* from the committed
`SiteOrigin` — the colour is browser-owned precisely so that neither half of that element comes from
a website.

### Allow-lists
The relevant allow-list is the palette itself, and this plan makes it enforceable in two directions:

1. **Closure.** Every colour in the Material `ColorScheme` handed to `MaterialTheme` must be a value
   declared in `WeboraColorScheme`. A role left to a `lightColorScheme()` default fails by
   construction — nobody has to remember to pass all thirty arguments, and a BOM upgrade that adds a
   role fails the test instead of silently shipping baseline purple. The same rule covers `Typography`
   (every `fontSize` from the compiled scale) and `Shapes` (every corner from the compiled radii).
2. **Completeness.** Every colour declared in `WeboraColorScheme` must appear in the contrast table,
   either as a measured pair or as a **named decorative exemption with a written reason**. Reflected
   over the declared roles rather than listed, so a token added later is covered before anyone
   remembers this rule exists.

Together they close the loop: the palette is exactly the closed set, and the closed set is entirely
measured.

### `C2` — no manifest value reaches a browser token
Tested on both sides, because neither side can fail for the other's reason:

- **Runtime sweep.** Snapshot both browser projections. Project a corpus of real manifests through
  the real `SiteSkinValidator` and `SiteSkinTheme.from`, including one whose branding requests
  colours that are conspicuously not Direction A's. Assert every browser token is bit-identical to
  its snapshot, **and** that the SiteSkin scheme did carry the manifest's colours — so a test that
  quietly stopped exercising the projection fails instead of passing.
- **Source scan.** Assert no source file in `app/src/main/java/app/webora/browser/design/` imports or
  mentions `dev.siteskin.core`, `app.webora.browser.siteskin`, or `SiteSkinConfiguration`. Modelled
  on `BrowserSurfaceConventionsTest`, which already reads sources for a rule no call site owns.

The sweep would pass a design that *derives* browser tokens from a manifest but happens to be stable
for the manifests tried; the scan would pass a design that reaches core through reflection or a third
module. The pair is the same belt-and-braces `:siteskin-core` uses for Android-freedom — a classpath
assertion **and** a CI job with no SDK installed.

**Negative control** (recorded in the tasklist, per `PROJECT_RULES.md`): wire a manifest-derived
colour into one browser token and confirm both halves go red; restore.

### Fallback on failure
None applies. There is no failure mode: no network, no parse, no decode, no permission. The
`ADR-010` graceful-degradation rule is about invalid manifests and is untouched — the browser palette
is what a failed manifest degrades *to*, and after this ticket that fallback state is better
specified than before rather than newly fragile.

## The values, and where they come from
Direction A, transcribed from `ADR-013`'s table and the token block at
`docs/design/directions/index.html:437-455`. Every ratio below was recomputed from the hex values
with the same relative-luminance formula `contrastRatio` implements; the six figures `ADR-013`
publishes are reproduced exactly.

| Role | Light | Dark | Purpose |
|---|---|---|---|
| `ground` | `#F7F6F3` | `#0E1414` | app background |
| `surface` | `#FFFFFF` | `#171F1F` | cards, sheets |
| `chrome` | `#D3EBEA` | `#1F2C2C` | the address pill and the dock |
| `container` | `#B4E5E3` | `#1F2C2C` | tonal containers, including the identity chip |
| `primary` | `#00696E` | `#5CDBD8` | the one accent |
| `ink` | `#191C1C` | `#DEE4E3` | body text |
| `muted` | `#45504F` | `#B2BEBD` | secondary text, and Material's `outline` |
| `onChrome` | `#00201F` | `#B4E5E3` | text and icons on `chrome` |
| `onContainer` | `#00201F` | `#B4E5E3` | text and icons on `container` |
| `onPrimary` | `#FFFFFF` | `#003736` | text and icons on `primary` |
| `secure` | `#0F5132` | `#6DD58C` | TLS secure, on `container` |
| `notSecure` | `#7A1B14` | `#FFB4AB` | TLS not secure, on `container` |
| `divider` | `#C6D2D1` | `#2C3838` | hairline separators — decorative |
| `scrim` | `#0E1414` | `#0E1414` | dialog scrim — decorative |

Two names differ from the direction's CSS, deliberately:

- **`divider`, not `outline`.** Material uses `outline` for boundaries that must reach 3:1 and
  `outlineVariant` for decorative hairlines. Direction A's `--f-outline` is a hairline (1.44:1 on
  ground) because A uses tonal containers *instead of* outlines. Naming it `outline` would invite the
  mapping that puts a 1.44:1 value where 3:1 is required. Material's `outline` takes `muted` instead
  — 7.73:1 light, 9.74:1 dark — and introduces no new colour.
- **`scrim`** is not in the direction at all; a dialog needs one and Material has the role. It takes
  the direction's own darkest value in both themes rather than a new black.

### The contrast table
Body pairs at 4.5:1, non-text at 3:1. Every pair the derivation can produce is measured; the two
decorative roles are exempted by name.

| Pair | Light | Dark | Target |
|---|---|---|---|
| `ink` on `ground` | 15.87 | 14.45 | 4.5 |
| `ink` on `surface` | 17.15 | 13.03 | 4.5 |
| `ink` on `chrome` | 13.76 | 11.21 | 4.5 |
| `ink` on `container` | 12.46 | 11.21 | 4.5 |
| `muted` on `ground` | 7.73 | 9.74 | 4.5 |
| `muted` on `surface` | 8.36 | 8.78 | 4.5 |
| `muted` on `chrome` | 6.70 | 7.56 | 4.5 |
| `muted` on `container` | 6.07 | 7.56 | 4.5 |
| `onChrome` on `chrome` | 13.73 | 10.49 | 4.5 |
| `onContainer` on `container` | **12.44** | **10.49** | 4.5 |
| `onPrimary` on `primary` | 6.47 | 7.86 | 4.5 |
| `secure` on `container` | **6.80** | **7.94** | 4.5 |
| `notSecure` on `container` | **7.65** | **8.50** | 4.5 |
| `primary` on `ground` | 5.99 | 11.14 | 3.0 |
| `primary` on `surface` | 6.47 | 10.05 | 3.0 |
| `primary` on `chrome` | 5.19 | 8.65 | 3.0 |
| `primary` on `container` | 4.70 | 8.65 | 3.0 |

Bold figures are the ones `ADR-013` published; they match. The lowest body pair has 1.44× headroom
over its target and the lowest non-text pair 1.57×, so **no value deviates from the ADR** — the test
confirms the transcription rather than forcing an amendment.

**Decorative exemptions, with reasons rather than silence:**

- `divider` — a hairline separator at 1.44:1 / 1.53:1 against ground. WCAG 1.4.11 governs visual
  information required to *identify* a component or its state; a separator identifies nothing, and
  every region it separates carries text that clears 4.5:1.
- `scrim` — an overlay, not a foreground or a background of any text. Contrast against it is
  undefined: the dialog surface sits on top of it.

`ADR-013` already ruled on the third case anyone will ask about — the identity chip separating from
its ground at 1.27:1 light / 1.29:1 dark — and said explicitly that this **is correct and should not
be "fixed"**: a chip is a status display rather than an interactive control, and its identity is
carried by text at 10.49:1 or better plus a glyph and a word, so no meaning rests on colour alone.
This plan does not reopen it. It shows up here as the container-against-ground pairs simply not
being members of the table, which is the same statement the ADR made.

### Type, shape, geometry
`ADR-013` gives type as `28 / 22 / 15 / 13 / 12, Roboto`, geometry as `radius 999 dp pills, 20 dp
cards; 4 dp base spacing, 20 dp gutter`, chrome as `52 dp pill + identity chip + 60 dp floating
dock`, icons `at 20 dp, stroke 1.9`.

Five sizes have to cover fifteen Material text roles. The mapping is by rank, not by taste — display
and headline roles take the largest, label roles the smallest — and the closure test asserts every
role's size is a member of the five, so nothing can quietly acquire a sixteenth value. Capping the
display roles at 28 sp is deliberate: the browser draws nothing bigger, and inventing a 45 sp display
role would be adding to a decided scale.

Intermediate shape steps are **multiples of the stated 4 dp base** — 4 / 8 / 12 / 20 / 999 — rather
than chosen values. `ADR-013` names the 20 and the 999 and the base unit; the steps between them
follow from it. Recorded because "derived from the stated base" and "picked to look right" are
indistinguishable in the resulting numbers, and only the first is reviewable.

Geometry reuses `MINIMUM_TOUCH_TARGET` from `BrowserAccessibility.kt` rather than restating 48 dp. A
second 48 dp constant is a second place for it to change.

## File-by-file plan

### New: `app/src/main/java/app/webora/browser/design/Contrast.kt`
`contrastRatio` and `relativeLuminance`, moved verbatim from `SiteSkinTheme.kt` with their sRGB
constants, plus `WcagContrast.BODY_TEXT = 4.5` and `WcagContrast.NON_TEXT = 3.0` replacing the
private `BODY_CONTRAST`/`UI_CONTRAST`. `internal`, so both palettes reach it and nothing outside the
module does. The move is mechanical and behaviour-preserving; `SiteSkinThemeTest` passing unchanged
except for an import is the evidence.

### New: `app/src/main/java/app/webora/browser/design/WeboraColorScheme.kt`
The fourteen-role `data class` and its two compiled instances. No factory function taking an
argument; the projections are `val`s.

### New: `app/src/main/java/app/webora/browser/design/WeboraTypography.kt`
The five-step scale as named constants, and the `Typography` derivation assigning every Material role
one of them with a line height derived from it.

### New: `app/src/main/java/app/webora/browser/design/WeboraShapes.kt`
The radius steps and the `Shapes` derivation.

### New: `app/src/main/java/app/webora/browser/design/WeboraDimensions.kt`
Spacing (4 dp base, its multiples, the 20 dp gutter) and chrome geometry (52 dp pill, 60 dp dock,
40 dp end slot, 20 dp icon), re-exporting `MINIMUM_TOUCH_TARGET` rather than redeclaring it.

### New: `app/src/main/java/app/webora/browser/design/WeboraTheme.kt`
`WeboraTheme(darkTheme: Boolean = isSystemInDarkTheme(), content: @Composable () -> Unit)` and the
`materialColorScheme(WeboraColorScheme)` mapping. Every Material role is assigned from a browser
role; the mapping contains no `Color(...)` literal, which is what the closure test enforces.

Notable mappings, all reusing measured pairs:

| Material role | Browser role | Why |
|---|---|---|
| `outline` | `muted` | 3:1 boundary duty; the direction's hairline cannot do it |
| `outlineVariant` | `divider` | the direction's hairline, doing what it is for |
| `error` / `onError` | `notSecure` / `container` | the browser's one flag colour, measured at 7.65 / 8.50 |
| `errorContainer` / `onErrorContainer` | `container` / `notSecure` | the same pair, roles swapped |
| `surfaceVariant` / `onSurfaceVariant` | `chrome` / `muted` | 6.70 / 7.56 |
| `secondary`, `tertiary` | `primary` | Direction A has one accent; pretending otherwise would invent colours |

### New: `app/src/main/res/drawable/ic_*.xml` — ten vectors
`ic_back`, `ic_forward`, `ic_reload`, `ic_home`, `ic_menu`, `ic_more`, `ic_lock`, `ic_close`,
`ic_search`, `ic_warning`. Path geometry transcribed from the `<symbol>` elements at
`docs/design/directions/index.html:611-620` — the same 24-unit viewport, the same 1.9 stroke, round
caps and joins. `<rect>` and `<circle>` become path data, which is all `<vector>` accepts.

They are stroked rather than filled because that is what the direction draws, and they carry a single
opaque stroke colour because Compose's `Icon` applies `ColorFilter.tint` over the whole painter — so
the drawable's own colour never reaches the screen and the call site's tint always does. Tinting is
therefore the token layer's job, not the asset's.

No Gradle dependency is added. `C6` rejected `material-icons-extended` as large and upstream-
deprecated, and a bundled vector has a second property worth naming: **a website cannot add a file to
`res/drawable`.** `NET-003` needs a signature check, a size cap and a bounded decode because a logo is
remote; a browser icon needs none of that because it is not.

### Modified: `app/src/main/java/app/webora/browser/siteskin/SiteSkinTheme.kt`
Delete the moved functions and constants, import them from `design`. Projection behaviour, roles,
guard and defaults are untouched.

### Modified: `app/src/main/java/app/webora/browser/browser/BrowserAccessibility.kt`
Add `WeboraIconButton`. It must land here: `BrowserSurfaceConventionsTest`'s `RAW_BUTTON_IMPORT` bans
`import androidx.compose.material3.\w*Button` in every file declaring a composable **except** the one
containing `fun WeboraButton(`. A new file turns the build red, and the failure reads as an unrelated
convention test breaking.

Its accessible name is a **non-optional** parameter, not a nullable one. An icon-only control with no
name is invisible to assistive technology, and `C4` already makes a hard-coded one a build failure —
so the only way to get a name wrong is to omit it, and the signature removes that option.

### Modified: `app/src/main/res/values/strings.xml`, new `app/src/main/res/values-night/themes.xml`
Accessible names for icons that do not already have one — `back`, `forward`, `reload`, `home`, `more`,
`settings` exist; `menu`, `close`, `search` and the warning do not. The night theme gives
`Theme.Webora` a dark platform parent so the window behind Compose, and the first frame before
composition, follow the same setting the palette does (`C7`).

### Modified: `app/src/main/java/app/webora/browser/MainActivity.kt`
`MaterialTheme {` becomes `WeboraTheme {`. One line plus the import; the destination logic inside is
untouched.

### Modified: `app/build.gradle.kts`
Pass `app/src/main/res` as a system property to the test task, with `inputs.dir`, so the icon-contract
scan reruns when a drawable changes — exactly how the Compose source roots and `:siteskin-core`'s
conformance corpus are already wired.

### Modified: `docs/accessibility/CONFORMANCE.md`
A Contrast row for the browser palette, marked **Gate**, naming the code and the test — and a row for
the closure property, since "no Material default reaches a surface" is an accessibility guarantee
whose absence is invisible.

## Tests
| Test | Asserts | Kind |
|---|---|---|
| `WeboraColorSchemeTest` — pair table | Every pair in the table clears 4.5 / 3.0 in **both** projections | Gate |
| `WeboraColorSchemeTest` — completeness | Every declared role appears in the table or in the named exemptions; reflected over the class, not listed | Gate |
| `WeboraColorSchemeTest` — exemptions are justified | Each exemption carries a reason string, so the escape hatch cannot be used silently | Gate |
| `WeboraThemeTest` — colour closure | Every colour in the derived `ColorScheme` is a value declared in `WeboraColorScheme`, in both projections | Gate |
| `WeboraThemeTest` — type and shape closure | Every `Typography` size is a member of the five-step scale; every `Shapes` corner a member of the radius steps | Gate |
| `WeboraThemeTest` — the projections differ | Light and dark are not the same object, so a mis-wired selector cannot pass | Gate |
| `BrowserTokenIsolationTest` — runtime sweep | Browser tokens are bit-identical across a manifest corpus, and the SiteSkin scheme did move | Gate |
| `BrowserTokenIsolationTest` — source scan | No `design` source mentions core or the siteskin package | Gate |
| `BrowserIconContractTest` | Ten drawables, each a 24-unit stroked `<vector>` with one stroke colour; the set is bounded | Gate |
| `BrowserAccessibilityTest` — icon button | `WeboraIconButton` raises the Material minimum, as its siblings do | Gate |
| `SiteSkinThemeTest` | Unchanged behaviour after the `contrastRatio` move | Gate |

**Reflection, and the fallback if it misbehaves.** The closure and completeness tests read properties
by Java reflection over zero-argument getters — `Color` and `TextUnit` are value classes, so their
getters are name-mangled and return `long`. `kotlin-reflect` is not on the test classpath and this
plan does not add it; if the mangling proves awkward the fallback is an explicit enumeration **plus a
count assertion against the reflected property count**, which keeps the anti-decay property that
matters. What is not acceptable is a hand-listed enumeration with nothing checking it is complete.

**Test thresholds stay independently restated.** `SiteSkinThemeTest` declares its own `4.5` and `3.0`
rather than importing them, and the new tests do the same. Sharing the constant with production would
mean lowering it silently lowers the assertion — the test would keep passing while the guarantee
shrank.

**Negative controls**, recorded in the tasklist with their results:

1. Wire a manifest colour into a browser token → both halves of `BrowserTokenIsolationTest` fail.
2. Add a role without a table entry → the completeness assertion fails.
3. Drop a Material role from the mapping, letting it default → the closure assertion fails.
4. Make `WeboraTheme` ignore `darkTheme` → the projection test fails.

Without (2) and (3) the two anti-decay assertions are decoration; this repository does not keep those.

## Rollout / versioning
Not a protocol change. No spec version, no fixture, no diagnostic, no manifest field, no persisted
state, no migration. `spec/` is untouched, `:siteskin-core` is untouched, and no `SS-*` code is added.

The user-visible change is that browser chrome stops being Material baseline purple, follows the
system dark setting, and gains an icon set that nothing yet uses. Surface structure is deliberately
unchanged: `UX-003` rebuilds the chrome and `UX-004` the remaining screens, and both consume this
layer rather than re-deciding it. `UX-005` adds its semantic SiteSkin icons to the same
`res/drawable` mechanism — which is the reason `DEVELOPER_PLAN.md` sequences it behind this ticket.

## Open questions
None. The two judgements `/researcher` flagged are settled above: a closed role model with the
Material types derived from it, and intermediate steps derived from the direction's own 4 dp base.

One handoff is recorded for `UX-003` rather than silently fixed here: Direction A's dock draws
unselected slots at 38% opacity (`index.html:.a-dockbar .slot.off`). At that opacity an enabled
control reads as disabled and its icon may fall below 3:1 whatever the token underneath it is. This
ticket supplies tokens, not opacity, so it cannot be resolved here — but it is a real `C5` problem in
the selected direction, and `UX-003` should treat unselected navigation state as a colour role rather
than as an alpha multiplier.
