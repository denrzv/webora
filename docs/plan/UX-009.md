# UX-009: Implementation plan
Status: PLAN_APPROVED

## Overview

One token collision, fixed at the role rather than at the call site, plus the assertion that would
have caught it.

`WEBORA_SHAPES.extraLarge` carries `WeboraRadius.PILL` (999 dp). Material resolves every
`AlertDialog` container to that role, `CornerBasedShape` clamps an over-large corner to half the
shorter side instead of rejecting it, and `Surface` clips the content to the result — so all five
dialogs in the app draw as stadiums and the consent heading loses its first characters.

The fix is three edits and two tests:

1. `extraLarge` becomes a container-sized radius, so every dialog is a rounded rectangle at once.
2. The one call site that read `extraLarge` *wanting* a pill names `WeboraRadius.PILL` directly.
3. A JVM test lays Webora's own shapes out at Material's narrowest dialog width and fails if a
   container role rounds a side away.

**`extraLarge` becomes 28 dp, as a new `WeboraRadius.EXTRA_LARGE`.** The alternative — reusing
`LARGE` (20 dp) and adding no token — produces an identical dialog and a scale whose top two roles
are the same number, which is an invitation for the next person to collapse them and land back here.
28 dp is a multiple of the stated 4 dp base, so `WeboraDimensionsTest`'s derivation assertion covers
it unchanged, and it is Material's own extra-large, so a Webora dialog and a system dialog do not
disagree about what a dialog corner is. The pill stays in `WeboraRadius` — it is still the correct
value for the address field, the identity chip and the dock — it just stops being reachable through a
Material container role.

## Flow

Not a runtime flow. `WEBORA_SHAPES` is a compile-time constant read by `WeboraTheme`; the change is
in what one of its five roles resolves to and in who reads it.

- **discovery / validation / normalization** — untouched. No network, no manifest, no origin.
- **UI state** — untouched. No composable gains or loses a parameter, no callback changes, no state
  is added. `SiteSkinConsentDialog`'s signature is unchanged, which is what lets `UX-007`'s existing
  assertions stand as evidence that the action hierarchy did not move.

## Data

- **Trust boundary** — none crossed. A radius is a compiled browser-owned constant; `UX-002`'s `C2`
  (no manifest value reaches a browser token) already covers `WeboraRadius.kt` from both directions
  — the `design/` source scan and the runtime sweep — and this ticket adds a `val` to that same file
  rather than a new mechanism. Neither guard needs changing, and both must still pass.
- **Storage / cache keys** — none.

## Security

- **Origin binding** — not applicable, with one dependency worth stating: the consent heading renders
  `SiteOrigin.canonical`, and `HARDEN-002` requires the *complete* canonical origin (scheme, host,
  non-default port) to be visible so the grant matches the persistence key. The clip was defeating
  that requirement in the drawn frame while the semantics tree still reported the whole string. The
  fix restores the visual half; nothing about how the string is derived changes.
- **Allow-lists** — unchanged.
- **Fallback on failure** — unchanged. No path here can fail at runtime.
- **What must not become possible** — a manifest value reaching a container shape. Nothing in this
  change introduces a parameter, a theme read or a call-site override through which one could, and
  the shape stays a constant rather than becoming a `SiteSkinTheme` output.

## File-by-file plan

### Modified: `app/src/main/java/app/webora/browser/design/WeboraRadius.kt`

- Add `val EXTRA_LARGE: Dp = 28.dp` with a KDoc saying what it is for: the largest *container* radius,
  the one Material resolves a dialog to, and why it is not the pill.
- Add it to `ALL`, so `WeboraDimensionsTest`'s base-multiple assertion picks it up automatically —
  the list is the inventory, and a token outside it is a token nothing checks.
- `WEBORA_SHAPES.extraLarge` = `RoundedCornerShape(WeboraRadius.EXTRA_LARGE)`.
- Extend the object's KDoc: the pill is a *control* value and no Material role may carry it, with the
  one-line reason (`AlertDialog` resolves its container to `extraLarge`) so the next reader does not
  have to rediscover the token path through a screenshot.

### Modified: `app/src/main/java/app/webora/browser/browser/HomeScreen.kt`

- Line 48's `shape = MaterialTheme.shapes.extraLarge` becomes
  `shape = RoundedCornerShape(WeboraRadius.PILL)`, with the import added and a short comment: the
  address field is a pill by `ADR-013`, and it says so itself rather than inheriting it from a role
  that also serves dialogs. This is the only call site that read `extraLarge`, confirmed by grep over
  `src/main`, `src/debug` and `src/release`.
- `HomeScreen.kt:102` already spells `androidx.compose.foundation.shape.RoundedCornerShape` inline;
  with the import present, that fully-qualified name is collapsed in passing. No behaviour change.

### Modified: `app/src/test/java/app/webora/browser/design/WeboraThemeTest.kt`

Two new assertions, both about geometry rather than about token values:

- `a container role never rounds a dialog into a stadium` — lay every settable `Shapes` role out at
  `280 × 560` dp (Material's `DialogMinWidth` by `DialogMaxWidth`) through the real
  `createOutline`, and require every resolved corner radius to be at most a quarter of the width.
  A quarter, not a half: at exactly half the side is fully round, so the bound has to sit strictly
  inside the degenerate case, and 28 dp against 280 dp (a tenth) clears it with room while 999 dp
  (clamped to a half) fails by a factor of two.
- `the pill is a control value and no shape role carries it` — a direct structural assertion over
  `WEBORA_SHAPES`, so the collision is named as itself and not only caught through its consequence.

The width constant carries a comment recording where 280 dp comes from and why transcribing it is
acceptable here: material3's `DialogMinWidth` is `internal`, and the assertion is conservative in the
safe direction — an absolute corner that clears the bound at the narrowest width clears it at every
larger one, because the clamp only ever shrinks.

**If `createOutline` proves unreachable from `testDebugUnitTest`** — Compose's inline-class returns
can drag in stubs the unit-test classpath does not have — the geometry test is *dropped, not faked*.
The structural assertion stays as the gate, the tasklist records the reachability failure as a result
rather than as an inconvenience, and the plan's claim weakens honestly from "the resolved geometry is
asserted" to "the collision is asserted". Do not substitute a hand-computed clamp: reimplementing
Compose's arithmetic in the test would assert the plan's belief about `createOutline` rather than
`createOutline`.

### Modified: `app/src/androidTest/java/app/webora/browser/browser/SiteSkinConsentDialogTest.kt`

Add one instrumented case that renders the dialog at 360 dp and requires the complete heading —
including a non-default port — to be displayed, per acceptance criterion 5.

**This assertion is documentation, not the gate, and the plan says so rather than implying
otherwise.** `assertIsDisplayed()` passes over a clipped heading — that is precisely why runs 14 and
15 were needed to find this — so the case pins the requirement for a future harness that can see
pixels, and cannot detect a regression by itself. The gate is the JVM geometry test. `androidTest` is
not compiled by `scripts/pre-commit-check.sh` at all, so this file is compiled deliberately during
implementation rather than assumed green.

## Tests

| Test | Layer | Fails on the defect? |
|---|---|---|
| `a container role never rounds a dialog into a stadium` | JVM, new | **Yes** — 999 dp clamps to 140 dp at 280 dp wide, the bound is 70 dp |
| `the pill is a control value and no shape role carries it` | JVM, new | **Yes**, structurally |
| `every shape corner comes from the compiled radii` | JVM, existing | No — 999 dp is in `ALL`. Must still pass, proving 28 dp is a declared token and not a literal |
| `every radius below the pill is a multiple of the same base` | JVM, existing | No. Must still pass with `EXTRA_LARGE` in `ALL`, proving 28 dp is derived from the base |
| `the shape scale covers every role the public API can set` | JVM, existing | No. Must still pass — the role count is unchanged |
| `SiteSkinConsentDialogTest`, four existing cases | instrumented, existing | No. Must pass **unmodified**, which is the evidence that `UX-007`'s hierarchy did not move |
| the new 360 dp heading case | instrumented, new | No — documents the requirement; see above |

**Negative control (mandatory, recorded in the tasklist):** restore
`extraLarge = RoundedCornerShape(WeboraRadius.PILL)`, run `./gradlew :app:testDebugUnitTest`, confirm
both new assertions fail, restore the fix, confirm green. A test that passes with and without the fix
is decoration.

**Closing evidence:** a hosted `02-siteskin-consent.png` from a run whose commit SHA matches the
branch head, showing a rounded-rectangle dialog with the heading complete. Cited by run number and
SHA per `DEVX-002`, because a stale artifact looks exactly like a current one.

## Rollout / versioning

No schema, no spec, no fixture, no ADR. `ADR-013`'s named values (4 dp base, 20 dp gutter/cards,
999 dp pills) are all still true — this adds a container radius the ADR did not name and does not
contradict. `CLAUDE.md` gains a short `UX-009` note under the browser-owned design tokens section:
the pill is a control value, `AlertDialog` resolves its container to `extraLarge`, and that is the
collision to not reintroduce.

## Open questions

None carried into implementation. The two the research raised are decided here: 28 dp as a new
declared token, and the JVM geometry test as the load-bearing gate with the instrumented case
explicitly demoted to documentation.
