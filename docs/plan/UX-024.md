# UX-024 plan — the browser's navigation commands become one control

Status: PLAN_APPROVED

PRD: `docs/prd/UX-024.prd.md`
Research: `docs/research/UX-024.md`
Source of record: GitHub issue [#122](https://github.com/denrzv/webora/issues/122)

## Overview

Integrated chrome spends 136 dp of header and five dock slots presenting Back, Forward and Refresh
as three unrelated controls, one of which (Back) appears twice and one of which (Refresh) has a
whole row to itself. Research F1 measures the row at **40 dp of page**; F3 measures the dock
reduction and finds every remaining slot gets *wider*.

Four layers, in the order the gate can defend them:

1. **Decision.** `browserNavigationActions(canGoBack, canGoForward, canRefresh)` — a pure, total
   function returning a compiled three-element list of a closed enum. Everything the security
   argument rests on — count, order, membership, enabled source — is drivable by `./gradlew test`.
2. **State.** `IntegratedOverlay?` replaces `siteActionsExpanded`. One value, so criterion 13's
   mutual exclusion is structural rather than a pair of assignments, and `UX-022`'s three resets
   keep serving both surfaces.
3. **Surface.** The collapsed hub takes Back's leading `BrowserControlTile`; the bouquet is a
   `Popup` in its own window, expanding downward. `BrowserControlRow` is deleted.
4. **Evidence.** Source scans for the trust boundary, instrumented cases for the rendered half,
   hosted journey edits declared as pending acceptance.

## Flow

```
state.mode.canNavigateBack() ─┐
state.canGoForward ───────────┼─► browserNavigationActions ─► [BACK, FORWARD, REFRESH]
refreshAction(state) != None ─┘        (compiled order)          each with .enabled

                    tap ─► onNavigationExpandedChange(true) ─► overlay = BROWSER_NAVIGATION
                                                                  │ (one value, so SITE_HUB closes)
                                                                  ▼
                                                          Popup, own window
                                                          ├ outside tap  ─► overlay = null
                                                          ├ system Back  ─► overlay = null
                                                          └ selection    ─► overlay = null, then
                                                                            onNavigationCommand(c)
                                                                              BACK    → navigateBack
                                                                              FORWARD → controller.goForward
                                                                              REFRESH → dispatchRefresh
```

Every arrow on the right is a call that already had a call site before this ticket. No new
navigation mechanism, no new history semantics, no second dispatch path.

## Origin and trust boundary

**Decided here, before the file list, per `PROJECT_RULES.md`.**

A website's influence over this surface is exactly what it was over the Back tile it replaces: the
`SiteSkinColorScheme` painting the header *behind* the browser-owned tile. It gains nothing.

| Website may influence | Browser owns, and what enforces it |
|---|---|
| the header's background colour | already contrast-guarded by `SiteSkinTheme`; unchanged |
| — | **which commands exist**: a compiled `enum class BrowserNavigationCommand` with three entries |
| — | **their order**: the list `browserNavigationActions` returns, pinned by a JVM assertion |
| — | **their icons**: `R.drawable.ic_back` / `ic_forward` / `ic_reload`, bundled |
| — | **their names**: `R.string.back` / `forward` / `reload` — the same names regular chrome uses, per `DEVX-003` |
| — | **their enabled state**: `canNavigateBack()`, `canGoForward`, `refreshAction` — browser-observed |
| — | **their dispatch**: `navigateBrowserBack`, `controller::goForward`, `dispatchRefresh` |
| — | **the hub's own ground**: `BrowserControlTile`'s `MaterialTheme.colorScheme.surfaceContainer`, per `UX-014` |
| — | **whether the bouquet opens**: one browser-owned state value |

**The new risk this ticket creates, and the shape that closes it.** Research names it: the browser
bouquet and `UX-015`'s site bouquet will look alike by design, and the moment they share an item
model a manifest can publish an item that renders identically to Back. So they share **no type**.
`BrowserNavigationAction` carries a closed enum and a `Boolean`; it has no `icon` field, no `label`
field, no `NavigationItem`, and nothing constructs one from a `SiteSkinConfiguration`. A site
selection still goes `NavigationItem → ActionResolver → ResolvedAction`; a browser command goes
`BrowserNavigationCommand → when → controller`. The two paths do not meet, and a source scan is
what can see that.

**`UX-022`'s hint keeps its single reader.** `presentation.hub` selects among the browser's own
*site* surfaces and has no business here. `HubSurface.kt` remains the only file naming a
`HubPresentation` constant; the new code must not become the second.

**`UX-008` and `UX-014` are amended, and the amendment is narrow.** Both require integrated top
chrome to carry a leading browser-owned affordance before site branding, with browser-observed
enabled state, a browser callback, and no manifest seam to suppress, relabel, reorder, restyle or
dispatch it. Every clause survives. What changes is that the slot holds a control which *opens*
Back rather than *being* Back — and it holds Forward and Refresh too, which is strictly more browser
capability in browser-owned chrome, not less. The purpose those tickets state — SiteSkin does not
replace the browser's history contract — is unaffected. `CLAUDE.md` records the amendment in TASK-5
rather than leaving it to be rediscovered from a diff.

**Nothing in discovery, validation, consent, the cache, the renderer, event routing, capture policy,
`spec/` or `siteskin-core` is touched.** Criterion 20 is met by not editing those files and is
verifiable from the diff.

## Security, accessibility and the decisions taken

- **The collapsed hub is never disabled.** A hub that greys out at the history root *is* a Back
  button — criterion 2's failure — and a user who cannot open it also cannot reach Forward or
  Refresh. It always opens; its three children carry state. This is why criterion 8 says enabled
  state is exposed on the actions.
- **No decoration on the collapsed control.** Research left open whether it could carry, say, a dot
  when Forward is available. **Refused**: it is scope the issue did not ask for, and any state on
  the collapsed control walks back toward the Back-button reading criterion 2 forbids.
- **Disabled state is semantic, not chromatic.** `WeboraIconButton(enabled = false)` sets the
  `Disabled` semantics property; Compose's `IconButton` also dims, but the semantics is the
  contract, per `A11Y-001`.
- **48 dp targets.** Bubbles are `WeboraIconButton` inside 52 dp circles inside 60 dp slots; the one
  `MINIMUM_TOUCH_TARGET` owner is unchanged and no second name is introduced (`UX-002`).
- **Back precedence.** `PopupProperties(focusable = true, dismissOnBackPress = true,
  dismissOnClickOutside = true)` — the bouquet is its own window, so it consumes Back before
  `BrowserBackHandler` sees it. Same mechanism `SiteActionBouquet` already uses and `UX-022`
  records; `BrowserBack.kt` is not touched.
- **Close, then dispatch.** `onDismiss(); onCommand(c)` in that order, matching `ActionPetal`.
- **Teardown.** The bouquet lives inside `SiteSkinTopBar`, which composes only under
  `PROTECTED_INTEGRATED`. Losing that projection makes it structurally unreachable, not merely
  hidden — criterion 14's second half.
- **Reduced motion gains no reader, deliberately.** The bouquet composes and decomposes immediately
  under both policies. The issue permits it ("minimal/fade/instant … rather than requiring radial
  animation"), and introducing the browser's first animation inside a security-relevant overlay,
  where no local gate can observe it, is the wrong place to spend that first. `UX-013`'s standing
  obligation passes to the next ticket that adds a *real* decorative transition.
- **No new canonical frame.** `CI-009`'s inventory is pinned at six and belongs to a `CI-*` ticket.
  Stated so it is a decision rather than an omission.
- **Capture constraint, written down because it is invisible in the layout.** The bouquet overhangs
  `BROWSER_CONTENT_TAG` by ~40 dp (research F4). A `Popup` contributes nothing to layout but its
  pixels are in a device screenshot, so **no frame may be captured with the navigation bouquet open
  under `requirePageContent = true`** — `CI-005`'s defect, which is what happens when a modal is
  measured as page content.

## The arithmetic this plan commits to

**Header** (research F1) — `heightIn(min = 96.dp)` absorbs the removal, so the saving is real:

| Band | Today | After |
|---|---|---|
| gutter + `BrandRow` + `BrowserControlRow` + curve | 20 + 48 + 48 + 20 = 136 | 20 + 48 + 20 = 88 |
| rendered (min 96) | **136** | **96** |

**Dock** (research F3) — 280 dp of slot width at the 320 dp floor:

| Slots | Each | 52 dp centre circle |
|---|---|---|
| 5 today | 56.0 dp | fits, 2 dp each side |
| 3 after | 93.3 dp | fits, 20.6 dp each side |

**Bouquet** — 20 dp gutter + 3 × 60 dp slots = 200 dp at 320 dp width, 120 dp spare; icon-only, so
200% font scale does not grow it.

**`headerIdentityPlacement` is untouched.** `HEADER_FIXED_WIDTH`'s first term is 48 + 8, and the hub
occupies the same 48 dp tile in the same slot. Only the KDoc's naming of that term changes — if this
plan needed to edit the constant, the footprint would have moved and criterion 17 would be at risk.

## File-by-file plan

### TASK-1 — the decision and the state type

- **New** `app/src/main/java/app/webora/browser/siteskin/BrowserNavigationCommands.kt`
  - `internal enum class BrowserNavigationCommand { BACK, FORWARD, REFRESH }`
  - `internal data class BrowserNavigationAction(val command: …, val enabled: Boolean)`
  - `internal fun browserNavigationActions(canGoBack, canGoForward, canRefresh): List<…>` — three
    entries, always, in declared order. The shape `browserMenuCommands()`, `refreshAction`,
    `rendererMountAction` and `routeRendererEvent` already use, for the reason `BROWSE-009` gives:
    the wiring lives inside a `@Composable`, so the decision has to leave it to be testable.
- **New** `app/src/main/java/app/webora/browser/siteskin/IntegratedOverlay.kt` —
  `internal enum class IntegratedOverlay { SITE_HUB, BROWSER_NAVIGATION }`, with the KDoc recording
  why it is one nullable value rather than two booleans (`UX-022`'s three resets).
- **New** `app/src/test/java/app/webora/browser/siteskin/BrowserNavigationCommandsTest.kt`
  - the list is exactly three, in order, for every combination of the three flags (8 cases);
  - each `enabled` tracks its own input and no other — the anti-vacuity guard, since a function
    returning three always-enabled actions would satisfy a count-and-order test;
  - the enum has exactly three constants, so a fourth is a test failure rather than a silent
    addition.
- Negative controls, recorded in the tasklist with their results:
  - make the function take a `List<SiteSkinItemModel>` and derive from it → must not compile /
    must fail the isolation scan in TASK-4;
  - return the three actions in a different order → the order assertion must fail;
  - hard-code `enabled = true` → the per-flag assertions must fail while count and order still pass,
    which is the point of separating them.

### TASK-2 — the hub, the bouquet, and the row that goes away

- **New** `app/src/main/res/drawable/ic_history.xml` — clock face plus counter-clockwise arrow, 24 dp
  / 24-unit viewport, `strokeWidth="1.9"`, round caps and joins, no `fillColor`, one declared colour.
  Research F7 rules out every reuse candidate; the issue names "a navigation/history icon", and Back,
  Forward and Refresh are the history family, so the glyph names the group rather than a member.
- **Modified** `app/src/test/java/app/webora/browser/design/BrowserIconContractTest.kt` — `EXPECTED`
  gains `ic_history`; `BUDGET` 20 → 21, with the reason at the constant, as `UX-005` and `UX-021`
  each did. A raise is a decision someone makes on purpose.
- **Modified** `app/src/main/res/values/strings.xml` — `siteskin_open_navigation` = *Browser
  navigation*. Distinct from `R.string.back`: criterion 2.
- **New** `app/src/main/java/app/webora/browser/siteskin/SiteSkinNavigationHub.kt`
  - `SiteSkinNavigationHub(actions, expanded, onExpandedChange, onCommand)` — the collapsed control
    inside `BrowserControlTile(SITESKIN_NAV_HUB_TAG)`, plus the `Popup`.
  - `Popup(alignment = Alignment.TopStart, offset = IntOffset(0, +…))` — the inversion of
    `SiteActionBouquet`'s upward anchor. `TopStart` resolves against layout direction, so RTL is
    correct with no physical constant (`UX-022`).
  - One bubble per action, tagged by command; its own composable, sharing **no type** with
    `ActionPetal`.
  - A separate file rather than more of `SiteSkinTopBar.kt`: it is a distinct surface with its own
    tags, and a source scan can then read its declaration without slicing.
- **Modified** `app/src/main/java/app/webora/browser/siteskin/SiteSkinTopBar.kt`
  - `BrandRow`'s leading `BrowserBack(...)` becomes `SiteSkinNavigationHub(...)`.
  - `private fun BrowserBack` and `private fun BrowserControlRow` are **deleted**, with
    `SITESKIN_CONTROLS_TAG`.
  - `BrowserControlTile` stays and is now shared by the hub and the bubbles — one ground, one owner,
    per the reason `UX-021` records about a `when` that shipped twice.
  - `SITESKIN_BACK_TAG` and `SITESKIN_REFRESH_TAG` **keep their exact values** and move onto the Back
    and Refresh bubbles. Research's open question resolved: the bubble genuinely *is* Back, so the
    tag stays honest, `SITESKIN_FORWARD_TAG` joins them, and the hosted diff is a wait-and-open
    rather than a rename. `SITESKIN_NAV_HUB_TAG` and `SITESKIN_NAV_BOUQUET_TAG` are new.
  - Parameters: `canGoBack, onBack, canRefresh, onRefresh` → `navigation: List<BrowserNavigationAction>,
    onNavigationCommand, navigationExpanded, onNavigationExpandedChange`. Seven parameters before,
    seven after.
- **Modified** `app/src/main/java/app/webora/browser/siteskin/HeaderIdentityPlacement.kt` — KDoc
  only: `HEADER_FIXED_WIDTH`'s first term is the hub's 48 + 8, not Back's. The number does not move,
  which is the point.
- **Modified** `app/src/test/java/app/webora/browser/siteskin/SiteSkinTopBarContractTest.kt` and
  `SiteSkinNavigationContractTest.kt` — see TASK-4's table; the assertions naming the deleted
  declarations move in this commit so the gate stays green.
- **Modified** `app/src/androidTest/java/app/webora/browser/siteskin/SiteSkinTopBarTest.kt` — the
  cases naming `SITESKIN_CONTROLS_TAG` and the standalone refresh tile.

### TASK-3 — three dock slots, and one overlay value

- **Modified** `app/src/main/java/app/webora/browser/siteskin/SiteSkinDock.kt`
  - `canGoBack`, `canGoForward`, `onBack`, `onForward` and their two `DockCommand` calls are removed;
    `SITESKIN_DOCK_BACK_TAG` and `SITESKIN_DOCK_FORWARD_TAG` go with them.
  - Brand Hub, Tabs, More remain, in that order, still `weight(1f)` each. No dimension, radius,
    height, colour or geometry constant changes — research F3 shows the slots simply get wider.
- **Modified** `app/src/main/java/app/webora/browser/browser/BrowserScreen.kt`
  - `var siteActionsExpanded by remember { mutableStateOf(false) }` becomes
    `var overlay by remember { mutableStateOf<IntegratedOverlay?>(null) }`. Every existing

    clears keep their sites unchanged.
  - `RegularBrowser` loses `siteActionsExpanded`, `onSiteActionsToggle`, `onSiteActionsDismiss` and

  - `RegularBrowser` builds `browserNavigationActions(canNavigateBack, state.canGoForward, canRefresh)`
    for the top bar and dispatches with an exhaustive `when`: `BACK → onBack`,
    `FORWARD → controller::goForward`, `REFRESH → onRefresh`. Exhaustive so a fourth command is a
    compile error, not a silent no-op.
  - `BrowserNavigationShell`'s regular/Home branch is **not touched**: `UX-016`'s six slots and their
    Reload stay exactly where they are.
- **Modified** `app/src/test/java/app/webora/browser/siteskin/SiteSkinNavigationContractTest.kt` —
  `fixedDock`'s ordered list becomes the three that remain, **paired in the same commit** with a
  negative control that fails when a model-derived command is added to them. Research names the risk

- **Modified** `app/src/androidTest/java/app/webora/browser/siteskin/SiteSkinDockTest.kt` — the

- Regular and Home chrome. `UX-016`'s dock and its Reload are untouched.
- `refreshAction`'s `Retry`/`Reload`/`None` decision, and `reload()`'s rule against rewriting
  `hostedUrl` (`BROWSE-010`, `BROWSE-011`).
- The site bouquet, the drawer, `presentation.hub`, and `actionBouquet()`'s name, order, dedup and
  cap (`UX-022`).
- The trust chip, its ground, its floor, its declaration order, and `headerIdentityPlacement`'s
  arithmetic (`UX-021`, `UX-023`).
- A seventh canonical frame, and any change to `RenderedContentPolicy`, `ScreenEvidencePolicy`,
  `AnrDismissalPolicy` or `candidateVerdict`.
- An animation. Deferred with a reason above, not forgotten.
