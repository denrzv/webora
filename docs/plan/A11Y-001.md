# A11Y-001: Implementation plan
Status: PLAN_APPROVED

## Overview
Accessibility is added as **browser-owned infrastructure with a gate**, not as a sweep of per-screen
fixes. A sweep is correct exactly once and then decays: the next screen forgets the 48 dp minimum
the same way `HomeScreen` forgot `strings.xml`. So each guarantee gets a single enforcement point
plus a test that fails when a call site bypasses it.

Three enforcement shapes are used, in decreasing order of preference:

1. **A wrapper the call site must use.** Touch targets and browser copy become impossible to get
   wrong because the raw component is no longer reachable from browser-owned UI.
2. **A pure function under JVM test.** Announcement selection, security-identity derivation, the
   bound on accessible manifest text, and light/dark projection are decided outside composition and
   tested without a device — the gate is JVM-only, so anything proven only on an emulator is
   documentation, not enforcement.
3. **Instrumented evidence.** Reflow at 2.0x font scale and the resulting TalkBack announcements are
   recorded in QA. They are evidence, never the sole proof of an acceptance criterion.

## Flow
- **discovery** — unchanged. No fetch, no origin comparison, and no cache interaction is added.
- **validation** — unchanged. `:siteskin-core` still owns truncation; the app re-applies the label
  bound at projection time as defense in depth, reading the limit from `SiteSkinLimits` so the two
  cannot drift.
- **normalization** — one new normalization step, in the app: manifest label text is bounded again
  before it becomes a `contentDescription`.
- **UI state** — `BrowserState` gains no field. Announcements are *derived* from a state transition
  by a pure function rather than stored, so no code path can forget to clear a stale announcement.

## Data
- **Trust boundary.** Unchanged in position, newly explicit in the accessible channel:

  | Accessible text | Source | May contain manifest text? |
  |---|---|---|
  | Security identity (domain + TLS) | `SecurityPresentation` ← `SiteOrigin` | **No** |
  | Loading / loaded / failed announcement | `strings.xml` | **No** |
  | Browser control names and state | `strings.xml` | **No** |
  | Site item name | `NavigationItem.label`, bounded | Yes — as a name only |
  | Top-bar title / subtitle | `toolbar.*`, core-truncated | Yes — as ordinary text, beside the security node |

  The rule the code must make true: **manifest text is never concatenated with browser security
  wording, and never becomes the description of a browser control.** A site may name its own
  button; it may not narrate the connection.
- **storage / cache keys** — none added. This ticket persists nothing.

## Security
- **Origin binding.** Accessible security text is derived only from `securityPresentation(mode)`,
  whose only input is the committed `SiteOrigin`. `state.addressText` is user-editable and page
  content is attacker-controlled; neither is reachable from the security node. A null origin
  produces **no node**, not an empty or guessed one — an absent announcement is honest, a blank one
  is a claim.
- **Allow-lists.** Unchanged. No new scheme, action, icon, or MIME decision. The decorative glyph
  map in `SiteSkinChrome` stays a closed local mapping with cleared semantics.
- **Bounding.** `SiteSkinChromeModel` truncates every label to `SiteSkinLimits.MAX_LABEL_LENGTH`
  before it can reach `contentDescription`. This duplicates core deliberately: the semantics tree is
  the one surface where a bound that exists only visually (`maxLines = 1`, ellipsis) provides no
  protection at all, because assistive technology reads the string, not the layout.
- **Fallback on failure.** Every added behaviour degrades to the current behaviour: no origin → no
  security node; no transition → no announcement; unparseable colour → the existing guarded default.
  Nothing here can prevent a page from rendering.
- **Non-suppressibility.** `ADR-006` is extended to the accessible channel by construction: the
  security node is emitted by browser code with browser copy, and no manifest field is an input to
  whether it exists.

## File-by-file plan

### New: `app/src/main/java/app/webora/browser/browser/BrowserAccessibility.kt`
The single enforcement point. Contains:
- `MINIMUM_TOUCH_TARGET: Dp = 48.dp` and `Modifier.browserTouchTarget()`.
- `WeboraButton` / `WeboraTextButton` — thin wrappers over Material 3 `Button` / `TextButton` that
  bake in the minimum. Material 3 `Button` applies `defaultMinSize(minHeight = 40.dp)` and does
  **not** call `minimumInteractiveComponentSize()`, so without these every browser control is a
  40 dp target. `Switch` already applies it and needs a name, not a size.
- `BrowserAnnouncement` (`LOADING` / `LOADED` / `FAILED`) and
  `browserAnnouncement(previous: BrowserState, current: BrowserState): BrowserAnnouncement?` —
  pure, returns `null` when nothing changed, so repeated recompositions do not re-announce.

### New: `app/src/test/java/app/webora/browser/browser/BrowserAccessibilityTest.kt`
JVM tests for `browserAnnouncement` transitions and the target constant.

### New: `app/src/test/java/app/webora/browser/browser/BrowserSurfaceConventionsTest.kt`
The convention gate, in the spirit of `assertNoAndroidDependencies` and `SpecCorpusTest` — a rule
that is checkable is a rule, and a rule that is only written down is a preference. It reads the
browser-owned Compose sources and asserts:
1. No string literal is passed directly to `Text(` — all visible copy resolves from `strings.xml`.
2. Browser-owned UI does not import Material 3 `Button` / `TextButton` directly; only
   `BrowserAccessibility.kt` may, so the touch-target minimum cannot be bypassed at a call site.

Scanned files are discovered, not listed: every `.kt` under the app source tree containing
`@Composable`, minus a small exemption set carrying its reason inline (`HardenedWebView.kt` hosts an
`AndroidView` and declares no copy; `BrowserAccessibility.kt` is the wrapper itself). Discovering
rather than listing is what makes a *new* screen subject to the rule.

The decorative glyph mapping in `SiteSkinChrome.SiteSkinIcon` remains exempt by construction: its
literals are assigned to a local before `Text(glyph)`, and the node carries
`clearAndSetSemantics { }`. It is iconography with no accessible presence, not copy.

### Modified: `app/build.gradle.kts`
Wire the app source directory into the `test` task as `webora.app.src` with `inputs.dir`, mirroring
`:siteskin-core`'s `siteskin.spec.dir`, so editing a composable reruns the convention gate instead
of hitting an up-to-date check.

### Modified: `app/src/main/res/values/strings.xml`
All copy currently inline in `HomeScreen` and `OnboardingScreen`; the accessible names for the
address-bar controls, the privacy `Switch`, and the per-origin reset action; the loading/loaded/
failed announcements; the regular-mode security description; navigation and toggle state
descriptions; the top-bar separator and quick-action glyph.

### Modified: `app/src/main/java/app/webora/browser/browser/BrowserScreen.kt`
- `AddressBar`: replace the plain interpolated security `Text` with a dedicated semantics node
  built from `SecurityPresentation`, matching what `SiteSkinTopBar` already does; move the control
  `Row` to a `FlowRow` so it wraps instead of clipping at large font scale; give each control an
  accessible name; route through `WeboraButton`.
- `LinearProgressIndicator`: attach an assertive live region carrying the derived announcement.
- `BrowserErrorPage`: mark the title as a heading and announce the failure; `WeboraButton`.
- Dialogs (`ExternalUrlDialog`, `ExternalNavigationDialog`, `SiteSkinConsentDialog`,
  `ClearBrowsingDataDialog`): `WeboraButton`. The consent dialog's three-button `Row` also wraps.
- `RegularBrowser`: select the SiteSkin projection with `isSystemInDarkTheme()`.

### Modified: `app/src/main/java/app/webora/browser/browser/HomeScreen.kt`, `OnboardingScreen.kt`
Resolve all copy from resources; `WeboraButton` / `WeboraTextButton`; make the onboarding `Column`
scrollable; give the step indicator a progress semantics description rather than bare text.

### Modified: `app/src/main/java/app/webora/browser/browser/PrivacySettingsScreen.kt`
Name the `Switch` (its role and 48 dp target already come from Material) and give it a textual state
description; make each reset button's accessible name include the origin it resets, so a screen full
of identical "Reset decision" buttons becomes distinguishable; make the `Column` scrollable.

### Modified: `app/src/main/java/app/webora/browser/siteskin/SiteSkinChromeModel.kt`
Bound `label` to `SiteSkinLimits.MAX_LABEL_LENGTH` in `NavigationItem.toModel()`, so every consumer
— visible label and `contentDescription` alike — receives the bounded string.

### Modified: `app/src/main/java/app/webora/browser/siteskin/SiteSkinChrome.kt`
Add a textual `stateDescription` for navigation selection; resolve the quick-action glyph from
resources.

### Modified: `app/src/main/java/app/webora/browser/siteskin/SiteSkinTheme.kt`
Add `scheme(darkTheme: Boolean)`. The projection choice is a browser decision from a system setting;
`from(configuration)` remains the only constructor and no colour role is added.

### Modified: `app/src/main/java/app/webora/browser/siteskin/SiteSkinTopBar.kt`
Resolve the separator from resources. No structural change — the security node and cleared logo
semantics are already correct.

### New: `docs/accessibility/CONFORMANCE.md`
Each guarantee mapped to the WCAG 2.2 AA criterion, the enforcing code, and the enforcing test.

### Modified: `CLAUDE.md`, `docs/ROADMAP.md`
An `A11Y-001` architecture section and the roadmap tick.

## Tests
| Guarantee | JVM test (gate) | Instrumented evidence (QA) |
|---|---|---|
| Copy is browser-owned | `BrowserSurfaceConventionsTest` literal rule | — |
| 48 dp targets cannot be bypassed | `BrowserSurfaceConventionsTest` import rule + constant assertion | target size at 1.0x/2.0x |
| Announcement selection | `BrowserAccessibilityTest` transitions | live-region announcement |
| Security identity is origin-only | `SecurityPresentationTest` (extended) | node present in both modes |
| Accessible manifest text is bounded | `SiteSkinChromeModelTest` — **negative control** | — |
| AA contrast, both projections | `SiteSkinThemeTest` adversarial corpus — **negative control** | — |
| Reflow at 2.0x | — | onboarding, privacy, control row, consent dialog |

Two negative controls are required and must be recorded in the tasklist: removing the label bound
must fail the chrome-model test, and removing `guardContainer` must fail the contrast corpus. A
contrast test that passes with the guard deleted is measuring the fixtures, not the guard.

## Rollout / versioning
No schema change, no manifest field, no migration, no persisted state. The one user-visible
behaviour change is that integrated chrome follows the system dark theme; it is a projection already
computed and guarded since `SKIN-001`, now selected instead of discarded.
