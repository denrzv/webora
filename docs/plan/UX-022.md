# UX-022 plan — A hub presentation hint, and a drawer that makes the whole menu reachable

Status: PLAN_APPROVED

Issue: [denrzv/webora#112](https://github.com/denrzv/webora/issues/112)
PRD: `docs/prd/UX-022.prd.md`
Research: `docs/research/UX-022.md`

## Overview

Four layers, landing in the order research finding F9 establishes, each independently green:

1. **Protocol.** An optional top-level `presentation` object with an optional `hub` string, carried
   as a closed normalized enum into `SiteSkinConfiguration`. Pattern in the schema, vocabulary in
   the security layer — the `normalizeIcon` shape, for `ADR-007`'s reason.
2. **Policy.** One pure `resolveHubPresentation(hint): HubSurface`, `AUTO → DRAWER` today, drivable
   by the JVM gate through every input.
3. **Component.** A browser-owned start-side drawer presenting quick actions, primary navigation and
   the extended menu as three headed groups, with all twenty permitted `menu` entries reachable.
4. **Wiring.** The dock's centre Brand Hub opens the resolved surface. One visibility state, the
   existing three resets, the existing `ActionResolver` path.

## Flow

1. `presentation.hub` survives parse as raw JSON; `SecurityValidator.Normalizer` maps `auto` /
   `bouquet` / `drawer` to `HubPresentation`, and anything else to `AUTO` plus a `warn` diagnostic
   pointing at `/presentation/hub`. Nothing is dropped and nothing is rejected.
2. `SiteSkinConfiguration` carries a **nullable** `presentation` holder — `null` means the manifest
   declared no object — plus one accessor collapsing `null` and `AUTO` so no consumer writes
   `?: AUTO` twice (F3).
3. `resolveHubPresentation` maps the normalized hint to `HubSurface.DRAWER` or `HubSurface.BOUQUET`.
4. `BrandHubCommand` opens whichever the resolver returned. `siteActionsExpanded` remains the one
   visibility state and keeps its three existing resets (F6).
5. Selecting any drawer row closes the drawer, then dispatches the original trusted `NavigationItem`
   through `dispatchSiteItem` → `ActionResolver`.
6. Back with the drawer open is consumed by the drawer's own window before `BrowserBackHandler`
   sees it (F7).

## Origin and trust boundary

The hint selects among **compiled browser components** and can do nothing else. Its whole value space
is three tokens, closed at the validator, so by the time any UI sees it an unknown token is
indistinguishable from an absent one. It has no path into origin binding, action validation, scheme
allow-listing, limits, contrast correction, consent, the dock's command set, or the browser trust
surface.

Drawer content is the same trusted `NavigationItem` values the bouquet already dispatches, projected
by the `SiteSkinChromeModel.from()` that already exists — no new projection of untrusted data.
Labels stay re-bounded by `accessibleLabel`. Colours come only from the guarded
`SiteSkinColorScheme` and `WeboraTheme`. No new network, storage, asset or permission surface.

`HARDEN-002`, `UX-015`'s five dock commands and their order, `UX-017`'s identity treatment and
`UX-012`'s teardown are all unchanged, and criterion 18's negative control proves no `presentation`
value can move any of them.

## Security and accessibility

- **Pattern, never `enum`** in `siteskin-1.0.schema.json`, anchored `(?![\s\S])` and not `$`. An
  enum turns `"drawr"` into `SS-E-SCHEMA-INVALID` and discards a working integration over a typo —
  the outcome `ADR-007` refuses, and `schemaDoesNotEnumerateActionTypesOrIcons` is the assertion
  that already argues it.
- **All three structural copies move together** (F1): the published schema, `ManifestStructure` in
  `ManifestValidation.kt`, and `UnknownFieldScanner.rootFields` in `ManifestParser.kt`. The third is
  cross-checked by nothing, and omitting it emits `SS-W-FIELD-UNKNOWN` on `/presentation` for every
  conforming manifest — the diagnostic drift `SPEC-003` exists to prevent.
- **The canonical result stays silent when the manifest was silent** (F3). A non-null field would
  rewrite every `.expected.json`, including `bloom-flowers.expected.json`, whose body is pinned by
  SHA-256 in two repositories.
- **The active-route pair must separate in both projections** (F8). `UX-020` found
  `surfaceVariant`/`primaryContainer` collapse in dark theme; the drawer uses
  `primary`/`onPrimary` against `secondary`/`onSecondary`, the pair `ActionPetal` already uses and
  `SKIN-001` already guards. State is never colour-only — `stateDescription` carries it, as
  `SiteSkinBottomNavigation` already does.
- **Only navigation rows publish selection.** Quick actions and menu rows are actions, not routes.
- Start-side via `Alignment.Start`/layout direction, never a physical left/right constant.
- Every interactive row meets the one 48 dp `MINIMUM_TOUCH_TARGET`; every icon-only affordance
  carries an accessible name; the drawer scrolls at 200% font scale on a 320 dp host.

## File-by-file plan

### TASK-1 — protocol, fixtures and spec

- **Modified** `spec/siteskin-1.0.schema.json` — optional `presentation` object with optional `hub`
  string, `pattern` constrained, anchored `(?![\s\S])`.
- **Modified** `siteskin-core/.../ManifestValidation.kt` — `ManifestStructure` gains the section;
  `DiagnosticCode` gains `PRESENTATION_UNKNOWN("SS-W-PRESENTATION-UNKNOWN")` beside
  `ICON_UNKNOWN`.
- **Modified** `siteskin-core/.../manifest/ManifestParser.kt` — `rootFields` gains `presentation`;
  `inspectKnownValue` dispatches its nested field set.
- **Modified** `siteskin-core/.../SecurityValidator.kt` — `Normalizer` gains the closed mapping,
  modelled directly on `normalizeIcon`: unknown value → `AUTO` + `warn` at `/presentation/hub`.
- **Modified** `siteskin-core/.../model/SiteSkinConfiguration.kt` — nullable `presentation` holder
  parameter on `create`, plus the collapsing accessor.
- **Modified** `siteskin-core/.../manifest/SiteSkinManifestDto.kt` — the field, so the DTO and the
  validation path do not describe different formats.
- **New** `spec/fixtures/valid/presentation-hub-unknown.json` + `.expected.json`.
- **Modified** `spec/diagnostics.json` — the registry entry, in the same commit as its fixture, or
  `SpecCorpusTest`'s both-directions assertion is red.
- **Modified** `spec/SPEC.md` — the field, its value space, its disposition, its §4.2 minor status,
  and the §12 statement that the canonical result carries `presentation` only when declared.

### TASK-2 — the resolution policy

- **New** `app/src/main/java/app/webora/browser/siteskin/HubPresentation.kt` — closed `HubSurface`
  and the pure `resolveHubPresentation`. Kept **out of** `ExpressiveSiteSkinPresentation`, which
  deliberately holds only colour and motion; a surface choice is a fourth kind of thing.
- **New** `app/src/test/.../HubPresentationTest.kt` — every input including null, with the negative
  control that `AUTO` routes through the policy rather than being a compiled alias (F4).

### TASK-3 — the drawer

- **New** `app/src/main/java/app/webora/browser/siteskin/SiteSkinHubDrawer.kt` — a
  `Dialog(usePlatformDefaultWidth = false)` over an opaque `Surface`, start-aligned. This is
  `UX-018`/`UX-020`'s established list-surface shape and, unlike `ModalNavigationDrawer`, it is a
  separate window that consumes Back structurally (F7). Header carries the validated identity and
  the already-published `BrandAsset` with its monogram fallback — no second fetch. Three headed
  groups; scrolling content; geometry private and browser-owned.
- **Modified** `siteskin/SiteSkinChromeModel.kt` — isolate the compact projection. `actionBouquet()`
  keeps its name, order, dedup and cap so `SiteSkinChromeModelTest` passes **unedited** (F5).
- **New** `app/src/test/.../SiteSkinHubDrawerContractTest.kt` — source structure: no raw manifest
  string comparison, no dock restructuring, selection semantics only on navigation rows.

### TASK-4 — wiring

- **Modified** `siteskin/SiteSkinDock.kt` — `BrandHubCommand` opens the resolved surface. The five
  commands, their order and their callbacks are untouched; `SiteSkinNavigationContractTest`'s
  `fixedDock` scan must pass unedited.
- **Modified** `browser/BrowserScreen.kt` — pass the resolved surface; keep `siteActionsExpanded` as
  the single visibility state with its existing three resets (F6). `BrowserBack.kt` is **not**
  touched.
- **Modified** `inspector/InspectorSnapshot.kt` — a requested-vs-effective row in the established
  `InspectorItemCount(trusted, rendered)` shape, so a site owner whose drawer did not appear has
  somewhere to look.
- **Modified** instrumented tests — drawer open/dismiss/Back, and the existing dock/sheet suites.

## Tests

- `./gradlew :siteskin-core:test` first — the protocol half needs no Android SDK.
- `./gradlew :app:testDebugUnitTest`
- `./gradlew :app:compileDebugAndroidTestKotlin` — explicitly; the gate never compiles `androidTest`,
  and `UX-021` broke two instrumented tests exactly that way.
- `bash scripts/pre-commit-check.sh`
- `pre-commit run end-of-file-fixer --all-files` and `trailing-whitespace` — the repo gate does
  **not** run the pre-commit hook set, which is how `UX-021` went red in CI on a green local gate.

Negative controls, run and recorded per task:

1. `enum` instead of `pattern` in the schema → an unknown `hub` must become a whole-manifest
   rejection, proving the pattern choice is load-bearing.
2. Omit `presentation` from `rootFields` → a conforming manifest must emit `SS-W-FIELD-UNKNOWN`.
3. Make the configuration's presentation field non-null → existing `.expected.json` files must
   fail, proving the nullable holder is what keeps the corpus byte-identical.
4. Map `AUTO` to the drawer at the call site instead of through the resolver → the policy test must
   fail.
5. Give the drawer its own visibility state → a tab-switch case must fail.

## Rollout / versioning

A **minor** schema bump: `SPEC.md` §4.2(1)/(7) make an optional top-level section additive by
definition, so no existing manifest migrates and no `versions.json` decision changes. `layerOrder`
is unchanged — the new code is a `security`-layer `warn`.

`spec/fixtures/valid/bloom-flowers.json` is **not** touched; publishing the hint on
`denrzv/bloom-flowers` is a separate cross-repository change with its own five-copy digest
discipline, and it must follow browser support rather than lead it.

## Out of scope

Raising any item cap, a new action type or icon token, a second asset path, removing the bouquet,
redesigning `BrowserNavigationShell` or the browser section of `IntegratedBrowserMenuSheet`, and
hosted cross-presentation acceptance — `CI-010` (#115) owns that.

## Open questions

None. Two PRD constraints are carried as decisions: pattern over enum, and a canonical result that
carries `presentation` only when the manifest declared one.
