# UX-015: Implementation plan
Status: PLAN_APPROVED

## Overview

Replace protected integrated mode's persistent site bottom navigation and over-content quick-action
launcher with the UX-013 floating dock. Fill it with five fixed browser commands—Back, Forward,
brand hub, Tabs, More—and move the existing trusted SiteSkin navigation/quick actions into a
separately attributed modal hub. Reuse the current pure chrome model, typed dispatch, browser menu
vocabulary, active controller, and tab switcher; do not create a second action or tab authority.

## Flow

1. Existing discovery, validation, consent, exact-origin activation, and selected-tab projection
   produce `BrowserMode.Integrated`; no pipeline or protocol stage changes.
2. `RegularBrowser` exhaustively reads `chromeHandoff()`. For `PROTECTED_INTEGRATED`, it constructs
   one `ExpressiveSiteSkinPresentation` and one `SiteSkinChromeModel` from the current trusted
   configuration and browser-observed page URL.
3. After WebView/error content, `ExpressiveSiteSkinDock` composes Back, Forward, brand hub, Tabs,
   and More in fixed order. History enabled state comes from current `BrowserState`; callbacks are
   explicit current-controller/session operations.
4. Brand hub or `open_menu` raises the same browser-owned visibility state. The current integrated
   model is projected into separately headed navigation and quick-action groups plus the closed
   browser section; selections close the hub before typed dispatch.
5. Tabs and browser More reuse existing `BrowserScreen` state/surfaces. Tab selection, page start,
   settings deactivation, origin handoff, or any non-integrated projection closes or makes the hub
   ineligible before another tab/mode can receive its callbacks.
6. Regular and Home projections continue to render `BrowserNavigationShell` unchanged.

## Origin-boundary implications and browser-owned contract

The UI receives only the active trusted `SiteSkinConfiguration`, whose `SiteOrigin` was already
canonicalized and exact-origin bound. It performs no URL/origin trust comparison. The website may
influence only existing trusted bounded site labels, local semantic icons, typed navigation/actions,
active-route result, bounded brand text, and contrast-guarded SiteSkin colour roles. The
browser-observed current URL is matching/resolution input, never manifest authority.

Dock count/order, icons, labels, enabled state, callbacks, targets, geometry, inset, motion,
attribution, open/dismiss policy, Tabs/More surfaces, favourite/browser menu commands, and
browser-token command sub-surfaces are browser-owned. A site item remains a `NavigationItem` until
the existing `ActionResolver`; no raw URI, intent, tab id, controller, or generic command crosses
the hub seam. Loss of `PROTECTED_INTEGRATED` authorization removes the dock/hub. Visibility state
alone is remembered, and every dispatch uses the current authorized model/callbacks.

## Data

- No schema, DTO, core model, persistence, network, consent, or asset change.
- Reuse `SiteSkinChromeModel` as the sole bounded navigation/quick-action/browser-menu projection.
- Hub state is an ephemeral boolean authorized by current integrated composition; it stores no site
  item, URL, configuration, origin, controller, or tab reference.
- Add no customizable dock-item collection; five explicitly named parameters preserve the closed
  browser command hierarchy.

## Security

- Origin/tab isolation: gate dock and hub on active `PROTECTED_INTEGRATED`; close hub on tab/session
  changes and navigation generation changes; callbacks are current-composition, current-controller.
- Typed dispatch: hub emits only original trusted `NavigationItem`; existing resolver and external
  confirmation paths remain unchanged.
- Browser ownership: local vector resources, localized strings, fixed slot order, explicit named
  callbacks, and browser menu enum. Manifest input cannot produce a browser command.
- Separation: site navigation/actions and browser commands have distinct headings/containers and
  callback types. Empty site content never removes the browser dock or browser hub section.
- Fallback: losing integrated mode closes/removes branded surfaces and ordinary chrome resumes;
  reduced motion never delays dismissal or command availability.

## File-by-file plan

### Modified: `app/src/main/java/app/webora/browser/siteskin/SiteSkinChrome.kt`

Replace the old standalone bottom navigation/quick-action presentation with a modal
`SiteSkinNavigationHub` that renders bounded navigation and quick actions under explicit
site-attributed headings, preserves active selected semantics/local decorative icon mapping, and
keeps the separately headed browser section. Retain typed callbacks and shared browser labels.

### New: `app/src/main/java/app/webora/browser/siteskin/SiteSkinDock.kt`

Define the integrated dock content API with explicit Back, Forward, brand hub, Tabs, and More slots.
Use `ExpressiveSiteSkinDock`, equal weighted minimum-48-dp browser buttons, local icons/strings,
fixed order, enabled semantics, and browser-token command treatment. The brand control may show a
bounded monogram/semantic brand cue but receives no arbitrary site content or callback list.

### Modified: `app/src/main/java/app/webora/browser/browser/BrowserScreen.kt`

Rename/generalize the existing site-menu visibility to the navigation hub, route `open_menu` and
the dock brand callback to it, close it at navigation/tab/mode boundaries, and reuse current
browser-command dispatch. In `RegularBrowser`, compute the integrated presentation/model once,
remove `SiteSkinQuickActions`/`SiteSkinBottomNavigation`, and render the expressive dock with current
Back/Forward/Tabs/More callbacks. Keep regular/Home shell and UX-014 top/status/error composition.

### Modified: `app/src/main/res/values/strings.xml`

Add localized browser-authored hub/dock content descriptions and explicit navigation/quick-action
section headings where existing copy is insufficient.

### Modified: `app/src/test/java/app/webora/browser/siteskin/SiteSkinNavigationContractTest.kt`

Add positive/source negative controls requiring explicit fixed dock order, browser resources and
named callbacks, typed hub sections, and integrated replacement; reject generic command/item lists,
manifest-derived order/geometry/browser styling, and continued old bottom/overlay composition.

### Modified: `app/src/test/java/app/webora/browser/siteskin/SiteSkinChromeModelTest.kt`

Retain caps/active-route evidence and add any pure hub grouping/authorization projection needed to
prove empty, selected, and bounded behavior without Android.

### New: `app/src/androidTest/java/app/webora/browser/siteskin/SiteSkinDockTest.kt`

Compose the dock at 320 dp/200% font in light/dark presentations. Assert five ordered, displayed,
at-least-48-dp targets; history enabled/disabled state; isolated callback invocation; and manifest
content cannot alter command labels/count.

### Modified: `app/src/androidTest/java/app/webora/browser/browser/BrowserSiteSkinLayoutTest.kt`

Assert protected integrated mode shows dock rather than old bottom navigation/quick-action overlay,
opens the hub, exposes selected site navigation and separate browser section, dispatches typed
items, and removes hub/dock for regular projection. Compile regardless of device availability.

### Modified: `CLAUDE.md`

After review/QA, record fixed dock ownership/order, hub typed/separated content, active-tab/origin
invalidation, and regular-shell preservation.

### Modified: `docs/ROADMAP.md`

Mark UX-015 complete only after review is resolved and QA passes.

### New: `reports/review/UX-015.md`

## Tests

- Focused JVM/source: dock ownership/order/negative controls and existing chrome-model route/cap
  tests.
- Focused instrumentation: dock targets/order/state/callbacks and integrated hub separation,
  dispatch, compact/large-text/theme layout, and regular teardown when a device exists.
- Existing JVM: action resolution, chrome handoff, session/tab isolation, navigation matching,
  theme/presentation, Back behavior, and browser menu command tests.
- Always compile instrumentation with `./gradlew :app:compileDebugAndroidTestKotlin`.
- Run `bash scripts/pre-commit-check.sh` before each task commit.

## Rollout / versioning

No protocol, storage, migration, permission, network, consent, or staged rollout change. This is a
perceptible integrated-mode UI placement change guarded by the existing active mode projection.
Capture a screenshot on a connected device; otherwise compile instrumentation and record the
managed-cloud device limitation without provisioning a software-only emulator.

## Open questions

- Exact compiled hub shape/spacing may be tuned from Compose bounds, but ownership, section
  separation, fixed dock order, and 48 dp targets cannot be tuned away.
- Existing `BrowserMenuCommand.TABS` may remain in the shared menu model for compatibility even
  though Tabs has a fixed dock entry; the rendered hub should avoid unnecessary duplication if that
  can be done without creating divergent command vocabularies.
