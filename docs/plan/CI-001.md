# CI-001: Implementation plan
Status: PLAN_APPROVED

## Overview

Add one purpose-built instrumentation journey that produces full-display PNG evidence, then expose
it through a manual, serialized GitHub Actions emulator workflow. The journey uses production Home,
network discovery, consent persistence and SiteSkin activation; no application production code or
trust decision changes.

## Flow

1. GitHub checks out the selected commit and installs Java 25.
2. The emulator action provisions an API 33 Google APIs x86_64 AVD with animations disabled.
3. The script clears package state, runs only `LiveSiteScreenshotTest`, captures instrumentation
   output and logcat, and pulls app-specific screenshot files.
4. Instrumentation skips onboarding, waits for Home, captures it, opens the compiled Bloom Flowers
   suggestion, waits for the exact canonical-origin consent title, captures it, selects Allow, and
   waits for both SiteSkin security and bottom-navigation tags before the final capture.
5. Shell validation rejects an empty PNG directory; artifacts upload even when the test fails.

## Data

- Screenshot names are fixed ordered evidence: `01-home.png`, `02-siteskin-consent.png`, and
  `03-siteskin-integrated.png`.
- Files live only in the debug package's app-specific external `files/screenshots` directory during
  execution and the workflow's `artifacts/screenshots` directory after `adb pull`.
- Instrumentation output and filtered/full logcat remain workflow diagnostics; nothing persists in
  Webora storage beyond the disposable AVD.

## Trust boundary

The real HTTPS response remains untrusted remote input through the existing bounded parse,
validation and origin-binding pipeline. The test interacts only after the browser emits its exact
canonical-origin consent statement, and declares integrated success only after browser-owned
security semantics and native SiteSkin navigation exist. It never constructs a trusted model,
writes consent preferences directly, mocks network bytes, or treats WebView page content as proof.

## Security

- Keep exact-origin HTTPS discovery and normal first-use Allow behavior; add no automation escape.
- Use the ordinary debug variant, not the cleartext-enabled `debugRelease` variant.
- Give the workflow `contents: read`, no secrets, and manual-only dispatch.
- Pin `ReactiveCircus/android-emulator-runner` to its immutable v2.34.0 commit.
- Full logcat is an internal workflow artifact for a public demo flow; retention is bounded to seven
  days and must not be published as a GitHub Release.

## File-by-file plan

### New: `app/src/androidTest/java/app/webora/browser/visual/LiveSiteScreenshotTest.kt`

Launch `MainActivity`, complete onboarding, drive the live SiteSkin journey with bounded semantic
waits, and write asserted full-device screenshots through `UiAutomation.takeScreenshot()`.

### New: `.github/workflows/android-screenshots.yml`

Add manual KVM emulator orchestration, focused connected instrumentation, screenshot/log pulling,
missing-evidence validation, and always-run artifact upload.

### New: `docs/SCREENSHOTS.md`

Document how to run the workflow, download the artifact, interpret each image, and distinguish a
live-origin failure from app failure.

### Modified: planning and ticket artifacts

Record CI-001 in the roadmap/development context and produce normal review, QA and validation
artifacts after implementation.

## Tests

- Compile the new journey with `./gradlew :app:assembleDebugAndroidTest` after its source change.
- Run the repository test/lint/detekt gate before each commit.
- Validate workflow YAML and shell fragments statically in the managed environment.
- Runtime: GitHub Actions runs the focused API 33 journey and produces three non-empty PNGs. The
  managed container has no `/dev/kvm`, so it must not provision a local software emulator.

## Rollout / versioning

Manual-only, one API level, no application version change. Expand the matrix or add visual diffs in
a later ticket only after runtime duration and stability are known.
