# UX-026 plan — a scrim that closes, and a panel the size of its menu
Status: PLAN_APPROVED

Issue: [denrzv/webora#121](https://github.com/denrzv/webora/issues/121)
PRD: `docs/prd/UX-026.prd.md`
Research: `docs/research/UX-026.md`

## Overview

Three changes, in the order a reviewer should read them:

1. **A browser-owned scrim gesture**, because research F1 proves the framework's own dismissal path
   is unreachable for this drawer. A gesture, not a `clickable`, so the scrim contributes no
   accessible control; and the panel consumes what its children did not, so a tap on empty panel
   space cannot reach the ancestor's detector.
2. **A pure height rule**, `hubDrawerHeight(available: Dp)`, returning a browser-owned min/max pair.
   `heightIn` plus the existing `verticalScroll` makes the panel wrap short content and bound-and-
   scroll long content, with no branch anywhere on what the site published.
3. **Top-start alignment**, so the scrim a short menu leaves behind is *below* the panel where a tap
   can land, and so the hosted journey's dismissal step stops depending on how tall the menu is.

`UX-022`'s `Dialog` is kept. Back still works because the dialog is its own window, no `BackHandler`
is added anywhere, and `BrowserBack.kt` is not touched.

## Flow

- **discovery / validation / normalization** — unchanged. Nothing in this ticket runs before
  composition, and no new value crosses the trust boundary.
- **UI state** — unchanged. One `IntegratedOverlay?` in `BrowserScreen`, its three existing resets,
  the same `SiteSkinHubHost` visibility test. This ticket adds no state at all: the height is derived
  during layout and the scrim is a gesture, not a flag.
- **composition** —

```
Dialog(usePlatformDefaultWidth = false)          # UX-022, unchanged: its own window, so Back
  └ BoxWithConstraints                           #   fillMaxSize + safeDrawing + scrim gesture
      │  hubDrawerHeight(maxHeight) -> (min, max)
      └ Surface  align TopStart                  #   heightIn(min, max) + consuming pointer input
          └ Column verticalScroll                #   unchanged content
```

## Data

No DTO, no domain model, no cache key, no persisted value. `HubDrawerHeight` is a transient pair of
`Dp` produced during layout and read once.

## Security

### Origin binding

Untouched. The drawer still renders the single trusted configuration of the committed integrated
origin, and `SKIN-004`/`UX-012`'s exact-origin activation and teardown are not on this path.

### The trust boundary this ticket has to hold

The manifest-controlled surface does not grow by one field. The specific pressure is **a dimension
arriving as a count**: `model.siteMenu.size` is a site-controlled number that looks like a layout
input, and a height rule reading it would let a website decide how much of the browser's window it
occupies — while passing every visual check, because the result would look right for Bloom.

The contract is therefore stated in the type: `hubDrawerHeight` takes `Dp` and returns `Dp`, and a
reflective assertion over its parameter and return types keeps it that way as it grows. This is
`headerIdentityPlacement`'s shape and `headerIdentityPlacement`'s reason — that rule deliberately
takes width, scale and a *browser-derived* domain length, and excludes the manifest's title because
otherwise a website chooses the browser's layout.

### Why the maximum is a fraction below 1

Research F5: a panel permitted to fill the viewport leaves no scrim to tap, and criterion 1 would
hold for Bloom and quietly stop holding for a site with twenty menu entries. The reachable scrim is a
**dismissal guarantee**, so `HUB_DRAWER_MAX_FRACTION` is load-bearing and its test is not decoration.

### Fallback on failure

Total by construction. A non-positive available height yields `(0.dp, 0.dp)` rather than a negative
bound, and the minimum is coerced under the maximum so a degenerate viewport cannot produce
`min > max` — which would be an `IllegalArgumentException` out of `heightIn`, i.e. a crash in the
browser caused by a small window. Nothing in this ticket can make an item unreachable: content taller
than the maximum scrolls, and no `take(`, cap or truncation is introduced.

### Accessibility

Two independent dismissal paths, and the scrim is not the accessible one — Back is. The scrim is a
`pointerInput` gesture and therefore publishes no role, no click action and no accessible name, so a
screen reader does not meet a full-screen button in front of the menu. Rows keep their 48 dp targets,
their labels and `UX-015`'s navigation-only selection semantics.

## The numbers, and where they come from

| Constant | Value | Why |
|---|---|---|
| `HUB_DRAWER_MAX_FRACTION` | `0.85f` | leaves ≈15% of the safe height as reachable scrim at every content height (F5). On the hosted Pixel 6 profile's ≈800 dp safe height that is ≈120 dp of scrim — well over a 48 dp target. |
| `HUB_DRAWER_MIN_HEIGHT` | `180.dp` | header 48 + gutters 40 + one heading 20 + `SMALL` 8 + one 48 dp row + `LARGE` 16 ≈ 180. The smallest panel that still reads as a menu rather than a strip. |

Research F4 measures Bloom's content at ≈272 dp against ≈800 dp of safe height, so the reference
integration wraps: neither bound binds, which is the point — the bounds exist for the degenerate ends
and the content decides the middle.

**Font scale is deliberately not an input** (F6). Large text makes the content taller and the
response to taller content is already scrolling at the maximum; how much of its own window the
browser will yield is not a function of the user's text size.

## File-by-file plan

### New: `app/src/main/java/app/webora/browser/siteskin/HubDrawerHeight.kt`

`HubDrawerHeight(min: Dp, max: Dp)` and the pure `hubDrawerHeight(available: Dp)`. Kept out of
`SiteSkinHubDrawer.kt` for `CI-003`'s reason: a decision inside a `@Composable` is a decision
`./gradlew test` cannot compile, let alone drive. The arithmetic above is recorded at the
declarations, per `UX-021`'s rule that a constant carries the measurement that chose it.

### New: `app/src/test/java/app/webora/browser/siteskin/HubDrawerHeightTest.kt`

The table, both bounds, the degenerate ends, and the reflective type assertion.

### Modified: `app/src/main/java/app/webora/browser/siteskin/SiteSkinHubDrawer.kt`

- `Box` → `BoxWithConstraints`, `Alignment.CenterStart` → `Alignment.TopStart`.
- The scrim gains `pointerInput { detectTapGestures { onDismiss() } }`.
- `windowInsetsPadding(WindowInsets.safeDrawing)` moves from the content column to that box, so the
  available height the maximum is taken against already excludes the system bars, and there is still
  exactly one read (F7).
- The panel loses `fillMaxHeight()` and gains `heightIn(min, max)` plus a consuming pointer-input
  node.
- `HubDrawerContent` keeps its signature and its body. Every existing instrumented test drives it
  directly and must keep passing unedited.

### Modified: `app/src/test/java/app/webora/browser/siteskin/SiteSkinHubDrawerContractTest.kt`

`the panel is placed by a direction-aware alignment` is **restated, not relaxed** — `UX-024`'s rule
about editing an ordered assertion applies to this one too. The vertical anchor moves from centre to
top; the property being asserted is that the horizontal anchor is direction-aware, so the assertion
names `Alignment.TopStart` and the forbidden list grows to cover every `End` and absolute spelling
rather than shrinking to accommodate the change.

New cases: the scrim carries a tap gesture and not a `clickable`; the panel consumes; the panel does
not `fillMaxHeight`; the height comes from the pure rule and the file names no model, configuration
or count.

### Modified: `app/src/androidTest/java/app/webora/browser/siteskin/SiteSkinHubDrawerTest.kt`

The behaviour a device can see: scrim tap closes and dispatches nothing; a tap on the panel does not;
a short menu's panel is materially shorter than the viewport; a twenty-entry menu is bounded and its
last row still reachable by scrolling. Instrumented evidence, never promoted to a gate claim.

### Modified: `app/src/androidTest/java/app/webora/browser/visual/LiveSiteScreenshotTest.kt`

The dismissal step becomes a tap at a point that is outside the panel for **every** permitted content
height, instead of the node's default centre (F3). Frame 04's acceptance checks — the drawer tag, the
five trusted action ids across drawer and dock, `UX-022`'s and `UX-025`'s assertions — are unchanged,
and this ticket adds no capture-policy change, no screenshot mode and no new deadline.

### Not modified, deliberately

`BrowserScreen.kt`, `BrowserBack.kt`, `SiteSkinDock.kt`, `HubSurface.kt`, `SiteSkinChromeModel.kt`,
`DockArrangement.kt`, `siteskin-core` and every fixture. Bloom's manifest is **read** by research and
not edited, so none of `DEMO-001`'s five pinned copies move and no checksum is touched.

## Tests

| Level | What it proves |
|---|---|
| `HubDrawerHeightTest` | the bounds table; `min ≤ max` at every input including zero; the reflective assertion that the rule takes only `Dp` |
| `SiteSkinHubDrawerContractTest` | the gesture exists and is not a `clickable`; the panel consumes and does not fill height; alignment is direction-aware; no count, model or configuration is named |
| `SiteSkinHubDrawerTest` (instrumented) | scrim closes without dispatch; panel tap does not close; short menu is materially shorter than the viewport; long menu is bounded and scrolls to its last row |
| `LiveSiteScreenshotTest` (hosted) | the journey's dismissal rests on a mechanism that exists |

### Negative controls

1. **Delete the scrim gesture.** The instrumented scrim case must fail. This is the control that
   matters most, because F1 says the framework path alone cannot close the drawer — so a green run
   without the gesture would mean the test is not testing dismissal.
2. **Delete the panel's consuming node.** The panel-tap case must fail (the tap reaches the
   ancestor's detector and dismisses).
3. **Restore `fillMaxHeight()`.** The short-menu bounds case must fail, and the contract assertion
   with it.
4. **Feed the item count into the rule** — `hubDrawerHeight(maxHeight, model.siteMenu.size)`. The
   reflective type assertion must fail. This is criterion 14's control and the one a reviewer should
   check by hand, because it is the change that would look reasonable.
5. **Raise `HUB_DRAWER_MAX_FRACTION` to `1f`.** The fraction assertion must fail rather than the
   scrim quietly becoming unreachable for a long menu.

`assertIsDisplayed()` is not evidence for any sizing claim — `UX-009` and `UX-023` both record that
semantics keep full text and unclipped bounds. The sizing cases assert bounds.

## Rollout / versioning

No protocol change, no schema change, no diagnostic, no fixture, no migration. `SPEC.md` is not
touched: the drawer's geometry has never been part of the protocol and this ticket is careful not to
make it one.

`CI-010`'s hosted acceptance must be re-taken — frame 04 photographs a compact panel now — and
compiled instrumentation cannot stand in for it. Run 45's failure (research F2) is the current
baseline, not a regression this ticket introduces.
