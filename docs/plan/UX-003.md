# UX-003: Implementation plan
Status: PLAN_APPROVED

## Overview and flow

Rebuild regular-mode browser chrome around the state and controller contracts already owned by
`BrowserScreen`. The page lifecycle does not change:

1. `BrowserState.mode` decides regular versus integrated presentation.
2. In regular mode, `securityPresentation(state.mode)` produces a typed committed-origin identity.
3. `BrowserChrome` renders the editable address pill and a distinct identity chip, then dispatches
   typed callbacks for submit, history, reload, home and the closed browser menu.
4. `BrowserStatusRegion` remains directly after the top chrome and before page content.
5. The WebView/error overlay remains inside `BROWSER_CONTENT_TAG`; the regular navigation dock stays
   outside the measured page rectangle.
6. Integrated mode keeps its SiteSkin top/bottom chrome. Only the shared browser-owned error/status
   visuals change.

There is deliberately no stop command in this plan. The existing controller has no stop contract;
retaining reload is more correct than drawing a control that cannot perform its named action.

## Trust and origin boundary

The committed `SiteOrigin` in `BrowserMode.Regular` is the only regular-mode identity source.
`securityPresentation` reduces it to browser-owned registrable-domain and TLS presentation before
composition. `BrowserChrome` receives that typed presentation separately from `addressText`; it
does not accept a raw identity string. This makes the required disagreement representable: a user
may edit the pill toward `attacker.example` while the chip continues to identify the committed
`example.com` page.

Page observations may affect address text, loading and navigation availability through the existing
reducer. A validated manifest can cause the parent to choose integrated mode, but no manifest field,
SiteSkin colour, icon, label or action enters regular chrome. Error copy and command inventory remain
closed browser-owned mappings.

No origin comparison, manifest validation or website-controlled capability is added. Storage and
cache keys are unchanged; no state is persisted by this ticket.

## Security and accessibility invariants

- The identity chip is always a separate composable and semantics node tagged
  `BROWSER_SECURITY_TAG`; focus/edit state of the address pill cannot remove it.
- Identity content comes from `SecurityPresentation`, never `addressText`, WebView title, document
  content or manifest.
- Secure/not-secure meaning uses local lock/warning glyph plus words, not colour alone.
- Menu items come only from `browserMenuCommands()` and dispatch the existing closed enum.
- Every icon action uses `WeboraIconButton`; menu/error actions use browser wrappers, preserving the
  48 dp minimum and resource-backed names.
- The live region remains persistent, polite for progress/completion and assertive for failure.
- Enabled unselected dock icons use an opaque measured browser colour. Alpha reduction is reserved
  for genuinely disabled controls and is not the enabled-state design mechanism.
- The dock is outside `BROWSER_CONTENT_TAG`, so browser pixels cannot satisfy page-render evidence.

## File-by-file plan

### New: `app/src/main/java/app/webora/browser/browser/BrowserChrome.kt`

Own `BrowserChrome`, the address pill, security identity chip, floating navigation dock, closed
overflow menu and `BrowserErrorPage`. Use `WeboraTheme`'s `MaterialTheme` roles, existing dimension
tokens, local vector painters and browser accessibility wrappers. Expose only typed internal inputs
and callbacks. Keep the existing security/status/error test tags stable.

### Modified: `app/src/main/java/app/webora/browser/browser/BrowserScreen.kt`

Remove the old `AddressBar`, `BrowserSecurityIdentity`, `BrowserErrorPage`, `BrowserButton` and their
obsolete imports. Wire `BrowserChrome` into the regular branch. Keep `BrowserStatusRegion`, state
ownership, controller dispatch and WebView/error ordering. Pass `state.isLoading` only for visual
state where useful; do not invent stop behaviour.

### Modified: `app/src/main/java/app/webora/browser/design/WeboraDimensions.kt`

Name any missing Direction A chrome geometry (52 dp address, 60 dp dock, icon sizing/gutters) rather
than scattering literals. Do not add a duplicate touch-target token; the accessibility wrapper
remains its sole owner.

### Modified: `app/src/main/res/values/strings.xml`

Add only missing accessible names/state copy for icon controls. Reuse current back, forward, reload,
home, more, address, security and error strings wherever they already express the action.

### New: `app/src/test/java/app/webora/browser/browser/BrowserChromeContractTest.kt`

Pin a pure chrome command/presentation model if extraction is required and add source-level negative
controls proving identity and address remain separate and the browser dock stays outside the page
evidence region. The negative controls must be exercised against deliberately broken snippets, not
only today's source.

### New: `app/src/androidTest/java/app/webora/browser/browser/BrowserChromeTest.kt`

Compose regular chrome with deterministic state. Assert identity content/tag, intentional
address/identity disagreement through edit focus, menu/command callbacks, enabled states, local
semantics names, 48 dp targets and status/error behaviour as appropriate.

### Modified: `app/src/androidTest/java/app/webora/browser/browser/BrowserFontScaleTest.kt`

Add a 200% regular-chrome case that asserts all controls and the load-bearing security/menu strings
remain displayed/unclipped. Reuse its density harness rather than creating a second font-scale
mechanism.

### Modified only if required by extracted visibility

`BrowserAccessibilityTest`, `BrowserRecoveryInstrumentedTest` and
`BrowserSurfaceConventionsTest` keep their existing assertions. Change them only where component
extraction requires an internal symbol relocation or where a focused negative control belongs in an
existing convention gate.

## Test plan

Per task, run its focused JVM or Android compilation checks and linters. Before every task commit run
the full `bash scripts/pre-commit-check.sh` gate.

- JVM: security presentation, announcement/live-region, command model, source negative controls,
  token contrast and browser surface conventions.
- Android compile: `:app:compileDebugAndroidTestKotlin` (or the repository's equivalent) ensures the
  Compose tests compile in managed cloud.
- Runtime Android: run focused connected tests when a device exists. With no `/dev/kvm` or connected
  device, report runtime instrumentation and screenshots as an environment limitation; do not create
  a software emulator.
- Full: core isolation, all unit tests, assemble debug, detekt and repository hygiene through the
  pre-commit script.

## Rollout and compatibility

This is an app-only visual change. There is no schema, protocol, migration, cache, preference or API
version. Invalid/no manifests still use regular mode; valid manifests still enter integrated mode.
Rollback is a normal app commit rollback with no data consequences.

## Documentation

After implementation and QA, mark `UX-003` complete in `docs/ROADMAP.md` and add the durable
browser-chrome decision/negative-control notes to `CLAUDE.md`. No new ADR is needed because
`ADR-006` and `ADR-013` already decide the security and visual mechanisms.
