# UX-013: Implementation plan
Status: PLAN_APPROVED

## Overview

Add an app-layer, closed expressive presentation policy and two reusable Compose containers without
wiring either into the currently shipped chrome. The policy reuses the existing trusted SiteSkin
colour projection and adds only browser-owned layout/motion choices. The containers own their
geometry and slot order while leaving security identity and browser command content to downstream
browser-owned callers. UX-014 and UX-015 will perform integration after this seam is stable.

## Flow

1. Core continues to parse, validate, normalize, and exact-origin-bind remote input into a trusted
   `SiteSkinConfiguration`; this ticket changes none of that pipeline.
2. App code calls `ExpressiveSiteSkinPresentation.from(configuration, darkTheme, reducedMotion)`.
3. The factory delegates brand colour projection to `SiteSkinTheme`, selects the platform-requested
   light/dark scheme, and maps the browser-owned reduced-motion input to a closed motion policy.
4. Curved-header and floating-dock primitives receive that presentation plus composable slots. They
   apply compiled geometry and always compose their content; motion policy may change decorative
   transitions, never content presence/order or interaction availability.
5. No production caller uses the primitives in UX-013. Existing SiteSkin and regular chrome remain
   byte-for-byte behaviorally unchanged until UX-014/UX-015.

## Origin-boundary implications and browser-owned contract

The exact serving origin remains upstream of this feature. A trusted configuration is already bound
to that origin, and UX-013 neither accepts a URL nor performs origin comparison. Logo URLs/bytes and
action destinations are absent from the presentation model and primitive APIs.

The website-controlled capability is one closed colour projection derived from already-normalized
branding values. The explicit browser-owned contract is:

- configuration cannot choose curve/path, dimensions, slot order, elevation, insets, theme mode,
  motion, touch-target size, semantics, identity, or callbacks;
- the projection contains no raw DTO, URL, asset reference, navigation/action list, arbitrary map,
  `Dp`, `Shape`, animation spec, or composable content;
- primitives accept site-coloured presentation and explicitly named slots, while UX-014/UX-015 are
  responsible for filling browser identity/command slots from browser-observed state;
- reduced motion and dark theme are explicit browser/platform inputs to a pure factory, so tests can
  ask both questions without mocking Android state;
- failure is total and deterministic because only a trusted configuration can enter and existing
  `SiteSkinTheme` supplies guarded defaults.

## Data

### `ExpressiveSiteSkinPresentation`

An `internal` immutable data class with:

- selected `SiteSkinColorScheme`;
- a closed `ExpressiveMotionPolicy` enum (`STANDARD` or `REDUCED`).

Geometry remains top-level/internal constants and shapes in the primitives file rather than data
fields. This makes it impossible for any caller—especially a future manifest projection—to vary
geometry by constructing a presentation instance. The factory is the only configuration-consuming
entry point and receives `darkTheme`/`reducedMotion` as separate browser inputs.

There is no persistence or cache key. The value is cheap, deterministic projection state scoped to
composition.

## Security

- Exact-origin activation, consent, generation invalidation, asset acceptance, and typed action
  dispatch remain unchanged and outside these APIs.
- `SiteSkinColorScheme` stays the complete website-influenceable visual vocabulary. No
  `WeboraTheme` token is derived from or passed into the configuration projection.
- A structural contract test inspects the projection and primitive source, rejects forbidden
  remote/layout/motion types and configuration access in primitives, and includes deliberately
  unsafe snippets as negative controls.
- A resolved-outline test exercises the actual curved shape at compact and broad bounds, preventing
  a declared-but-degenerate token from satisfying the gate.
- Slots are always composed in fixed source order. Reduced motion changes policy only and cannot
  remove content or defer the security surface.

## File-by-file plan

### New: `app/src/main/java/app/webora/browser/siteskin/ExpressiveSiteSkinPresentation.kt`

Define the closed presentation and motion policy, with a factory that reuses `SiteSkinTheme` and
explicit browser-owned dark/reduced-motion inputs. KDoc states the trust and origin assumptions.

### New: `app/src/main/java/app/webora/browser/siteskin/ExpressiveSiteSkinChrome.kt`

Define a deterministic browser-owned curved-bottom `Shape`, an expressive header container, and a
floating dock container. Centralize fixed dimensions, curve depth, tonal/elevation treatment,
minimum size, and slot order. Accept a modifier so downstream owners can apply explicit integration
insets; do not read `WindowInsets.safeDrawing` or `SiteSkinConfiguration` here.

### New: `app/src/test/java/app/webora/browser/siteskin/ExpressiveSiteSkinPresentationTest.kt`

Verify total deterministic light/dark projection, closed reduced/standard policy, preserved
contrast, and absence of geometry/remote/browser-control data in the public internal model.

### New: `app/src/test/java/app/webora/browser/siteskin/ExpressiveSiteSkinChromeContractTest.kt`

Verify actual outline bounds/curve behavior at 320 dp and larger sizes; source-scan the primitive
and projection boundary; exercise negative-control snippets that introduce configuration-driven
dimensions, slot reordering, browser-token derivation, global inset consumption, or animation input.

### New: `app/src/androidTest/java/app/webora/browser/siteskin/ExpressiveSiteSkinChromeTest.kt`

Compose both primitives at 320 dp under 200% font scale and light/dark projections. Assert tagged
required content remains displayed, dock controls retain at least 48 dp bounds, slot ordering is
stable, and reduced policy renders the same required semantics. This suite is compiled explicitly;
runtime execution is attempted only if a connected device exists.

reused, why global insets remain with `BrowserScreen`, and the integration obligations handed to
UX-014/UX-015.

## Tests

- Focused JVM tests for each production task.
- `./gradlew :app:compileDebugAndroidTestKotlin` for instrumentation source.
- `./gradlew :app:connectedDebugAndroidTest` only when `adb devices` reports a connected device;
  otherwise report the managed-cloud limitation without provisioning an emulator.
- `bash scripts/pre-commit-check.sh` before every task/fix/documentation commit.
- The repository gate already runs core tests/check, all JVM tests, app assembly variants, detekt,
  lint CLI smoke tests, and workflow consistency.

## Rollout / versioning

No protocol/schema, persisted-state, network, consent, or rollout change. The primitives are
internal and unused in shipped composition, so this ticket is an API/security-foundation change for
UX-014/UX-015 with no user-visible rollout or screenshot requirement.

## Open questions

- UX-014/UX-015 may tune centralized browser-owned geometry after real-device evidence. They must
  not widen the presentation model or add configuration-driven geometry to do so.
- The platform wrapper for obtaining animator preference belongs to the first integration ticket;
  it must call the pure reduced-motion input defined here rather than bury a framework read inside
  the policy factory.
