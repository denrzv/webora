# UX-006: Implementation plan
Status: PLAN_APPROVED

## Overview

Give `SiteSkinConsentDialog` a pure app-layer projection of the candidate configuration so the user
decides against the manifest being granted rather than against a compiled description of the
feature. `ADR-011`'s decision semantics, `SKIN-004`'s activation checks and `HARDEN-002`'s canonical
origin identity are preserved exactly; the only new capability a website gains is the right to place
bounded, attributed, browser-formatted text and one colour swatch **below** the browser's own
framing inside that dialog.

The work is four commits: generalize the existing untrusted-text treatment, add the model, render
it, then document. No `:siteskin-core` change, no new network work, no change to when consent is
asked.

## Flow

- Discovery, validation and origin binding are unchanged. `candidateDisposition()` still returns
  `Ask` only after proving `configuration.origin` equals the browser-observed origin and the
  generation still matches (`SiteSkinRuntime.kt:31-47`).
- `BrowserScreen` holds the `SiteSkinCandidate` in `pendingConsent` as it does today. At render
  time it projects `candidate.configuration` through `SiteSkinConsentModel.from(...)` and passes the
  model plus `candidate.origin.canonical` to the dialog.
- The dialog renders: browser-authored title carrying the canonical origin → browser-authored
  framing copy → browser-authored attribution heading → the site's requested title, its subtitle if
  present, its colour swatch if it supplied one, and the per-surface counts → the three buttons.
- **Allow / Not now / Never behave exactly as before.** Allow saves, rechecks
  `candidate.isCurrent(currentOrigin, generation)` and activates; Not now clears `pendingConsent`;
  Never persists refusal. The model is display-only and participates in no decision.
- No branch of this flow performs I/O. The brand logo is not fetched — `BrandAssetLoader` stays
  bound to the post-activation `LaunchedEffect` at `BrowserScreen.kt:148-157`, so refusing consent
  still costs the site nothing beyond the discovery request it already received.

## Data

**Trust boundary.** `SiteSkinConfiguration` is already trusted, normalized and origin-bound — this
ticket adds no new parsing and no new DTO. The boundary this ticket draws is a *display* boundary:
`SiteSkinConsentModel` is the only path from a configuration into the consent dialog, and it is a
closed data class of already-bounded values. The dialog takes the model, never the configuration, so
there is no field a future edit can reach for without going through the projection.

**What the model carries**, and nothing else:

| Field | Source | Bound applied in the model |
|---|---|---|
| `title: String` | `toolbar.title ?: site.name` | `untrustedText(_, MAX_TITLE_LENGTH)` |
| `subtitle: String?` | `toolbar.subtitle` | `untrustedText(_, MAX_SUBTITLE_LENGTH)`, null when blank after flattening |
| `brandColor: Color?` | `branding.primaryColor` | present only when the manifest supplied one; value is the **guarded** projection |
| `navigationCount: Int` | `bottomNavigation` | `coerceAtMost(MAX_NAVIGATION_ITEMS)` |
| `quickActionCount: Int` | `quickActions` | `coerceAtMost(MAX_QUICK_ACTIONS)` |
| `menuCount: Int` | `menu` | `coerceAtMost(MAX_MENU_ITEMS)` |

Every limit is read from `dev.siteskin.core.SiteSkinLimits`, never copied.

**Title resolution — open question 1, decided.** The sheet uses `toolbar.title ?: site.name`,
identical to `SiteSkinTopBarModel.kt:18`. The sheet is a promise about the chrome, so it must show
the string the chrome will actually display; showing `site.name` when `toolbar.title` is what would
render makes the preview wrong in exactly the case a site would exploit. Bounding it at
`MAX_TITLE_LENGTH` (64) covers both spellings: core clamps `toolbar.title` to that already, and
`site.name` — the one displayed string core never clamps — is bounded here for the first time.

**Swatch — open question 2, decided.** Present only when `branding?.primaryColor != null`. When
present it is `SiteSkinTheme.from(configuration).scheme(darkTheme).primary`, the contrast-guarded
value. Drawing the raw hex would preview a colour `guardContainer` has already decided the chrome
will not use; drawing the projection unconditionally would show Webora's compiled `#3F51B5` default
and attribute it to a site that requested nothing. Both failures are attribution failures, which is
the one thing this sheet exists to get right.

**Storage.** None. No new preference, no new cache key, no change to `SiteConsentStore`'s
base64-of-`SiteOrigin.canonical` key.

## Security

**Origin binding.** Unchanged and untouched. The model is constructed from a configuration whose
origin `candidateDisposition` has already compared to the browser-observed origin, so every string
it carries provably belongs to the origin in the dialog's title. The dialog continues to display
`SiteOrigin.canonical` — complete scheme, host and non-default port — per `HARDEN-002`, and a test
pins that the displayed string is exactly that value.

**Allow-lists.** The model is a closed data class; the projection reads six fields and cannot be
parameterized to read a seventh. Deliberately excluded, with reasons that belong in the code:
`logoUrl` (would require a pre-consent fetch), `homeUrl` and every `action` payload (the sheet
describes; it does not offer navigation), and item `label`s — five labels of 32 attacker-chosen
characters each, stacked directly above an Allow button, is a site-authored message, not a
description. Counting is the form that stays a description.

**Untrusted text.** Every manifest string reaching the dialog passes through the character walk
currently named `inspectorValue`: flattened to one line, whitespace and ISO control characters
collapsed, `Character.FORMAT` characters removed, bounded. `U+202E RIGHT-TO-LEFT OVERRIDE` inside
`site.name` would otherwise reverse the text that follows it — inside a security dialog, that can
reorder browser-authored copy — and it contains no newline, which is why the strip has to cover
format characters and not just whitespace.

**Identity separation.** The origin is the dialog title and is browser-authored. Manifest strings
render as separate `Text` nodes beneath a browser-authored attribution heading; nothing is
concatenated across the boundary. The swatch is a bounded decorative box with cleared semantics and
is never the only carrier of any information — the sheet says the site sets a colour in text as
well.

**Fallback on failure.** The projection is total: it cannot throw on any trusted configuration.
Optional values absent means the corresponding element is omitted, never a blank row. There is no
failure mode in which the dialog is skipped — skipping it would mean either silently activating or
silently dropping, both worse than any display defect.

**Non-goals restated as prohibitions.** No manifest field may influence the dialog's layout,
ordering, emphasis, button set, or the dark/light choice — `isSystemInDarkTheme()` owns the last of
those, per `A11Y-001`.

## File-by-file plan

### Modified: `app/src/main/java/app/webora/browser/inspector/InspectorText.kt`
Generalize the walk: rename to `untrustedText(raw: String?, limit: Int)` and move it to
`app/src/main/java/app/webora/browser/siteskin/UntrustedText.kt`, since it is now shared between a
debug panel and a security dialog and neither package owns it. The character walk, the
`isDisplaySeparator` helper and both explanatory comments move verbatim — the `U+2028`/`U+00A0`
note is why it is not a regex, and the overshoot note is why the walk itself ends rather than only
its result being trimmed. `InspectorText.kt` remains as a one-line delegation
(`internal fun inspectorValue(raw: String?) = untrustedText(raw, SiteSkinLimits.MAX_SUBTITLE_LENGTH)`)
so the panel's ~15 call sites and `InspectorTextTest` are untouched.

### New: `app/src/main/java/app/webora/browser/siteskin/UntrustedText.kt`
The moved walk, with the bound as a parameter and KDoc restated for two callers.

### New: `app/src/main/java/app/webora/browser/siteskin/SiteSkinConsentModel.kt`
`internal data class SiteSkinConsentModel` with the six fields above and
`from(configuration: SiteSkinConfiguration, darkTheme: Boolean): SiteSkinConsentModel`. Pure — no
Compose runtime, no `Context`; it imports `androidx.compose.ui.graphics.Color` only as a value type,
exactly as `SiteSkinTheme` already does, so it stays JVM-testable. KDoc records what is excluded and
why, since the exclusions are the security content.

### Modified: `app/src/main/java/app/webora/browser/browser/BrowserScreen.kt`
`SiteSkinConsentDialog` gains a `model: SiteSkinConsentModel` parameter (5 total, under detekt's 6)
and renders it: attribution heading, title, optional subtitle, optional swatch row, count rows —
all above the existing `confirmButton`/`dismissButton`. The content column scrolls
(`verticalScroll`) so the added block cannot push a decision button off-dialog at 200% font scale,
which the `FlowRow` comment at `:361` already establishes is a live constraint. Call site at `:219`
projects the model with `isSystemInDarkTheme()`.

### Modified: `app/src/main/res/values/strings.xml`
New browser-authored strings: the attribution heading, the swatch label, and three quantity strings
for the counts (`plurals`, so "1 tab" and "4 tabs" are both correct). No existing string changes.

### New: `app/src/test/java/app/webora/browser/siteskin/SiteSkinConsentModelTest.kt`
The gate for every bound. Adversarial name (over-length, newline-bearing, `U+202E`), title
resolution precedence, swatch presence/absence and its guarded value, counts capped, empty
configuration producing a complete model.

### New: `app/src/test/java/app/webora/browser/siteskin/UntrustedTextTest.kt`
The generalized function at a non-default bound, proving the parameter is honoured rather than
`MAX_SUBTITLE_LENGTH` being hard-coded behind a parameter.

### Modified: `app/src/androidTest/java/app/webora/browser/browser/SiteSkinConsentDialogTest.kt`
Construct the dialog with the new parameter; **assertions unchanged**. Add cases: the canonical
origin is the title, an adversarial site name renders bounded, and the three decisions still fire.

### Modified: `docs/adr/ADR-011-first-use-consent.md`
Amendment section: what the sheet now shows, why the manifest half is attributed rather than
blended, what is excluded and why, and what would constitute a violation.

### Modified: `docs/ROADMAP.md`, `docs/BACKLOG.md`, `docs/DEVELOPMENT_PLAN.md`, `CLAUDE.md`
Add `UX-006` as an M6 ticket distinct from the descoped `UX-005`, and record the consent-sheet
contract in `CLAUDE.md`'s security notes.

## Tests

| Assertion | Where | Negative control |
|---|---|---|
| `site.name` over 64 chars is bounded | `SiteSkinConsentModelTest` | remove the `take` → test fails |
| `U+202E` in the name is stripped | `SiteSkinConsentModelTest` | drop the `FORMAT` clause → test fails |
| Newline in the name is flattened | `SiteSkinConsentModelTest` | — |
| `toolbar.title` wins over `site.name` | `SiteSkinConsentModelTest` | — |
| Swatch absent when branding absent | `SiteSkinConsentModelTest` | unconditional swatch → test fails |
| Swatch value is guarded, not raw | `SiteSkinConsentModelTest` | `#FFFFFF` on white must not be white |
| Counts capped at 5/5/20 | `SiteSkinConsentModelTest` | raise a list past the cap → test fails |
| Bound parameter is honoured | `UntrustedTextTest` | hard-coded limit → test fails |
| Displayed origin is `SiteOrigin.canonical` | `SiteSkinConsentDialogTest` | show registrable domain → test fails |
| Three decisions still fire | `SiteSkinConsentDialogTest` | — (existing, unmodified) |

JVM tests run per task via `bash scripts/pre-commit-check.sh`, which covers `:app:check` and so
carries `assertInspectorAbsentFromReleaseVariants` — required here because a file moves out of the
inspector's orbit. Instrumented tests are compiled; connected runs happen only if a device is
available, and their absence is recorded rather than claimed as evidence.

## Rollout / versioning

No schema change, no protocol change, no spec fixture, no migration. `spec/` is untouched — this is
browser presentation of an already-conformant manifest. Existing stored decisions keep working;
a user who already allowed an origin never sees this sheet again, which is `ADR-011` working as
designed and not a gap.

## Open questions

None. Both questions carried from research are decided above: the title resolves as
`toolbar.title ?: site.name` bounded at `MAX_TITLE_LENGTH`, and the untrusted-text helper moves to
`app/.../siteskin/UntrustedText.kt` with the bound as a parameter and a delegating
`inspectorValue` left in place.
