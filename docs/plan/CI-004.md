# CI-004: Plan
Status: PLAN_APPROVED

Input: [`../research/CI-004.md`](../research/CI-004.md) (`RESEARCH_READY`), **including its §10**,
which arrived after this plan was first approved and changed it.

> **Revised 2026-08-13, before any task was implemented.** The diagnostics artifact showed the ANR
> dialog had been on screen for **63 seconds** before the test process started, and the failure
> reproduced byte-identically across two attempts. The zero is **deterministic**, so the mechanism
> this plan originally led with — make every zero `NotYet` and let the 20-second deadline absorb it —
> would produce forty identical failures and then fail the run anyway. Patience is now a secondary
> property. **Reachability and diagnosis lead.** The revision is recorded rather than rewritten: the
> three-way verdict, the budget rule and the trust boundary below are unchanged and were right.

## Flow

```
before                                          after
──────                                          ─────
requireAppOwnsScreen (20s deadline, 500ms poll)  requireAppOwnsScreen (unchanged budget)
  DismissableSystemAnr →                           DismissableSystemAnr →
    dismissSystemAnr(...)                            attemptDismissal(...)
      rootInActiveWindow                               observe the DIALOG's window, not just
        └─ one tree, maybe the wrong one ✗               the active one → WaitAffordances
      size != 1 → THROW ✗                              AnrDismissalPolicy.verdict(observation)
                                                         Press     → click, dismissals++
                                                         NotYet    → lastReason, loop retries
                                                         Ambiguous → THROW (immediate)
                                                       on any non-Press: record what was on
                                                         screen → dismissal-<label>.txt
  Blocked → lastReason, loop retries               Blocked → unchanged
  OwnedByApp → capture                             OwnedByApp → unchanged
```

Two changes, and the **order matters**:

1. **Look in the right place.** `rootInActiveWindow` returns one tree and the evidence suggests it is
   not the `SYSTEM_ALERT` dialog's — WindowManager logged `Cannot find window which accessibility
   connection is added to` 0.5 s before the refusal. The observation must enumerate the windows the
   automation can see and search the one whose title the policy already classified.
2. **Record what was actually there.** Every non-`Press` outcome writes the ids present, the windows
   seen, and whether view-id reporting is in effect. This is the deliverable that does not depend on
   the diagnosis being right, which is why it is `TASK-1`.

The retry remains — the loop keeps its deadline, poll and `waitForIdle`, and **patience stays in
exactly one place** (research risk 1) — but it is no longer claimed as the fix. It is what stops a
genuinely transient zero from failing on first contact, which is still worth having and is no longer
the point.

## Trust boundary

**No origin is contacted, no manifest is parsed, and no website-controlled value reaches any decision
in this ticket.** Stating it explicitly because `PROJECT_RULES.md` requires the boundary to be
decided here: there is no website-controlled capability in scope, and the plan adds no path for one.

The boundary this ticket *does* touch is one layer up, and it is `CI-002`'s: **what the harness may
hide from the person looking at the picture.** That contract is unchanged, and the plan is bound by
it as follows.

- **The allow-list does not grow.** `DISMISSABLE_ANR_PROCESS` stays `com.android.systemui`;
  `WAIT_VIEW_IDS` stays `android:id/button2`, `android:id/aerr_wait`. This ticket changes *when the
  harness concludes it cannot press*, never *what it may press*.
- **Ambiguity is never resolved by choosing.** Two or more pressable candidates fails immediately and
  is not retryable. Only the zero case becomes patient. Making `Ambiguous` retryable would be a worse
  bug than the one being fixed.
- **Decisions read sanctioned resource ids only.** A node's `text` is recorded for the reader and
  never consulted — the same rule that keeps `focusVerdict` on process-derived titles rather than
  translated strings. No new input to the decision may be text, and none is.
- **Patience buys refusal later, never permission.** A dialog that never becomes pressable still
  fails the run at the deadline. Nothing here can make a contaminated screen photographable, and
  `SETTLE_TIMEOUT_MILLIS` is not raised — raising it instead of fixing the lookup is the shortcut
  this plan refuses, the same way `CI-003` refused to raise its threshold.

## Security / integrity

| Rule | Mechanism |
|---|---|
| One process, one action | `ScreenEvidencePolicy` untouched; `ScreenEvidencePolicyTest`'s fixtures must pass **unedited** |
| No `else` branch that dismisses | the new verdict is a **sealed** interface with three cases, mirroring `FocusVerdict` |
| Ambiguity fails closed | `Ambiguous` throws at the call site, before the loop can sleep on it |
| The budget counts presses | `dismissals++` moves to the `Press` branch only — a `NotYet` costs nothing, because `"survived N dismissals"` is false if nothing was pressed |
| A refusal keeps its evidence | `evidenceFailure` still writes the full `window-<label>.txt` |
| The decision is gate-testable | pure function in `src/screenshotPolicy/java`, run by `./gradlew test` with no emulator and no `/dev/kvm` |

## Files

### New: `app/src/screenshotPolicy/java/app/webora/browser/evidence/AnrDismissalPolicy.kt`

The third capture-time decision, joining `focusVerdict` and `RenderedContentPolicy.verdict` in the
source set shared by `test` and `androidTest` and by no variant.

```kotlin
/** What the guard saw when it looked for the one sanctioned affordance. */
data class WaitAffordances(
    val pressable: List<String>,             // sanctioned ids, clickable and visible
    val matchedButNotPressable: List<String>, // sanctioned ids present, not yet pressable
    val rootAvailable: Boolean,               // rootInActiveWindow was non-null
    val viewIdReportingEnabled: Boolean,      // FLAG_REPORT_VIEW_IDS is in effect
)

sealed interface DismissalVerdict {
    data class Press(val viewId: String) : DismissalVerdict
    data class NotYet(val reason: String) : DismissalVerdict
    data class Ambiguous(val viewIds: List<String>) : DismissalVerdict
}

object AnrDismissalPolicy { fun verdict(found: WaitAffordances): DismissalVerdict }
```

The decision, total over the input:

| Condition | Verdict | Why |
|---|---|---|
| `pressable.size == 1` | `Press` | the sanctioned affordance |
| `pressable.size >= 2` | `Ambiguous` | genuine ambiguity, never guessed |
| empty, `!rootAvailable` | `NotYet` | no tree to search — an observation gap, not an absence |
| empty, `!viewIdReportingEnabled` | `NotYet` | the lookup cannot report ids at all; a zero here means nothing |
| empty, `matchedButNotPressable` non-empty | `NotYet` | the dialog is assembling |
| empty, nothing matched | `NotYet` | may still be arriving; the deadline decides |

Every zero is `NotYet` — criterion 1 — and each carries a *different* reason string, which is what
makes the eventual timeout diagnosable. `Ambiguous` is the only immediate failure, and the ordering
puts it second so it can never be reached through a "not yet" path.

The input is `List<String>` plus two booleans rather than nodes: `isClickable`/`isVisibleToUser` are
*observations* and stay in the guard, because a policy taking `AccessibilityNodeInfo` would need
Android types and would land back in `androidTest` — the exact mistake `CI-003` recorded.

### Modified: `app/src/androidTest/java/app/webora/browser/visual/ScreenEvidenceGuard.kt`

- `dismissSystemAnr` becomes `attemptDismissal(...): DismissalOutcome` — it observes, asks the
  policy, and acts. It throws only on `Ambiguous` and on a refused click.
- **One root fetch**, hoisted out of the `flatMap`. Today `rootInActiveWindow` is read once per view
  id, so two lookups can see different trees.
- `requireAppOwnsScreen` handles the outcome: `Press` increments the budget, `NotYet` stores the
  reason and lets the existing sleep/`waitForIdle`/re-dump run, `Ambiguous` propagates.
- `enableViewIdReporting()` returns whether the flag is in effect and the guard keeps it. A null
  `serviceInfo` no longer returns silently: it is carried into every observation, makes zero results
  `NotYet` rather than a false absence, and appears in the diagnostic. **It does not fail the run at
  construction** — the flag may already be set by the framework, and failing early would turn a
  possibly-fine run red on a condition we can report instead.
- New `dismissal-<label>.txt` diagnostic, written when a dismissal cannot proceed: the pressable and
  matched-but-not-pressable ids, `rootAvailable`, the view-id reporting status, and a **bounded**
  sample of the ids actually present on the focused window. That last field is criterion 6 — the
  message today names only the ids we searched for, which is why two hosted runs produced no more
  information than the first assertion.

## Tests

| Test | Asserts |
|---|---|
| `oneSanctionedAffordanceIsPressed` | a single pressable id yields `Press` with that id |
| `twoAffordancesAreAmbiguousAndNeverPressed` | ≥2 yields `Ambiguous`, carrying both ids |
| `aMissingAccessibilityRootIsNotYet` | `rootAvailable = false` yields `NotYet`, never a refusal |
| `viewIdReportingOffIsNotYet` | the flag being absent yields `NotYet` — a zero from a lookup that cannot report ids proves nothing |
| `presentButUnpressableIsNotYet` | matched-but-not-pressable yields `NotYet`, with a reason distinct from the empty case |
| `nothingFoundIsNotYet` | the plain zero is still retryable |
| `everyNotYetCarriesADistinctReason` | the reason strings differ, so the timeout message identifies which condition persisted |
| `ambiguityIsNotReachableFromAZeroState` | a coverage guard: no input with `pressable.isEmpty()` yields `Ambiguous` |
| `ScreenEvidencePolicyTest` | unchanged and green — 20 fixtures, unedited |
| `RenderedContentPolicyTest` | unchanged and green |

**Negative control:** collapse the policy back to the old rule — `if (pressable.size != 1) fail`.
Every `NotYet` test must fail while `oneSanctionedAffordanceIsPressed` and
`twoAffordancesAreAmbiguousAndNeverPressed` still pass, proving the retryable cases are what the new
tests actually cover and that the surviving pair cannot stand in for them.

**Second negative control:** make `Ambiguous` retryable (return `NotYet` for `size >= 2`).
`twoAffordancesAreAmbiguousAndNeverPressed` must fail alone. Without this, nothing proves the
fail-closed half survived the change that made the other half patient.

**A correct outcome that is not a press — now much less likely.** Run 14's `interference-*` records
show `pressed=android:id/aerr_wait`, `label=Wait`, `click_accepted=true`, twice. The sanctioned
affordance exists and is pressable when the lookup can see the dialog, so "this dialog has no Wait
button" is eliminated (research §11) and no new view id is needed. The plan still does not require a
press to count as success — a run that fails with `no sanctioned affordance among [ids actually
present: …]` is a good outcome — but the expected result is now a press.

**Not verifiable here:** that a real System UI ANR is now cleared on the device. That needs a hosted
run; recorded as instrumented evidence and never promoted to a gate claim, exactly as `CI-002` and
`CI-003` recorded theirs.
