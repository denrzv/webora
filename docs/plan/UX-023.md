# UX-023 plan — the trust chip takes its own row when the brand row cannot hold it

Status: PLAN_APPROVED

PRD: `docs/prd/UX-023.prd.md`
Research: `docs/research/UX-023.md`
Source of record: `docs/BACKLOG.md` § `UX-023`

## Overview

Research finding F4 rules out both alternatives on measurement: dropping the subtitle frees vertical
space for a horizontal failure, and shrinking the logo frees 16 dp against a ~34 dp shortfall while
weakening the guarantee `extremeAspectRatioBitmapCannotResizeLogoSlot` exists for. **The chip wraps
to its own row**, which removes it from the horizontal budget entirely rather than rationing it.

Three layers, in F9's order:

1. **Decision.** `headerIdentityPlacement(availableWidth, fontScale, domainLength)` — pure, total,
   and the whole of it drivable by `./gradlew test`.
2. **Layout.** `SiteSkinTopBar` consumes it. One `BoxWithConstraints` supplies the width; the
   composable reads `LocalDensity.current.fontScale`.
3. **Evidence.** Instrumented at 320 dp × 200%, plus the default-scale case that proves the wrap is
   *not* taken when it is not needed.

## Flow

```
BoxWithConstraints.maxWidth ─┐
LocalDensity.fontScale ──────┼─► headerIdentityPlacement ─► INLINE   → chip inside BrandRow
security.registrableDomain ──┘                            └ OWN_ROW  → chip on its own row
   (browser-derived)
```

At 100% on a 360 dp host — the hosted emulator's width — `denrzv.github.io` stays `INLINE`, so
`CI-009`/`CI-010`'s frames are unchanged. On a 320 dp host at 200% it becomes `OWN_ROW`.

## Origin and trust boundary

**The decision takes three inputs and a website controls none of them.** `availableWidth` and
`fontScale` are platform facts. `domainLength` is the length of `SecurityPresentation.registrableDomain`,
which `UX-021` derives only from the committed `SiteOrigin` — never editable address text, never page
content, never a manifest field.

The two site-controlled values in this row — `model.title` and `model.subtitle` — are **deliberately
not inputs**. Research F3 names the reachable outcome if they were: a manifest choosing a title
length that pushes the browser's trust mark onto a second row, or off one. That is `HARDEN-002`'s
impersonation surface arriving through layout instead of text, and criterion 3's negative control
exists to prove it cannot happen. The rule is phrased on what the *browser* must fit, never on how
much the site asked for.

**The wrapped row makes the existing guarantee stronger, not weaker.** `UX-021`'s protection is that
the chip is declared after the weighted title and carries no weight, so a long title yields to it. In
`OWN_ROW` the chip shares its row with no site content at all, so a title cannot affect it by any
mechanism. Both branches satisfy the requirement; the plan restates the contract to cover both rather
than deleting the assertion that covers one.

Nothing in discovery, consent, activation, the renderer, event routing, capture policy or `spec/` is
touched. Criterion 10 is met by not editing those files, verifiable from the diff.

## Security and accessibility

- **The estimate fails safe by over-estimating.** A wrap that was not needed costs one row of
  height; a wrap that was needed and did not happen costs `ADR-006`'s visible domain. The character
  width constant is therefore chosen generous: it predicts ~122 dp for `example.co.uk` at 100%
  against `UX-021`'s measured ~117, and ~208 dp at 200% against ~198.
- **The rule is total.** Every `(width, scale, length)` returns a placement; there is no width or
  scale that falls through to a layout with no chip. A negative or zero width returns `OWN_ROW` —
  the branch that cannot truncate.
- `SITESKIN_SECURITY_TAG` keeps its exact value and stays on the chip in both branches. `CI-009` and
  `CI-010` assert on it, including the `assertDoesNotExist` proving `UX-012`'s teardown.
- The chip's `contentDescription`, its `primaryContainer` ground, both shield tints and
  `transportLabel`'s single ownership are untouched. No new colour is introduced, so
  `WeboraColorSchemeTest`'s measured table is unchanged.
- 48 dp targets for Back and Refresh are untouched; neither moves rows.
- `EXPRESSIVE_HEADER_MIN_HEIGHT` is a **minimum**, so the header already grows with content and no
  constant changes when a row is added.

## The arithmetic the rule encodes

Measured in research F1, at the 320 dp floor: gutters leave 280 dp, fixed children take 116 dp.

| Constant | Value | Derivation |
|---|---|---|
| `HEADER_FIXED_WIDTH` | 116 dp | Back 48 + 8 + logo 40 + 12 + 8 |
| `CHIP_CHROME_WIDTH` | 36 dp | shield 16 + gap 4 + horizontal padding 16 |
| `CHIP_CHARACTER_WIDTH` | 6.6 dp | 12 sp Medium at 100%, deliberately generous |
| `MINIMUM_TITLE_WIDTH` | 40 dp | what the site's name currently gets at 100% and 320 dp |

`INLINE` when `CHIP_CHROME + length × CHAR × fontScale ≤ availableWidth − 116 − 40`.

| Host | Scale | Domain | Chip needs | Budget | Placement |
|---|---|---|---|---|---|
| 320 dp | 100% | `example.co.uk` (13) | 122 | 124 | `INLINE` |
| 320 dp | 200% | `example.co.uk` | 208 | 124 | `OWN_ROW` |
| 360 dp | 100% | `denrzv.github.io` (16) | 142 | 164 | `INLINE` |
| 360 dp | 200% | `denrzv.github.io` | 247 | 164 | `OWN_ROW` |

**One consequence to state rather than discover later:** on a 320 dp host at 100%, a 16-character
domain now wraps where it previously rendered inline. That is a layout change at default scale, and
it is the right one — inline it left the site's title 22 dp, which is an ellipsis and nothing else.
The hosted emulator is 360 dp, so `CI-009`/`CI-010`'s frames are unaffected; criterion 7's assertion
pins the 13-character case at 100%, which is the case that genuinely fits.

## File-by-file plan

### TASK-1 — the decision

- **New** `app/src/main/java/app/webora/browser/siteskin/HeaderIdentityPlacement.kt` — the closed
  enum and the pure function, with the arithmetic table above at the declaration so the next reader
  meets it before reaching for a constant. This is the shape `rendererMountAction`, `refreshAction`
  and `resolveHubPresentation` already use, and research F2 records why it matters here in
  particular: it is the only part of a responsive layout the JVM gate can defend.
- **New** `app/src/test/java/app/webora/browser/siteskin/HeaderIdentityPlacementTest.kt` — every row
  of the table, the totality cases (zero and negative width), and the anti-vacuity guard that the
  function returns **both** values across its inputs.
- Negative controls: make the rule read a title length → the isolation test must fail; make it
  return `INLINE` unconditionally → the 200% row must fail; make it return `OWN_ROW`
  unconditionally → the anti-vacuity and 100% rows must fail.

### TASK-2 — the layout

- **Modified** `app/src/main/java/app/webora/browser/siteskin/SiteSkinTopBar.kt`
  - `SiteSkinTopBar` wraps its `Column` in one `BoxWithConstraints` and computes the placement once.
  - `BrandRow` gains an `inlineIdentity: Boolean` parameter; the chip and its 8 dp spacer are
    composed only when it is true.
  - **New** `private fun SiteSkinIdentityRow(security)` — the chip alone on a full-width row,
    composed between `BrandRow` and `BROWSE-011`'s `BrowserControlRow` when the placement is
    `OWN_ROW`.
  - `SECURITY_CHIP_MAX_WIDTH` is **not touched**. Its KDoc already records why raising it is wrong;
    a diff that changes it would have to re-measure, and this ticket removes the pressure to.
- **Not** joining `BrowserControlRow`. Research F5 measured that it fits, and it is rejected on a
  named mechanism: `the browser control row does not compete with the brand row for width` asserts
  the control row declares no weight and uses `Arrangement.End`, because the title-column locator
  finds the file's *first* `Modifier.weight(1f)`. Putting the chip there means either a conditional
  arrangement or a weighted child, and both make a live assertion depend on something unrelated to
  what it asserts. A separate row costs height only when the rule fires.

### TASK-3 — the contracts

- **Modified** `app/src/test/java/app/webora/browser/siteskin/SiteSkinTopBarContractTest.kt`
  - `the security identity is laid out after the flexible title` keeps working unedited: the *first*
    `SiteSkinSecurityChip(` in the file is still the one inside `BrandRow`, still after the first
    `Modifier.weight(1f)`.
  - `the browser control row does not compete with the brand row for width` keeps working unedited:
    the control row is not touched.
  - **New** `both identity placements keep the chip away from site content` — in `BrandRow` the chip
    follows the weighted title; in `SiteSkinIdentityRow` the row contains no model text at all.
    This is the restatement that covers the second branch, and it is what makes the guarantee
    branch-complete rather than assertion-shaped.
  - **New** `the placement decision reads no manifest value` — the source of the decision file
    names no `model.`, `title`, `subtitle`, `presentation` or `SiteSkinConfiguration`.
- **Modified** `app/src/androidTest/java/app/webora/browser/siteskin/SiteSkinTopBarTest.kt`
  - **New** case at 320 dp × 200%: the chip is displayed, at or above the existing
    `SECURITY_CHIP_FLOOR`, and the title node still exists and is non-empty.
  - **New** case at 320 dp × 100%: the chip is still inside the brand row — the anti-vacuity guard
    for criterion 7, since a rule that always wrapped would satisfy the 200% case while changing the
    layout everyone else sees.
  - `compactLargeTextKeepsBrowserIdentityInsideTheBrandRow` is renamed and re-pointed rather than
    deleted: at 200% the identity is no longer *inside* the brand row, so the name would become a
    lie. Its `SECURITY_CHIP_FLOOR` assertion survives, which is criterion 6.

## Tests

| Layer | File | What it can prove |
|---|---|---|
| Decision | `HeaderIdentityPlacementTest` | every row of the table, totality, both values reachable, no manifest input |
| Structure | `SiteSkinTopBarContractTest` | chip never shares a row with site content; decision reads no model value |
| Rendered | `SiteSkinTopBarTest` (instrumented) | the domain renders without ellipsis at 200%; the title survives; 100% unchanged |

The rendered layer is **instrumented evidence and never a gate claim** — `A11Y-001`'s rule. This
checkout has no emulator, so criterion 1 compiles here and is verified on a device or in CI.

## Out of scope, and stated so the next reader does not re-litigate

- Raising `SECURITY_CHIP_MAX_WIDTH`. Inert; arithmetic at its declaration.
- Removing the domain from integrated chrome. `UX-021` rejected the bare-shield sketch on `ADR-006`.
- Making regular chrome responsive. Different surface, different arithmetic, its own ticket.
- A general responsive framework. One decision for one row; the second surface that needs one can
  generalise from it with a real second case in hand.
