# UX-005: Implementation plan
Status: PLAN_APPROVED

## Overview
Extend the existing trusted icon vocabulary, add matching bundled vectors to the `UX-002` optical
system, and replace `SiteSkinChrome` text glyphs with a closed mapping to those resources. The UI
continues to receive only trusted `NavigationItem` values and emit those original values.

## Flow
1. Manifest parsing keeps `icon` as a bounded forward-compatible string.
2. Security validation maps supported names through unchanged and warns/substitutes `generic` for
   everything else before `SiteSkinConfiguration` can exist.
3. `SiteSkinChromeModel` projects the trusted string without interpreting it.
4. `SiteSkinIcon` selects a compiled vector from an exhaustive closed `when`; its fallback is the
   bundled generic icon.
5. Bottom navigation and menu render that decorative icon. The quick-action launcher previews the
   first trusted action's icon and still opens the complete bounded menu.

## Data
No DTO shape, persistence, cache key, origin key, or schema version changes. The trusted domain
continues to carry a normalized string because the protocol is forward-compatible; construction
remains exclusive to core validation.

## Trust and origin boundary
This ticket does not alter origin activation or action resolution. Manifest influence ends at a
semantic token in the core allow-list. The app mapping is a browser-owned constant mapping to
specific `R.drawable` ids; input is never passed to Android resource lookup or any asset/network
API. Thus the serving origin gains no new cross-origin or native capability, and the canonical
domain/TLS identity remains independent and unsuppressible.

## Security
- Allow-list: core alone decides which icon tokens become trusted.
- Resource isolation: UI uses a closed mapping, never `Resources.getIdentifier` or manifest bytes.
- Fallback: unknown, null, or inconsistent values display `ic_siteskin_generic`; browsing and the
  item remain available, with the existing warning for an unknown manifest value.
- Negative control: a resource-like token is structurally valid but normalizes to `generic`, and a
  source contract fails if dynamic resource lookup is introduced.

## File-by-file plan
### Modified: `siteskin-core/src/main/kotlin/dev/siteskin/core/SecurityValidator.kt`
Add `catalog`, `flower`, and `search` to the closed icon vocabulary; retain all existing names.

### Modified: `siteskin-core/src/test/kotlin/dev/siteskin/core/SecurityValidatorTest.kt`
Pin the expanded vocabulary and resource-like-input negative control.

### Modified: `spec/SPEC.md`
Document the supported semantic names, browser-owned rendering, and generic fallback.

### New: `app/src/main/res/drawable/ic_siteskin_*.xml`
Add catalog, flower, cart, person, call, share, and generic vectors in the established 24 dp,
1.9-stroke, single-color, no-fill system; reuse existing home/menu/search vectors.

### Modified: `app/src/main/java/app/webora/browser/siteskin/SiteSkinChrome.kt`
Render `Icon`/`painterResource` through the closed semantic mapping and use the first quick action's
trusted icon in the launcher. Preserve item labels, state descriptions, and cleared icon semantics.

### Modified: `app/src/test/java/app/webora/browser/design/BrowserIconContractTest.kt`
Raise the reviewed budget, pin the complete set, and forbid dynamic resource lookup in the
SiteSkin icon source.

### Modified: `app/src/androidTest/java/app/webora/browser/siteskin/SiteSkinChromeTest.kt`
Assert icon nodes, selected state, quick-action behavior, and large-font layout semantics.

### Modified: `reports/review/UX-005.md`, `reports/qa/UX-005.md`, and architecture context
Record review, QA/evidence results, and the durable icon trust-boundary contract.

resource-like token assertion fail; introducing dynamic lookup makes the source contract fail.

## Rollout / versioning
No schema bump. The schema intentionally permits future bounded strings while core owns the current
allow-list. Existing manifests remain compatible, and older clients safely fall back for new names.
