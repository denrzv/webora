# CI-008 — Automatic post-merge Android visual acceptance

Status: BACKLOG

**Priority:** P1  
**Depends on:** `BROWSE-008`, restored hosted acceptance of `CI-007`  
**Found by:** the delayed discovery of the `CI-007` regression in Android screenshot runs **30** (`31874095039`) and **31** (`31879413875`)

## Goal

Turn the existing hosted Android screenshot journey into a lightweight post-merge sentinel for
`main`. Every merge that can affect the browser/runtime/evidence path should automatically produce an
attributable Pixel 6 / API 33 visual-acceptance result, while documentation-only changes stay cheap
and the existing manual dispatch remains available for deliberate reruns.

## Problem

The screenshot workflow is currently `workflow_dispatch` only. During M8, several tickets were merged
to `main` without running it. `CI-007` introduced a real product/navigation regression, but it was
not discovered until after later tickets and `DEMO-004` had already landed. Runs 30 and 31 then failed
in the same place, leaving investigation to determine which earlier merge first broke the journey.

The canonical screenshot journey is intentionally heavier and more environment-dependent than the
normal PR gate, so making it a required check for every pull request would add unnecessary latency and
live-origin coupling. The missing layer is instead a post-merge signal: once `main` changes in a way
that can affect Android browsing, run the trusted journey automatically and attach the result to that
exact commit.

## Scope

- Keep `workflow_dispatch` so a developer can still request an explicit rerun or acceptance pair.
- Add an automatic `push` trigger for `main` with path filters covering code/configuration that can
  affect the Android browser or its visual evidence. At minimum consider:
  - `app/**`;
  - `siteskin-core/**`;
  - `evidence-sheet/**`;
  - the Android screenshot/readiness scripts;
  - `.github/workflows/android-screenshots.yml` itself;
  - Gradle wrapper/version/build configuration used to build the app or Android-test APKs.
- Do not trigger the hosted emulator for documentation-only changes that cannot affect the journey.
- Replace the current "new run cancels old run" behavior with a serial queue for this workflow.
  Use one concurrency group with `queue: max` and do not combine it with
  `cancel-in-progress: true`, so multiple relevant merges remain individually attributable rather
  than silently dropping an intermediate commit.
- Preserve the existing CI-006 device contract (Pixel 6 / API 33, 2 cores, 4 GiB, quiet-readiness
  gate and hosted settle budget), CI-005 frame-integrity checks, screenshot/diagnostic artifact split,
  and the current canonical journey. This ticket schedules the trusted workflow; it does not weaken
  or redesign it.
- Keep this as a post-merge sentinel rather than a required pull-request gate. Normal CI/security/
  guardrails continue to decide whether a PR may merge.
- Preserve exact commit/run attribution in the job summary and artifact names so a red run identifies
  the merge that introduced the regression without archaeology across later tickets.
- Do not auto-rerun a red result until it turns green. A failure should remain visible and require
  triage; transient reruns stay deliberate through `workflow_dispatch`.

## Acceptance

- A relevant push/merge to `main` (for example an `app/**` change) automatically starts the Android
  screenshot workflow without manual dispatch.
- A documentation-only merge outside the selected path filters does not start the hosted emulator.
- `workflow_dispatch` still starts the same canonical workflow on demand.
- Two relevant `main` pushes arriving while the first screenshot run is active are both retained and
  execute serially; neither the running nor the pending merge-run is canceled or replaced.
- The automatic run remains tied to the exact `main` commit SHA in its summary and artifacts, making
  the first red merge directly identifiable.
- A red automatic run publishes the same diagnostics currently available to manual runs and is not
  converted to green by retry, timeout inflation, weaker readiness, or relaxed frame assertions.
- After `BROWSE-008` restores the journey, an automatic relevant-main run completes with the current
  four canonical frames, `png_count=4`, and a four-tile contact sheet under the unchanged evidence
  policy.
- `bash scripts/pre-commit-check.sh` passes.
