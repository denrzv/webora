Webora Browser · M6 · UX-001

Three directions for the browser's own chrome

Webora gives every website that publishes a SiteSkin manifest a six-role colour system, a dark projection and a WCAG contrast guard. It gives itself a bare MaterialTheme {} and five text-labelled buttons in a wrapping row. Pick one of the three directions below and that inversion gets corrected.

What each direction is answering

Seven constraints, and one of them decides the argument

These come from the audit in docs/design/AUDIT.md. Six are hygiene — a direction either respects them or gets amended. C1 is the one that can eliminate a direction outright, so every direction below states its answer to C1 explicitly rather than leaving it to implementation.

C1 Domain + TLS are browser-owned and non-suppressible
C2 Browser tokens are never manifest-influenceable
C3 Every control routes through a Webora* wrapper
C4 No string literal reaches the screen
C5 48 dp targets · 4.5:1 body · 3:1 UI · 200% scale
C6 ~8 bundled vector icons, no icon library
C7 Edge-to-edge, both system bar regions styled
A

Material 3 Expressive

Soft instrument

Leans all the way into the platform's current language: a tall rounded search pill, tonal containers instead of outlines, and a floating pill action bar that lifts the navigation controls off the bottom edge. The identity lives in its own tonal chip below the field — adjacent to the address, never inside it.

C1 · Security identity

Separate element, always. The identity is a tonal chip below the field, fed by securityPresentation(state.mode). The pill above it renders state.addressText and is never the identity claim — the two can visibly disagree, which is exactly the signal ADR-006 wants preserved.

Lowest C1 risk of the three. The chip costs a row of vertical space on every page.

Verdict

StrengthFeels current; the floating dock is thumb-reachable and reads as deliberate.
CostTallest chrome of the three — pill, chip and dock eat ~140 dp of a 720 dp screen.
EffortMedium. Tonal roles need a full container/on-container token set.
RiskLow. Nothing here fights an existing gate.
B

Browser-native · cites shipping precedent

Get out of the way

The conventions people already know from Chrome, Safari and Firefox: one compact 48 dp omnibox that shows the domain rather than the URL, a hairline bottom toolbar of icon-only controls, and as little chrome as the job allows. Maximum room for the page, minimum learning cost — and the direction that has to answer C1 most carefully.

C1 · Security identity — read this one

Two states, and the second one is mandatory. In display state the omnibox is not a text field at all: it renders securityPresentation(state.mode) as non-editable browser-owned text, with the path in a dimmer weight. Tapping it swaps to edit state — the real editable field — and the identity moves to a separate row beneath it (frame 03), so an editable value and an identity claim are never the same pixels.

If that second state is dropped for simplicity, this direction violates ADR-006. It is the single most important thing to hold onto if B is chosen.

Verdict

StrengthMost page area of the three; zero learning cost; densest at 200% font scale.
CostWebora looks like every other browser — no identity of its own.
EffortHighest. The two-state omnibox is real interaction work plus its own tests.
RiskHighest C1 exposure. Also the only direction whose look is hard to distinguish in a demo.
C

Webora identity · the security argument, made visible

The instrument frame

One idea, carried everywhere: the browser's frame is always the browser's. The identity bar is the same graphite in light mode and in dark mode, and it never takes a colour from anything — so the boundary between what Webora says and what the site says is a thing you can see rather than a thing you have to read about. The product's central contract, rendered as chrome.

C1 · Security identity

The identity is the frame. Domain and TLS sit on graphite that no page, manifest or theme setting can tint, above a visually subordinate address field. Compare frames 01 and 02: the page inverts, the frame does not. That makes an impersonating manifest structurally unable to produce a screen where its own colours surround the identity claim.

Also the direction that reads best in the SiteSkin demo, since the branded site and the unbranded frame stay visibly separate.

Verdict

StrengthWebora gets an identity, and it is the same argument as the product's security thesis.
CostAn always-dark bar is a strong opinion; some users will read it as heavy in light mode.
EffortMedium. One extra token concept — a colour outside the light/dark pair.
RiskContrast must be checked once against the fixed frame rather than per theme, which is simpler, not harder.

What happens after you pick

Choosing is UX-001's only deliverable

  1. Name a direction, and any amendments to it — “C, but the frame lightens on Home” is a valid answer and belongs in the record.
  2. ADR-013 is written from that choice: the browser-owned token layer, and why the browser's palette is compiled rather than derived from anything remote.
  3. UX-002 builds WeboraTheme — colour, type, shape, spacing, plus the eight vector drawables and the WeboraIconButton wrapper that C3 requires.
  4. UX-003 and UX-004 rebuild the chrome, then Home, onboarding and settings against those tokens.

SiteSkin's integrated chrome is untouched by all of this and keeps its placeholder glyphs — parked as UX-005. Worth knowing before a demo: the Bloom Flowers screen is the one screen M6 does not improve.
