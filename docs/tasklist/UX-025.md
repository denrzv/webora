- [x] TASK-1: carry `presentation.dock` through validation as resolved ordered ids
  - Schema, `ManifestStructure`, `UnknownFieldScanner.presentationFields`, DTO, `SecurityValidator`,
    trusted model — all three structural copies move together.
  - Bound to 3 (`SS-W-LIMIT-TRUNCATED`), de-duplicate first-wins (`SS-E-DUPLICATE-ID`), drop
    unresolvable with `SS-W-DOCK-UNRESOLVED`. Never rejects.
  - Acceptance: PRD criteria 1–5.
  - Tests: `:siteskin-core:test`, two new fixture pairs, registry, `SPEC.md`.
  - Negative controls: `enum` in the schema; omit `dock` from `presentationFields`; resolve against
    the raw DTO rather than the normalized items.
  - Result: **done**. `bash scripts/pre-commit-check.sh` green; 171 core tests.

    **Three fixtures, not two, and the third exists because a control found nothing.** The plan
    named a happy-path pair and an unresolved pair. Control C — resolving against the raw manifest
    instead of the normalized collections — passed, because no fixture named an id that security
    validation had *dropped*. `SPEC.md` states that rule normatively ("an item dropped for origin,
    scheme or action reasons MUST NOT become reachable by naming it here") and nothing tested it.
    `invalid/presentation-dock-dropped-item.json` does: a `javascript:` item is dropped for its
    scheme, the dock names it, and it must resolve to nothing.

    | Control | Result |
    |---|---|
    | `enum` replaces the id `$ref` in the schema | `securityLayerFixturesPassTheSchema` FAILED |
    | `dock` omitted from `UnknownFieldScanner.presentationFields` | `valid/presentation-dock expected:<[]> but was:<[SS-W-FIELD-UNKNOWN]>` |
    | resolve against the raw manifest | **passed at first** — then FAILED 2 cases once the third fixture existed |

    **Truncation runs before resolution**, and the unresolved fixture pins it: four ids are bounded
    to three *first*, so a site cannot name six, have three fail, and quietly receive its fourth
    choice. Resolving first would have made the cap count survivors instead of requests.

    `dock` is omitted from the canonical result when empty, like every other absent optional —
    a materialised `[]` would mean "asked for a dock and nothing survived", which is a different
    document from one that never asked (`SPEC.md` §12).

- [x] TASK-2: resolve ids into a closed slot arrangement
  - Sealed `DockSlot`; closed `DockArrangement`; pure `dockArrangement`. Brand and More are produced
    unconditionally, so "unreplaceable" is a property of the type.
  - Acceptance: PRD criteria 6, 7, 8, 13.
  - Negative control: give `DockSlot` a shared `(icon, label, onClick)` constructor → the reflective
    inventory fails.
  - Result: **done**. `bash scripts/pre-commit-check.sh` green.

    Control: turning `DockSlot.Tabs` from an object into `data class Tabs(icon, label)` fails both
    `the browser and site slots share no shape` and `no slot exposes an icon, a label or a callback`.
    That is the exact refactor the sealed model exists to refuse — one `DockSlot(icon, label,
    onClick)` for all four positions reads as tidier and hands a manifest the shape of a browser
    command.

    **A test found a real gap: `dockArrangement` did not cap.** Core bounds the list to three, and
    the app layer was trusting it. `SiteSkinChromeModel` already runs its own 5/5/20 caps over core's
    limits for exactly this reason, so the dock now takes three too — and the assertion checks *which*
    three, since a cap that kept the wrong ones would still satisfy a count.

    Fewer than three still projects rather than falling back: a site nominating one item has
    expressed the same preference as one nominating three, and the brand hub sits between the leading
    and trailing groups at every size. Tabs leaves the dock whenever anything is projected, to the
    More menu that has carried it since `DEVX-003`.

- [x] TASK-3: render the arrangement and subtract from the drawer
  - `SiteSkinDock` consumes the arrangement; `SiteSkinHubDrawer` subtracts rendered ids.
    `fixedDock` re-stated, not edited — its control must still refuse a fourth site slot.
  - Acceptance: PRD criteria 9–12, 15.
  - Result: **done**. `bash scripts/pre-commit-check.sh` green;
    `:app:compileDebugAndroidTestKotlin` green.

    `fixedDock` was **re-stated, not edited**, and the reason it had to be is worth keeping: the old
    predicate asserted three commands in *source* order, and source order stopped being render order
    the moment the dock rendered a `DockArrangement`. Left alone it would have kept passing while
    asserting something that is no longer the mechanism. It now reads the slot `when` — four sealed
    branches, no `else` — and `DockArrangementTest` owns the complementary half, because "Brand and
    More are always present" is a property of the decision rather than of the file.

    | Control | Result |
    |---|---|
    | drawer stops subtracting (`model.bottomNavigation` unfiltered) | `the drawer hides only what the dock rendered` FAILED |
    | the sealed `when` gains an `else -> Unit` | `expressive dock exposes only fixed browser owned commands` FAILED |

    Two scans needed scoping rather than loosening. `!source.contains("else ->")` matched
    `actionLift`'s unrelated lift table, so it is sliced to the slot loop — `UX-024`'s
    scope-the-scan-to-its-subject rule arriving from the other side. And the de-duplication scan was
    anchored on `HubGroup(R.string`, which a line-wrap for detekt split in two; the anchor is now the
    call name alone.

    Subtraction happens in the drawer, never in the model: `SiteSkinChromeModel` still carries every
    item, so `NavMatcher` still resolves a projected item's active route, and an id that failed to
    project is not in `projectedIds` and therefore still listed. Criterion 12's fallback is automatic
    rather than a branch anyone has to remember.

- [x] TASK-5: re-point the hosted journey
  - `BloomReferenceContract` splits into projected and drawer id sets; the hub frame asserts the
    drawer's remaining rows. Hosted acceptance re-taken in CI, not here.
  - Result: **done** on the code; **hosted acceptance not taken** — no emulator here.

    `BloomReferenceContract` now carries `DOCK_ACTION_IDS` and `DRAWER_ACTION_IDS`, with `ACTION_IDS`
    their union. Both journeys assert **both halves at the hub frame**: the drawer still shows
    `home` and `call-shop`, and the three projected ids are `assertDoesNotExist()` there while

    being absent, and now fails the other half.

    Frame 05's click moved from the drawer to the dock, and had to gain a dismissal with it:
    `profile` is a dock slot now, and a dock slot sits *behind* the drawer's window while the drawer
    is up, so the scrim is tapped first. The old `actionTag` lookup would simply have found nothing.

    The smoke test's `home` click stays on `actionTag` — `home` was deliberately left un-nominated,
    so it is still a drawer row. That is the same choice that keeps the de-duplication assertion from
    being vacuous.
