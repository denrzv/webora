- [x] TASK-1: reproduce the pipeline end to end in the JVM gate
  - Real Bloom fixture, real PNG bytes, real `OkHttpBrandAssetSource` and `BrandAssetLoader`, real
    `publishesBrandAsset`; a decoder stand-in only for the `BitmapFactory` call a JVM cannot make.
  - Acceptance: PRD criteria 1 (mechanism), 9.
  - Result: **done, and it does not reproduce the reported defect.** Five cases, all green:

    | Case | Result |
    |---|---|
    | Bloom's real manifest + real 512×512 PNG → `stage=DECODED`, `httpStatus=200` | PASS |
    | monogram **before**, `BitmapAsset` **after** — the transition itself | PASS |
    | a foreign configuration cannot receive the published asset | PASS |
    | a reader holding a different configuration falls back rather than borrowing | PASS |
    | no `logoUrl` → `NOT_DECLARED`; 404 → `TRANSPORT_REJECTED` + fallback | PASS |

    Nothing is stubbed except `BitmapFactory`, which a JVM cannot run — so URL resolution, the
    exact-origin recheck, the redirect policy, the size cap, the media/signature checks, the
    publication guard and the configuration-identity read are all genuinely exercised, against the
    checked-in fixture and the reference repository's actual artwork.

    Two things had to follow existing idiom rather than be invented, and both are worth knowing:
    SiteSkin is HTTPS-only at *both* layers, so the test presents a real
    `https://bloomflowers.example` origin and rewrites only the socket — `OkHttpBrandAssetSourceTest`
    established that shape. And test working directories are module-relative, so the fixture and the
    logo are reached via `../` and `../../`.

    **What this rules out.** Combined with research F1 — artwork present, origin serving `200
    image/png`, loader unchanged since `NET-004` — the defect is not in resolution, transport, media
    validation, decode gating, publication, or the identity association. That leaves composition, or
    the environment.
