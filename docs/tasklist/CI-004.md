- [x] TASK-1: The dismissal decision, as a pure function
  - New: `app/src/screenshotPolicy/java/app/webora/browser/evidence/AnrDismissalPolicy.kt`
  - New tests in: `app/src/test/java/app/webora/browser/evidence/AnrDismissalPolicyTest.kt`
  - Acceptance: `AnrDismissalPolicy.verdict(found: WaitAffordances): DismissalVerdict` over a
    `data class WaitAffordances(pressable, matchedButNotPressable, rootAvailable,
    viewIdReportingEnabled)` and a **sealed** `Press(viewId)` / `NotYet(reason)` /
    `Ambiguous(viewIds)`. Total over its input and evaluated in the plan's order: exactly one
    pressable id is `Press`; two or more is `Ambiguous` and is **never** resolved by choosing; every
    zero is `NotYet`, each carrying a *different* reason. There is no fourth case and no `else` that
    presses, mirroring `FocusVerdict`.
  - The input is `List<String>` plus two booleans, never `AccessibilityNodeInfo`:
    `isClickable`/`isVisibleToUser` are *observations* and stay in the guard. An Android type in this
    signature would drag the decision into a source set `./gradlew test` cannot compile, which is the
    mistake `CI-003` recorded and the reason this ticket exists at all — the one capture-time decision
    that was not a pure function is the one that failed on `main`.
  - Tests: the eight in the plan's table — `oneSanctionedAffordanceIsPressed`,
    `twoAffordancesAreAmbiguousAndNeverPressed`, `aMissingAccessibilityRootIsNotYet`,
    `viewIdReportingOffIsNotYet`, `presentButUnpressableIsNotYet`, `nothingFoundIsNotYet`,
    `everyNotYetCarriesADistinctReason`, and `ambiguityIsNotReachableFromAZeroState` as a sweep over
    every combination with `pressable.isEmpty()`.
  - Negative control: collapse the policy back to the old rule — every non-single count fails
    immediately. Every `NotYet` test must fail while `oneSanctionedAffordanceIsPressed` and
    `twoAffordancesAreAmbiguousAndNeverPressed` still pass, proving the surviving pair cannot stand in
    for the retryable cases.
  - Second negative control: make `Ambiguous` retryable (`size >= 2` returns `NotYet`).
    `twoAffordancesAreAmbiguousAndNeverPressed` must fail. Without this, nothing proves the
    fail-closed half survived the change that made the other half patient.
  - Result: 8 tests in `AnrDismissalPolicyTest`, 0 failures. `bash scripts/pre-commit-check.sh` OK.
  - Negative control 1 (collapse to the old rule): **6 of 8 fail** — the four `NotYet` cases, the
    zero-state sweep, and the distinct-reason test. `one sanctioned affordance is pressed` and
    `two affordances are ambiguous and never pressed` still pass, which is the point: neither of the
    surviving tests can tell the fixed policy from the one that failed run 13 twice.
  - Negative control 2 (`size >= 2` returns `NotYet`): **1 fails**, and it is
    `two affordances are ambiguous and never pressed` alone — as the plan predicted. The zero-state
    sweep does not catch it, because ambiguity is unreachable from a zero either way; that is the
    sweep being correctly scoped rather than the control being weak.
  - Both controls restored from a copy taken before editing, and the gate re-run green afterwards.
  - Gate: `bash scripts/pre-commit-check.sh`

- [x] TASK-2: The guard searches the dialog's own window, and records what it saw
  - Modified: `app/src/androidTest/java/app/webora/browser/visual/ScreenEvidenceGuard.kt`
  - New: `app/src/androidTest/java/app/webora/browser/visual/AnrDialogInspection.kt` — **a deviation
    from the plan's file list, recorded rather than absorbed.** The observation machinery, the flag
    handling and the journal are ~9 functions; folded into the guard they would have pushed it past
    detekt's `TooManyFunctions` ceiling of 20 and buried the orchestration the guard exists to do.
    The guard now decides *when* and the inspector observes *what*, which is the same split the guard
    already has with `ScreenEvidencePolicy`. `WAIT_VIEW_IDS` moves to the inspector's companion
    unchanged — the constant belongs with the thing doing the looking, and its value and KDoc are
    untouched.
  - Acceptance, and the order matters — **reachability and diagnosis lead, patience is secondary**
    (plan, revised after research §10 proved the zero was deterministic rather than transient):
    1. **Scope the search to the ANR dialog's window.** `rootInActiveWindow` returns one tree and the
       evidence says it was not the `SYSTEM_ALERT` dialog's — WindowManager logged `Cannot find window
       which accessibility connection is added to` 0.5 s before run 13's refusal. The observation
       enumerates `uiAutomation.windows` and searches the window whose OS-supplied title equals the
       title `focusVerdict` already classified.
    2. **Widening the search must not widen the allow-list.** `android:id/button2` is the negative
       button of *any* `AlertDialog`, Webora's included, so a search across all windows could press a
       Webora dialog whenever the system dialog's tree is unreachable — the precise violation `CI-002`
       forbids, arriving through a mechanism `CI-002` never had. Every searched root is therefore
       identified twice: by the classified window title, and by an OS-supplied `packageName` of
       `android`. The active-window fallback carries the same package check.
    3. **One root fetch per window**, hoisted out of the per-id loop — today `rootInActiveWindow` is
       read once per view id, so two lookups can see different trees — and roots are de-duplicated by
       window id, so one window cannot supply the same node twice and manufacture an `Ambiguous`.
    4. `dismissSystemAnr` becomes `attemptDismissal(...)`: it observes, asks `AnrDismissalPolicy`, and
       acts. `Press` clicks and writes the existing `interference-<label>-<n>.txt`; `Ambiguous` throws
       immediately; `NotYet` returns and lets the existing sleep / `waitForIdle` / re-dump run.
       **Patience stays in exactly one place** (research risk 1) — no second retry loop inside the
       helper, and `SETTLE_TIMEOUT_MILLIS` is not raised.
    5. **The budget counts presses.** `dismissals++` moves to the `Press` branch only, because
       `"survived N dismissals"` is false if nothing was pressed (research §4). A `NotYet` costs
       nothing; conflating the two would reintroduce this bug with a larger constant.
    6. `enableViewIdReporting()` stops returning silently on a null `serviceInfo`. It also requests
       `FLAG_RETRIEVE_INTERACTIVE_WINDOWS`, without which `uiAutomation.windows` is empty and step 1
       has nothing to enumerate. Both flags are **re-read at observation time** rather than cached, so
       a reconnect that drops one is visible; neither failure aborts construction, because the flag
       may already be set by the framework and failing early would turn a possibly-fine run red on a
       condition we can report instead.
    7. **`dismissal-<label>.txt`** — criterion 6. One compact line per poll (verdict, reason,
       pressable and matched ids, root availability, both flag states, window count) plus a detail
       block for the final observation listing every window seen and a bounded sample of the view ids
       actually present on the searched tree. Written once, when the guard leaves the dismissable
       state or fails, so forty polls cost one file rather than forty writes on a device the harness
       is supposed to be leaving alone. Today's message names only the ids we *looked for*, which is
       why two hosted runs and a log download produced no more information than the first assertion.
    8. A node's `text` is recorded for the reader and never consulted — the same rule that keeps
       `focusVerdict` on process-derived titles rather than translated strings.
  - Unchanged and asserted so: `ScreenEvidencePolicy`, `RenderedContentPolicy`, `candidateVerdict`,
    `captureWhenRendered`, `sampleRegion`, `WAIT_VIEW_IDS`, `DISMISSABLE_ANR_PROCESS`,
    `MAX_DISMISSALS`, and every timing constant. `ScreenEvidencePolicyTest`'s 20 fixtures must pass
    **unedited** — needing to edit one is the signal the change reached too far (research §5).
  - Tests: `./gradlew :app:compileDebugAndroidTestKotlin` explicitly. The gate never compiles that
    source set, which is how a compile error in `BrowserFontScaleTest` once survived a green
    `scripts/pre-commit-check.sh`.
  - Result: `bash scripts/pre-commit-check.sh` OK, `:app:compileDebugAndroidTestKotlin` BUILD
    SUCCESSFUL. `ScreenEvidencePolicyTest`, `RenderedContentPolicyTest` and `CandidateVerdictTest`
    pass unedited.
  - **The window identification is three ordered rules, not one, and the extra two are why.** The
    plan named the title match. `AccessibilityWindowInfo.getTitle()` is not guaranteed to carry the
    `dumpsys` window title, and a title-only rule that missed would leave the fix a silent no-op, so
    `focused` was added between it and the `active-window` fallback: the window holding input focus is
    the same notion as the `mCurrentFocus` line that produced the classification this branch is
    already acting on. **Every rule sits behind the package check**, so none of them widens what may
    be pressed — they differ only in how the system-owned dialog is recognised, and each records which
    one fired.
  - **A hole the plan did not name, found while implementing.** `android:id/button2` is the negative
    button of *every* `AlertDialog`, Webora's consent dialog included. Enumerating windows without a
    package check would have let the harness press a Webora dialog whenever the system dialog's tree
    was unreachable — a *worse* outcome than run 13's refusal, arriving through a mechanism `CI-002`
    never had to consider because `rootInActiveWindow` was one tree. Every searched root must now
    report a package in a closed set of two OS-supplied names (`android`, and the already-allow-listed
    `com.android.systemui`); Webora's windows carry the app package and match neither.
  - **Observation: `./gradlew detekt` does not analyse `androidTest`.** Verified directly — a 140-char
    line appended to the new file passed a green `detekt`, and `:app:detektDebugAndroidTest` reports it
    immediately. This is `CI-003`'s "the gate never compiles `androidTest`" one rule further along, and
    it is **out of scope here**: wiring the variant task into the gate would surface pre-existing
    findings across the whole instrumented suite and belongs in its own ticket. Recorded for
    `/review`. The new code was held to the gate's limits anyway and
    `:app:detektDebugAndroidTest` reports exactly one finding, `captureWhenRendered` at 54 lines,
    which predates this ticket (`CI-003`/`CI-005`) and is untouched by it.
  - Gate: `bash scripts/pre-commit-check.sh` plus `./gradlew :app:compileDebugAndroidTestKotlin`

- [x] TASK-FIX-2: Run 21 deletes the title rule and moves the walk back to where it is read
  - Source: hosted run 21 (`31771876172`, `8e9d8860`), field observation
  - Modified: `app/src/androidTest/java/app/webora/browser/visual/AnrDialogInspection.kt`, `CLAUDE.md`
  - **The plan's named mechanism does not work on this platform, and the record says so directly.**
    `dismissal-01-home.txt` reports the dialog's accessibility window title as
    `title=System UI isn't responding` — the *user-facing, translated* string, not the `dumpsys`
    window title `Application Not Responding: com.android.systemui` that `focusVerdict` classifies.
    The `title` rule therefore matched nothing on either frame; `matched=focused` is what found the
    dialog, twice. That rule was added during TASK-2 on the reasoning that input focus and
    `mCurrentFocus` are the same fact read through two APIs, and the field evidence is that it is
    carrying the entire fix.
  - Acceptance: delete the `title` rule rather than repair it. It cannot be repaired — matching
    `System UI isn't responding` would make dialog identification depend on a **translated string**,
    which is precisely what `CI-002` refused when it keyed `focusVerdict` on process-derived titles.
    What remains reads structural facts only: input focus, then the active window, both behind
    `mayBeSearchedForWaitAffordance`. `inspect` loses its `dialogTitle` parameter entirely, so no
    OS-authored text reaches the observation path at all; the journal already takes the title
    separately for its `window=` line. A rule that never fires and could only be revived as a
    locale-dependent match is decoration, and this repository does not keep those.
  - Acceptance: `presentViewIds` is forced when the verdict is **not** `Press`. `TASK-FIX-1` made the
    walk lazy to keep it off the per-poll path, and run 21 shows the cost of deferring it all the way
    to `report()`: `view_ids_present=[]` on both frames, consistent with the dialog being gone by the
    time the record was written. Forcing on the refusal path costs nothing on the success path — where
    the field is useless anyway — and keeps it live on the path it exists for.
  - Tests: no policy change, so no new JVM test. `./gradlew :app:compileDebugAndroidTestKotlin` plus
    the gate; `AnrDismissalPolicyTest`'s 12 must pass unedited, since this touches observation only.
  - Result: `bash scripts/pre-commit-check.sh` OK, `:app:compileDebugAndroidTestKotlin` BUILD
    SUCCESSFUL, `AnrDismissalPolicyTest` 12/12 unedited.
  - Worth stating plainly: **the rule this deletes is one I added in TASK-2 beyond the plan, and the
    rule it leaves is also one I added there.** The record that names which rule fired is what made
    both facts checkable after a single run rather than after someone eventually wondered.
  - Gate: `bash scripts/pre-commit-check.sh` plus `./gradlew :app:compileDebugAndroidTestKotlin`
