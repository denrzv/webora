- [x] TASK-1: The rendered-content rule, where the JVM gate can fail it
  - New: `app/src/screenshotPolicy/java/app/webora/browser/evidence/RenderedContentPolicy.kt`
  - New: `app/src/test/java/app/webora/browser/evidence/RenderedContentPolicyTest.kt`
  - Acceptance: `RenderedContentPolicy.verdict(samples: IntArray): ContentVerdict` returns
    `Rendered(differingFraction)` when the fraction of samples differing from the **modal** sampled
    colour is at least `MINIMUM_DIFFERING_FRACTION` (0.01), and `Blank(differingFraction, modalColor,
    sampleCount)` otherwise. It takes an `IntArray` of ARGB values and **never** a `Bitmap` — an
    Android type would drag the rule into a source set `./gradlew test` cannot compile, which is the
    entire reason this file sits beside `ScreenEvidencePolicy` in `src/screenshotPolicy/java` rather
    than in `androidTest`. An empty array is `Blank`: no samples is not evidence of rendering, and it
    must not throw. The file contains no polling, no timing, no I/O and no Android import.
  - Tests: `RenderedContentPolicyTest` — `aUniformRegionIsBlank`; `aUniformWhiteRegionIsBlankToo`
    (white is not special-cased; the modal colour is whatever dominates); `aRenderedPageIsRendered`;
    `justBelowTheThresholdIsBlank` and `atTheThresholdIsRendered` (the boundary is where the constant
    says, from both sides); `noSamplesIsBlank`; `oneStrayPixelIsNotRendering` (one differing sample
    in 40,000 — the case that would let a cursor artefact or a compression fringe pass for a page).
  - Negative control: invert the comparison so any non-empty array returns `Rendered`.
    `aUniformRegionIsBlank`, `justBelowTheThresholdIsBlank`, `noSamplesIsBlank` and
    `oneStrayPixelIsNotRendering` must fail while both positive cases still pass — proving the
    positives cannot stand in for the rule.
  - Result: 7 tests, 0 failures. `bash scripts/pre-commit-check.sh` OK.
  - Negative control A (inverted comparison): **4 of 7 failed — but not the four the plan named.**
    Failing: `aUniformRegionIsBlank`, `aUniformWhiteRegionIsBlankToo`, `justBelowTheThresholdIsBlank`,
    `oneStrayPixelIsNotRendering`. The plan predicted `noSamplesIsBlank` instead of the white case,
    and it was wrong: the empty-array early return sits *before* the threshold comparison, so
    inverting that comparison never reaches it. The prediction was right about the count and wrong
    about the set, which is recorded here rather than quietly reconciled.
  - Negative control B, added because of what A revealed: removed the empty-array guard.
    `noSamplesIsBlank` alone failed (1 of 7). Two separate protections needed two separate controls
    — with only control A, the empty case would have been covered by a test that could never fail.
  - Note: the threshold is a **liveness** bar, not a content-quality bar, and the tests say so from
    both sides — `atTheThresholdIsRendered` and `justBelowTheThresholdIsBlank` pin the boundary where
    the constant claims it is, so raising the constant to "fix" a flaky run is a visible edit that
    breaks a test rather than a quiet retune.
  - Deviation: none.
  - Gate: `bash scripts/pre-commit-check.sh`

- [x] TASK-3: Poll for drawn content, and explain a refusal
  - Modified: `app/src/androidTest/java/app/webora/browser/visual/ScreenEvidenceGuard.kt`
  - Acceptance: `captureWhenRendered(label: String, region: Rect?): Bitmap` takes a screenshot, reads
    `region` with a stride of 4 on both axes into an `IntArray`, asks `RenderedContentPolicy`, and
    polls to a bounded deadline — an observed condition, never a fixed `sleep`, per
    `scripts/android-emulator-ready.sh`'s precedent. A `null` region means no content requirement:
    capture once and return. It returns **the bitmap that satisfied the check**, so the caller saves
    the frame it verified rather than taking a second screenshot that could differ from the one that
    passed. On deadline it writes `diagnostics/rendered-<label>.txt` — every sample's fraction, modal
    colour, sample count and elapsed time — then throws, matching how `window-<label>.txt` explains a
    refused capture, and landing in the diagnostics artifact beside `CI-002`'s files. All decision
    logic stays in the policy; this class reads, waits and records.
  - Tests: none possible here — `androidTest`, no emulator. Verified by
    `./gradlew :app:compileDebugAndroidTestKotlin`, which the gate does **not** run and which this
    session has already seen swallow a compile error in this exact source set. Behaviour is
    instrumented evidence from `TASK-5`, recorded as such and never promoted to a gate claim.
  - Result: `bash scripts/pre-commit-check.sh` OK; `./gradlew :app:compileDebugAndroidTestKotlin`
    SUCCESSFUL. The guard keeps the `CI-002` split intact — it reads, waits and records, and every
    rendered-vs-blank decision goes through `RenderedContentPolicy`.
  - Note: the diagnostic records **every** sample, not just the last, with elapsed time per attempt.
    A single final reading cannot distinguish "never started drawing" from "was drawing and ran out
    of time", and those want different fixes.
  - Deviation: none.
  - Gate: `bash scripts/pre-commit-check.sh` **plus** `./gradlew :app:compileDebugAndroidTestKotlin`
    run explicitly.
