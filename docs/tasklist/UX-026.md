- [x] TASK-1: the pure height rule
  - New: `app/src/main/java/app/webora/browser/siteskin/HubDrawerHeight.kt` —
    `HubDrawerHeight(min, max)` and `hubDrawerHeight(available: Dp)`.
  - New: `app/src/test/java/app/webora/browser/siteskin/HubDrawerHeightTest.kt`.
  - `max = available * HUB_DRAWER_MAX_FRACTION` (0.85), `min = HUB_DRAWER_MIN_HEIGHT (180 dp)`
    coerced under `max`. Total: a non-positive available height returns `(0.dp, 0.dp)`, never a
    negative bound and never `min > max`.
  - Acceptance: PRD criteria 6, 9, 14 (the type half).
  - Tests: the bounds table; `min <= max` at every input including zero and a viewport under the
    minimum; the reflective assertion that every parameter and the two component types are `Dp`.
  - Negative controls: (a) add an `itemCount: Int` parameter — the reflective assertion must fail;
    (b) raise the fraction to `1f` — the fraction assertion must fail; (c) drop the `coerceAtMost`
    — the small-viewport case must fail with `min > max`.
  - Result: **done**. `bash scripts/pre-commit-check.sh` green.

    | Control | Result |
    |---|---|
    | `itemCount: Int = 0` added to the signature | `the rule reads a dimension and nothing else` FAILED, alone |
    | `HUB_DRAWER_MAX_FRACTION = 1f` | `the bounds are a fraction of the available height` FAILED, alone |
    | `min = HUB_DRAWER_MIN_HEIGHT` uncoerced | `a viewport under the minimum still yields usable bounds` FAILED, alone |

    **The first control had to be made to compile before it proved anything.** Written as a bare
    second parameter it broke `:app:compileDebugUnitTestKotlin`, and a build that never ran the test
    is not a control that bit — `UX-024` records the same trap from the other side. Given a default
    value it compiles everywhere, which is also the shape somebody would actually write to avoid
    touching call sites.

    **Erasure is why the assertion is two-sided.** `Dp` is a value class, so a `Dp` parameter is a
    `float` at the JVM boundary and an added `fontScale: Float` would be indistinguishable from a
    dimension by reflection alone. Arity and erasure come from the compiled method; the declared
    types come from the declaration line. `kotlin-reflect` would have answered it in one assertion
    and is deliberately not on the test classpath — `ColorRoles.kt` records that rule, and adding a
    dependency to satisfy a test is the trade it refuses.

    **Deviation from the plan: the file is `HubDrawerHeight.kt`, not `HubDrawerGeometry.kt`.** detekt's
    `MatchingDeclarationName` requires a file with one top-level type to be named after it, and the
    type is the pair rather than the field of study.

    **The third control passed on its first run, for the second time in this ticket.** The assertion
    counted one `WindowInsets.safeDrawing` and required `windowInsetsPadding` somewhere in
    `SiteSkinHubDrawer`'s body — and the *old* placement was inside that body too, on the content. One

    presence checks over a scope that contained the defect as well as the fix.

- [x] TASK-4: the evidence a device can see
  - Modified: `app/src/androidTest/.../SiteSkinHubDrawerTest.kt` — scrim tap closes and dispatches
    nothing; a tap on the panel does not close; a short menu's panel height is materially under the
    viewport; a twenty-entry menu is bounded at the maximum and its last row is still reachable.
  - Acceptance: PRD criteria 1, 2, 3, 7, 8, 16.
  - Tests: `./gradlew :app:compileDebugAndroidTestKotlin` (this checkout has no emulator, so
    compilation is the local gate and the assertions are instrumented evidence, never a gate claim).
  - Sizing is asserted as **bounds**, never `assertIsDisplayed()` — `UX-009` and `UX-023` both record
    that semantics keep full text and unclipped bounds, so a presence assertion cannot see a sizing
    defect.
  - Result: **done**, as instrumented evidence and not a gate claim.
    `./gradlew :app:compileDebugAndroidTestKotlin` compiles and
    `bash scripts/pre-commit-check.sh` is green; this checkout has no emulator, so the four new cases
    are unrun here and their first execution is the hosted job.

    Four cases: scrim tap closes with zero selections; a tap on the panel's own header space leaves it
    open; Bloom's panel measures under half the available height; a twenty-entry menu measures
    strictly under it and still scrolls to `m20`.

    **The scrim tap is placed at `bottomCenter`, not the node's centre.** The panel is top-aligned and
    bounded below the available height, so the bottom strip is scrim at *every* content height, while
    the centre is scrim only for a menu short enough — a case that would pass for Bloom and silently
    stop testing dismissal for a site with a real menu.

    Both sizing cases read `size.height` from the semantics tree rather than asserting displayed-ness,
    and both compare against the scrim's own height so neither depends on a device profile.
