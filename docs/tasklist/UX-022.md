    Two deviations from the plan, both recorded rather than silently taken:

    - **`SPEC.md` §5's code block does not gain the field.** That block is the reference

      in §5 prose immediately below, with its own example and value table. Whether Bloom adopts
      `drawer` is a cross-repository change belonging to a DEMO ticket.
    - **`SecurityValidatorTest` gained four cases the plan did not list**, covering the criterion-2
      rows no fixture reaches: each recognised token, a wrongly-cased token, an empty `presentation`
      object, and the accessor collapsing absent-versus-declared-`auto`. The wrongly-cased row is
      the load-bearing one — `HUBS` is a lookup and not a case-insensitive comparison, so `"Drawer"`
      warns. Lower-casing at read time would make two spellings of one token, which is the
      leading-zero `schemaVersion` mistake `SPEC-002` fixed by narrowing the grammar rather than
      normalizing.

- [x] TASK-2: resolve the hint through one browser-owned policy
  - `HubSurface` + pure `resolveHubPresentation`, `AUTO → DRAWER`, outside
    `ExpressiveSiteSkinPresentation`.
  - Acceptance: PRD criteria 8.
  - Tests: `HubPresentationTest`, every input including null.
  - Negative control: map `AUTO` to the drawer at the call site → the policy test must fail.
  - Result: **done**. `bash scripts/pre-commit-check.sh` green.

    `HubSurface` is a **different type** from core's `HubPresentation`, not a re-export. Core's is
    what a site *asked for*, closed by the validator; the app's is what the browser *decided*, closed
    by the components that exist. One enum for both would make the two questions indistinguishable at
    every call site, and the bug worth catching is a surface composed because a manifest named it
    rather than because the browser chose it.

    Named `HubSurface.kt`, not `HubPresentation.kt`: detekt's `MatchingDeclarationName` requires the
    file to be named for its single top-level declaration, and the app file naming itself after the
    app type is the clearer outcome anyway.

    Both negative controls failed as required:

    | Control | Result |
    |---|---|
    | A second reader of the enum — a `compiledHubDefault(hint)` appended to `SiteSkinDock.kt` | `the hint is read in exactly one file` FAILED |
    | `BOUQUET -> DRAWER`, making the drawer unconditional | `the policy can produce both surfaces` FAILED |

    Control A is the one the plan asked for and the one worth keeping. The value assertions cannot
    catch it — a hardcoded `AUTO -> DRAWER` at a call site agrees with the policy on the day it is
    written, which is what makes the drift silent. The source scan is what forbids the copy, and it
    has to strip comments before matching: every KDoc in this file names `HubPresentation`, so an
    unstripped scan reports every documented file as a reader (`BROWSE-009`'s rule, and the sharpest
    instance of it in the repository so far).

    Control B was added beyond the plan. A total function returning one constant satisfies every
    value assertion, and "the drawer is what `AUTO` resolves to anyway" is exactly the reasoning that
    would make it unconditional and remove the site's only influence over this choice.

  - `actionBouquet()` keeps its name, order, dedup and cap; `SiteSkinChromeModelTest` unedited.
  - Acceptance: PRD criteria 10–16, 19.
  - Tests: `SiteSkinHubDrawerContractTest`, instrumented open/dismiss/Back.
  - Result: **done**. `bash scripts/pre-commit-check.sh` green. `SiteSkinChromeModelTest` unedited,
    as planned — `actionBouquet()` keeps its name, order, dedup and cap, and the drawer is asserted
    not to consult it.

    Four negative controls bite; two written controls did not, and both findings were worth more
    than the controls that worked:

    | Control | Result |
    |---|---|
    | `Alignment.CenterStart` → `CenterEnd` | `the panel is placed by a direction-aware alignment` FAILED |
    | `items.take(5)` in `HubGroup` | `the drawer caps nothing it was handed` FAILED |
    | `if (item.isNavigation)` → `if (true)` | `selection semantics are reachable only for navigation rows` FAILED — **after** the assertion was added |
    | `model.siteMenu + model.siteMenu` | `each group reads one bounded collection…` FAILED |

    **The selection control found a missing assertion, which is the outcome to want from a control.**
    Criterion 14 — only navigation rows publish selection — had no guard at all on the first run: the
    control compiled, ran and passed. The assertion added for it reads `HubRow`'s body rather than
    the file, because a whole-file scan cannot tell an unconditional `selected` from a guarded one.

    **The `configuration.` control could not be written, and the reason is stronger than the
    assertion.** `HubDrawerContent` has no `SiteSkinConfiguration` parameter, so every attempt to
    re-derive a group from it is a compile error (`Unresolved reference 'configuration'`), not a test
    failure. The scan stays because it becomes load-bearing the moment someone adds that parameter,
    but today the type is what forbids it and the assertion is documentation of intent.

    A `Dialog(usePlatformDefaultWidth = false)` rather than `ModalNavigationDrawer`, and the reason
    is structural rather than visual: the dialog is its own window, so Back is consumed before
    `BrowserBackHandler` sees it. `ModalNavigationDrawer` shares the browser's window and would need
    its own back handler racing the browser's — a second answer to `BROWSE-002`'s single Back
    contract. `BrowserBack.kt` is untouched, as the plan required.

    Group order follows criterion 12 literally — quick actions, navigation, menu. An empty group
    renders no heading rather than an empty one: a "Quick actions" heading over nothing tells the
    user the site offered something the browser dropped, which this component has no evidence for.

    The header shows the site name and the already-published `BrandAsset` and deliberately carries
    **no origin and no TLS state**. `UX-021`'s chip is visible in the browser-owned header the whole
    time the drawer is open; a second identity surface inside a site-coloured panel would put the
    browser'''s trust mark on a ground the site chose — `UX-021`'s own colour argument, one surface
    along.

- [x] TASK-4: open the resolved surface from the Brand Hub
  - Dock's five commands, order and callbacks untouched; `fixedDock` scan unedited. One visibility
    state with its three existing resets. `BrowserBack.kt` not touched. Inspector gains a

  - Acceptance: PRD criteria 9, 17, 18, 20.

    Dock commands, order, tags and callbacks untouched; `fixedDock` scan unedited. `BrowserBack.kt`
    not touched — the drawer's own window consumes Back, which is why the container was chosen.

    | Control | Result |
    |---|---|
    | A second `hubDrawerVisible` state | `the hub has one visibility state and both surfaces read it` FAILED |
    | `surface = HubSurface.DRAWER` literal at the call site | `both surfaces are told the same resolved surface` FAILED |

    **The plan's control had no test to fail, and writing one was the work.** `siteActionsExpanded`
    is a `remember` inside a composable, so the gate cannot drive a tab switch at all — the plan's
    "a tab-switch case must fail" described a case that does not exist. The rule is enforced as a
    source contract instead: exactly one hub visibility state, read by both surfaces under the
    names they actually use. The naive control (declaring the state in `BrowserScreen`) does not
    even compile, because the reader is in `RegularBrowser`; the control that *does* compile
    declares it beside the call site, and that is the one the scan catches.

    **`CI-009`'s frame 04 changed subject, and this is the decision to look at first in review.**
    Bloom declares no `presentation`, so `AUTO` now resolves to the drawer and the hub frame
    photographs a full-window modal rather than a popup over a visible page. `requirePageContent`
    was therefore removed from that frame — **not as a weakening**: `RenderedContentPolicy` asks
    whether `BROWSER_CONTENT_TAG`'s rectangle is non-uniform, the drawer's window covers that
    rectangle, and a drawer is gloriously non-uniform. Keeping the check would have measured the
    drawer and passed for the wrong reason, which is `CI-005`'s defect verbatim. The consent frame
    has been in this category since `CI-001` for the same reason.

    What replaces it is stricter for that frame than a pixel fraction could be: the drawer's own tag
    displayed, plus all five of the reference integration's trusted action ids present as rows. A
    blank or half-composed hub fails those; a fraction over a covered rectangle could not.
    `ExpressiveBloomJourneyContractTest` now pins *which* check each frame carries — page frames
    require rendered content, modal frames require their own surface assertion — so this is not a
    place to opt out of a check, and the modal list is two named frames rather than a predicate.

    `BloomReferenceContract.actionTag` is the one line that follows the surface, so the showcase and
    the smoke exercise address the same hub. **Hosted acceptance must be re-taken:** `CI-009` was
    already pending two consecutive cold runs, and frame 04 now depicts a different surface. This
    checkout has no emulator, so that evidence is not available here.

    The inspector gains `Hub requested` / `Hub composed` as two rows rather than one. `requested` is
    `not declared` when the manifest said nothing — the distinction core'''s nullable holder exists to
    preserve, and the one a site owner most needs: "I asked for the default" and "I forgot to ask"
    produce the same drawer and are different things to be told.
