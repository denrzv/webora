## Tasks

- [x] TASK-1: carry an optional `presentation.hub` through validation as a closed enum
  - Schema gains an optional `presentation` object with a `pattern`-constrained `hub`, anchored
    `(?![\s\S])`. All three structural copies move together — schema, `ManifestStructure`,
    `UnknownFieldScanner.rootFields`.
  - `Normalizer` maps `auto`/`bouquet`/`drawer`, and anything else to `AUTO` plus
    `SS-W-PRESENTATION-UNKNOWN` at `/presentation/hub`. Nothing dropped, nothing rejected.
  - `SiteSkinConfiguration` gains a **nullable** holder plus one accessor collapsing `null`/`AUTO`.
  - Registry entry and fixture land in the same commit; `SPEC.md` documents the field, disposition,
    §4.2 minor status and the §12 canonical-result rule.
  - Acceptance: PRD criteria 1–7.
  - Tests: `./gradlew :siteskin-core:test`, `SpecCorpusTest`, `SecurityConformanceTest`,
    `ProductionSchemaConformanceTest`, `SchemaValidatorTest`, `SecurityValidatorTest`.
  - Negative controls: `enum` instead of `pattern` → whole-manifest rejection; omit `presentation`
    from `rootFields` → `SS-W-FIELD-UNKNOWN`; non-null holder → existing `.expected.json` fail.
  - Result: **done**. `bash scripts/pre-commit-check.sh` green; 172 core tests.

    Two fixtures, not one. The plan named `valid/presentation-hub-unknown.json`; a fixture whose
    document contains a mistake belongs beside `icon-unknown` in `invalid/`, which is the bucket
    convention `SpecCorpusTest` actually enforces (`valid/` may carry warnings — `forward-compat-1.1`
    does — but it is where exemplary documents live). The happy path went to
    `valid/presentation-hub-drawer.json`, which pins the no-diagnostic result and is what caught
    control 2.

    All three negative controls failed as required:

    | Control | Caught by |
    |---|---|
    | `enum` replaces `pattern` in the schema | `securityLayerFixturesPassTheSchema` — `/presentation/hub: element is not in enum` |
    | `presentation` dropped from `UnknownFieldScanner.rootFields` | `valid/presentation-hub-drawer expected:<[]> but was:<[SS-W-FIELD-UNKNOWN]>` |
    | non-null `PresentationConfiguration` holder | `valid/bloom-flowers` — the canonical result that is SHA-256 pinned in two repositories |

    Control 3 is the one worth keeping: the holder's nullability is not a style preference, and the
    test that fails first when it is removed is the reference integration's own pinned body.

    Two deviations from the plan, both recorded rather than silently taken:

    - **`SPEC.md` §5's code block does not gain the field.** That block is the reference
      integration's manifest field-for-field, and `DEMO-005` makes the fixture, the published copy
      and the specification example one coordinated artifact. Adding `"hub": "drawer"` there would
      have made the spec's canonical example describe something `bloom-flowers.json` does not
      publish, while criterion 5 requires that file to stay byte-identical. The field is documented
      in §5 prose immediately below, with its own example and value table. Whether Bloom adopts
      `drawer` is a cross-repository change belonging to a DEMO ticket.
    - **`SecurityValidatorTest` gained four cases the plan did not list**, covering the criterion-2
      rows no fixture reaches: each recognised token, a wrongly-cased token, an empty `presentation`
      object, and the accessor collapsing absent-versus-declared-`auto`. The wrongly-cased row is
      the load-bearing one — `HUBS` is a lookup and not a case-insensitive comparison, so `"Drawer"`
      warns. Lower-casing at read time would make two spellings of one token, which is the
      leading-zero `schemaVersion` mistake `SPEC-002` fixed by narrowing the grammar rather than
      normalizing.
