- [x] TASK-4: `WeboraTheme`, and no Material default behind it
  - New: `app/src/main/java/app/webora/browser/design/WeboraTheme.kt`,
    `app/src/test/java/app/webora/browser/design/WeboraThemeTest.kt`
  - New: `app/src/main/res/values-night/themes.xml`
  - Modified: `app/src/main/java/app/webora/browser/MainActivity.kt`
  - `WeboraTheme(darkTheme = isSystemInDarkTheme(), content)` supplies `MaterialTheme` with the
    derived `ColorScheme`, `Typography` and `Shapes`. `darkTheme` is a parameter with the framework
    read as its default, so a test can pass the other value.
  - Acceptance: every Material colour role is assigned from a browser role and the mapping contains
    no `Color(...)` literal; the night theme gives `Theme.Webora` a dark platform parent so the
    pre-composition frame and the system-bar regions agree with the palette.
  - Tests: `WeboraThemeTest` — colour closure over the derived `ColorScheme`; size closure over
    `Typography`; corner closure over `Shapes`; light and dark are distinct.
  - **Negative controls — passed, three of them.**
    (a) *Omitting a role.* `ColorScheme`'s primary constructor turned out to declare **no default
    values** — 48 arguments, no mask constructor — so `ColorScheme(...)` is used in preference to
    `lightColorScheme(...)`, whose every argument defaults to the baseline palette this ticket exists
    to remove. Deleting `surfaceDim` is therefore a *compile* error (`e: WeboraTheme.kt:60 None of
    the following candidates is applicable`), not a silent fallback. Stronger than the planned
    control, and it makes the closure test the second line rather than the first.
    (b) *A literal in the mapping.* Assigning `surfaceDim` Material's baseline purple compiles and
    fails `every Material colour comes from the browser palette` in both projections — 8 tests, 1
    failed. This is the mistake the test is actually for: a literal is a colour nothing has measured.
    (c) *A selector that ignores the setting.* `WeboraColors.scheme` returning `LIGHT` unconditionally
    fails `the system theme selects the projection and nothing else does` — 7 tests, 1 failed.
  - **Finding, recorded rather than papered over.** Material 3's `Shapes` declares two further roles,
    `extraLargeIncreased` (32 dp) and `extraExtraLarge` (48 dp), which are `internal` to the library
    and absent from its constructor. No public API can supply them, so they keep Material's values in
    any component that reads them. They are excluded from the corner-closure scan **structurally** —
    Kotlin mangles an `internal` member's JVM name with a `$module` suffix — rather than by name, and
    a separate assertion pins that the five settable roles are all covered. Adding 32 and 48 dp to
    `WeboraRadius` was rejected: that is inventing values to satisfy a test.

- [x] TASK-5: `C2` — prove no manifest value can reach a browser token
  - New: `app/src/test/java/app/webora/browser/design/BrowserTokenIsolationTest.kt`
  - Two halves, because neither can fail for the other's reason: a runtime sweep projecting real
    manifests through the real `SiteSkinValidator` and asserting browser tokens are bit-identical
    **while the SiteSkin scheme did move**; and a source scan asserting nothing under
    `design/` mentions `dev.siteskin.core`, `app.webora.browser.siteskin` or `SiteSkinConfiguration`.
  - Acceptance: the sweep includes branding that is conspicuously not Direction A's, and fails if the
    projection stops being exercised.
  - **Negative controls — passed, and each half caught what the other could not.** This is the
    ticket's security test; `ADR-013` hands it over by name.
    (a) *A compile-time path.* Referencing `SiteSkinTheme` from `WeboraColorScheme.kt` fails both
    scan assertions — `no design source imports the website side` and `no design source mentions the
    website side in code` — 7 tests, 2 failed. The sweep stayed green: nothing had moved yet.
    (b) *A token that moves.* Making `WeboraColors.LIGHT` a `var` and writing the manifest's primary
    into its `chrome` from `SiteSkinTheme.from` — with **no reference at all** in the design package —
    fails `projecting manifests does not move a browser token`, 7 tests, 1 failed. Both scans stayed
    green, because structurally there was nothing to see.
    Neither control alone would have justified two halves; run together they are the evidence that
    the plan's belt-and-braces claim is real rather than symmetrical-sounding.
  - The comment stripper the code scan trusts has its own test, in both directions: a commented-out
    import must not survive it, and code following a string containing `//` must. A regex `//`-to-EOL
    strip eats the rest of the line after `"https://…"`, and a scan that quietly removes real code
    is a scan that stops finding things — the same reason `inspectorValue` is a character walk.

  - Geometry transcribed from `docs/design/directions/index.html:611-620`: 24-unit viewport, 1.9

  - Acceptance: no Gradle dependency is added; each drawable declares one stroke colour, since
