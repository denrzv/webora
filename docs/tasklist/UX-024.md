# UX-024 tasklist — the browser's navigation commands become one control

Status: TASKLIST_READY

References:
- PRD: `docs/prd/UX-024.prd.md`
- Research: `docs/research/UX-024.md`
- Plan: `docs/plan/UX-024.md`
- Source of record: GitHub issue [#122](https://github.com/denrzv/webora/issues/122)

Each task is a green checkpoint: `bash scripts/pre-commit-check.sh` passes, then commit, then push
before the next one starts. Source changes that break an existing assertion carry that assertion's
re-statement in the same commit — a task that leaves the gate red is not a checkpoint.

## Tasks

- [ ] TASK-1: the command list and the overlay value, as pure types
  - New: `app/src/main/java/app/webora/browser/siteskin/BrowserNavigationCommands.kt` —
    `BrowserNavigationCommand { BACK, FORWARD, REFRESH }`, `BrowserNavigationAction(command, enabled)`,
    and `browserNavigationActions(canGoBack, canGoForward, canRefresh)`. Total, compiled order, no
    Android type in the signature, nothing constructible from a `SiteSkinConfiguration`.
  - New: `app/src/main/java/app/webora/browser/siteskin/IntegratedOverlay.kt` —
    `IntegratedOverlay { SITE_HUB, BROWSER_NAVIGATION }`, with the KDoc recording why one nullable
    value replaces two booleans (`UX-022`'s three resets, and criterion 13's exclusion becoming
    structural).
  - Nothing consumes either type yet. The wiring is TASK-2 and TASK-3; this commit is the seam the
    JVM gate can drive, per `BROWSE-009`'s reason for `routeRendererEvent`.
  - Acceptance: PRD criteria 3 (list half), 8 (source half), 12 (type half).
  - Tests: new `BrowserNavigationCommandsTest` — exactly three actions in declared order for all
    eight flag combinations; each `enabled` tracks its own input and no other; the enum has exactly
    three constants.
  - Negative controls, with results recorded here:
    - order the list `FORWARD, BACK, REFRESH` → the order assertion must fail;
    - hard-code `enabled = true` → the per-flag assertions must fail **while count and order still
      pass**, which is why they are separate assertions;
    - give `browserNavigationActions` a `List<SiteSkinItemModel>` parameter → must not compile
      against a file that imports no site type.

- [ ] TASK-2: the hub replaces Back, and the refresh row goes away
  - New: `app/src/main/res/drawable/ic_history.xml` — 24 dp / 24-unit viewport, `strokeWidth="1.9"`,
    round caps and joins, no `fillColor`, one declared colour, real `pathData`.
  - New: `app/src/main/java/app/webora/browser/siteskin/SiteSkinNavigationHub.kt` — the collapsed
    control in `BrowserControlTile(SITESKIN_NAV_HUB_TAG)` plus the downward `Popup`
    (`Alignment.TopStart`, `focusable`, `dismissOnBackPress`, `dismissOnClickOutside`), one bubble
    per action, closing before dispatch.
  - Modified: `SiteSkinTopBar.kt` — `BrandRow`'s leading control becomes the hub; `BrowserBack`,
    `BrowserControlRow` and `SITESKIN_CONTROLS_TAG` are deleted; `BrowserControlTile` stays and is
    shared; `SITESKIN_BACK_TAG` and `SITESKIN_REFRESH_TAG` keep their exact values on the Back and
    Refresh bubbles; `SITESKIN_FORWARD_TAG`, `SITESKIN_NAV_HUB_TAG`, `SITESKIN_NAV_BOUQUET_TAG` are
    new. Parameters go seven → seven.
  - Modified: `strings.xml` — `siteskin_open_navigation` (*Browser navigation*), distinct from
    `R.string.back`.
  - Modified: `HeaderIdentityPlacement.kt` — **KDoc only**. `HEADER_FIXED_WIDTH` does not move; if
    this task needs to change the number, the footprint moved and criterion 17 is at risk.
  - Modified: `BrowserIconContractTest` (`EXPECTED` + `BUDGET` 20 → 21, reason at the constant),
    `SiteSkinTopBarContractTest` and `SiteSkinNavigationContractTest` (the assertions naming the
    deleted declarations), `SiteSkinTopBarTest` (instrumented cases naming the deleted tags) — all
    in this commit, so the gate stays green.
  - Acceptance: PRD criteria 1, 2, 4, 9, 17.
  - Tests: `BrowserIconContractTest` (the new glyph obeys the drawing contract);
    `SiteSkinTopBarContractTest` (the hub is the leading control and uses the shared tile; the
    deleted row does not return); `HeaderIdentityPlacementTest` passes **unedited**.
  - Negative controls:
    - ground the hub tile on `presentation.colors.secondary` → the isolation scan must fail;
    - label the hub `R.string.back` → criterion 2's assertion must fail;
    - `HeaderIdentityPlacementTest` needing an edit is itself a finding, not a fix.

- [ ] TASK-3: three dock slots, and one overlay value doing the work of two booleans
  - Modified: `SiteSkinDock.kt` — `canGoBack`, `canGoForward`, `onBack`, `onForward`, their two
    `DockCommand` calls and `SITESKIN_DOCK_BACK_TAG` / `SITESKIN_DOCK_FORWARD_TAG` are removed. Brand
    Hub, Tabs, More keep their order and their `weight(1f)`; no dimension, radius, height, colour or
    geometry constant changes.
  - Modified: `BrowserScreen.kt` — `siteActionsExpanded` becomes `overlay: IntegratedOverlay?`; every
    existing reset becomes `overlay = null` at its existing site; `RegularBrowser` loses three
    parameters and gains two; it builds `browserNavigationActions(...)` for the top bar and
    dispatches with an exhaustive `when`. `BrowserNavigationShell`'s branch is not touched.
  - Modified: `SiteSkinNavigationContractTest` — `fixedDock`'s ordered list becomes the three that
    remain, **paired in this commit** with a negative control that fails when a model-derived command
    joins them. Modified: `SiteSkinDockTest` — five tags become three.
  - Acceptance: PRD criteria 5, 8 (wiring half), 11, 12, 13, 14, 20.
  - Tests: `SiteSkinNavigationContractTest` (three fixed commands; a model-driven dock is rejected);
    `SiteSkinDockTest`; `BrowserSiteSkinLayoutTest` passes unedited — it asserts the dock's presence
    and its position relative to `BROWSER_CONTENT_TAG`, neither of which this task moves.
  - Negative controls:
    - add a fourth `DockCommand` driven by `siteActions.size` → the fixed-dock assertion must fail;
    - keep two booleans instead of the overlay value and reset only one → the exclusion case must
      fail. (This is `UX-022`'s recorded failure mode: *"a tab switch tears down the dock while a
      drawer nobody reset stays composed over the next origin's page."*)

- [ ] TASK-4: evidence, rendered and hosted
  - New: `app/src/androidTest/java/app/webora/browser/siteskin/SiteSkinNavigationHubTest.kt` — the

    not; an outside tap and `pressBack()` each close without navigating; 320 dp × 200% keeps all
    three reachable; the standalone refresh tile no longer exists.
  - Modified: `SiteSkinTopBarContractTest` — the new scan assertions: no manifest value reaches the

    than as a new row count.
  - Modified: `LiveSiteScreenshotTest`, `LiveSiteNavigationSmokeTest` — history traversal opens the
    hub and clicks the bubble, with `CI-008`'s prerequisite asserted on the bubble immediately before
    the click; no frame is captured while the bouquet is open.
  - Modified: `ExpressiveBloomJourneyContractTest` — `SMOKE_MARKERS`' two dock-tag names become the
    hub markers. `CANONICAL_FRAMES` is unchanged and stays at six.
  - Acceptance: PRD criteria 6, 7, 10, 15, 16, 18, 19, 21.
  - Tests: the files above, plus `./gradlew :app:compileDebugAndroidTestKotlin`.
  - Negative controls:
    - dispatch before dismissing → the close-then-dispatch cases must fail;
    - reintroduce `BrowserControlRow` → criterion 10's comparison must fail;
    - pass a `NavigationItem` into a bubble → the type-boundary scan must fail.

    instrumented suite is not that evidence, per `CI-009`'s own record.
